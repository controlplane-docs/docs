This page lists every tool the [MCP Server](/ai/mcp) exposes, grouped by the resource it operates on. Tool names are the exact identifiers the AI calls — you normally describe what you want in natural language and let the assistant pick the tool, but knowing what exists helps you prompt precisely and understand what an assistant is doing on your behalf.

<Tip>
  You don't call these tools directly. Describe the outcome you want — see [Usage Examples](/ai/examples) for prompt patterns — and the assistant selects and chains the right tools.
</Tip>

## Toolset profiles

The server advertises a different set of tools depending on the `toolsets` query parameter on the endpoint URL. A smaller set keeps the assistant focused and fits comfortably in its context window; the larger sets unlock specialized resource families.

| Profile | Tools | Endpoint | Includes |
| :------ | :---: | :------- | :------- |
| `readonly` | 34 | `https://mcp.cpln.io/mcp?toolsets=readonly` | Investigation only: observability, runtime state, inventory, generic reads, and one-call workload diagnosis. Nothing that creates, updates, deletes, or executes, so an assistant on this profile cannot change a live resource. |
| `core` | 71 | `https://mcp.cpln.io/mcp` | The default. [Job tools](#jobs) that do a whole task in one call (deploy an app, add a database, create or rotate a secret, and diagnose, restart, roll back, or promote a workload), plus workloads, GVCs, image builds (from a repository, or from source the assistant writes itself), domains, identities, policies, templates, volume sets, observability (logs, metrics, traces, audit), quotas, and Terraform export. |
| `mk8s` | 73 | `https://mcp.cpln.io/mcp?toolsets=mk8s` | Everything in `core` plus `create_mk8s` and `update_mk8s`, which provision and update [managed Kubernetes](/mk8s/overview) clusters on every supported provider. |
| `full` | 119 | `https://mcp.cpln.io/mcp?toolsets=full` | Every tool, including agents, cloud accounts, IP sets, service accounts, groups, audit contexts, external logging, advanced workload configuration, and volume snapshots. |

<Note>
  Connecting to `https://mcp.cpln.io/mcp` with no query parameter gives you the `core` profile. To switch profiles, point your client at the URL with the `?toolsets=` parameter — see your tool's [setup page](/ai/mcp#compatible-tools) for where the endpoint URL is configured.
</Note>

### Reading the tables

Each tool is listed with its name, its label, and what it does. The **Access** column flags how the tool behaves:

| Marker | Meaning |
| :----- | :------ |
| **Read** | Read-only. Fetches data without changing anything. |
| **Write** | Creates or modifies a resource. |
| **Destructive** | Deletes, removes, or overwrites data. Assistants present the impact and ask for your confirmation before running these. |

Tools available only in a larger profile are marked **`mk8s`** or **`full`** next to the access marker; everything else is in `core`.

The single read and delete tools that work for every resource kind. Use these to list, inspect, or delete resources — pass the `kind` (`workload`, `secret`, `gvc`, and so on); secrets are read-only. All are in `core`.

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |
| `list_resources` | List Resources of a Kind | List resources of one kind as a summary table. | Read |
| `get_resource` | Get a Resource | Fetch one resource by kind and name, with its full JSON. Secrets return metadata only — the API never includes their data. | Read |
| `delete_resource` | Delete a Resource | Delete one resource by kind and name. The single delete tool for every deletable kind — secrets are not deletable. | Destructive |

## Jobs

Each job tool does a whole task in one call: it reads the state it needs, makes the change, waits up to about 40 seconds for the result, and returns the outcome. When the task needs longer, the result names the exact call that continues it. `create_secret` and `rotate_secret` under [Secrets](#secrets) and `create_domain` under [Custom domains](#custom-domains) work the same way. All are in `core`.

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |
| `deploy_app` | Deploy an App | Build and deploy an HTTP app: from the app files stored with `write_app_files`, a GitHub or GitLab repository, or an existing image. Creates or updates a standard workload with production defaults (health checks, and two replicas so a deploy never takes it offline), grants access to the secrets its env references, and returns the public URL once it is ready. `timeoutSeconds` raises the platform's 5 second request limit for slow requests, and more replicas than the org's quota allows are refused before anything is built. With no GVC named, it uses the GVC it created for apps, asks before using any other, and creates the org's first one in the location you choose. It replaces a workload it didn't create only after your explicit yes. Serverless, multi-container, cron, and non-HTTP workloads use `create_workload`. | Destructive |
| `add_database` | Add a Database | Install PostgreSQL, MySQL, MariaDB, MongoDB, or Redis from the Template Catalog with credentials Control Plane generates, let the named workloads connect, and return the host, port, and the env values an app uses as `cpln://secret` references. No credential passes through the chat. It starts one instance: Redis also has a failover tier, and PostgreSQL and MongoDB failover are separate templates. With no GVC named, it places the database the way `deploy_app` places an app. | Write |
| `diagnose_workload` | Diagnose a Workload | Find out why a workload is unhealthy: reads its deployments, events, and recent error logs, and returns each likely cause with its evidence and the fix. Also in `readonly`. | Read |
| `restart_workload` | Restart a Workload | Replace every replica with a fresh one on the same spec, so the workload rereads its secrets and env, then wait until it is ready. | Destructive |
| `rollback_workload` | Rollback a Workload | Put a workload back on its previous image, or on a given one, changing nothing else, then wait until it is ready. | Destructive |
| `promote_workload` | Promote a Workload | Run a workload in another GVC of the same org with its current spec, such as staging to production, with an optional image and env values for the target. Grants access to the secrets its env references and overwrites a workload of the same name there. | Destructive |
| `allow_workload_access` | Allow Workload Access | Let other workloads reach a workload through its internal firewall, keeping every other rule, and return the internal URL the callers use. Also takes callers back out. | Write |
| `grant_cloud_access` | Grant Cloud Access | Give a workload credential-free access to AWS, GCP, or Azure through an existing cloud account: sets up its identity, binds the access, and waits until the identity reports it usable. | Write |

## Images

Build container [images](/reference/image) on Control Plane and follow the build. An image record is created by pushing, so there is no create or update tool — list, inspect, and delete image records with the [generic tools](#generic-resource-tools) using `kind: image`.

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |
| `write_app_files` | Write App Files | Write or edit an app's files (whole text files, appends for a large file in parts, exact-text edits, deletions, and moves or renames, uploaded files included) under an app name, for chats that cannot write files or agents without the `cpln` CLI (an agent with a filesystem and the CLI writes a local folder and builds it with the CLI instead). Files you have to provide yourself, such as pictures, come in through an upload link from `create_app_files_upload_link`; files attached to the chat cannot be forwarded. The files are stored on Control Plane between calls; the same name is the image name `build_image` produces. Limits match GitHub's: 100 MB per file, 1 GB per app. | Write |
| `build_image` | Build an Image | Build an image from a GitHub or GitLab repository, or from the app files stored with `write_app_files`, and push it to the org's private registry. Returns a build id; the build keeps running after the call returns. Building an existing `NAME:TAG` replaces that image. | Destructive |
| `get_image_build` | Get an Image Build Status and Log | Read a build's status, progress events, and log by its build id. | Read |
| `create_app_files_upload_link` | Create an App Files Upload Link | Get an upload link for files you have to provide (pictures, fonts, PDFs, data). Open it in a browser and drop every file at once: the page sorts each one into place, such as the logo into its own spot and a set of photos into their folder, where order does not matter, and you can move any file before uploading. The link works for an hour, up to 100 MB per file. | Write |
| `get_app_files` | Get App Files | List an app's stored files, read one (in slices for a large file), or get a short-lived download link (tar.gz) for all of them. Also reports where each of the app's images was built from: stored files, a repository, a folder uploaded with the CLI, or a push outside a Control Plane build. | Read |

No Docker daemon is involved: the build service clones the repository or assembles the stored app files, detects how to build it (using the Dockerfile when one is present, otherwise by auto-detecting the stack), and always produces a `linux/amd64` image. Building an existing `NAME:TAG` replaces that image, so prefer a fresh tag. `deploy_app` under [Jobs](#jobs) builds and deploys in one call.

<Note>
  The MCP server has no access to your filesystem, so a folder on your machine builds through the CLI instead: [`cpln image build --remote --dir PATH --name NAME:TAG`](/cli-reference/get-started/images#build-options) uploads the folder and builds it the same way, also without Docker.
</Note>

A **private** repository needs a one-time browser authorization per organization. The first build that needs it returns an authorization link instead of starting a build; open the link, approve access, then ask the assistant to build again. The link is single-use and expires shortly. Later builds in that organization run without prompting.

## Secrets

[Secret](/reference/secret) values never pass through the chat. `list_resources` and `get_resource` show a secret's metadata, never its data. `create_secret` fills a new secret with values Control Plane generates, or hands you a Console link where you type values only you have; `rotate_secret` replaces the values and restarts the workloads that use them. No tool accepts, reveals, or deletes a secret value, and deleting a secret stays in the [Console](https://console.cpln.io), the [CLI](/cli-reference/overview), [Terraform](/iac/terraform), [Pulumi](/iac/pulumi), or the [API](/api-reference/api). To let a workload read a secret, use `grant_workload_secret_access` under [Workloads](#workloads); `deploy_app` and `promote_workload` grant it for the secrets their env references.

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |
| `create_secret` | Create a Secret | Create a secret with random values Control Plane generates now, or get a Console link prefilled with its name, type, and keys where you type the values. No input accepts a value and no result contains one. | Write |
| `rotate_secret` | Rotate a Secret | Replace a secret's values, generated again or entered by you through a Console link, and restart the workloads that use it. Anything outside Control Plane that holds the old values stops working. | Destructive |

## Terraform & IaC

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |

| `export_terraform` | Export an existing resource to Terraform | Generate Terraform HCL for existing resources from a self link, single or in bulk. | Read |

<Note>
  Terraform and Pulumi tag every resource they manage with `cpln/managedByTerraform: "true"`. When `get_resource` reads such a resource, or any tool changes one, the result tells the assistant to warn you: a change made through the MCP server drifts from your code, and the next apply can revert it unless your code gets the change too.
</Note>

## Managed Kubernetes

Provision and update [managed Kubernetes](/mk8s/overview) clusters on every supported provider with two tools that take the provider and its settings. They are available in the `mk8s` and `full` profiles: connect to `https://mcp.cpln.io/mcp?toolsets=mk8s` to use them.

| Name | Label | Description | Access |
| :--- | :---- | :---------- | :----- |
| `create_mk8s` | Create an mk8s Cluster | Create a cluster on AWS, GCP, Azure, DigitalOcean, Hetzner, Linode, Lambda Labs, Oblivus, Paperspace, or Triton, or on hardware you own with `generic`. The provider's credential secret must exist first; the tool names any required setting that is missing. | Write · `mk8s` |
| `update_mk8s` | Update an mk8s Cluster | Update a cluster by sending only what changes. Node pool changes provision or remove nodes, region and network settings cannot change, and the Kubernetes version moves one minor version at a time. | Destructive · `mk8s` |
