A sandbox gives you a persistent cloud environment in one call. A **dev sandbox** is a browser IDE and terminal for a person; an **agent sandbox** is a box where AI agents run code in isolated sessions. Your files live on a home volume that survives restarts, and the sandbox suspends itself when nobody is using it. This page creates one of each, gets you inside, and explains what happens when you walk away. For the model behind it see the [sandbox concept](/concepts/sandbox); for every field see the [sandbox reference](/reference/sandbox/general).

## Choose a sandbox type

| | Dev sandbox | Agent sandbox |
| :-- | :-- | :-- |
| Made for | One person writing code | Agents and automation running code |
| You get | VS Code in the browser, a terminal, SSH for desktop IDEs, your app at a URL | An HTTP API where your agent opens sessions, runs commands, moves files, and previews ports |
| Sign in with | Your Control Plane account (`connect` on the sandbox) | A token the server generates |
| Default size | 1 CPU, 2 GiB | 4 CPU, 8 GiB |
| Console label | Dev Sandbox | Agent Sandbox |

## Prerequisites

- An [org](/reference/org). Every sandbox lives in the org's sandbox GVC, tagged `cpln/sandboxGvc`: `default` in orgs created with the built-in default GVC, otherwise `sandboxes`, created with your first sandbox; `GET /org/{org}/gvc/-sandbox` names it. Creating that GVC needs `create` on GVCs, only when the org has no sandbox GVC yet.
- `connect` on the sandbox to sign in to a dev sandbox or create sessions on an agent sandbox; `view` to see it.
- The `cpln` CLI if you want to work from your terminal. The `cpln sandbox` commands find the org's sandbox GVC themselves; do not pass `--gvc`. They need a current CLI; run `cpln sandbox --help` to see what yours supports.

## Dev sandbox in five minutes

<Steps>
  <Step title="Create it">
    <Tabs>
      <Tab title="Console UI">
        Open **Sandboxes** in the Console, start a new sandbox, give it a name, keep **Dev Sandbox**, and create. The **GVC** field is fixed to the org's sandbox GVC; every other field has a default.
      </Tab>
      <Tab title="CLI">
        ```bash
        cpln sandbox create my-dev --org my-org
        ```
      </Tab>
    </Tabs>

    The sandbox shows **Ready** within a minute or two.
  </Step>
  <Step title="Open the IDE">
    In the Console, open the sandbox from **Dev Sandboxes** and choose the IDE. From your terminal:

    ```bash
    cpln sandbox connect my-dev --org my-org
    ```

    Either way you are signed in as yourself. There is no password.
  </Step>
  <Step title="Get your code in and run it">
    In the IDE's terminal:

    ```bash
    cd ~/workspace
    git clone https://github.com/you/your-app.git
    cd your-app
    npm install && npm run dev -- --host 0.0.0.0 --port 8080
    ```

    Bind the server to `0.0.0.0` on port `8080`, the sandbox's app port. `~/workspace` is on the home volume, so the clone survives restarts.
  </Step>
  <Step title="Open your app">
    The sandbox's endpoint serves your app at `/`. Print it from inside the box with `sandbox url 8080`, or use the **App** button in the Console. Until something listens on the port, the URL shows a waiting page.
  </Step>
</Steps>

Everything else about a dev sandbox, from desktop IDEs to the AI coding assistants it ships with, is in [Work in a dev sandbox](/guides/sandbox/dev-sandbox).

## Agent sandbox in five minutes

<Steps>
  <Step title="Create it">
    ```bash
    cpln sandbox create my-agent --type worker --org my-org
    ```

    An agent sandbox is `type: worker` in the spec; the Console form does the same with **Type: Agent Sandbox**. The server sizes it at 4 CPU and 8 GiB and generates its token.
  </Step>
  <Step title="Open a session">
    A session is where one task runs: its own workspace, its own container, its own token.

    ```bash
    cpln sandbox session create --sandbox my-agent --id task-1 --image python:3.12-slim --org my-org
    ```
  </Step>
  <Step title="Run something and get the result back">
    ```bash
    echo 'print(sum(range(10)))' > task.py
    cpln cp ./task.py my-agent:task.py --session task-1 --org my-org
    cpln sandbox session exec task-1 --sandbox my-agent --org my-org -- python3 task.py
    ```

    The command's output streams to your terminal and its exit code becomes the CLI's. Files the task writes come back the same way: `cpln cp my-agent:out.json ./out.json --session task-1 --org my-org`.
  </Step>
  <Step title="End the session">
    ```bash
    cpln sandbox session delete task-1 --sandbox my-agent --org my-org
    ```

    The session's log stays readable afterwards. The sandbox keeps running for the next task and suspends itself when idle.
  </Step>
</Steps>

Doing the same from your own code, with per-task images, previews, logs, and an orchestrator pattern, is in [Run agents in an agent sandbox](/guides/sandbox/agent-sandbox).

## When you walk away

- **It suspends itself.** After 5 minutes with no requests and nothing running inside (a build or an agent you left going keeps it up), the sandbox suspends in place. Opening it again wakes it in seconds. Files stay; running processes do not. Set `scaleToZeroDelay` (30 to 3600 seconds) to change the wait.
- **Suspend it on purpose.** `cpln sandbox stop my-dev --org my-org` stops it until `cpln sandbox start my-dev --org my-org`. Nothing wakes it in between. The Console offers the same on the sandbox's row as **Suspend** and **Unsuspend**.
- **Delete it.** `cpln sandbox delete my-dev --org my-org` removes the sandbox and its home volume.

<Warning>
  Deleting a sandbox deletes its home volume: cloned repos, credentials, IDE settings, installed packages, and session logs. Suspend it instead when you want to keep the state.
</Warning>
