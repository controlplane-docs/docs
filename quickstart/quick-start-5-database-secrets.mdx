## Overview

Add a PostgreSQL database to your GVC: create a credentials secret, install the database from the [Template Catalog](/template-catalog/overview), and connect a real application (Grafana) to it the way every workload reads every secret on Control Plane, through the identity, policy, and secret reference chain.

**What you'll build:**

- A dictionary secret holding the database credentials; the database and Grafana both read it.
- A PostgreSQL database (workload, volume, identity, policy) installed from the Template Catalog, consuming that secret.
- Grafana running against that database, with credentials it never stores.

## Prerequisites

- Completed [1. Deploy your first workload](/quickstart/quick-start-1-deploy-workload): the `quickstart-gvc` GVC exists and the CLI is installed and authenticated.
- For the CLI path: [Helm](https://helm.sh/docs/intro/install/) v3 or later installed.
- For the Terraform or Pulumi path: the provider configuration from part 1.

## How secret access works

A workload reads a [secret](/reference/secret) only when three things are all in place. Miss any one and the value is absent at runtime:

| Step | What must be true | Without it |
| ---- | ----------------- | ---------- |
| 1. Identity | An [identity](/reference/identity) is linked to the workload (`spec.identityLink`) | The workload has nothing to authenticate as; its secret references cannot resolve and its deployment pauses |
| 2. Policy | A [policy](/reference/policy) grants that identity `reveal` on the secret | The identity is not allowed to read the secret; the deployment stays paused until access is granted |
| 3. Reference | The secret is injected as `cpln://secret/NAME` (env var or volume) | The workload never receives the value; there is nothing to inject |

<Note>
The permission to grant is `reveal`. The similarly named `view` permission exposes only a secret's metadata, never its value.
</Note>

The postgres template builds this chain for its own workload; in this part you build the secret it consumes, then extend the chain to Grafana.

<Steps>

<Step title="Open the Template Catalog">
In the left menu under `Templates`, click `Catalog`, then select the `postgres` template.
</Step>

<Step title="Configure the release">
Click `Create Template Release`. On the `Install` page, enter `db` as the `Release Name`, select `quickstart-gvc` as the `GVC`, and select `3.4.1` from the `Template Version` dropdown. This part is written against 3.4.1; other versions differ.

## Step 5: Deploy Grafana wired to the database

Click `apply` in the upper right corner of the Console and paste the following manifest:

```yaml
kind: workload
name: grafana
gvc: quickstart-gvc
spec:
  type: standard
  identityLink: //identity/grafana-identity
  containers:
    - name: grafana
      image: grafana/grafana:latest
      cpu: 200m
      memory: 256Mi
      ports:
        - number: 3000
          protocol: http
      env:
        - name: GF_DATABASE_TYPE
          value: postgres
        - name: GF_DATABASE_HOST
          value: db-postgres.quickstart-gvc.cpln.local:5432
        - name: GF_DATABASE_NAME
          value: 'cpln://secret/db-credentials.database'
        - name: GF_DATABASE_USER
          value: 'cpln://secret/db-credentials.username'
        - name: GF_DATABASE_PASSWORD
          value: 'cpln://secret/db-credentials.password'
  defaultOptions:
    autoscaling:
      metric: disabled
      minScale: 1
      maxScale: 1
    capacityAI: false
  firewallConfig:
    external:
      inboundAllowCIDR:
        - 0.0.0.0/0
```

Grafana stores its dashboards, users, and settings in the database. Its identity link plus the policy let the three `cpln://secret/` references resolve to the values stored in `db-credentials`; the manifest itself contains no credentials.

## Step 1: Create the credentials secret

Create a dictionary secret with the three keys the template expects:

```bash
cpln secret create-dictionary --name db-credentials \
  --entry username=postgres \
  --entry password="$(openssl rand -hex 24)" \
  --entry database=quickstart
```

## Step 2: Install the postgres template

Install the template as a release named `db`, pointing it at your secret:

```bash
cpln helm install db oci://ghcr.io/controlplane-com/templates/postgres \
  --version 3.4.1 \
  --gvc quickstart-gvc \
  --set config.credentialsSecretName=db-credentials
```

The release creates the `db-postgres` workload, the `db-pg-vs` volume set, and the `db-pg-identity` identity with its `db-pg-policy` policy granting `reveal` on your secret. List the org's releases to confirm `db` appears:

```bash
cpln helm list
```

<Warning>
The postgres template runs a single replica. Do not scale it up.
</Warning>

## Step 3: Create an identity for Grafana

```bash
cpln identity create --name grafana-identity --gvc quickstart-gvc
```

## Step 4: Grant access with a policy

Create a policy targeting the credentials secret:

```bash
cpln policy create --name grafana-secrets-policy \
  --target-kind secret \
  --resource db-credentials
```

Bind the `reveal` permission to the identity:

```bash
cpln policy add-binding grafana-secrets-policy \
  --permission reveal \
  --identity grafana-identity \
  --gvc quickstart-gvc
```

## Step 1: Define the credentials secret

Add to your `main.tf` from part 1. The password arrives through a sensitive variable, so no credential lands in your configuration:

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}

resource "cpln_secret" "db_credentials" {
  name = "db-credentials"

  dictionary = {
    username = "postgres"
    password = var.db_password
    database = "quickstart"
  }
}
```

## Step 2: Install the postgres template

The values are the template's complete 3.4.1 defaults with `config.credentialsSecretName` pointed at your secret; the [template's values file](https://github.com/controlplane-com/templates/blob/main/postgres/versions/3.4.1/values.yaml) documents each option.

```hcl
resource "cpln_catalog_template" "db" {
  name     = "db"
  template = "postgres"
  version  = "3.4.1"
  gvc      = cpln_gvc.quickstart.name

  values = <<-EOT
    image: postgres:18

    resources:
      minCpu: 200m
      minMemory: 128Mi
      maxCpu: 500m
      maxMemory: 256Mi

    config:
      credentialsSecretName: ${cpln_secret.db_credentials.name}

    volumeset:
      capacity: 10
      autoscaling:
        enabled: false
        maxCapacity: 100
        minFreePercentage: 10
        scalingFactor: 1.2

    internalAccess:
      type: same-gvc
      workloads:

    pgbouncer:
      enabled: false
      image: edoburu/pgbouncer:v1.25.1-p0
      poolMode: transaction
      defaultPoolSize: 25
      maxClientConn: 1000
      replicas: 1
      resources:
        cpu: 200m
        memory: 128Mi

    backup:
      enabled: false
      image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0
      schedule: '0 2 * * *'
      resources:
        cpu: 100m
        memory: 128Mi
      provider: aws
      aws:
        bucket: my-postgres-bucket
        region: us-east-1
        cloudAccountName: my-s3-cloud-account
        policyName: my-postgres-backup-policy
        prefix: postgres/backups
      gcp:
        bucket: my-postgres-bucket
        cloudAccountName: my-gcs-cloud-account
        prefix: postgres/backups
      minio:
        endpoint: http://my-minio-workload:9000
        bucket: my-postgres-bucket
        credentialsSecretName: my-postgres-minio-credentials
        prefix: postgres/backups
  EOT
}
```

The release creates the `db-postgres` workload, the `db-pg-vs` volume set, and the `db-pg-identity` identity with its `db-pg-policy` policy granting `reveal` on your secret. The resource's `resources` output lists everything it created.

## Step 3: Define the identity, policy, and Grafana workload

The workload depends on the policy so its secret references resolve on the first deployment:

```hcl
resource "cpln_identity" "grafana" {
  gvc  = cpln_gvc.quickstart.name
  name = "grafana-identity"
}

resource "cpln_policy" "grafana_secrets" {
  name         = "grafana-secrets-policy"
  target_kind  = "secret"
  target_links = [cpln_secret.db_credentials.name]

  binding {
    permissions     = ["reveal"]
    principal_links = [cpln_identity.grafana.self_link]
  }
}

resource "cpln_workload" "grafana" {
  depends_on = [cpln_policy.grafana_secrets]

  gvc  = cpln_gvc.quickstart.name
  name = "grafana"
  type = "standard"

  identity_link = cpln_identity.grafana.self_link

  container {
    name   = "grafana"
    image  = "grafana/grafana:latest"
    cpu    = "200m"
    memory = "256Mi"

    ports {
      protocol = "http"
      number   = 3000
    }

    env = {
      GF_DATABASE_TYPE     = "postgres"
      GF_DATABASE_HOST     = "db-postgres.quickstart-gvc.cpln.local:5432"
      GF_DATABASE_NAME     = "cpln://secret/db-credentials.database"
      GF_DATABASE_USER     = "cpln://secret/db-credentials.username"
      GF_DATABASE_PASSWORD = "cpln://secret/db-credentials.password"
    }
  }

  options {
    capacity_ai     = false
    timeout_seconds = 5

    autoscaling {
      metric    = "disabled"
      min_scale = 1
      max_scale = 1
    }
  }

  firewall_spec {
    external {
      inbound_allow_cidr = ["0.0.0.0/0"]
    }
  }
}

output "grafana_endpoint" {
  value = cpln_workload.grafana.status[0].canonical_endpoint
}
```

Grafana stores its dashboards, users, and settings in the database; the configuration itself contains no credentials.

Grafana reaches the database because the template sets the `db-postgres` internal firewall to accept traffic from the same GVC, the mechanism from [part 4](/quickstart/quick-start-4-service-to-service). A workload's `inboundAllowType` governs only who may connect to that workload: `grafana` staying at `none` means nothing can connect to Grafana internally, and takes nothing away from what Grafana itself can reach.

<Note>
A workload whose `cpln://secret/` reference is missing its secret or its `reveal` policy pauses its deployment, and the deployment status states the reason; installing the template before the secret exists pauses `db-postgres` the same way. Create the missing piece, then resume immediately with `cpln workload force-redeployment` or, in the Console, `Actions` then `Force Redeployment`.
</Note>

## Verify

Both workloads report `Ready` once the database volume finishes provisioning; `db-postgres` comes up first, then Grafana connects to it.

<Steps>

<Step title="Open Grafana">
Open the `grafana` workload's canonical endpoint (under `Endpoints` on its summary page, or from `cpln workload get grafana`). Log in with `admin` / `admin` and set a new password when prompted. Grafana is running entirely on your database: every dashboard, user, and setting it saves is a row in postgres.
</Step>

<Step title="See the application's tables">
List the tables Grafana created in the database. From the CLI:

```bash
cpln workload exec db-postgres --gvc quickstart-gvc -- psql -U postgres -d quickstart -c "\dt"
```

Or in the Console: open the `db-postgres` workload, click `Connect` in the left pane, keep `bash` as the `Command`, click `Connect`, and run the `psql` command in the terminal. The table list includes Grafana's schema (`dashboard`, `user`, `org`, and dozens more): the application wrote all of it through the secret chain.
</Step>

<Step title="See your login stored in your database">
Grafana's `user` table holds the account whose password you just set. Query it:

```bash
cpln workload exec db-postgres --gvc quickstart-gvc -- psql -U postgres -d quickstart -c 'SELECT login, email, password FROM "user";'
```

```text
 login |      email      |                                               password
-------+-----------------+------------------------------------------------------------------------------------------------------
 admin | admin@localhost | 9c4ecbe4f8fb9f8e56694c54f463f9229566403008efde5646edf4c03a1e46b5b5c6b56746061dd578d589e4937f7c0419f0
(1 row)
```

That row is your Grafana login with its password stored as a salted hash: real application data, in your database, written through the secret chain.
</Step>
