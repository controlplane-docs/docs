## Overview

TimescaleDB Highly Available deploys [TimescaleDB](https://www.tigerdata.com/docs) — the time-series database built as a PostgreSQL extension — as a multi-member PostgreSQL 18 cluster in one location. [Patroni](https://patroni.readthedocs.io/) manages the members, elects a leader and fails over automatically when the leader is lost; a dedicated [etcd](/template-catalog/templates/etcd) cluster holds the consensus state. An HAProxy workload gives applications one stable address that always routes to the current leader, and an optional PgBouncer in front of it pools connections. The TimescaleDB extension is preloaded on every member and created automatically in your database, so hypertables, compression, continuous aggregates and retention policies work from the first connection. Scheduled `pg_dumpall` backups to S3, GCS or MinIO are optional.

Database credentials are **not** template values. The cluster reads its username, password and database name from a [dictionary secret](/guides/create-secret/dictionary) you create before installing, so no password passes through Helm or lands in the release. The template creates no credential secret of its own.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have. It does not create or manage a GVC. Every workload runs in each location the GVC has, so use a GVC with a single location for this template.
</Note>

<Info>
TimescaleDB Community is licensed under the Timescale License (TSL) plus the PostgreSQL License. It is free to self-host at any scale, including compression, continuous aggregates and retention; the license only forbids reselling TimescaleDB itself as a managed database service.
</Info>

## Prerequisites

One secret must exist before you install. It holds the credentials your applications put in their connection strings. Secrets are org-level, so no GVC flag is involved.

<Steps>
  <Step title="Create the database credentials secret">
    A [dictionary secret](/guides/create-secret/dictionary) holding exactly three keys — `username`, `password` and `database`. Patroni creates that user as the cluster superuser and that database the first time the cluster is initialized, runs `CREATE EXTENSION timescaledb` in it, and uses the same password for its internal replication role:

    ```bash
    cpln secret create-dictionary --name CREDENTIALS_SECRET_NAME \
      --entry username=postgres \
      --entry password='YOUR-STRONG-PASSWORD' \
      --entry database=mydb
    ```

    Set `postgres.credentialsSecretName` to this name. Read it back later with `cpln secret reveal CREDENTIALS_SECRET_NAME -o yaml` — a bare `cpln secret reveal` prints only a summary table, not the values. Secret names are org-wide, so give each release its own.
  </Step>
</Steps>

<Warning>
**Create the secret before installing, or the deployment wedges silently.** The chart refuses to render when `postgres.credentialsSecretName` is blank, but a name pointing at a secret that does not exist installs successfully and then never starts. The container never runs, so `cpln logs` returns zero lines. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-timescaledb-ha --gvc GVC_NAME -o yaml
```

```text
The secret CREDENTIALS_SECRET_NAME no longer exists. Workload updates are paused until the
secret is added or the reference to the secret removed.
```

Use `get-deployments` — plain `cpln workload get` has no `versions` key. Creating the missing secret repairs the deployment on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-timescaledb-ha --gvc GVC_NAME` to skip the wait.
</Warning>

Backups are optional and need a bucket plus, for AWS or GCP, a Control Plane [cloud account](/guides/create-cloud-account); MinIO backups need a second dictionary secret holding `accessKey` and `secretKey` — see [Backing Up](#backing-up). Nothing else is required for a default install.

## Configuration

Each block below is the shipped default for that part of `values.yaml`.

### Cluster and Resources

```yaml
replicas: 3   # 1 leader + 2 hot standbys; Patroni forms the cluster and handles failover

resources:
  minCpu: 500m
  minMemory: 1Gi        # time-series ingest is memory-sensitive; 2Gi ceiling is the small-prod floor
  maxCpu: 1
  maxMemory: 2Gi

image: timescale/timescaledb-ha:pg18.4-ts2.28.3  # PostgreSQL 18 + TimescaleDB 2.28.3 Community, Patroni bundled

multiZone: false        # spread replicas across zones in the location
```

- `replicas` — Number of TimescaleDB members. Keep at least 3 for a cluster that survives the loss of one member; one member is the leader and accepts writes, the others stream from it. `replicas: 1` renders a single-member cluster with no failover.
- `image` — The `timescale/timescaledb-ha` image bundles PostgreSQL, the TimescaleDB extension and Patroni. Keep the PostgreSQL major at 18 unless you also change `backup.image` to match.
- `multiZone` — Spread the members across availability zones within the location, when the location supports it.

<Note>
On a stateful workload the ratio of `maxCpu` to `minCpu` may not exceed 4:1. Raising `maxCpu` without raising `minCpu` can cross that limit and is rejected when the workload is applied.
</Note>

### Credentials

```yaml
postgres:
  # REQUIRED PREREQUISITE SECRET — CREATE IT BEFORE YOU INSTALL.
  # A `dictionary` secret holding exactly three keys: `username`, `password`
  # and `database`. The TimescaleDB extension is created automatically in the
  # database that secret names. If it does not exist at install time the
  # deployment WEDGES silently — `cpln logs` returns nothing at all. See
  # Prerequisites in the README for the create-dictionary command.
  credentialsSecretName: my-timescaledb-ha-credentials
```

The three keys are applied when the cluster is first initialized. Changing the secret afterwards does not change the stored passwords — see [Rotating the Password](#rotating-the-password). The TimescaleDB extension is created only in the database the secret names; any other database you create needs its own `CREATE EXTENSION IF NOT EXISTS timescaledb`.

### Storage

```yaml
volumeset:
  capacity: 10          # initial capacity in GiB per replica (minimum 10)
  autoscaling:
    enabled: false      # set to true to grow each volume automatically
    maxCapacity: 100    # maximum capacity in GiB when autoscaling is enabled
    minFreePercentage: 10 # free-space threshold that triggers scaling
    scalingFactor: 1.2  # how much to scale up by
```

Each member has its own volume of this size. The cluster caps the WAL retained for a member that is offline at a quarter of `volumeset.capacity`, so a member that stays down does not fill the leader's disk; a member that exceeds the cap is re-cloned from the leader when it returns.

### Internal Access

```yaml
internal_access:
  type: same-gvc        # options: same-gvc, same-org, workload-list
  workloads:            # only when type is same-gvc or workload-list
    #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

| Type | Who can reach port `5432` |
|------|-------------|
| `same-gvc` | Every workload in the same GVC |
| `same-org` | Every workload in the same org |
| `workload-list` | Only the workloads listed in `internal_access.workloads` |

The cluster has no public endpoint. The same setting is applied to the members, the HAProxy workload and the PgBouncer workload. A change can take several minutes to take effect — re-test before concluding it did not apply.

<Warning>
With `workload-list`, the list must also contain the release's own workloads, because the members replicate from each other and HAProxy, PgBouncer and the backup job all connect to them: `//gvc/GVC_NAME/workload/RELEASE_NAME-timescaledb-ha`, `//gvc/GVC_NAME/workload/RELEASE_NAME-timescaledb-ha-proxy`, and `RELEASE_NAME-pgbouncer` and `RELEASE_NAME-timescaledb-ha-backup` when they are enabled — plus your applications. A list without them leaves HAProxy waiting for members it cannot reach.
</Warning>

### etcd Cluster

The bundled [etcd](/template-catalog/templates/etcd) template provides the consensus store. Its own values are passed through under `etcd`:

```yaml
etcd:
  replicas: 3
  resources:
    cpu: 500m
    memory: 512Mi
  multiZone: false
  tuning:
    # Passed through to the bundled etcd. Without compaction its backend grows
    # with time alone — Patroni renews its lease every ~10s and every renewal is
    # a revision — until it hits the quota and etcd goes READ-ONLY.
    autoCompactionMode: periodic # periodic (retention is a duration) or revision (a revision count)
    autoCompactionRetention: 1h # periodic needs an explicit unit (1h, 30m, 24h); revision takes a count
    quotaBackendBytes: 0 # backend size limit in bytes; 0 = etcd's own default of 2 GiB
  volumeset:
    capacity: 10
  internal_access:
    type: same-gvc
    workloads:
      #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

- `etcd.replicas` — Must be an **odd** number of at least 3 (3, 5, 7); the chart refuses other values at render. Choose it at install time — the etcd template does not support changing the member count on a running release.
- `etcd.internal_access` — Must allow the TimescaleDB members to reach etcd on port `2379`. With `workload-list`, include `//gvc/GVC_NAME/workload/RELEASE_NAME-timescaledb-ha` and `//gvc/GVC_NAME/workload/RELEASE_NAME-etcd`.

#### etcd History Compaction

Patroni renews its leader lease every few seconds and every renewal is a new etcd revision, so the etcd backend grows with time alone unless old revisions are compacted. Uncompacted, an otherwise idle cluster reaches etcd's 2 GiB backend quota in a matter of months, etcd raises a `NOSPACE` alarm and goes read-only, and the TimescaleDB members can no longer renew their leases. The `etcd.tuning` defaults — `periodic`, `1h` and `0` (etcd's own 2 GiB limit) — keep the backend flat and should be left alone. The [etcd template](/template-catalog/templates/etcd#compaction-and-backend-growth) documents the mechanism, the accepted value formats and the read-only inspection commands.

Template version `1.0.0` did not compact — see [Upgrading From 1.0.0](#upgrading-from-1-0-0).

### HAProxy Leader Endpoint

Only the leader accepts writes; the other members are read-only. HAProxy checks every member's Patroni REST API and sends port `5432` traffic only to the one that reports itself primary, so applications keep one address through a failover.

```yaml
proxy:
  enabled: true
  image: haproxy:2.9
  resources:
    cpu: 100m
    memory: 128Mi
  minReplicas: 2
  maxReplicas: 2
```

| Endpoint on `RELEASE_NAME-timescaledb-ha-proxy` | Purpose |
|---|---|
| `:5432` | PostgreSQL, routed to the current leader |
| `:8404/healthz` | Returns healthy while at least one member reports itself primary |
| `:8405/stats` | HAProxy stats page showing each member's health-check state |

<Note>
HAProxy must be enabled for backups, which connect through it. It is forced on when `pgbouncer.enabled: true`. HAProxy reads the member list from `replicas` when it starts, so after changing `replicas` force a redeployment of `RELEASE_NAME-timescaledb-ha-proxy`.
</Note>

### PgBouncer Connection Pooling

PgBouncer multiplexes many application connections into a smaller pool of real database connections. It connects to HAProxy, so leader routing and failover are handled for it, and it reads the same credentials secret — nothing extra to configure. When enabled it becomes the endpoint your applications connect to.

```yaml
pgbouncer:
  enabled: false
  image: edoburu/pgbouncer:v1.25.1-p0
  poolMode: transaction   # options: session, transaction, statement
  defaultPoolSize: 25      # real Postgres connections PgBouncer maintains per pod
  maxClientConn: 1000      # maximum client connections PgBouncer accepts per pod
  maxDbConnections: 100    # hard cap on total Postgres connections across all pods
  minReplicas: 2
  maxReplicas: 4
  resources:
    cpu: 200m
    memory: 128Mi
```

| `poolMode` | Behaviour |
|------|-------------|
| `transaction` | The server connection is held for one transaction. Best for most web and API workloads; not compatible with `SET` variables, temporary tables or advisory locks. |
| `session` | Held for the whole client session. Compatible with everything, less reuse — raise `defaultPoolSize` to your expected concurrency. |
| `statement` | Returned after every statement. Transactions are not supported. |

<Warning>
**`maxDbConnections` is enforced per PgBouncer replica, not across the deployment.** PgBouncer replicas do not coordinate, so the real ceiling on server connections is `maxReplicas × maxDbConnections` — 4 × 100 = 400 with the shipped values, against a cluster `max_connections` of 100, of which 3 are reserved for superuser maintenance. Size `maxReplicas × maxDbConnections` to stay under 97, and treat `defaultPoolSize` the same way, or clients get `remaining connection slots are reserved` under load instead of being queued.
</Warning>

PgBouncer autoscales on requests per second between `minReplicas` and `maxReplicas`.

### Backup

A cron workload dumps every database and role with `pg_dumpall` through HAProxy on the schedule and uploads the compressed script to your bucket. Each provider's bucket, cloud account and policy steps are under [Backing Up](#backing-up).

```yaml
backup:
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0  # PG18 client, matches server major
  schedule: "0 2 * * *"   # daily at 2am UTC
  resources:
    cpu: 100m
    memory: 512Mi # 128Mi OOMKills the dump mid-backup (exitCode 137) and silently produces no backup

  provider: aws           # options: aws, gcp, minio

  aws:
    bucket: my-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: timescaledb/backups # folder where backups are stored

  gcp:
    bucket: my-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: timescaledb/backups

  minio:  # self-hosted MinIO or any S3-compatible endpoint
    endpoint: http://my-minio-workload:9000 # e.g. http://WORKLOAD_NAME:9000 for an internal MinIO deployment
    bucket: my-backup-bucket
    # REQUIRED PREREQUISITE SECRET when provider is `minio` — a `dictionary`
    # secret holding exactly two keys: `accessKey` and `secretKey`. For the
    # minio template these are its admin.username and admin.password.
    credentialsSecretName: my-timescaledb-ha-minio-credentials
    prefix: timescaledb/backups
```

- `backup.image` — The backup container's `pg_dumpall` must match the server major: tag `18.1.0` for the default PostgreSQL 18 image.
- `backup.schedule` — Standard five-field cron expression, evaluated in UTC.

## Connecting

This template exposes no public endpoint. Everything below is reachable from inside the GVC, subject to `internal_access.type`.

| What | Address | Notes |
|---|---|---|
| TimescaleDB, writes and reads | `RELEASE_NAME-timescaledb-ha-proxy.GVC_NAME.cpln.local:5432` | HAProxy routes to the current leader. Use this unless PgBouncer is enabled. |
| TimescaleDB, pooled | `RELEASE_NAME-pgbouncer.GVC_NAME.cpln.local:5432` | Only when `pgbouncer.enabled: true`. Prefer it when the pooler is on. |
| Any member, unrouted | `RELEASE_NAME-timescaledb-ha.GVC_NAME.cpln.local:5432` | Reaches whichever member answers, which may be a read-only replica. For diagnostics only. |
| HAProxy health and stats | `RELEASE_NAME-timescaledb-ha-proxy.GVC_NAME.cpln.local:8404/healthz`, `:8405/stats` | HTTP. |
| Credentials | `cpln secret reveal CREDENTIALS_SECRET_NAME -o yaml` | The `username`, `password` and `database` keys. Never stored in the Helm release. |

To verify from your own machine, tunnel to HAProxy and connect with `psql`:

```bash
cpln port-forward RELEASE_NAME-timescaledb-ha-proxy 5432:5432 --gvc GVC_NAME
```

```bash
psql "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -c "select pg_is_in_recovery(), extversion from pg_extension where extname = 'timescaledb'"
```

`pg_is_in_recovery()` returns `f` through HAProxy, because it always reaches the leader, and `extversion` confirms the TimescaleDB extension is installed in your database. The same query on a member directly returns `t` on a replica:

```bash
cpln workload exec RELEASE_NAME-timescaledb-ha --gvc GVC_NAME --replica RELEASE_NAME-timescaledb-ha-0 --container patroni-timescaledb -- psql -h 127.0.0.1 -U USERNAME -d DATABASE -c 'select pg_is_in_recovery()'
```

Use `--replica` to pick a member (`RELEASE_NAME-timescaledb-ha-0` through `RELEASE_NAME-timescaledb-ha-N`); without it the CLI picks one for you. The superuser credentials are already present in the container's environment, so `psql` does not prompt.

Applications should retry on connection errors with backoff. A failover, a rolling restart or a scale-down moves the leader, and connections open at that moment are reset while HAProxy re-routes to the new leader.

### Using Hypertables

Any PostgreSQL client or ORM works unchanged. Turn a regular table into a hypertable, partitioned by time, and query it with time buckets:

```sql
CREATE TABLE metrics (time timestamptz NOT NULL, device text, value double precision);
SELECT create_hypertable('metrics', by_range('time'));

INSERT INTO metrics VALUES (now(), 'sensor-1', 23.5);

SELECT time_bucket('1 hour', time) AS bucket, device, avg(value)
FROM metrics
GROUP BY bucket, device
ORDER BY bucket;
```

From here you can add columnar compression, continuous aggregates and retention policies — all Community features included in the default image. See the [hypertables guide](https://www.tigerdata.com/docs/learn/hypertables/understand-hypertables).

## Operations

### Checking Cluster State

Patroni's own tool shows every member, its role, its state and its replication lag:

```bash
cpln workload exec RELEASE_NAME-timescaledb-ha --gvc GVC_NAME --replica RELEASE_NAME-timescaledb-ha-0 --container patroni-timescaledb -- patronictl -c /tmp/patroni_config.yml list
```

`/tmp/patroni_config.yml` is the configuration the startup script writes in each member; `patronictl` needs it to find etcd. The same tool shows the cluster-wide settings Patroni keeps in etcd:

```bash
cpln workload exec RELEASE_NAME-timescaledb-ha --gvc GVC_NAME --replica RELEASE_NAME-timescaledb-ha-0 --container patroni-timescaledb -- patronictl -c /tmp/patroni_config.yml show-config
```

For HAProxy's view of the members — which one passes the primary health check — tunnel to the stats page and open `http://127.0.0.1:8405/stats` in a browser:

```bash
cpln port-forward RELEASE_NAME-timescaledb-ha-proxy 8405:8405 --gvc GVC_NAME
```

### Backing Up

Backups are off by default. Enable them with `backup.enabled: true`, pick a `backup.provider`, and complete that provider's setup below first. `RELEASE_NAME-timescaledb-ha-backup` runs on `backup.schedule`, connects through HAProxy with the `username` and `password` from your credentials secret, and uploads one `postgres-TIMESTAMP.sql.gz` object per run under `backup.PROVIDER.prefix`. The object is a gzip-compressed `pg_dumpall` script: every role and every database in the cluster, as plain SQL. HAProxy must be enabled.

Check the recent runs after enabling, and confirm the object actually landed in your bucket:

```bash
cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-timescaledb-ha-backup"}' --limit 50 --since 48h
```

<Warning>
**A zero-length backup object is a failed run, not a backup.** If `pg_dumpall` cannot reach the cluster, the upload still writes a tiny empty gzip under a normal-looking timestamped name and the job exits non-zero. Check the object size before restoring from it — a real dump is kilobytes at minimum. Keep `backup.resources.memory` at the shipped `512Mi` or above: at `128Mi` the dump is OOM-killed part-way through (`exitCode 137`), logs nothing, and produces no backup.
</Warning>

<Note>
This is a logical backup only. The image has no WAL archiver, so there is no continuous archiving or point-in-time recovery; what you can restore is the state at the last successful run. The volume set also keeps a final snapshot for 7 days when it is deleted.
</Note>

#### Backup Prerequisites

Complete the steps for your provider before enabling backups.

#### AWS S3

1. Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.

2. If you do not have one yet, create a Control Plane [cloud account](/guides/create-cloud-account) for the AWS account holding the bucket. Set `backup.aws.cloudAccountName` to its name.

3. Create an IAM policy scoped to exactly that bucket, replacing `YOUR_BUCKET_NAME`:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion",
                "s3:GetBucketLocation",
                "s3:AbortMultipartUpload",
                "s3:ListBucketMultipartUploads",
                "s3:ListMultipartUploadParts"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.policyName` to that policy's name. The template attaches it to the workload identity together with `cpln-connector` and nothing else — the bucket in your policy is the only storage the backup container can reach. Upgrading from `1.1.0` or earlier narrows this; see [Upgrading From 1.1.0](#upgrading-from-1-1-0).

#### GCS

1. Create a GCS bucket. Set `backup.gcp.bucket` to its name.

2. Create a Control Plane [cloud account](/guides/create-cloud-account) for the GCP project holding the bucket, and set `backup.gcp.cloudAccountName` to its name. Access is keyless — no credentials are stored.

3. Grant the cloud account's service account the **Storage Admin** role. The template additionally binds the identity to `roles/storage.objectAdmin` on exactly the bucket in `backup.gcp.bucket`.

#### MinIO

No cloud account is needed — the backup container authenticates with a second prerequisite secret and uses path-style addressing, so any S3-compatible endpoint works.

1. Create the bucket in MinIO. Set `backup.minio.bucket` to its name.

2. Set `backup.minio.endpoint` to the S3 API address including the port. For the [minio](/template-catalog/templates/minio) template deployed in the same GVC that is `http://WORKLOAD_NAME.GVC_NAME.cpln.local:9000`.

3. Create a [dictionary secret](/guides/create-secret/dictionary) holding exactly the keys `accessKey` and `secretKey`, and set `backup.minio.credentialsSecretName` to its name. For the `minio` template these are its admin username and password:

```bash
cpln secret create-dictionary --name MINIO_CREDENTIALS_SECRET_NAME \
  --entry accessKey=MINIO_ACCESS_KEY \
  --entry secretKey=MINIO_SECRET_KEY
```

The policy this template creates grants the identity `reveal` on this secret as well as the database credentials secret. If the secret does not exist at install time the deployment wedges exactly as described in [Prerequisites](#prerequisites).

### Restoring a Backup

<Warning>
**Neither procedure below has been rehearsed against this template.** Both follow TimescaleDB's own documentation and the chart's configuration, but a restore that has not been practised is not a recovery plan. Rehearse the one you depend on against a scratch release before you need it.
</Warning>

Restoring hypertables is **not** the vanilla PostgreSQL procedure. The target must run the **same TimescaleDB extension version** as the source (`2.28.3` for the default image — upgrade the extension after restoring, never before), and the data must be loaded with TimescaleDB's background workers stopped and its `timescaledb.restoring` setting on, which is what `timescaledb_pre_restore()` and `timescaledb_post_restore()` do. Loading hypertable rows without that fails with `invalid INSERT on the root table of hypertable`.

#### Restoring the Scheduled pg_dumpall Backup

The scheduled backup is a whole-cluster plain SQL script. TimescaleDB's documented restore wraps a single-database `pg_dump -Fc` archive in `timescaledb_pre_restore()` / `timescaledb_post_restore()`; a `pg_dumpall` script does not fit that shape directly, because it reconnects to each database as it goes, so there is no single point at which to call `timescaledb_pre_restore()` for the database being loaded. **Replaying the scheduled dump into a TimescaleDB database is therefore unverified on this template.** Use it to recover roles, non-hypertable databases, and as the source for a per-database restore: extract the `\connect DATABASE` section of the script and load it as in [Restoring a Single Database](#restoring-a-single-database) with the restoring setting on. Downloading the object is the same for every provider:

<Tabs>
  <Tab title="AWS S3">
    ```bash
    aws s3 cp "s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - | gunzip > postgres-TIMESTAMP.sql
    ```
  </Tab>
  <Tab title="GCS">
    ```bash
    gsutil cp "gs://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - | gunzip > postgres-TIMESTAMP.sql
    ```
  </Tab>
  <Tab title="MinIO">
    ```bash
    export AWS_ACCESS_KEY_ID="MINIO_ACCESS_KEY"
    export AWS_SECRET_ACCESS_KEY="MINIO_SECRET_KEY"
    aws configure set default.s3.addressing_style path

    aws s3 cp "s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - --endpoint-url "http://MINIO_ENDPOINT:9000" | gunzip > postgres-TIMESTAMP.sql

    unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
    ```
  </Tab>
</Tabs>

#### Restoring a Single Database

This is the procedure TimescaleDB documents, and the one to rehearse. It needs a `pg_dump` custom-format archive of one database, taken with a PostgreSQL 18 client; the scheduled job does not produce one, so take it yourself through HAProxy with `cpln port-forward RELEASE_NAME-timescaledb-ha-proxy 5432:5432 --gvc GVC_NAME` open:

```bash
export PGPASSWORD="PASSWORD"
pg_dump -h 127.0.0.1 -p 5432 -U USERNAME -d DATABASE -Fc -f DATABASE.bak
```

Restore it into a database on the target cluster that already has the extension — on a fresh install of this template, the database named in your credentials secret qualifies. Connect through HAProxy so every statement lands on the leader; the replicas receive the data through normal streaming replication:

```bash
psql -h 127.0.0.1 -p 5432 -U USERNAME -d DATABASE -c "CREATE EXTENSION IF NOT EXISTS timescaledb;"
psql -h 127.0.0.1 -p 5432 -U USERNAME -d DATABASE -c "SELECT timescaledb_pre_restore();"
pg_restore -h 127.0.0.1 -p 5432 -U USERNAME -d DATABASE -Fc --no-owner DATABASE.bak
psql -h 127.0.0.1 -p 5432 -U USERNAME -d DATABASE -c "SELECT timescaledb_post_restore();"
unset PGPASSWORD
```

Do not add `-j` to `pg_restore` — parallel restore does not restore the TimescaleDB catalogs correctly. A `must be owner of extension timescaledb` error from `pg_restore` can be ignored when the extension already exists. Until `timescaledb_post_restore()` has run, background jobs (compression, retention, continuous aggregate refresh) stay stopped on that database.

### Rotating the Password

Patroni writes its configuration from the secret each time a member starts and applies the password to the database only when the cluster is first initialized. After that the stored passwords live in PostgreSQL, so a rotation touches three places, and the order matters. **This procedure has not been rehearsed on this template — practise it on a scratch release first.**

1. Update the `password` key in your credentials secret to the new value — for example with `cpln apply -f` of the full secret manifest — so any member that restarts from now on reads the new one. Nothing running changes yet: workloads resolve a secret only when a replica starts.

2. On the leader (through HAProxy), change **both** roles that share the password. The replication role `repl` was created with the same password as the superuser, and every member's Patroni configuration will expect the new one after its next restart:

   ```sql
   ALTER ROLE USERNAME WITH PASSWORD 'NEW-STRONG-PASSWORD';
   ALTER ROLE repl WITH PASSWORD 'NEW-STRONG-PASSWORD';
   ```

3. Force a redeployment of the members, then of PgBouncer if it is enabled, so every process holds the new password. Expect a brief write outage while the members restart:

   ```bash
   cpln workload force-redeployment RELEASE_NAME-timescaledb-ha --gvc GVC_NAME
   cpln workload force-redeployment RELEASE_NAME-pgbouncer --gvc GVC_NAME
   ```

The backup job reads the secret fresh on its next scheduled run and needs nothing else.

### Upgrading From 1.0.0

Template version `1.0.0` did not compact the bundled etcd cluster, so its backend grows with time alone and goes read-only once it reaches the 2 GiB quota — after which the TimescaleDB members restart-loop with `exitCode: 0` and `reason: Completed`, which reads as healthy and is easily mistaken for a database fault. Upgrading to `1.0.1` or later turns compaction on and stops further growth, but it cannot shrink a backend that has already grown, and a cluster that has already raised a `NOSPACE` alarm needs operator recovery rather than an upgrade. Check first, with the read-only commands in [If the Backend Quota Is Already Full](/template-catalog/templates/etcd#if-the-backend-quota-is-already-full), run against `RELEASE_NAME-etcd`.

### Upgrading From 1.0.x

Template version `1.1.0` removed `postgres.username`, `postgres.password` and `postgres.database`. They are now the prerequisite dictionary secret named by `postgres.credentialsSecretName`, and `backup.minio.accessKey` / `backup.minio.secretKey` moved the same way to `backup.minio.credentialsSecretName`. An upgrade that still carries any of the old keys is refused at render, before anything is applied, so your running cluster is left untouched:

```text
timescaledb-highly-available: postgres.username, postgres.password and postgres.database were
REMOVED — they are now a `dictionary` secret you create, named by postgres.credentialsSecretName,
holding the keys `username`, `password` and `database`. Delete them from your values. See
Prerequisites in the README.
```

| | 1.0.x | 1.1.0 and later |
|---|---|---|
| Database credentials | `postgres.username`, `postgres.password`, `postgres.database` values | `postgres.credentialsSecretName` → a dictionary secret you create |
| Where they were stored | `RELEASE_NAME-tsdb-ha-config`, created by the chart | Only in your secret; `RELEASE_NAME-tsdb-ha-config` now holds backup settings and is created only when backups are enabled |
| MinIO backup credentials | `backup.minio.accessKey`, `backup.minio.secretKey` values | `backup.minio.credentialsSecretName` → a dictionary secret you create |

<Steps>
  <Step title="Read the credentials the cluster already uses">
    An existing cluster keeps the credentials it was initialized with. Recover them **before** upgrading, from your values file or from the secret the old version created:

    ```bash
    cpln secret reveal RELEASE_NAME-tsdb-ha-config -o yaml
    ```
  </Step>
  <Step title="Create the prerequisite secret with those same values">
    Follow [Prerequisites](#prerequisites) using the existing `username`, `password` and `database`. Different values here do not change the database — they leave every member unable to authenticate after its next restart.
  </Step>
  <Step title="Remove the old keys from your values">
    Delete `postgres.username`, `postgres.password` and `postgres.database` and set `postgres.credentialsSecretName`. If you back up to MinIO, replace `backup.minio.accessKey` and `backup.minio.secretKey` with `backup.minio.credentialsSecretName`.
  </Step>
  <Step title="Upgrade, then rotate any default password">
    Versions `1.0.x` shipped `username: username` and `password: password` as defaults, published in the public template repository. If your cluster still runs it, treat it as compromised and follow [Rotating the Password](#rotating-the-password) after the upgrade.
  </Step>
</Steps>

<Warning>
**The chart no longer writes credentials into `RELEASE_NAME-tsdb-ha-config`.** Anything outside this release that read that secret by name — another workload's environment, a policy, a parent chart bundling this template — must be pointed at the secret you created instead. A reference to a key that no longer exists wedges the referring workload silently.
</Warning>

### Upgrading From 1.1.0

Template version `1.1.1` removes `aws::ReadOnlyAccess` from the backup identity. That AWS managed policy granted read access to every bucket in your AWS account and contains no write actions, so it never carried the backup itself — but it *was* silently supplying any read action your own bucket-scoped policy happened to omit. **Update your IAM policy to the full action list in [AWS S3](#aws-s3) before upgrading**; if it already matches, no action is needed. The identity now carries `cpln-connector` and your bucket-scoped policy only.

### Upgrading From a Version Before 1.2.0

Template version `1.2.0` changes how new clusters are initialized, and an upgrade does not apply those changes to a cluster that already exists:

- **Patroni's consensus timeouts.** The chart now initializes new clusters with `ttl: 45`, `loop_wait: 10` and `retry_timeout: 15`. Earlier versions asked for `ttl: 30` with `retry_timeout: 30`, a combination Patroni silently clamps rather than rejecting, so those clusters tolerated a shorter etcd outage than configured before demoting a healthy leader. Patroni reads these values only while the data directory is empty; afterwards they live in etcd, and an existing cluster keeps the ones it was created with. Move it with `patronictl` — all three together, because Patroni requires `loop_wait + 2 × retry_timeout ≤ ttl` and quietly rewrites the others when one is changed alone:

  ```bash
  cpln workload exec RELEASE_NAME-timescaledb-ha --gvc GVC_NAME --replica RELEASE_NAME-timescaledb-ha-0 --container patroni-timescaledb -- patronictl -c /tmp/patroni_config.yml edit-config --force -s ttl=45 -s loop_wait=10 -s retry_timeout=15
  ```

  Confirm with the `show-config` command in [Checking Cluster State](#checking-cluster-state).

- **Riding out an etcd outage.** Clusters created from `1.2.0` have Patroni's `failsafe_mode` on: when the leader loses etcd but every member still answers its REST API, it keeps serving instead of demoting. A cluster created earlier gains it only through `edit-config -s failsafe_mode=true`.

Also in `1.2.0`: `backup.resources.memory` rose from `128Mi` to `512Mi` because the smaller value OOM-killed the dump; passwords containing quotes or backslashes now work on both Patroni and PgBouncer. Before upgrading, confirm a recent backup actually completed — see [Backing Up](#backing-up).

### Scaling and Availability

- **Leader loss fails over automatically.** When the leader stops answering, Patroni promotes the most up-to-date replica and HAProxy's health checks move port `5432` to it. Writes are refused in between and connections open at that moment are reset — build retry with backoff into your applications.
- **Planned restarts hand leadership off first.** Before a leader is stopped, the chart asks Patroni to switch over to a replica, so a rolling restart costs a few seconds of refused writes rather than a full failover. A `cpln helm upgrade` that changes the member workload can restart members together; expect a brief write outage and plan upgrades as maintenance.
- **Losing etcd does not fail the cluster over.** With `failsafe_mode` on (clusters created from `1.2.0`), a leader that cannot reach etcd keeps serving as long as every other member still answers its REST API, and only a member Patroni recorded as eligible can win the next leader race. An etcd outage that also hides a replica still demotes the leader.
- **A member that stays down is re-cloned, not fatal.** WAL retained for an absent member is capped at a quarter of `volumeset.capacity`; past that, its slot is dropped and it re-clones from the leader when it returns.
- **Keep `replicas` at 3 or more and `etcd.replicas` odd.** Two members cannot fail over safely, and an even etcd count adds nothing to its fault tolerance. Choose `etcd.replicas` at install time.
- **Changing `replicas` on a running release** adds or removes members; a removed member that held the leader role triggers a failover. Afterwards force a redeployment of `RELEASE_NAME-timescaledb-ha-proxy` so HAProxy picks up the new member list.
- **The first `cpln helm upgrade` after an install** can re-apply resources that did not change and restart them. Plan it as a short outage.
- **`multiZone: true`** on the members and on etcd spreads each across zones within the location, when the location supports it.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Workload never becomes ready and cpln logs returns nothing">
    **Symptom:** the install succeeds, `RELEASE_NAME-timescaledb-ha` stays not ready indefinitely, and `cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-timescaledb-ha"}' --limit 50 --since 10m` returns zero lines.

    **Cause:** `postgres.credentialsSecretName` (or, with MinIO backups, `backup.minio.credentialsSecretName`) names a secret that does not exist, so the container is never started. The message is only visible in `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-timescaledb-ha --gvc GVC_NAME -o yaml
    ```

    ```text
    The secret CREDENTIALS_SECRET_NAME no longer exists. Workload updates are paused until the
    secret is added or the reference to the secret removed.
    ```

    **Fix:** create the secret as in [Prerequisites](#prerequisites). The deployment recovers on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-timescaledb-ha --gvc GVC_NAME`.
  </Accordion>
  <Accordion title="Upgrade fails with 'postgres.username, postgres.password and postgres.database were REMOVED'">
    **Symptom:** `cpln helm upgrade` stops before touching any resource:

    ```text
    Error: ... timescaledb-highly-available: postgres.username, postgres.password and postgres.database were
    REMOVED — they are now a `dictionary` secret you create, named by postgres.credentialsSecretName ...
    ```

    `backup.minio.accessKey` / `backup.minio.secretKey` produce the same kind of message under their own names.

    **Cause:** your values still carry keys that were removed in `1.1.0`.

    **Fix:** follow [Upgrading From 1.0.x](#upgrading-from-1-0-x). Your running cluster is unaffected until the upgrade succeeds.
  </Accordion>
  <Accordion title="HAProxy logs 'waiting for patroni endpoints to answer before starting haproxy'">
    **Symptom:** `RELEASE_NAME-timescaledb-ha-proxy` never becomes ready and `cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-timescaledb-ha-proxy"}' --limit 50 --since 10m` repeats `tsdb-ha proxy: waiting for patroni endpoints to answer before starting haproxy — pgN (...) not responding yet`.

    **Cause:** HAProxy will not start until every member's Patroni REST API answers on port `8008`. Either the members are still starting (normal for the first minutes of an install), or `internal_access.type: workload-list` does not include the proxy workload, so it cannot reach them.

    **Fix:** wait for `RELEASE_NAME-timescaledb-ha` to become ready. If it is ready and HAProxy still waits, add `//gvc/GVC_NAME/workload/RELEASE_NAME-timescaledb-ha-proxy` to `internal_access.workloads` as described in [Internal Access](#internal-access). The container gives up and restarts after ten minutes, so it recovers on its own once the members are reachable.
  </Accordion>
  <Accordion title="Members restart-loop with exitCode 0 and reason Completed">
    **Symptom:** the TimescaleDB members restart repeatedly with a climbing restart count in `cpln workload get-deployments RELEASE_NAME-timescaledb-ha --gvc GVC_NAME -o yaml`, each exit reading `exitCode: 0` and `reason: Completed`, while nothing in the database logs looks wrong.

    **Cause:** etcd has gone read-only. A Patroni member that cannot renew its lease exits cleanly, so the failure reads as healthy. The usual reason is an uncompacted etcd backend that has reached its 2 GiB quota and raised a `NOSPACE` alarm (template version `1.0.0`).

    **Fix:** check etcd first, with two read-only commands:

    ```bash
    cpln workload exec RELEASE_NAME-etcd --gvc GVC_NAME --container etcd -- etcdctl endpoint status --cluster -w table
    cpln workload exec RELEASE_NAME-etcd --gvc GVC_NAME --container etcd -- etcdctl alarm list
    ```

    A healthy cluster prints nothing for `alarm list`. `NOSPACE` confirms it; recovery is the operator procedure in [If the Backend Quota Is Already Full](/template-catalog/templates/etcd#if-the-backend-quota-is-already-full), followed by an upgrade to `1.0.1` or later so it does not recur.
  </Accordion>
  <Accordion title="Clients get 'remaining connection slots are reserved' through PgBouncer">
    **Symptom:** under load, connections through `RELEASE_NAME-pgbouncer` fail with `FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute` (or `... for non-replication superuser connections`) instead of waiting in the pool.

    **Cause:** `pgbouncer.maxDbConnections` is enforced per PgBouncer replica, so `maxReplicas × maxDbConnections` server connections can be opened against a cluster `max_connections` of 100 (97 usable).

    **Fix:** lower `pgbouncer.maxDbConnections` or `pgbouncer.maxReplicas` so their product stays under 97, and keep `pgbouncer.defaultPoolSize` within the same budget — see [PgBouncer Connection Pooling](#pgbouncer-connection-pooling).
  </Accordion>
  <Accordion title="Queries fail with 'function create_hypertable does not exist'">
    **Symptom:** `SELECT create_hypertable(...)` or `time_bucket(...)` fails with `ERROR: function create_hypertable(unknown, ...) does not exist`, usually in a database other than the one in your credentials secret.

    **Cause:** the TimescaleDB extension is preloaded on every member but *created* only in the database named by the `database` key of your credentials secret, at first initialization. A database you created afterwards does not have it.

    **Fix:** connect to that database through HAProxy as the superuser and run `CREATE EXTENSION IF NOT EXISTS timescaledb;`. The replicas pick it up through streaming replication.
  </Accordion>
  <Accordion title="Backup job exits with exitCode 137 and no object appears in the bucket">
    **Symptom:** `cpln workload get-deployments RELEASE_NAME-timescaledb-ha-backup --gvc GVC_NAME -o yaml` shows the `backup` container ending with `exitCode: 137`, `cpln logs` for it stops after `Running pg_dumpall against ...`, and no new `postgres-TIMESTAMP.sql.gz` lands under the prefix.

    **Cause:** the dump is being OOM-killed mid-run. Nothing is logged from inside the container when that happens; `backup.resources.memory` is below what `pg_dumpall` plus the upload needs (template versions before `1.2.0` shipped `128Mi`).

    **Fix:** set `backup.resources.memory` to at least the shipped `512Mi` and upgrade. The next scheduled run produces a backup.
  </Accordion>
  <Accordion title="Apply rejected with 'The ratio between cpu and minCpu must be less than 4:1'">
    **Symptom:** an install or upgrade fails and the member workload is not created or updated.

    **Cause:** `resources.maxCpu` is more than four times `resources.minCpu`, which the platform rejects on a stateful workload.

    **Fix:** raise `resources.minCpu` or lower `resources.maxCpu` so the ratio is at most 4:1.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the credentials secret before installing.** A reference to a secret that does not exist wedges the members with no log output; see [Prerequisites](#prerequisites) for the one command that shows the reason.
- **Connect through HAProxy** (`RELEASE_NAME-timescaledb-ha-proxy`), or PgBouncer when enabled. A member reached directly may be a read-only replica.
- **Credentials are applied only when the cluster is first initialized**, and the `repl` replication role shares the superuser password. Rotate in the order given in [Rotating the Password](#rotating-the-password).
- **The TimescaleDB extension is created only in the database your secret names.** Run `CREATE EXTENSION IF NOT EXISTS timescaledb` in any other database before creating hypertables there.
- **Keep `replicas` at 3 or more and `etcd.replicas` odd**, and choose `etcd.replicas` at install time.
- **Do not change `etcd.tuning` to disable compaction** — an uncompacted etcd takes the whole cluster read-only months later.
- **With `workload-list` access, list the release's own workloads** as well as your applications, or HAProxy cannot reach the members.
- **Backups are logical only** — a scheduled `pg_dumpall` with no WAL archiving or point-in-time recovery. Keep `backup.resources.memory` at `512Mi` or more.
- **Restore procedures are unverified on this template**, and the scheduled whole-cluster dump does not fit TimescaleDB's documented single-database restore directly — rehearse against a scratch release, and take a per-database `pg_dump -Fc` for anything you must be able to restore.
- **`cpln helm uninstall` deletes both volume sets** and the data with them; the TimescaleDB volume set leaves a final snapshot for 7 days. Your credentials secrets are yours and are left alone.
- **Upgrading from 1.0.x is a breaking change** — the removed keys stop the upgrade rather than resetting a password. See [Upgrading From 1.0.x](#upgrading-from-1-0-x).
