## Overview

Supabase is an open-source backend-as-a-service built on PostgreSQL: authentication, an auto-generated REST and GraphQL API, realtime database subscriptions, file storage and a web dashboard, all driven by one Postgres database. This template deploys the full self-hosted stack — a Supabase-patched Postgres 15 with pgvector, pg_graphql, pg_net and pgjwt pre-installed, plus GoTrue, PostgREST, Realtime, Storage and Studio behind a Kong API gateway — into your own GVC, with no dependency on Supabase Cloud. Kong is the single entry point and the authorization layer: API keys map to consumer groups, so the public `anonKey` reaches the API routes while the admin routes and the dashboard login are restricted.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have — it does not create one.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-postgres` | Supabase Postgres 15 on port `5432` (stateful, 1 replica, container `postgres`); gains a `wal-g-backup` sidecar container in WAL-G backup mode | — |
| Volume Set | `RELEASE_NAME-postgres-vs` | Postgres data directory at `/var/lib/postgresql/data` | — |
| Workload | `RELEASE_NAME-kong` | Kong API gateway on port `8000` — routes `/rest/v1/`, `/auth/v1/`, `/realtime/v1/`, `/storage/v1/`, `/pg/` and the Studio dashboard at `/`; the only workload the service tiers accept traffic from (standard, autoscales 1–3, container `kong`) | — |
| Workload | `RELEASE_NAME-postgrest` | PostgREST REST and GraphQL API on port `3000` (standard, autoscales 1–3, container `postgrest`) | — |
| Workload | `RELEASE_NAME-auth` | GoTrue auth service on port `9999` (standard, autoscales 1–3, container `auth`) | — |
| Workload | `RELEASE_NAME-realtime` | Realtime WebSocket change feed on port `4000` (standard, 1 replica, container `realtime`) | `realtime.enabled` (default `true`) |
| Workload | `RELEASE_NAME-storage` | Storage API on port `5000` (container `storage`); standard and autoscaled 1–3 with the `s3` or `gcs` backend, stateful and single-replica with `local` | `storage.enabled` (default `true`) |
| Volume Set | `RELEASE_NAME-storage-vs` | File store at `/var/lib/storage` | `storage.backend: local` |
| Workload | `RELEASE_NAME-studio` | Studio dashboard on port `3000` (container `studio`) with the pg_meta metadata API as a sidecar (container `meta`, port `8080`); standard, 1 replica | `studio.enabled` (default `true`) |
| Workload | `RELEASE_NAME-pgbouncer` | Connection pooler for your application workloads on port `5432` (standard, container `pgbouncer`) | `pgbouncer.enabled: true` |
| Workload | `RELEASE_NAME-backup` | Cron job running a scheduled `pg_dumpall` to S3 or GCS (container `backup`) | `backup.enabled: true` with `backup.mode: logical` |
| Secret | `RELEASE_NAME-supabase-kong-config` | Kong declarative routing template; API keys and the dashboard password are substituted from your prerequisite secrets at container start | — |
| Secret | `RELEASE_NAME-supabase-preinit`, `RELEASE_NAME-supabase-postinit` | Database init scripts that create the `supabase_admin` role and password the service roles on first boot | — |
| Secret | `RELEASE_NAME-supabase-walg-script` | WAL-G base-backup loop for the sidecar | `backup.enabled: true` with `backup.mode: walg` |
| Identity & Policy | `RELEASE_NAME-supabase-identity`, `RELEASE_NAME-supabase-policy` | One shared identity with `reveal` on exactly the chart's secrets and your prerequisite secrets; carries the AWS or GCP cloud-account binding when S3 storage or backups are on | — |

## Prerequisites

Three secrets must exist **before** you install — none of their values ever passes through Helm values, so none lands in the Helm release. Secrets are org-level, so no `--gvc` flag is involved.

<Steps>
  <Step title="JWT signing secret and API keys">
    A [dictionary secret](/guides/create-secret/dictionary) with exactly the keys `secret`, `anonKey`, `serviceRoleKey` and `secretKeyBase`. `anonKey` and `serviceRoleKey` must be HMAC-SHA256 JWTs **signed by** `secret` — you cannot invent them independently. This snippet mints all four consistently; run it as-is:

    ```bash
    JWT_SECRET="$(openssl rand -hex 32)"

    b64url() { openssl base64 -A | tr '+/' '-_' | tr -d '='; }
    mint_key() {
      header=$(printf '%s' '{"alg":"HS256","typ":"JWT"}' | b64url)
      iat=$(date +%s); exp=$((iat + 157680000))   # 5 years
      payload=$(printf '{"role":"%s","iss":"supabase","iat":%s,"exp":%s}' "$1" "$iat" "$exp" | b64url)
      sig=$(printf '%s.%s' "$header" "$payload" | openssl dgst -sha256 -hmac "$JWT_SECRET" -binary | b64url)
      printf '%s.%s.%s' "$header" "$payload" "$sig"
    }

    cpln secret create-dictionary --name JWT_SECRET_NAME \
      --entry secret="$JWT_SECRET" \
      --entry anonKey="$(mint_key anon)" \
      --entry serviceRoleKey="$(mint_key service_role)" \
      --entry secretKeyBase="$(openssl rand -hex 32)"
    ```

    Set `jwt.secretName` to this name. Your client apps need `anonKey`; read it back later with `cpln secret reveal JWT_SECRET_NAME -o yaml`. `serviceRoleKey` bypasses row-level security — keep it server-side.
  </Step>
  <Step title="Postgres credentials">
    A dictionary secret with exactly the keys `password` and `database`. The login role name is fixed at `postgres` by the Supabase image, so it is not part of the secret:

    ```bash
    cpln secret create-dictionary --name POSTGRES_SECRET_NAME \
      --entry password="$(openssl rand -hex 24)" \
      --entry database=postgres
    ```

    Set `postgres.credentialsSecretName` to this name.
  </Step>
  <Step title="Studio dashboard password">
    Required while `studio.enabled: true` (the default). An [opaque secret](/guides/create-secret/opaque) with `--encoding plain` holding only the dashboard password on a single line. Kong enforces it as HTTP basic auth in front of the dashboard, so it is the only thing between the internet and full database control once Kong is public:

    ```bash
    printf '%s' 'YOUR-STRONG-PASSWORD' | cpln secret create-opaque --name STUDIO_SECRET_NAME --encoding plain -f -
    ```

    Set `studio.passwordSecretName` to this name.
  </Step>
  <Step title="File storage bucket (default install)">
    The default `storage.backend: s3` targets AWS S3 and needs a bucket, a Control Plane [Cloud Account](/guides/create-cloud-account) and a bucket-scoped IAM policy — set `storage.s3.bucket`, `storage.s3.region`, `storage.s3.cloudAccountName` and `storage.s3.policyName`. The IAM policy must grant `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on the bucket. For an S3-compatible store (MinIO, Cloudflare R2, Wasabi, Backblaze B2) or GCS, create a dictionary secret holding the access key pair instead — see [Storage](#storage). Install with `--set storage.enabled=false` if your app has no file uploads.
  </Step>
  <Step title="SMTP password (optional)">
    Only when `auth.smtp.enabled: true`. An opaque secret with `--encoding plain` holding the SMTP password:

    ```bash
    printf '%s' 'YOUR-SMTP-PASSWORD' | cpln secret create-opaque --name SMTP_SECRET_NAME --encoding plain -f -
    ```

    Set `auth.smtp.passwordSecretName` to this name.
  </Step>
  <Step title="OAuth client secrets (optional)">
    One opaque secret per provider, holding only the client secret the provider issued:

    ```bash
    printf '%s' 'YOUR-GITHUB-CLIENT-SECRET' | cpln secret create-opaque --name GITHUB_SECRET_NAME --encoding plain -f -
    ```

    Set `auth.providers.github.clientSecretName` (or `auth.providers.google.clientSecretName`) to this name — see [Auth](#auth).
  </Step>
</Steps>

Backup buckets are optional and separate from the storage bucket — see [Backing Up](#backing-up).

<Warning>
Create the secrets **before** installing. A name that points at a secret which does not exist installs "successfully" and then wedges silently: `cpln logs` shows nothing, and the only place the missing secret is named is `status.versions[].message` in `cpln workload get-deployments RELEASE_NAME-kong --gvc GVC_NAME -o yaml` (check the other workloads the same way). The workloads recover on their own once the secret exists, or immediately after `cpln workload force-redeployment RELEASE_NAME-kong --gvc GVC_NAME`.
</Warning>

## Installation

A default install needs the three secret names plus the S3 storage bucket details:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/supabase \
  --version 1.1.1 --gvc GVC_NAME \
  --set jwt.secretName=JWT_SECRET_NAME \
  --set postgres.credentialsSecretName=POSTGRES_SECRET_NAME \
  --set studio.passwordSecretName=STUDIO_SECRET_NAME \
  --set storage.s3.bucket=YOUR_BUCKET_NAME \
  --set storage.s3.region=us-east-1 \
  --set storage.s3.cloudAccountName=YOUR_CLOUD_ACCOUNT_NAME \
  --set storage.s3.policyName=YOUR_IAM_POLICY_NAME
```

Replace the four `storage.s3.*` lines with `--set storage.enabled=false` to install without file storage. Or install using your preferred method:

## Configuration

### Postgres

```yaml
postgres:
  image: supabase/postgres:15.8.1.060  # Supabase-patched image — required, the stock postgres image lacks the extensions
  credentialsSecretName: my-supabase-postgres-credentials  # prerequisite dictionary secret: password, database
  resources:
    minCpu: 500m
    minMemory: 512Mi
    maxCpu: 2
    maxMemory: 2Gi
  volumeset:
    capacity: 10  # initial capacity in GiB (minimum is 10)
    autoscaling:
      enabled: false
      maxCapacity: 100
      minFreePercentage: 10
      scalingFactor: 1.2
  internalAccess:
    type: same-gvc  # options: none, same-gvc, same-org, workload-list
    workloads:
      #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

- `postgres.image` — Must stay a `supabase/postgres` tag. GoTrue, PostgREST, Realtime and Storage depend on extensions (pgvector, pg_graphql, pg_net, pgjwt) that the stock `postgres` image does not ship.
- `postgres.credentialsSecretName` — The dictionary secret from [Prerequisites](#prerequisites). The login role is always `postgres`; the same password is applied to the internal service roles on first boot.
- `postgres.internalAccess.type` — Who can reach Postgres directly on port `5432`. All Supabase services connect inside the GVC; use `workload-list` with `workloads` to add your own application workloads. PgBouncer inherits the same setting.

### Kong API Gateway

```yaml
kong:
  image: kong:2.8.1  # pinned — Supabase's routing config is tested against this version
  resources:
    minCpu: 100m
    minMemory: 256Mi
    maxCpu: 1000m
    maxMemory: 1Gi
  minReplicas: 1
  maxReplicas: 3
  publicAccess:
    enabled: false
    siteUrl: ""  # e.g. https://api.my-app.com — required when publicAccess is enabled
```

- `kong.publicAccess.enabled` — Publish Kong on the internet. This also publishes the Studio dashboard at `/` behind its basic-auth login when `studio.enabled: true`.
- `kong.publicAccess.siteUrl` — Required when public access is on. GoTrue puts it in OAuth redirect callbacks and magic-link emails, so it must be the HTTPS URL your clients actually reach Kong at: a [custom domain](/guides/configure-domain) attached to `RELEASE_NAME-kong`, or the workload's canonical `*.cpln.app` endpoint. With public access off, the template falls back to the internal Kong hostname and email or OAuth links only work inside the GVC.

Kong is also where authorization happens. Requests are identified by the `apikey` header they carry:

| Path | Who may call it |
|---|---|
| `/auth/v1/verify`, `/auth/v1/callback`, `/auth/v1/authorize`, `/auth/v1/health` | anyone, no key |
| `/rest/v1/`, `/auth/v1/`, `/realtime/v1/`, `/storage/v1/` | `anonKey` or `serviceRoleKey` |
| `/auth/v1/admin/` (user administration), `/pg/` (pg_meta) | `serviceRoleKey` only |
| `/` (Studio dashboard, when `studio.enabled`) | dashboard username and password |

### PostgREST

```yaml
postgrest:
  image: postgrest/postgrest:v12.2.3
  resources:
    minCpu: 100m
    minMemory: 128Mi
    maxCpu: 500m
    maxMemory: 512Mi
  minReplicas: 1
  maxReplicas: 3
```

Stateless; autoscales on CPU between `minReplicas` and `maxReplicas`. Reachable only through Kong.

### Auth

GoTrue provides email/password, magic links, OAuth and JWT sessions.

```yaml
auth:
  image: supabase/gotrue:v2.170.0
  resources:
    minCpu: 100m
    minMemory: 128Mi
    maxCpu: 500m
    maxMemory: 512Mi
  minReplicas: 1
  maxReplicas: 3
  disableSignup: false  # set true to prevent new user registration
  smtp:
    enabled: false
    host: smtp.example.com
    port: 587
    user: smtp-user
    passwordSecretName: ""  # prerequisite opaque secret (encoding plain) with the SMTP password — required when enabled
    senderName: Supabase
    senderEmail: noreply@example.com
  # providers:
  #   github:
  #     clientId: "Iv1.0123456789abcdef"
  #     clientSecretName: my-supabase-github-oauth
  #   google:
  #     clientId: "1234567890-abc.apps.googleusercontent.com"
  #     clientSecretName: my-supabase-google-oauth
```

- `auth.smtp.*` — Required for magic links, signup confirmation and password reset. With SMTP disabled, signups are auto-confirmed and the email flows are unavailable. Any SMTP provider works; the password is the opaque secret from [Prerequisites](#prerequisites).
- `auth.providers.github` / `auth.providers.google` — The two OAuth providers this template wires up. Uncomment a block, set the provider's client ID (not sensitive) and name the prerequisite opaque secret holding its client secret. In the provider's developer console set the JavaScript origin to `kong.publicAccess.siteUrl` and the redirect URI to `SITE_URL/auth/v1/callback`. OAuth needs `kong.publicAccess.enabled: true` — providers will not redirect to internal hostnames.

### Realtime

```yaml
realtime:
  enabled: true
  image: supabase/realtime:v2.34.47
  resources:
    minCpu: 100m
    minMemory: 128Mi
    maxCpu: 500m
    maxMemory: 512Mi
```

Realtime runs as a **single replica** and has no replica knobs: the image seeds its own tenant row on every boot, so a second replica would delete the row the first one is serving. Disable it if your app has no realtime subscriptions.

### Storage

```yaml
storage:
  enabled: true  # disable if your app has no file uploads — saves a workload
  image: supabase/storage-api:v1.14.6
  resources:
    minCpu: 125m  # keep maxCpu:minCpu at or under 4:1 — backend local makes this workload stateful, which enforces it
    minMemory: 128Mi
    maxCpu: 500m
    maxMemory: 512Mi
  minReplicas: 1
  maxReplicas: 3
  backend: s3  # options: local, s3, gcs
  volumeset:      # only used when backend is local
    capacity: 10  # initial capacity in GiB (minimum is 10)
    autoscaling:
      enabled: false
      maxCapacity: 100
      minFreePercentage: 10
      scalingFactor: 1.2
  s3:             # only used when backend is s3
    bucket: my-supabase-storage-bucket
    region: us-east-1  # set `auto` for Cloudflare R2
    cloudAccountName: my-s3-cloudaccount  # AWS S3 only (endpoint empty) — keyless access through a cloud account
    policyName: my-supabase-storage-policy  # IAM policy granting s3:GetObject, s3:PutObject, s3:DeleteObject on the bucket
    endpoint: ""  # e.g. http://my-minio-workload:9000 — empty means AWS S3
    forcePathStyle: true  # required by MinIO; harmless on R2, Wasabi and B2
    credentialsSecretName: ""  # prerequisite dictionary secret (accessKeyId, secretAccessKey) — required when endpoint is set
  gcs:            # only used when backend is gcs
    bucket: my-supabase-storage-bucket
    credentialsSecretName: my-supabase-gcs-hmac  # prerequisite dictionary secret (accessKeyId, secretAccessKey) — HMAC pair issued by Google
```

| Backend | Shape | Credentials |
|---|---|---|
| `s3` with `endpoint` empty | AWS S3; stateless, autoscaled | Keyless, through `cloudAccountName` and the bucket-scoped IAM policy named by `policyName` |
| `s3` with `endpoint` set | MinIO, Cloudflare R2, Wasabi or Backblaze B2; stateless, autoscaled | Access key pair in the dictionary secret named by `s3.credentialsSecretName`; `cloudAccountName` and `policyName` are unused |
| `gcs` | GCS over its S3-compatible API; stateless, autoscaled | HMAC pair in the dictionary secret named by `gcs.credentialsSecretName`; no Cloud Account needed |
| `local` | Single replica on the `RELEASE_NAME-storage-vs` volume set; for development or simple use | None |

For an S3-compatible store or GCS, create the access key pair on the provider (scoped to the one bucket: read, write and delete objects, list the bucket) and put it in a dictionary secret before installing:

```bash
cpln secret create-dictionary --name S3_SECRET_NAME \
  --entry accessKeyId=YOUR_ACCESS_KEY_ID \
  --entry secretAccessKey=YOUR_SECRET_ACCESS_KEY
```

Then set `storage.s3.endpoint` and `storage.s3.region` for the provider — a MinIO workload in the same GVC is `http://WORKLOAD_NAME.GVC_NAME.cpln.local:9000` with region `us-east-1` (its `internalAccess` must admit `RELEASE_NAME-storage`); Cloudflare R2 is `https://ACCOUNT_ID.r2.cloudflarestorage.com` with region `auto`; Wasabi and Backblaze B2 use their regional S3 endpoint and the bucket's region. For GCS, generate the HMAC key under **Cloud Storage → Settings → Interoperability** for a service account with **Storage Object Admin** on the bucket.

The storage bucket and the backup bucket must be **separate** — each with its own bucket, Cloud Account and IAM policy.

### Studio

```yaml
studio:
  enabled: true
  image: supabase/studio:2025.06.02-sha-8f2993d
  username: supabase  # dashboard login name (not sensitive)
  passwordSecretName: my-supabase-studio-password  # prerequisite opaque secret (encoding plain) with the dashboard password
  resources:
    minCpu: 100m
    minMemory: 256Mi
    maxCpu: 500m
    maxMemory: 512Mi
  allowedCidrs: []  # DIRECT inbound access to the Studio workload, bypassing Kong and therefore the login — keep empty
  #  - 203.0.113.0/24   # example: office IP range (unauthenticated access!)
  internalAccess:
    type: workload-list  # options: none, same-gvc, same-org, workload-list
    workloads: []        # Kong is added automatically; list any extra callers here
  meta:
    image: supabase/postgres-meta:v0.86.0
    resources:
      minCpu: 100m
      minMemory: 64Mi
      maxCpu: 200m
      maxMemory: 256Mi
```

The dashboard login is enforced by Kong's basic-auth plugin on the `/` route using `studio.username` and the password secret — **Studio itself has no login**. Reach it through Kong (see [Connecting](#connecting)). `studio.allowedCidrs` and a wider `studio.internalAccess.type` open the Studio workload directly, which skips Kong and therefore skips the password: anyone who reaches it gets an unauthenticated dashboard holding the `serviceRoleKey`. Leave both at their defaults unless you have a reason, and never set `0.0.0.0/0`.

### JWT

```yaml
jwt:
  secretName: my-supabase-jwt  # prerequisite dictionary secret: secret, anonKey, serviceRoleKey, secretKeyBase
```

`secret` is the HMAC-SHA256 signing key every service verifies tokens against; `anonKey` (role `anon`) is the public client key; `serviceRoleKey` (role `service_role`) bypasses row-level security and is the full-admin credential for your data — server-side only, never in client code; `secretKeyBase` is Realtime's cookie-signing key. The keys must be signed by `secret` or every service returns `bad_jwt` — mint them together with the snippet in [Prerequisites](#prerequisites).

### PgBouncer

```yaml
pgbouncer:
  enabled: false
  image: edoburu/pgbouncer:v1.25.1-p0
  poolMode: transaction  # options: session, transaction, statement
  defaultPoolSize: 25
  maxClientConn: 1000
  replicas: 1
  resources:
    minCpu: 100m
    minMemory: 64Mi
    maxCpu: 200m
    maxMemory: 128Mi
```

PgBouncer is a pooler for **your application workloads**; the Supabase services keep connecting to Postgres directly. `transaction` mode suits most web and API workloads but breaks session-level features (`SET` variables, temporary tables, advisory locks); use `session` if you need those. It accepts connections per `postgres.internalAccess`.

### Backup

```yaml
backup:
  enabled: false
  mode: logical  # options: logical (pg_dump cron), walg (continuous WAL archiving + base backups, supports PITR)
  provider: aws  # options: aws, gcp
  resources:
    minCpu: 100m
    minMemory: 128Mi
    maxCpu: 200m
    maxMemory: 256Mi
  logical:
    image: ghcr.io/controlplane-com/backup-images/postgres-backup:17.1.0  # pg_dump 17 is backward-compatible with Postgres 15
    schedule: "0 2 * * *"  # daily at 2am UTC
  walg:
    intervalSeconds: 21600  # base backup interval in seconds (default: every 6 hours)
  aws:
    bucket: my-supabase-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: supabase/backups
  gcp:
    bucket: my-supabase-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: supabase/backups
```

See [Backing Up](#backing-up) for the bucket, Cloud Account and IAM setup and what each mode produces.

## Connecting

All API traffic goes through Kong. Read the public address from `status.canonicalEndpoint` in `cpln workload get RELEASE_NAME-kong --gvc GVC_NAME -o yaml`.

| What | Address | Notes |
|---|---|---|
| API gateway (public) | `kong.publicAccess.siteUrl` | Only when `kong.publicAccess.enabled: true`; a custom domain or the canonical `*.cpln.app` endpoint of `RELEASE_NAME-kong`. |
| API gateway (internal) | `http://RELEASE_NAME-kong.GVC_NAME.cpln.local:8000` | Reachable from any workload in the GVC. |
| API keys | `cpln secret reveal JWT_SECRET_NAME -o yaml` | Keys `anonKey` (clients) and `serviceRoleKey` (trusted server-side code only). Every request carries one in the `apikey` header. |
| Studio dashboard | `/` on the Kong address | Log in with `studio.username` and the password from `cpln secret reveal STUDIO_SECRET_NAME -o yaml`. |
| Postgres (direct) | `RELEASE_NAME-postgres.GVC_NAME.cpln.local:5432` | User `postgres`; password and database from `cpln secret reveal POSTGRES_SECRET_NAME -o yaml`. Subject to `postgres.internalAccess`. |
| Postgres (pooled) | `RELEASE_NAME-pgbouncer.GVC_NAME.cpln.local:5432` | When `pgbouncer.enabled: true`; same credentials. |

API paths through Kong: `/rest/v1/` (PostgREST), `/auth/v1/` (GoTrue), `/storage/v1/` (Storage), `/realtime/v1/` (Realtime), `/pg/` (pg_meta, `serviceRoleKey` only). The Supabase client libraries set the `apikey` header for you:

```js
import { createClient } from '@supabase/supabase-js'

const supabase = createClient('https://SITE_URL', 'YOUR_ANON_KEY')  // kong.publicAccess.siteUrl
```

To verify the gateway from your machine without publishing it, forward Kong's port and call the unauthenticated health route:

```bash
cpln port-forward RELEASE_NAME-kong 8000:8000 --gvc GVC_NAME
```

```bash
curl -s http://localhost:8000/auth/v1/health
```

## Operations

### Backing Up

Backups are off by default. Pick a `backup.mode`, a `backup.provider`, complete the storage setup below, then set `backup.enabled: true`. Neither mode has been exercised against a live install of this template version — rehearse on a throwaway release before relying on it.

| Mode | What runs | What lands in the bucket |
|---|---|---|
| `logical` | The `RELEASE_NAME-backup` cron workload runs `pg_dumpall` as `postgres` on `backup.logical.schedule` | A gzipped whole-cluster SQL script, `postgres-TIMESTAMP.sql.gz`, under `backup.*.prefix` |
| `walg` | Postgres starts with `archive_mode=on` and `archive_command=wal-g wal-push`, and a `wal-g-backup` sidecar container in `RELEASE_NAME-postgres` runs `wal-g backup-push` every `backup.walg.intervalSeconds` | Continuous WAL segments plus periodic base backups, for point-in-time recovery |

The logical job connects as `postgres`, which the Supabase image does not keep as a superuser, and `pg_dumpall` reads cluster-wide role data. Whether the dump completes on this image has not been verified — after enabling it, check the first run's output with `cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-backup"}' --limit 50 --since 10m` and confirm an archive landed in the bucket.

<Warning>
Switching `backup.mode` between `logical` and `walg` changes Postgres's `wal_level` and `archive_mode` startup flags, which restarts the database. Plan the switch accordingly.
</Warning>

### Restoring a Backup

<Warning>
These procedures were written against the chart's configuration and the backup image's output format. They have **not been exercised against a live install of this template** — rehearse on a throwaway release, and treat any step that errors as a stop. An invented restore is worse than none, so what cannot be traced to the chart is left out.
</Warning>

**Logical.** The archive is `pg_dumpall` output: a whole-cluster SQL script that recreates roles and databases, so it is meant for a **fresh** release installed with the same prerequisite secrets. Download it from your bucket (`aws s3 cp` or `gsutil cp`), forward the new Postgres port, and stream the script into `psql` on `localhost`:

```bash
cpln port-forward RELEASE_NAME-postgres 5432:5432 --gvc GVC_NAME
```

```bash
export PGPASSWORD='YOUR-POSTGRES-PASSWORD'
gunzip -c postgres-TIMESTAMP.sql.gz | psql --host=localhost --port=5432 --username=postgres --dbname=postgres
unset PGPASSWORD
```

Expect `already exists` errors for the roles and databases the Supabase image creates on first boot — the rest of the script continues past them. Review the output before pointing clients at the restored release.

**WAL-G.** The sidecar's backup list is available with `wal-g backup-list` inside the `wal-g-backup` container of `RELEASE_NAME-postgres`. A WAL-G restore (`wal-g backup-fetch` into an **empty** data directory, then starting Postgres against it) needs a fresh volume set and a one-off workload that this template does not provide, and it has not been verified here. Follow the [WAL-G documentation](https://github.com/wal-g/wal-g) and, before re-enabling backups on the restored cluster, set a new `backup.aws.prefix` or `backup.gcp.prefix` so it does not collide with the original cluster's WAL stream.

### Rotating a Credential

The prerequisite secrets live outside Helm, so changing one does nothing by itself — running workloads keep the value they booted with. Update the secret by applying its full manifest, then force a redeployment of every workload that reads it:

```yaml
kind: secret
name: STUDIO_SECRET_NAME
type: opaque
data:
  encoding: plain
  payload: YOUR-NEW-PASSWORD
```

```bash
cpln apply -f studio-secret.yaml
cpln workload force-redeployment RELEASE_NAME-kong --gvc GVC_NAME
```

| Secret | Workloads to force-redeploy after the change |
|---|---|
| Studio password | `RELEASE_NAME-kong` (Kong renders its config at container start) |
| SMTP password, OAuth client secret | `RELEASE_NAME-auth` |
| JWT keys | `RELEASE_NAME-kong`, `RELEASE_NAME-postgrest`, `RELEASE_NAME-auth`, `RELEASE_NAME-realtime`, `RELEASE_NAME-storage`, `RELEASE_NAME-studio` — re-mint `anonKey` and `serviceRoleKey` from the new `secret` in the same update (the snippet in [Prerequisites](#prerequisites) does this) and re-issue `anonKey` to your clients |
| Postgres password | `RELEASE_NAME-auth`, `RELEASE_NAME-postgrest`, `RELEASE_NAME-realtime`, `RELEASE_NAME-storage`, `RELEASE_NAME-studio`, plus `RELEASE_NAME-pgbouncer` and `RELEASE_NAME-backup` when enabled — **after** changing it in the database (below) |

Two values are consumed only once, when the Postgres data directory is first initialized, so rotating them later does not reach what the database already stores:

- **Postgres password** — change it on the roles first, then update the secret to match, or every service fails to authenticate. The same password is set on `postgres`, `supabase_admin`, `authenticator`, `supabase_auth_admin` and `supabase_storage_admin`; `supabase_admin`'s current password is already in the container's environment:

  ```bash
  cpln workload exec RELEASE_NAME-postgres --gvc GVC_NAME --container postgres -- \
    sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U supabase_admin -d "$POSTGRES_DB" -c "ALTER ROLE postgres PASSWORD '"'"'NEW-PASSWORD'"'"'; ALTER ROLE supabase_admin PASSWORD '"'"'NEW-PASSWORD'"'"'; ALTER ROLE authenticator PASSWORD '"'"'NEW-PASSWORD'"'"'; ALTER ROLE supabase_auth_admin PASSWORD '"'"'NEW-PASSWORD'"'"'; ALTER ROLE supabase_storage_admin PASSWORD '"'"'NEW-PASSWORD'"'"';"'
  ```

  This command has not been run against a live install of this template — try it on a throwaway release first.
- **JWT values on the Postgres workload** — the database keeps the JWT settings it was initialized with; a redeployment does not re-run the init scripts.

### Upgrading from 1.0.0

Template version 1.1.0 moved every credential out of values and into prerequisite secrets. These keys no longer exist and are ignored if you still pass them: `jwt.secret`, `jwt.anonKey`, `jwt.serviceRoleKey`, `jwt.secretKeyBase`, `postgres.password`, `postgres.database`, `studio.password`, `auth.smtp.password`, `storage.gcs.accessKeyId`, `storage.gcs.secretAccessKey` and `auth.providers.*.clientSecret`. Before upgrading:

1. Create the secrets from [Prerequisites](#prerequisites) holding your **current** values — the Postgres password and the JWT settings are baked into the initialized database, so new values need the [rotation procedure](#rotating-a-credential), not just an upgrade.
2. Set `jwt.secretName`, `postgres.credentialsSecretName`, `studio.passwordSecretName` and, where used, `auth.smtp.passwordSecretName`, `storage.gcs.credentialsSecretName` and `auth.providers.*.clientSecretName` to those names, and remove the old keys from your values.
3. If you never changed 1.0.0's default JWT values, **rotate them**: they were Supabase's publicly published demo keys, so every default install shared one known `serviceRoleKey`.

Other changes in 1.1.0 that affect an existing install:

- The Studio dashboard login moved to Kong — reach Studio at `/` on the Kong address, not on the Studio workload. `studio.internalAccess.type` now defaults to `workload-list` (Kong only), and `studio.allowedCidrs` has become a login bypass; clear it unless you understand the consequence.
- `realtime.minReplicas` and `realtime.maxReplicas` were removed; Realtime is a single replica.
- `storage.backend: s3` gained `endpoint`, `forcePathStyle` and `credentialsSecretName` for S3-compatible stores; the default `storage.s3.bucket` placeholder was renamed and `storage.resources.minCpu` rose to `125m` so the `local` backend can install.

### Upgrading from 1.1.0

Template version 1.1.1 removes the AWS-managed `ReadOnlyAccess` policy from the backup identity. That policy granted read access to **every bucket in your AWS account** and contained no write actions, so it never carried the backup itself — but it was silently supplying any read action your own bucket-scoped policy omitted. **Update your IAM policy to the full action list in [Backing Up](#backing-up) before upgrading**; if it already matches, no action is needed. The identity now carries `cpln-connector` and your bucket-scoped policies only. Nothing else changes.

The first `cpln helm upgrade` after an install can restart the Postgres workload even when no database value changed, so run it during a quiet period.

### Scaling and Availability

Kong, PostgREST, Auth and Storage (with the `s3` or `gcs` backend) are stateless and autoscale on CPU between their `minReplicas` and `maxReplicas`. Realtime, Studio, PgBouncer and Storage with the `local` backend run as single replicas. Postgres is a single stateful instance with no HA option in this template: a restart or upgrade is a brief interruption, and its data persists on `RELEASE_NAME-postgres-vs` across redeploys under the same release name. Scale Postgres vertically through `postgres.resources` and grow the volume with `postgres.volumeset.capacity` or its autoscaling block.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Workloads never become ready and cpln logs shows nothing">
    **Symptom:** After install, one or more workloads stay not ready and `cpln logs` returns no lines for them.

    **Cause:** A prerequisite secret named in your values does not exist, so the container never starts.

    **Fix:** Read `status.versions[].message` in `cpln workload get-deployments RELEASE_NAME-kong --gvc GVC_NAME -o yaml` (or the affected workload) — it names the missing secret. Create it as shown in [Prerequisites](#prerequisites); the workload recovers on its own, or immediately after `cpln workload force-redeployment RELEASE_NAME-kong --gvc GVC_NAME`.
  </Accordion>
  <Accordion title="Every API call fails with bad_jwt">
    **Symptom:** Requests through Kong return `bad_jwt` or `invalid JWT` from PostgREST, GoTrue or Storage.

    **Cause:** `anonKey` or `serviceRoleKey` is not an HMAC-SHA256 JWT signed by the `secret` in the same dictionary secret — typically a key copied from elsewhere or a rotated `secret` without re-minted keys.

    **Fix:** Re-mint all four values together with the snippet in [Prerequisites](#prerequisites), apply the updated secret, and force-redeploy the six workloads listed under [Rotating a Credential](#rotating-a-credential).
  </Accordion>
  <Accordion title="Admin request returns 403 You cannot consume this service">
    **Symptom:** A call to `/auth/v1/admin/...` or `/pg/...` is refused with `403 You cannot consume this service`.

    **Cause:** The request carries `anonKey`. Kong admits only the `serviceRoleKey` consumer to the admin routes.

    **Fix:** Send `serviceRoleKey` in the `apikey` header from trusted server-side code only. This is the intended behavior for the public key.
  </Accordion>
  <Accordion title="Render fails with credentialsSecretName is required when storage.s3.endpoint is set">
    **Symptom:** Install or upgrade stops with `supabase: storage.s3.credentialsSecretName is required when storage.s3.endpoint is set`.

    **Cause:** You pointed `storage.s3.endpoint` at an S3-compatible store without naming the access-key secret. Keyless cloud identity is AWS-only.

    **Fix:** Create the dictionary secret (`accessKeyId`, `secretAccessKey`) shown under [Storage](#storage) and set `storage.s3.credentialsSecretName` to it.
  </Accordion>
  <Accordion title="Services fail with password authentication failed after changing the Postgres password">
    **Symptom:** After updating the Postgres credentials secret, Auth, PostgREST, Storage or Studio log `password authentication failed for user`.

    **Cause:** The password in the secret is applied only when the data directory is first initialized. The roles in the running database still have the old password.

    **Fix:** Change the password on the roles with `ALTER ROLE` as shown under [Rotating a Credential](#rotating-a-credential), then force-redeploy the consumers — or put the old value back in the secret and redeploy.
  </Accordion>
  <Accordion title="Realtime WebSocket handshake returns 403 TenantNotFound">
    **Symptom:** Subscriptions never open; the Realtime workload answers every `/realtime/v1/` handshake with `403 TenantNotFound`.

    **Cause:** You are on template version 1.0.0, which shipped Realtime without seeding its tenant.

    **Fix:** Upgrade to 1.1.1 following [Upgrading from 1.0.0](#upgrading-from-1-0-0); Realtime seeds its own tenant on boot from 1.1.0 onward.
  </Accordion>
  <Accordion title="Studio opens without asking for a password">
    **Symptom:** The dashboard loads with no login prompt.

    **Cause:** You reached the Studio workload directly — through `studio.allowedCidrs` or a widened `studio.internalAccess.type` — instead of through Kong. Studio enforces no login of its own.

    **Fix:** Clear `studio.allowedCidrs`, leave `studio.internalAccess.type: workload-list`, and reach the dashboard at `/` on the Kong address, where basic auth applies.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the three prerequisite secrets before installing** — JWT keys, Postgres credentials and the Studio password; a missing one wedges the deployment silently.
- **`serviceRoleKey` bypasses row-level security** — server-side only, never in client code; it is also the only key Kong admits to `/auth/v1/admin/` and `/pg/`.
- **Keep the JWT keys and the signing secret in sync** — `anonKey` and `serviceRoleKey` must be signed by `secret`, or every service returns `bad_jwt`; mint them together.
- **The dashboard login only applies through Kong** — leave `studio.allowedCidrs` empty and `studio.internalAccess.type` at `workload-list`; anything else exposes Studio, and the `serviceRoleKey` it holds, without a password.
- **Publishing Kong publishes the dashboard too** — `kong.publicAccess.enabled: true` puts Studio at `/` behind the Studio password, so make it a strong one.
- **Keep the `supabase/postgres` image** — a stock Postgres image lacks the extensions GoTrue, PostgREST, Realtime and Storage require.
- **The database login role is `postgres`** — fixed by the Supabase image; there is no username knob. The image's own superuser is `supabase_admin`, which the services use internally.
- **Changing a secret restarts nothing** — force-redeploy the consumers after a rotation, and change the Postgres password on the roles before changing the secret.
- **Realtime does not scale out** — single replica by design; clients must handle a dropped socket and reconnect after it restarts.
- **Storage and backup buckets must be separate** — each with its own bucket, Cloud Account and IAM policy.
- **Switching `backup.mode` restarts Postgres** — the two modes need different startup flags.
- **Access changes are not instant** — a change to `kong.publicAccess` or `studio.allowedCidrs` takes a little while to take effect; re-test rather than assuming it failed.
- **Data survives redeploys under the same release name** — the database on `RELEASE_NAME-postgres-vs`, local files on `RELEASE_NAME-storage-vs`; `cpln helm uninstall RELEASE_NAME --gvc GVC_NAME` deletes both.
