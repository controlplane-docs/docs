## Overview

pgEdge is an active-active distributed PostgreSQL cluster built on the Spock multi-master replication extension. Every node accepts reads and writes, and a row written on any node replicates to all the others with last-update-wins conflict resolution. This template deploys one set of PostgreSQL 17 nodes in each location you list, a per-location HAProxy failover tier that keeps a location serving when one of its nodes fails, a per-location pgcat connection pooler that gives applications a single endpoint, and an optional scheduled backup to S3 or GCS.

Database credentials are **not** template values. The nodes, the pooler, the failover tier and the backup job read the username, password and database name from a [dictionary secret](/guides/create-secret/dictionary) you create before installing, so no password passes through Helm or lands in the release.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have; it does not create, provision or manage one. Every location you list in `locations` must already be one of that GVC's locations. A GVC location you do not list starts nothing — its deployment reads `This workload location is deactivated because maxScale is set to 0.`, which is what a healthy install looks like in a shared GVC, not a fault.
</Note>

### What Gets Created

| Workload | `RELEASE_NAME-pgedge-backup` | Scheduled `pg_dumpall` of the first location's first node to S3 or GCS (cron). Suspended in every location except the first entry of `locations` | `backup.enabled: true` |

## Prerequisites

Two things must exist before you install: a GVC that already has the locations you intend to use, and the credentials secret. Secrets are org-level, so no GVC flag is involved when creating one.

<Steps>
  <Step title="A GVC that contains every location you will list">
    The template deploys into the GVC you pass to `--gvc`. It may have more locations than you list — nothing pgEdge-related runs in those — but it must have every one you do list. Check its locations under `spec.staticPlacement.locationLinks`:

    ```bash
    cpln gvc get GVC_NAME -o yaml
    ```

    Set `locations` to a subset of what you see there. A location that is not on the GVC is not caught at install time — the install succeeds and the nodes then refuse to initialize (see [Troubleshooting](#troubleshooting)).
  </Step>
  <Step title="Create the database credentials secret">
    A [dictionary secret](/guides/create-secret/dictionary) holding exactly three keys — `username`, `password` and `database`. The nodes create that user and that database on first boot, and pgcat uses the same password for its admin console:

    ```bash
    cpln secret create-dictionary --name SECRET_NAME \
      --entry username=myuser \
      --entry password='YOUR-STRONG-PASSWORD' \
      --entry database=mydb
    ```

    Set `postgres.credentialsSecretName` to the name you used. Secret names are org-wide, so give each release its own.
  </Step>
  <Step title="Read the secret back later">
    Pass `-o yaml`. A bare `cpln secret reveal` prints only a summary table, not the values:

    ```bash
    cpln secret reveal SECRET_NAME -o yaml
    ```
  </Step>
</Steps>

<Warning>
**Create the secret before installing, or the deployment wedges silently.** The template refuses to render when `postgres.credentialsSecretName` is blank, but a name that points at a secret which does not exist installs "successfully" and then never starts. The container never runs, so `cpln logs` returns **zero lines** — there is nothing to log. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-pgedge --gvc GVC_NAME -o yaml
```

Use `get-deployments` — plain `cpln workload get` has no `versions` key. Creating the missing secret repairs the deployment on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-pgedge --gvc GVC_NAME` to skip the wait.
</Warning>

Backups need a bucket and, for AWS or GCP, a Control Plane Cloud Account before they can be enabled — see [Backing Up](#backing-up). Nothing else is required.

## Installation

The default `locations` list names three AWS regions with three nodes each, so a real install nearly always carries its own location list. Lists cannot be set piecemeal with `--set` — Helm replaces the whole list, and a `--set locations[0].name=...` without `replicas` fails to render with `location 'aws-us-east-1' must have at least 1 replica` — so put them in a values file:

```yaml
# values.yaml
locations:
  - name: aws-us-east-1
    replicas: 1
postgres:
  credentialsSecretName: SECRET_NAME
```

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/pgedge \
  --version 2.2.0 --gvc GVC_NAME \
  -f values.yaml
```

## Configuration

### Locations and Replicas

Each entry pairs a location with a node count. Every location listed must already be on the GVC you install into; extra GVC locations run nothing. Listing the same location twice is rejected at render, because duplicates would produce duplicate Spock node names.

```yaml
locations: # For replicas: use 1 for dev/testing, 3 for production
  - name: aws-us-west-2
    replicas: 3
  - name: aws-us-east-2
    replicas: 3
  - name: aws-eu-central-1
    replicas: 3

multiZone: false  # Set to true to spread replicas across availability zones within each location
```

| Environment | Replicas per location |
|---|---|
| Dev / testing | 1 |
| Production | 3 |

The **first** entry of `locations` is special: it is the only location the backup job runs in, and with the failover tier off and `pgcat.routing: single-writer` its first node is the cluster's single write target.

Verify that your locations support multiple availability zones before enabling `multiZone`.

### Image and Resources

The node container exposes both a reservation and a limit. `maxCpu: 2` against `minCpu: 500m` is exactly the 4:1 ratio a stateful workload allows, so raise `minCpu` whenever you raise `maxCpu`.

```yaml
image: ghcr.io/pgedge/pgedge-postgres:17-spock5-standard

resources:
  minCpu: 500m
  minMemory: 1Gi
  maxCpu: 2
  maxMemory: 4Gi
```

### Credentials

```yaml
postgres:
  credentialsSecretName: my-pgedge-credentials
```

The named [dictionary secret](/guides/create-secret/dictionary) must exist before install and hold `username`, `password` and `database` — see [Prerequisites](#prerequisites). The nodes, pgcat, HAProxy and the backup job all read it; nothing else in the release carries a credential.

### Volume Set

Set the initial storage capacity per node (minimum 10 GiB). Set `autoscaling.enabled: true` to expand volumes as data grows:

```yaml
volumeset:
  capacity: 10  # Initial capacity in GiB (minimum is 10)
  autoscaling:
    enabled: false  # Set to true to enable autoscaling
    maxCapacity: 100  # Maximum capacity in GiB when autoscaling is enabled
    minFreePercentage: 10  # Minimum free percentage to trigger scaling
    scalingFactor: 1.2  # How much to scale up when triggered
```

### HAProxy Failover Tier

The request flow is `app → pgcat (pooler) → HAProxy (failover) → pgEdge node`. pgcat pools connections; HAProxy picks the node. Both run one set per location, and the endpoint applications connect to stays the pgcat one.

Each location's HAProxy sends all of that location's traffic to **its own** first node (`replica-0`) and, if that node is unhealthy, fails over in order to the other local nodes, then to the nodes of the other locations in `locations` order — so applications keep serving through a node failure without changing anything. It is on by default; set `proxy.enabled: false` to have pgcat connect to the nodes directly (the template version 2.1.0 shape).

```yaml
proxy:
  enabled: true
  image: haproxy:3.0.28  # pinned exact; Debian variant (perl needed by the startup gate)
  resources:
    cpu: 100m
    memory: 128Mi
  minReplicas: 2         # per location
  maxReplicas: 2         # per location
```

With the tier on, pgcat has exactly one backend — the local HAProxy — so read/write splitting is off and every statement from a location lands on whichever node HAProxy currently prefers. Local reads are therefore not spread across a location's other nodes; that is the deliberate trade for read-your-writes consistency within a location.

### pgcat Connection Pooler

pgcat multiplexes application connections into a smaller pool of real database connections, reducing overhead and protecting PostgreSQL from connection exhaustion. `defaultPoolSize` sets how many real connections pgcat maintains per pool; `minReplicas` and `maxReplicas` are per location, and pgcat autoscales between them on request rate.

```yaml
pgcat:
  image: ghcr.io/postgresml/pgcat:v1.2.0 # pinned: `latest` makes installs non-reproducible
  poolMode: transaction  # options: session, transaction, statement
  defaultPoolSize: 25    # Real Postgres connections pgcat maintains per pool
  routing: local         # local | single-writer — ignored when proxy.enabled (default)
  resources:
    cpu: 500m
    memory: 256Mi
  minReplicas: 2         # per location
  maxReplicas: 4         # per location
```

| Pool mode | Behavior |
|---|---|
| `transaction` | Connection held only for the duration of a transaction. Best for most web and API workloads. Not compatible with `SET` variables, temporary tables, or advisory locks. |
| `session` | Connection held for the entire client session. Compatible with all PostgreSQL features but provides less connection reuse. |
| `statement` | Connection returned after every statement. Transactions are not supported. Rarely used. |

### pgcat Read and Write Routing

**With the failover tier on (the default), `routing` does not apply** — pgcat pools a single backend, the local HAProxy, and all node selection is HAProxy's. The two modes below take effect only with `proxy.enabled: false`, where pgcat pools the pgEdge nodes directly and parses each query to split reads from writes.

- **`local` (default)** — each location's pgcat pools **only that location's nodes**: the local `replica-0` is the write target, and the other local nodes serve reads. Every location reads *and* writes locally, so this is true active/active, and losing one location does not stop writes in the others. With a single node in a location, that node serves reads too.
- **`single-writer`** — every pgcat, in every location, pools the **whole cluster** with a single write target (`replica-0` of your first location); reads go to the other nodes. Use this only if your application cannot tolerate multi-master last-update-wins conflict resolution and needs one write target. Writes stop if the first location is down, and reads are served cross-region.

<Warning>
**Routing is decided by statement shape, not by what the statement does.** A data-modifying CTE such as `WITH ins AS (INSERT ... RETURNING *) SELECT * FROM ins` is classified as a read and routed to a replica. Every node accepts writes, so the write still succeeds — but "writes go to the primary" is a routing convention, not an enforced guarantee. Send anything whose placement matters through a direct connection to the node you intend.
</Warning>

### Internal Access

Controls which workloads can connect to the nodes, the failover tier and pgcat. Nothing in this template is exposed publicly, and there is no public access option.

```yaml
internal_access: # Sets both pgedge and pgcat workloads
  type: same-gvc  # options: same-gvc, same-org, workload-list
  workloads:  # Only used when type is workload-list; list only your clients --
              # this release's pgedge and pgcat workloads are added automatically
    #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

- `same-gvc` — Allow access from all workloads in the same GVC.
- `same-org` — Allow access from all workloads in the org.
- `workload-list` — Allow access only from the workloads you list, **plus this release's own workloads**, which the template adds for you.

<Warning>
**With `workload-list`, list only your own client workloads.** The same list governs Spock replication between the nodes, HAProxy's and pgcat's connections to the nodes, and the backup job's connection — so a list naming only your applications would cut the cluster off from itself. Template version 2.0.1 and later add this release's pgedge, pgcat, HAProxy (when enabled) and backup (when enabled) workloads automatically; anything of the release's you add by hand is de-duplicated. On version 2.0.0 the release's own workloads were not added, every node kept accepting writes that never replicated while reporting ready, and every backup uploaded an empty file — upgrade to 2.0.1 or later and verify replication with `SELECT subscription_name, status FROM spock.sub_show_status();` on every node.
</Warning>

### Backup

When `backup.enabled` is `true`, a cron workload dumps the first node of the first location on the configured schedule and uploads the result to S3 or GCS. Keep `schedule` quoted; any valid cron expression works, including one beginning with `*`. The bucket, cloud account and IAM setup are described under [Backing Up](#backing-up).

```yaml
backup:
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/postgres-backup:17.1.0
  schedule: "0 2 * * *"   # daily at 2am UTC — runs in locations[0] only

  resources:
    cpu: 100m
    memory: 128Mi

  provider: aws  # Options: aws or gcp

  aws:
    bucket: my-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: pgedge/backups  # folder where backups will be stored

  gcp:
    bucket: my-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: pgedge/backups  # folder where backups will be stored
```

## Connecting

Connect through pgcat for all application traffic. With the failover tier on (default), the per-location HAProxy behind pgcat handles node failover and the endpoint is unchanged. Always use the fully-qualified `.GVC_NAME.cpln.local` form — the bare workload name does not resolve reliably from every workload type.

| What | Address | Notes |
|---|---|---|
| Pooled endpoint (use this) | `RELEASE_NAME-pgcat.GVC_NAME.cpln.local:5432` | Internal only. Each location's clients are served by that location's pgcat |
| A single node, directly | `replica-N.RELEASE_NAME-pgedge.LOCATION_NAME.GVC_NAME.cpln.local:5432` | Needed for schema changes and per-node checks. `N` runs from `0` to `replicas - 1` |
| pgcat admin console | Pooled endpoint, database `pgcat`, user `pgcat_admin` | Password is the `password` entry of your credentials secret |
| Database, username, password | `cpln secret reveal SECRET_NAME -o yaml` | The `database`, `username` and `password` entries of your credentials secret |
| Public endpoint | None | The template has no public access option |

To verify from your own machine, tunnel to pgcat and open a `psql` session against the tunnel:

```bash
cpln port-forward RELEASE_NAME-pgcat 5432:5432 --gvc GVC_NAME
```

```bash
psql "host=localhost port=5432 user=USERNAME dbname=DATABASE"
```

To check replication from inside a node, run `psql` on it — the container already carries the credentials in its environment:

```bash
cpln workload exec RELEASE_NAME-pgedge --gvc GVC_NAME --replica RELEASE_NAME-pgedge-0 --location LOCATION_NAME --container pgedge -- bash -c 'psql -U "$PG_USERNAME" -d "$PG_DATABASE" -c "SELECT subscription_name, status FROM spock.sub_show_status();"'
```

On a healthy cluster of N nodes every node returns N−1 rows and each reads `replicating`.

### Schema Changes and DDL

Spock replicates row-level changes (`INSERT`, `UPDATE`, `DELETE`) automatically. **DDL does not replicate.** A plain `CREATE TABLE` or `ALTER TABLE` applies only to the node you ran it on; the other nodes never learn about it, and rows written into that table on one node cannot be applied on a node where it does not exist. Run DDL against a node directly, never through pgcat.

<Warning>
**Every table must have a `PRIMARY KEY`.** The template adds each new table to the `default` replication set automatically, and that set replicates `UPDATE` and `DELETE`, which Spock cannot do without a key. A table without one does not merely fail to replicate — the `CREATE TABLE` itself is rejected:

```text
ERROR:  table events cannot be added to replication set default
DETAIL:  table does not have PRIMARY KEY and given replication set is configured to replicate UPDATEs and/or DELETEs
```
</Warning>

#### Creating a Table

The simplest correct procedure is to run the same `CREATE TABLE` on **every** node. The auto-add trigger fires locally on each one, so the table ends up in the `default` replication set everywhere and DML replicates in all directions:

```sql
-- Run on EVERY node, connecting to each directly (not through pgcat)
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  amount numeric,
  created_at timestamptz DEFAULT now()
);
```

For larger clusters you can broadcast the DDL instead — but it takes **two** steps, and the second one runs on the other nodes, not on the node that broadcast:

```sql
-- Step 1: on ONE node -- creates the table on all nodes
SELECT spock.replicate_ddl('CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  amount numeric,
  created_at timestamptz DEFAULT now()
);');

-- Step 2: on every OTHER node -- adds the table to that node's replication set
SELECT spock.repset_add_table('default', 'orders'::regclass);
```

Step 2 is needed because Spock suppresses event triggers while applying replicated changes, so the auto-add trigger fires only on the node that called `replicate_ddl`. Running step 2 on *that* node fails with `duplicate key value violates unique constraint "replication_set_table_pkey"`, and skipping it strands writes made on the other nodes. Confirm on every node — each must return a row:

```sql
SELECT * FROM spock.tables WHERE relname = 'orders';
```

#### Other DDL

`ALTER TABLE` and `DROP TABLE` follow the same rule — apply on every node, or broadcast once:

```sql
SELECT spock.replicate_ddl('ALTER TABLE orders ADD COLUMN status text DEFAULT ''pending'';');
SELECT spock.replicate_ddl('DROP TABLE orders;');
```

#### Primary Keys

Use `uuid` primary keys instead of `serial` or `bigserial`. Each node maintains its own sequence, so auto-increment integers collide when the same value is generated on two nodes at once:

```sql
-- Good: globally unique, no conflicts
id uuid PRIMARY KEY DEFAULT gen_random_uuid()

-- Avoid: causes duplicate key conflicts under concurrent multi-node writes
id serial PRIMARY KEY
```

## Operations

### Backing Up

When `backup.enabled` is `true`, the `RELEASE_NAME-pgedge-backup` cron workload runs `pg_dumpall` against `replica-0` of the **first** location in `locations`, compresses the output and uploads it as `PREFIX/postgres-YYYY-MM-DDTHH-MM-SSZ.sql.gz`. Because every node holds a full copy of the data, one node is enough, and the job runs in that first location only, however many locations the GVC has. The backup job connects over the internal network like any other client, so it is subject to [Internal Access](#internal-access); version 2.0.1 and later add it to a `workload-list` automatically.

#### AWS S3 Prerequisites

1. Create your S3 bucket and note its name and region. Set `backup.aws.bucket` and `backup.aws.region`.
2. If you do not have a Cloud Account set up, refer to the docs to [Create a Cloud Account](/guides/create-cloud-account). Note the cloud account name.
3. Create a new AWS IAM policy with the following JSON (replace `YOUR_BUCKET_NAME`):

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion",
                "s3:GetBucketLocation",
                "s3:AbortMultipartUpload",
                "s3:ListBucketMultipartUploads",
                "s3:ListMultipartUploadParts"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.cloudAccountName` to your cloud account name.
5. Set `backup.aws.policyName` to the policy created in step 3.

<Note>
**If your IAM policy predates template version 1.1.1**, update it to the full action list above. Earlier versions attached the AWS managed policy `ReadOnlyAccess` to the backup identity as well, which granted read access to every bucket in your account and silently supplied any read action your own policy omitted. The identity now carries `cpln-connector` and your bucket-scoped policy only.
</Note>

#### GCS Prerequisites

1. Create your GCS bucket and note its name. Set `backup.gcp.bucket`.
2. If you do not have a Cloud Account set up, refer to the docs to [Create a Cloud Account](/guides/create-cloud-account). Note the cloud account name.

4. Set `backup.gcp.cloudAccountName` to your cloud account name.

### Restoring a Backup

<Warning>
**No restore procedure has been verified for this template.** The constraints below are taken from the chart and the backup image; the outline that follows them is the shape a restore must take, not a tested recipe. Rehearse it on a scratch release before relying on it.
</Warning>

What the backup file is and what the cluster requires of a restore:

- **The file is a whole-server `pg_dumpall` dump**, gzip-compressed: roles, every database, and `\connect` statements between them. It cannot be replayed through pgcat, which pools one database in transaction mode.
- **DDL does not replicate.** A dump applied to one node creates the tables on that node only, and rows that then replicate out fail to apply on nodes that lack the table. The schema must exist on every node before data is loaded on any of them (see [Schema Changes and DDL](#schema-changes-and-ddl)).
- **Nodes added later do not catch up on existing data.** The template creates Spock subscriptions without initial synchronization, so a node that joins after data exists receives only changes made from that point on. Restore into a release that already has its final topology.

The outline, unverified:

1. Download the dump to a machine with `psql` and access to the bucket, for example `aws s3 cp s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz - | gunzip > pgedge-backup.sql` (or `gsutil cp` for GCS).
2. Install the target release with its final `locations`, and confirm every subscription reads `replicating` (see [Connecting](#connecting)).
3. Put the schema on every node first, following [Schema Changes and DDL](#schema-changes-and-ddl). A `pg_dumpall` file mixes schema and data, so this means separating the `CREATE TABLE` statements for your database from the rows yourself.
4. Load the data on **one** node through a direct connection — for example a tunnel to that node — and let Spock replicate the rows to the others. Load it nowhere else.

```bash
cpln port-forward RELEASE_NAME-pgedge 5432:5432 --gvc GVC_NAME --replica RELEASE_NAME-pgedge-0 --location LOCATION_NAME
```

Each node's volume also keeps 7 days of snapshots, with a final snapshot taken on deletion, but restoring a single node's volume into a running multi-master cluster has not been verified either and is not a substitute for the procedure above.

### Upgrading from 1.x

Template versions through 1.1.1 created their own GVC, so that GVC is part of a 1.x release's manifest. Version 2.0.0 and later do not declare one — and Helm deletes what a chart stops declaring.

<Warning>
**An in-place `helm upgrade` from 1.x to any 2.x version is not supported and destroys the cluster.** The upgrade would delete the GVC the 1.x chart created together with every workload, volume set and identity inside it — including your data. The only supported path is the migration below: install 2.x as a new release into an existing GVC, move the data, then remove the old release.

The chart refuses to render when your values still carry the 1.x `gvc` key, so an upgrade that passes your old values file stops before a single API call is made:

```text
Error: execution error at (pgedge/templates/identity.yaml:2:4): pgedge 2.0.0: the `gvc` values key was REMOVED. This chart no longer creates a GVC -- it deploys into the GVC you install into, and `gvc.locations` moved to the top-level `locations`. DO NOT `helm upgrade` a 1.x release onto 2.0.0: the upgrade drops `kind: gvc` from the manifest and Helm deletes what a chart no longer declares, which DESTROYS that GVC and every workload, volumeset and identity inside it. Install 2.0.0 as a NEW release against an existing GVC, move your data, then uninstall the old release. See `Migrating from 1.x` in the README.
```

**The guard cannot cover an upgrade run with no values at all.** A 1.x release installed on pure defaults has no `gvc` key for the chart to see, so nothing fires. Do not run `helm upgrade` on a 1.x release against any 2.x chart under any circumstances.
</Warning>

The 1.0.x credential values (`postgres.username`, `postgres.password`, `postgres.database`) are refused at render as well, with their own message, so pasting an old values file into a 2.x install produces an error rather than a silent misconfiguration.

<Steps>
  <Step title="Back up the old cluster">
    Use `backup.enabled` on the 1.x release, or take a manual dump against one of its nodes directly:

    ```bash
    pg_dump "host=replica-0.OLD_RELEASE-pgedge.LOCATION_NAME.OLD_GVC.cpln.local user=USERNAME dbname=DATABASE" \
      | gzip > pgedge-backup.sql.gz
    ```

    If replication on the old cluster was never switched on — which is every 1.x install that did not apply the fix below — the nodes may hold **different** data. Compare row counts per node before deciding which one to dump, or reconcile them first.
  </Step>
  <Step title="Choose the GVC for the new release">
    Pick a GVC that already has every location you intend to list in `locations`. See [Prerequisites](#prerequisites).
  </Step>
  <Step title="Create the credentials secret and install 2.x as a new release">
    Use a **different release name** — secret names are org-wide, so a same-named release collides with the 1.x one even in another GVC. Coming from 1.0.2 or earlier, the credentials were plain values with a published default password; choose a new password now and put it in the dictionary secret, since a fresh install creates its roles from that secret.
  </Step>
  <Step title="Restore and cut over">
    Load the data into the new cluster following the constraints in [Restoring a Backup](#restoring-a-backup), then point your applications at the new pooled endpoint, `NEW_RELEASE-pgcat.NEW_GVC.cpln.local:5432`.
  </Step>
  <Step title="Uninstall the old release against the GVC you installed it into">
    Not the GVC it created — the GVC you passed at install time is where Helm tracks the release, and uninstalling from there removes the created GVC with it.
  </Step>
</Steps>

#### Switching Replication On for an Existing 1.x Cluster

PostgreSQL 17.11 ships `output_plugin_libraries = 'pgoutput, test_decoding'`, and Spock's output plugin is not on that list. On every template version through 1.1.1 this means **no replication slot could ever be created**: each subscription sits at `down`, each node accepts writes that never leave it, and every status surface still reports healthy. The reason appears in the node's own PostgreSQL server log, not in `cpln logs`:

```text
ERROR:  library "spock_output" may not be used as an output plugin
```

Version 2.0.0 and later write the setting into `postgresql.conf` during `initdb`, so a **fresh** 2.x install needs nothing. An existing data directory keeps the old setting, so if you are staying on 1.x while planning the migration, apply it by hand **on every node**, connecting to each node directly rather than through pgcat:

```bash
psql "host=replica-0.RELEASE_NAME-pgedge.LOCATION_NAME.GVC_NAME.cpln.local user=USERNAME dbname=DATABASE" \
  -c "ALTER SYSTEM SET output_plugin_libraries = pgoutput, test_decoding, spock_output;" \
  -c "SELECT pg_reload_conf();"
```

<Warning>
**The value must be unquoted here, and `pg_reload_conf()` is the whole procedure — do not restart a 1.x node to apply it.** `ALTER SYSTEM` adds the quoting for you; quoting it yourself stores a single bogus plugin literally named `"pgoutput, test_decoding, spock_output"` and the error persists (confirm with `SHOW output_plugin_libraries;` — the output must contain no quotation marks). And the pre-2.0.0 startup routine drops every replication slot that is momentarily inactive, on every peer it can reach, so restarting even one 1.x node breaks the mesh in a way that does not heal on its own. Version 2.0.0 fixes that.
</Warning>

Subscriptions move to `replicating` shortly after the reload. Check on every node:

```sql
SELECT subscription_name, status FROM spock.sub_show_status();
```

### Upgrading from 2.0.x

- **2.0.0 → 2.0.1** fixes `internal_access.type: workload-list`: the release's own pgedge, pgcat and backup workloads are now added to the list automatically. If you ran 2.0.0 with `workload-list`, upgrade and then verify replication with `SELECT subscription_name, status FROM spock.sub_show_status();` on every node — see [Internal Access](#internal-access).
- **2.0.x → 2.1.0** adds `pgcat.routing` and **changes the default write model**. A 2.0.x install routed every write to the first location's first node (what 2.1.0 calls `single-writer`); after the upgrade each location's pgcat writes to its own local node (`local`). If your application depends on a single write target to avoid conflicts, set `pgcat.routing: single-writer` **before** upgrading. Your data is preserved — each node's volume is retained — but the upgrade changes the node startup script, so the nodes restart as part of it; treat it as a planned write interruption (see [Scaling and Availability](#scaling-and-availability)).

### Upgrading from 2.1.0

Version 2.2.0 adds the per-location HAProxy failover tier, **on by default**, and changes what pgcat connects to:

- pgcat now pools a single backend, the local HAProxy, instead of the nodes directly. **`pgcat.routing` is ignored while `proxy.enabled` is `true`.** If you set `pgcat.routing: single-writer` on 2.1.0 and need that behavior kept, set `proxy.enabled: false` before upgrading — with the tier on, every location writes to its own local node.
- With the tier on, pgcat's read/write splitting is off: all of a location's statements go to the node HAProxy currently prefers (the local `replica-0` while it is healthy). Local reads are no longer spread across a location's other nodes.
- A new workload, `RELEASE_NAME-pgedge-proxy`, and its startup secret are created; pgcat's startup script and readiness check change, so the pgcat replicas restart. With `internal_access.type: workload-list` the node firewall gains the new proxy workload.
- `proxy.enabled: false` renders the same resources as 2.1.0, so an install that opts out of the tier keeps its existing shape.

Treat any `helm upgrade` of this template as a possible restart of every node at once — see [Scaling and Availability](#scaling-and-availability).

### Scaling and Availability

**Nodes per location.** Use at least 3 nodes per location in production so the failover tier has a local node to fail over to; a single node per location fails over to a remote location instead. All nodes in all locations are writable at all times.

**What the failover tier covers.** With `proxy.enabled: true`, a failed node in a location is routed around automatically — first to another node in the same location, then to a remote location — and the application endpoint does not change. When the failed node recovers, connections pgcat already holds keep using the failover target until the pool recycles them, so traffic returns to the local node gradually rather than instantly.

**What it does not cover.** If a location is lost entirely, applications **in that location** are not redirected to another location's pooler; the other locations keep serving their own clients and keep writing. An application that must survive the loss of its own location has to reach another location itself. With `proxy.enabled: false` there is no node failover at all beyond pgcat's own backend health checks, and `pgcat.routing: single-writer` additionally makes the first location's first node a single point of failure for writes.

**Upgrades and restarts.** Any change that restarts the node workload restarts **every node in every location at once** — nothing serializes a rolling restart of this stateful workload. Treat a `helm upgrade` as a short, planned write interruption. Data is preserved on each node's volume, and the mesh reconciles itself on boot: each node keeps replication slots a subscription still owns, drops only genuinely orphaned ones, skips that cleanup entirely while any peer is unreachable, and rebuilds any subscription whose slot has gone missing.

<Warning>
**Self-repair restores replication, not history.** When a broken subscription is rebuilt, replication resumes from the current position — rows written on a node while its subscription was down are **not** backfilled, and a node that took writes while cut off needs those rows reconciled by hand.
</Warning>

**Growing or shrinking the cluster.** Changing `locations` after data exists is not a verified path. The template creates subscriptions without initial synchronization, so a node added to a cluster that already holds data starts without its tables and rows and receives only changes made after it joins. Plan the final topology before loading data, or rebuild through a new release and a restore. If you remove a location from the GVC, remove it from `locations` in the same change; otherwise every node logs a `WARNING` about the missing location on each restart.

**Storage.** Each node's volume starts at `volumeset.capacity` GiB. Enable `volumeset.autoscaling` to grow volumes automatically up to `maxCapacity`; the volume set is never shrunk by the template.

### Troubleshooting

<AccordionGroup>
  <Accordion title="The deployment never starts and cpln logs returns nothing">
    **Symptom:** no replica ever becomes ready, and `cpln logs` for the node, pgcat or HAProxy workload returns zero lines.

    **Cause:** the credentials secret named by `postgres.credentialsSecretName` does not exist, so the container is never started and has nothing to log.

    **Fix:** read the message, which names the missing secret:

    ```bash
    cpln workload get-deployments RELEASE_NAME-pgedge --gvc GVC_NAME -o yaml
    ```

    Create the secret as described in [Prerequisites](#prerequisites). The deployment recovers on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-pgedge --gvc GVC_NAME`.
  </Accordion>
  <Accordion title="Nodes restart with FATAL locations declared in values are not in GVC">
    **Symptom:** the install succeeds, but the node containers exit and restart, and the node logs show:

    ```text
    [pgedge] FATAL: locations declared in values are not in GVC 'GVC_NAME': aws-eu-central-1
    [pgedge] GVC 'GVC_NAME' has: aws-us-west-2 aws-us-east-2
    ```

    **Cause:** `locations` names a location the GVC does not have. The platform does not validate this at install, so the nodes check it themselves at startup and refuse to initialize a cluster whose declared members can never exist.

    **Fix:** either add the location to the GVC or remove it from `locations`, then upgrade the release. Read the lines with a server-side filter:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-pgedge"} |= "[pgedge]"' --limit 50 --since 10m
    ```

    A node that has **already** initialized logs `[pgedge] WARNING: locations declared in values are not in GVC` instead and keeps serving, so this check never takes down a running cluster. A line reading `[pgedge] WARNING: could not read the location list of GVC` means the check could not run at all and was skipped — verify the GVC's locations yourself with `cpln gvc get GVC_NAME -o yaml`.
  </Accordion>
  <Accordion title="CREATE TABLE fails with cannot be added to replication set default">
    **Symptom:**

    ```text
    ERROR:  table events cannot be added to replication set default
    DETAIL:  table does not have PRIMARY KEY and given replication set is configured to replicate UPDATEs and/or DELETEs
    ```

    **Cause:** the template adds every new table to the `default` replication set, which replicates `UPDATE` and `DELETE`; Spock cannot do that for a table without a primary key.

    **Fix:** give the table a `PRIMARY KEY` — a `uuid` column with `DEFAULT gen_random_uuid()` is the recommended shape (see [Primary Keys](#primary-keys)).
  </Accordion>
  <Accordion title="A table exists on one node only, or rows written on one node never appear on the others">
    **Symptom:** a table you created is missing on other nodes, or the other nodes' subscriptions stop at `down` after you created it.

    **Cause:** DDL does not replicate. A plain `CREATE TABLE` applied to one node only, or `spock.replicate_ddl()` was run without the follow-up `spock.repset_add_table()` on the other nodes.

    **Fix:** follow [Schema Changes and DDL](#schema-changes-and-ddl) — create the table on every node directly, or broadcast it and then add it to the replication set on every other node. Confirm with `SELECT * FROM spock.tables WHERE relname = 'TABLE_NAME';` on each node.
  </Accordion>
  <Accordion title="spock.sub_show_status() shows subscriptions down">
    **Symptom:** `SELECT subscription_name, status FROM spock.sub_show_status();` returns `down` for one or more rows, and writes made on one node do not appear on another.

    **Causes and fixes, in order of likelihood:**

    - **Template version 2.0.0 with `internal_access.type: workload-list`** — the nodes could not reach each other. Upgrade to 2.0.1 or later, which adds the release's own workloads to the list (see [Internal Access](#internal-access)).
    - **A 1.x data directory** — the server log (not `cpln logs`) shows `library "spock_output" may not be used as an output plugin`. Apply the fix under [Switching Replication On for an Existing 1.x Cluster](#switching-replication-on-for-an-existing-1-x-cluster).
    - **A node that is still booting or restarting** — the mesh reconciles itself on boot. Give it a few minutes and re-check; rows written while a subscription was down are not backfilled (see [Scaling and Availability](#scaling-and-availability)).
  </Accordion>
  <Accordion title="pgcat returns could not get connection from the pool - AllServersDown">
    **Symptom:** connections through the pooled endpoint fail with `could not get connection from the pool - AllServersDown`, typically right after an upgrade or a node restart.

    **Cause:** pgcat's backend failed a health check. pgcat bans a failed backend for 60 seconds (its default `ban_time`), so errors can continue for up to a minute after the backend itself is healthy again.

    **Fix:** wait out the ban and retry. If it persists, check that the backend is actually serving — with the failover tier on, that is the local HAProxy, whose stats page shows every node's state (next entry); with it off, check the node directly as in [Connecting](#connecting).
  </Accordion>
  <Accordion title="HAProxy replicas never become ready and log pgedge proxy waiting for">
    **Symptom:** the `RELEASE_NAME-pgedge-proxy` replicas stay not ready, and their logs repeat lines like `pgedge proxy: waiting for replica-1.RELEASE_NAME-pgedge.LOCATION_NAME.GVC_NAME.cpln.local (attempt 12, 36s elapsed)`.

    **Cause:** at startup HAProxy waits until **every** node in **every** location answers PostgreSQL on port 5432 before it starts serving. A node that is down, still initializing, or blocked by a `workload-list` firewall holds the whole proxy back; after 900 seconds the container exits and is restarted to try again.

    **Fix:** find out why the named node is not answering (see the entries above), then let the proxy come up on its own. Once HAProxy is running, its stats page shows which node is active, which are backups, and which are `UP` or `DOWN`:

    ```bash
    cpln port-forward RELEASE_NAME-pgedge-proxy 8405:8405 --gvc GVC_NAME
    ```

    Then open `http://localhost:8405/stats` in a browser.
  </Accordion>
  <Accordion title="Scheduled backups upload an empty file or fail with server closed the connection unexpectedly">
    **Symptom:** backup objects in the bucket are empty, and the backup job's logs show `pg_dumpall: error: ... server closed the connection unexpectedly`.

    **Cause:** on template version 2.0.0 with `internal_access.type: workload-list`, the backup workload was not allowed to reach the node it dumps.

    **Fix:** upgrade to 2.0.1 or later, which adds the backup workload to the list automatically when `backup.enabled` is `true`. Check the job's output with:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-pgedge-backup"}' --limit 50 --since 10m
    ```
  </Accordion>
</AccordionGroup>

## Important Notes

- **Never run `helm upgrade` on a 1.x release against any 2.x version** — it deletes the GVC the 1.x chart created and everything in it. Migrate to a new release instead: [Upgrading from 1.x](#upgrading-from-1-x).
- **The GVC must already contain every location you list**, and may contain more. A missing location is not caught at install — the nodes exit with `[pgedge] FATAL: locations declared in values are not in GVC ...`. Locations you do not list start nothing.
- **DDL does not replicate** — create every table on every node (or broadcast it and add it to the replication set on the others), and give every table a `PRIMARY KEY` or `CREATE TABLE` fails outright.
- **With `internal_access.type: workload-list`, list only your clients** — the release's own workloads are added for you on 2.0.1 and later.
- **`pgcat.routing` has no effect while `proxy.enabled` is `true`.** To keep a single global write target, set `proxy.enabled: false` and `pgcat.routing: single-writer`.
- **Use at least 3 nodes per location in production** so a node failure is covered within the location.
- **A `helm upgrade` can restart every node at once** — plan it as a short write interruption. Data is preserved; rows written on a node while its subscriptions were down are not backfilled.
- **Fix the topology before loading data** — nodes added to a cluster that already holds data do not receive existing rows.
- **Rotating the database password is not a supported path in this version.** The password is written into each node's Spock node and subscription definitions when they are created, so changing the secret alone would break replication; plan a new release and a restore if you must rotate.
- **Release names must be unique per org** — secrets are org-wide, so two releases with the same name collide even in different GVCs.
- **Conflict resolution is last-update-wins** by commit timestamp. Route writes for a given entity to one node in your application if you need stronger guarantees.
- **No restore procedure is verified for this template yet** — rehearse [Restoring a Backup](#restoring-a-backup) on a scratch release before you depend on it.
