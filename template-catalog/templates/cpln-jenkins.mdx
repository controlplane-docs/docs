## Overview

Jenkins is an open-source automation server for CI/CD pipelines. This template deploys a single Jenkins controller with the [Control Plane cloud plugin](https://github.com/controlplane-com/cpln-jenkins-plugin) built in: when a job is queued, Jenkins provisions a build agent as its own Control Plane workload and deletes it once idle, so build capacity costs nothing between builds.

The controller is configured entirely from code and boots straight to a login screen, with no setup wizard. The admin password and the Control Plane API key Jenkins uses to create agents both come from secrets you create **before** installing; neither passes through Helm values.

<Note>
This template does not create a GVC. It deploys into an existing GVC that you already have. By default agents are provisioned into that same GVC, which must have exactly one location.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-jenkins` | Jenkins controller (stateful, 1 replica, HTTP port `8080`) | — |
| Volume set | `RELEASE_NAME-jenkins-vs` | `/var/jenkins_home` — jobs, build history and installed plugins (`ext4`, final snapshot kept 7 days on delete) | — |
| Secret | `RELEASE_NAME-jenkins-cloud` | The Control Plane cloud settings, rendered from `cloud.*` and read by Jenkins at boot as Configuration as Code | `cloud.enabled: true` (default) |
| Identity | `RELEASE_NAME-jenkins-identity` | Controller identity | — |
| Policy | `RELEASE_NAME-jenkins-policy` | `reveal` on exactly the secrets the controller reads: your admin password secret, plus your API key secret and `RELEASE_NAME-jenkins-cloud` when the cloud is enabled | — |
| Workloads | names start with `cloud.agentWorkload` (`jenkins-agent`) | Build agents, created and deleted **by Jenkins** at build time — not by the chart | `cloud.enabled: true` (default) |

## Prerequisites

**Two `opaque` secrets must exist before you install.** Secrets are org-level, so no GVC flag is involved, and their names are org-wide — give each Jenkins release its own.

<Steps>
  <Step title="Create the admin password secret">
    Anyone holding this password controls your CI, so use a strong one:

    ```bash
    printf '%s' "$(openssl rand -hex 32)" | cpln secret create-opaque --name ADMIN_PASSWORD_SECRET_NAME --encoding plain -f -
    ```

    Read it back to sign in:

    ```bash
    cpln secret reveal ADMIN_PASSWORD_SECRET_NAME -o yaml
    ```

    Set `admin.passwordSecretName` to this name.
  </Step>
  <Step title="Create a service account and key">
    Jenkins calls the Control Plane API to create, list and delete agent workloads, and it authenticates with a [service account](/guides/create-service-account) key. Create a service account and add a key to it:

    ```bash
    cpln serviceaccount create --name SERVICE_ACCOUNT_NAME --description jenkins-agents
    cpln serviceaccount add-key SERVICE_ACCOUNT_NAME --description jenkins
    ```

    Copy the `key` value from the output — it is shown only once.
  </Step>
  <Step title="Grant the service account permissions">
    Create a [policy](/guides/policy) binding the service account to exactly these permissions:

    | Target kind | Permissions | Scope |
    |---|---|---|
    | Workload | `view`, `create`, `delete` | Workloads in the agent GVC |
    | GVC | `view` | The agent GVC |
    | Identity | `view` | The agent GVC |
    | Volume set | `view` | The agent GVC |

    A key with **no policy bindings authenticates successfully but provisions nothing** — this is the most common reason agents never appear (see [Troubleshooting](#troubleshooting)).
  </Step>
  <Step title="Store the key in a secret">
    Paste the key value from the previous step in place of `THE-KEY-VALUE`:

    ```bash
    printf '%s' 'THE-KEY-VALUE' | cpln secret create-opaque --name API_KEY_SECRET_NAME --encoding plain -f -
    ```

    Set `cloud.apiKeySecretName` to this name. With `cloud.enabled: false` the API key secret is not needed.
  </Step>
</Steps>

<Warning>
**The agent GVC must have exactly one location.** The plugin rejects multi-location GVCs. With `cloud.gvc` left empty, the agent GVC is the GVC you install Jenkins into, so check it before installing:

```bash
cpln gvc get GVC_NAME -o yaml
```

`spec.staticPlacement.locationLinks` must list a single location.
</Warning>

<Warning>
**A missing prerequisite secret wedges the deployment silently.** `cpln helm install` still succeeds, the resources are created, and the controller never starts. `cpln logs` returns nothing at all, because the container never ran. The only place the reason appears is `status.versions[].message`, which names the missing secret:

```bash
cpln workload get-deployments RELEASE_NAME-jenkins --gvc GVC_NAME -o yaml
```

Note this is `get-deployments` — plain `cpln workload get` has no `versions` key. Create the missing secret and the deployment recovers on its own, or force a redeployment to skip the wait:

```bash
cpln workload force-redeployment RELEASE_NAME-jenkins --gvc GVC_NAME
```
</Warning>

## Installation

Once both secrets exist and the service account has its permissions, install from the marketplace registry with the two secret names:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/cpln-jenkins \
  --version 1.0.0 --gvc GVC_NAME \
  --set admin.passwordSecretName=ADMIN_PASSWORD_SECRET_NAME \
  --set cloud.apiKeySecretName=API_KEY_SECRET_NAME
```

## Configuration

### Image

```yaml
image: ghcr.io/controlplane-com/cpln-jenkins:2.0.1
```

Jenkins LTS with the Control Plane cloud plugin baked in and Configuration as Code enabled, built from [cpln-jenkins-plugin](https://github.com/controlplane-com/cpln-jenkins-plugin).

### Admin Login

```yaml
admin:
  username: admin
  # REQUIRED prerequisite `opaque` secret holding the password, created BEFORE
  # install. The deployment wedges silently until it exists.
  passwordSecretName: my-jenkins-admin-password
```

`admin.username` is the login name and stays an ordinary value. The password is applied on **every** boot, not only the first: change the secret and force a redeployment to change the login (see [Rotating the Admin Password](#rotating-the-admin-password)).

### Control Plane Cloud

These values pre-configure the **Control Plane cloud inside Jenkins** — the settings you would otherwise fill in by hand under **Manage Jenkins → Clouds**. The chart renders them into a Configuration as Code file the controller reads at boot, so a fresh install already knows how to provision agents.

```yaml
cloud:
  enabled: true                # false = no cloud is configured; builds have nowhere to run
  # REQUIRED prerequisite `opaque` secret holding a Control Plane API key, with
  # create/delete/view on workloads in the target GVC plus view on GVCs,
  # identities and volume sets. See the README.
  apiKeySecretName: my-jenkins-cpln-api-key
  # GVC the agents run in. Empty = the GVC Jenkins itself runs in. It MUST have
  # exactly ONE location — the plugin rejects multi-location GVCs.
  gvc: ""
  agentWorkload: jenkins-agent   # name prefix for provisioned agent workloads
  agentImage: jenkins/inbound-agent:latest
  labels: cpln                   # space-separated; jobs target these
  allowJobsWithoutLabels: true   # false = only jobs requesting a label above
  useUniqueAgents: true          # one dedicated agent per queued job
  executors: 1                   # concurrent builds per agent
  cpu: 300                       # millicores per agent (minimum 50)
  memory: 512                    # MiB per agent (minimum 128)
  retentionMins: 5               # delete an idle agent after this long
  provisioningCooldownSecs: 60   # gap between provisions; prevents over-scaling
```

The chart refuses to render with `cloud.cpu` below 50, `cloud.memory` below 128 or `cloud.retentionMins` below 1. The organization and the controller address agents connect back to are derived from where the controller runs, so you never supply them.

<Warning>
The cloud file is re-applied on **every** boot, so editing these settings in the Jenkins UI does not survive a restart. Change them in values, upgrade, then run `cpln workload force-redeployment RELEASE_NAME-jenkins --gvc GVC_NAME` (see [Changing Cloud Settings](#changing-cloud-settings)).
</Warning>

### Controller Resources and Storage

```yaml
resources:
  minCpu: 500m
  maxCpu: 1000m
  minMemory: 1Gi
  maxMemory: 2Gi

volumeset:
  capacity: 10                   # GiB (minimum 10); holds JENKINS_HOME
```

These size the controller only; each agent is sized by `cloud.cpu` and `cloud.memory`.

### Access

```yaml
publicAccess:
  enabled: false                 # true publishes the Jenkins login to the internet

internalAccess:
  type: same-gvc                 # none | same-gvc | same-org | workload-list
  workloads: []                  # used with workload-list
```

| `internalAccess.type` | Description |
|---|---|
| `none` | No internal access. |
| `same-gvc` | Allow access from all workloads in the same GVC (default). |
| `same-org` | Allow access from all workloads in the same org. |
| `workload-list` | Allow access only from the workloads listed in `internalAccess.workloads`. |

`publicAccess` defaults to off, because the controller serves a login form and a CI server holds credentials for everything it deploys. A private controller is still reachable through a port-forward — see [Connecting](#connecting). A change to either access setting can take a few minutes to take effect.

## Connecting

The controller is private by default. Open a tunnel to it from your machine:

```bash
cpln port-forward RELEASE_NAME-jenkins 8080:8080 --gvc GVC_NAME
```

Then open `http://localhost:8080`. To publish the UI instead, set `publicAccess.enabled: true` and read the public address from `status.canonicalEndpoint`:

```bash
cpln workload get RELEASE_NAME-jenkins --gvc GVC_NAME -o yaml
```

| What | Address | Notes |
|---|---|---|
| Jenkins UI (private, default) | `http://localhost:8080` | Through the port-forward above |
| Jenkins UI (public) | `https://CANONICAL_ENDPOINT` | Only with `publicAccess.enabled: true`; `status.canonicalEndpoint` of `RELEASE_NAME-jenkins` |
| Internal (same GVC) | `http://RELEASE_NAME-jenkins.GVC_NAME.cpln.local:8080` | Subject to `internalAccess`; always use the fully qualified name |
| Login | `admin.username` and the payload of your admin password secret | `cpln secret reveal ADMIN_PASSWORD_SECRET_NAME -o yaml` |

Verify the controller is serving before you sign in — with the port-forward open:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/login
```

### First Run

There is no setup wizard. Open the UI and sign in with `admin.username` (default `admin`) and the password in your admin password secret. The Control Plane cloud is already configured under **Manage Jenkins → Clouds**.

### Running Builds on Control Plane Agents

A job runs on a Control Plane agent when it requests one of the labels in `cloud.labels` (default `cpln`):

```groovy
pipeline {
    agent { label 'cpln' }
    stages {
        stage('Build') {
            steps { sh 'echo building on a Control Plane agent' }
        }
    }
}
```

When the job is queued, Jenkins creates an agent workload in the agent GVC whose name starts with `cloud.agentWorkload` (default `jenkins-agent`), runs the build on it, and deletes it once it has been idle for `cloud.retentionMins`. Each agent runs `cloud.agentImage` with `cloud.cpu` millicores and `cloud.memory` MiB.

- `cloud.useUniqueAgents: true` (default) gives every queued job its own agent; `cloud.executors` sets how many builds one agent runs at once.
- `cloud.allowJobsWithoutLabels: true` (default) also sends jobs with **no** label to Control Plane agents. Set it to `false` so only jobs requesting one of `cloud.labels` are picked up.

## Operations

### Backing Up

Jobs, build history and installed plugins all live on the volume set `RELEASE_NAME-jenkins-vs`. Take a snapshot at any time:

```bash
cpln volumeset snapshot create RELEASE_NAME-jenkins-vs --gvc GVC_NAME --snapshot-name SNAPSHOT_NAME
cpln volumeset snapshot get RELEASE_NAME-jenkins-vs --gvc GVC_NAME
```

When the volume set is deleted — including by uninstalling the release — a final snapshot is kept for 7 days. Your two prerequisite secrets are not part of the release and are never deleted by it.

### Restoring a Backup

The CLI restores a snapshot into the volume set with the command below. This path has been checked against the CLI help only and has **not** been verified against a Jenkins install, so take a fresh snapshot first and expect to restart the controller afterwards:

```bash
cpln volumeset snapshot restore RELEASE_NAME-jenkins-vs --gvc GVC_NAME \
  --snapshot-name SNAPSHOT_NAME --location LOCATION --volume-index 0
cpln workload force-redeployment RELEASE_NAME-jenkins --gvc GVC_NAME
```

`LOCATION` is the single location of your GVC.

### Rotating the Admin Password

The password is re-applied at every boot, so a new secret value becomes the login after the next restart. Replace the secret's value with the file below, then force a redeployment — a running controller keeps the old password until it restarts:

```yaml
kind: secret
name: ADMIN_PASSWORD_SECRET_NAME
type: opaque
data:
  encoding: plain
  payload: NEW-VALUE
```

Save it as `rotate.yaml`, then:

```bash
cpln apply -f rotate.yaml
cpln secret reveal ADMIN_PASSWORD_SECRET_NAME -o yaml
cpln workload force-redeployment RELEASE_NAME-jenkins --gvc GVC_NAME
```

Rotate the API key the same way against `API_KEY_SECRET_NAME`, with a new key from `cpln serviceaccount add-key` as the payload, then force a redeployment.

### Changing Cloud Settings

Change `cloud.*` values with an upgrade; settings edited in the Jenkins UI are overwritten at the next boot:

```bash
cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/cpln-jenkins \
  --version 1.0.0 --gvc GVC_NAME \
  --set cloud.labels=cpln
```

Repeat every `--set` you passed at install, including both secret names.

Most `cloud.*` settings change only the `RELEASE_NAME-jenkins-cloud` secret, and a running controller keeps the file it booted with. Force a redeployment after the upgrade so the controller boots with the new cloud settings:

```bash
cpln workload force-redeployment RELEASE_NAME-jenkins --gvc GVC_NAME
```

### Scaling and Availability

The controller is a single replica pinned to one volume set; it is not clustered, and there is no replicas knob. Build capacity scales through agents instead: each queued job gets its own agent workload, with `cloud.provisioningCooldownSecs` between provisions. A controller restart interrupts the UI and running builds; jobs, history and plugins survive on the volume set.

### Troubleshooting

<AccordionGroup>
  <Accordion title="The controller never starts and cpln logs shows nothing">
    **Cause:** A prerequisite secret is missing, so the container never ran.

    **Fix:** Read `status.versions[].message`, which names the missing secret, then create it:

    ```bash
    cpln workload get-deployments RELEASE_NAME-jenkins --gvc GVC_NAME -o yaml
    ```

    The deployment recovers on its own once the secret exists, or force a redeployment to skip the wait.
  </Accordion>
  <Accordion title="Jenkins is up but no agents ever appear">
    **Cause:** The API key lacks permissions. The controller log shows `Failed to list workloads: 403`, while the Jenkins UI only shows an idle cloud.

    **Fix:** Confirm the error in the controller log, then grant the service account the permissions listed in [Prerequisites](#prerequisites):

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-jenkins"} |= "Failed to list workloads"' --limit 50 --since 10m
    ```
  </Accordion>
  <Accordion title="Agents are never provisioned into a multi-location GVC">
    **Cause:** The agent GVC has more than one location. The plugin only accepts single-location GVCs.

    **Fix:** Point `cloud.gvc` at a GVC with exactly one location and upgrade.
  </Accordion>
  <Accordion title="Cloud settings changed in the UI revert after a restart">
    **Cause:** Configuration as Code re-applies `cloud.*` at every boot.

    **Fix:** Change the values and upgrade — see [Changing Cloud Settings](#changing-cloud-settings).
  </Accordion>
  <Accordion title="Install fails with a cloud.cpu or cloud.memory minimum error">
    **Cause:** The chart refuses agent sizes below 50 millicores or 128 MiB, and a `cloud.retentionMins` below 1, because the agent JVM fails to start or is OOM-killed below those floors.

    **Fix:** Raise `cloud.cpu`, `cloud.memory` or `cloud.retentionMins` and install again.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create both secrets before installing** — a missing one wedges the deployment silently.
- **The agent GVC must have exactly one location** — by default that is the GVC Jenkins is installed into.
- **The API key needs policy bindings** — workload `view`/`create`/`delete` in the agent GVC, plus `view` on GVCs, identities and volume sets.
- **`publicAccess.enabled: true` puts a Jenkins login on the internet** — use a strong admin password, or stay private and use the port-forward.
- **Edit cloud settings in values, not in the Jenkins UI** — UI edits are lost at the next restart.
- **A rotated secret needs a forced redeployment** — the running controller keeps the old value until it restarts.
- **Uninstalling deletes the volume set** — jobs and build history then survive only in the 7-day final snapshot.
