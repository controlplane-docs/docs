## Overview

CPLN Trivy scans the images in your Control Plane image registry for known vulnerabilities. A scheduled daemon finds images that have not been scanned yet (or whose last scan is older than `rescanAfter`), runs [Trivy](https://trivy.dev) against each one, and hands the HTML report to a small web server that stores it in your own S3 bucket or Azure file share. The daemon then tags the image with a direct link to its report, so the result is one click away in the Control Plane console.

<Note>
This template does not create a GVC. It deploys into an existing GVC that you already have, passed with `--gvc GVC_NAME` at install time.
</Note>

<Warning>
**A scan run covers every image in the organization, not only images this install created.** The daemon enumerates the whole registry, writes two tags to each image it scans, and uploads one report per image to your storage. Before pointing it at a production organization, decide on a `schedule` and set `rescanAfter` to `""` if you want each image scanned only once.
</Warning>

After each scan the image carries two tags:

| Tag | Value |
|---|---|
| `cpln/trivy-scan` | URL of the HTML vulnerability report |
| `cpln/trivy-scan-time` | Timestamp of the scan |

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `daemon` | Cron workload running on `schedule`. Container `daemon` selects images and orchestrates scans; container `trivy-api` runs Trivy and returns an HTML report | — |
| Workload | `web-server` | Serverless workload on port `8080` that receives reports from the daemon, stores them, and serves them by URL. Autoscales between `webServer.autoscaling.minScale` and `maxScale` | — |
| Identity | `RELEASE_NAME-identity` | Shared by both workloads. Carries the AWS cloud-account binding with your IAM policy (`storage.type: s3`) or the Azure **Reader and Data Access** role at `storage.azureFileshare.scope` (`storage.type: azureFileshare`) | — |
| Policy | `RELEASE_NAME-manage-images` | Grants the identity `manage` on all images in the org, so it can write the scan tags | — |
| Policy | `RELEASE_NAME-trivy-credentials` | Grants the identity `reveal` on exactly the two prerequisite secrets named by `postToken.secretName` and `trivyAuth.secretName` | — |
| Policy | `RELEASE_NAME-read-images` | Grants the service account named by `serviceAccountName` `pull` and `view` on all images in the org, so Trivy can pull what it scans | — |

The workload names `daemon` and `web-server` do not include the release name, so install this template only once per GVC. The template creates no secrets of its own.

## Prerequisites

Two opaque secrets, a service account and report storage must exist before you install. Secrets are org-level, so no GVC flag is involved. This template uses two secrets, so the commands below call them `POST_TOKEN_SECRET_NAME` and `REGISTRY_SECRET_NAME`.

<Steps>
  <Step title="Create the report post token secret">
    The daemon presents this bearer token when it uploads a report to the web server. The upload endpoint is reachable from the public internet, and this token is the only thing guarding it. Create an [opaque secret](/guides/create-secret/opaque) holding a random token:

    ```bash
    printf '%s' "$(openssl rand -hex 32)" | cpln secret create-opaque --name POST_TOKEN_SECRET_NAME --encoding plain -f -
    ```

    Set `postToken.secretName` to this name.
  </Step>
  <Step title="Create a registry service account and key">
    Trivy pulls images from your registry as a service account. [Create a service account](https://docs.controlplane.com/reference/serviceaccount) (or pick an existing one), add a key to it, and copy the key value, which cannot be retrieved later. The template grants this service account `pull` and `view` on images.

    Set `serviceAccountName` to the service account name.
  </Step>
  <Step title="Store the service account key in an opaque secret">
    ```bash
    printf '%s' 'SERVICE-ACCOUNT-KEY' | cpln secret create-opaque --name REGISTRY_SECRET_NAME --encoding plain -f -
    ```

    Set `trivyAuth.secretName` to this name.
  </Step>
  <Step title="Prepare report storage">
    Set `storage.type` to `s3` or `azureFileshare` and complete the matching steps.

    <Tabs>
      <Tab title="AWS S3">
        1. Create an S3 bucket. Set `storage.s3.bucket` to its name and `storage.s3.region` to its region.
        2. [Create an AWS cloud account](https://docs.controlplane.com/guides/create-cloud-account) in Control Plane if you do not have one. Set `storage.s3.cloudAccountName` to its name.
        3. Create an IAM policy scoped to the bucket (replace `YOUR_BUCKET_NAME`) and set `storage.s3.policyName` to the policy name. Access is keyless: the identity receives temporary credentials, so no AWS keys are stored.

        ```json
        {
            "Version": "2012-10-17",
            "Statement": [
                {
                    "Effect": "Allow",
                    "Action": [
                        "s3:GetObject",
                        "s3:PutObject",
                        "s3:DeleteObject",
                        "s3:ListBucket"
                    ],
                    "Resource": [
                        "arn:aws:s3:::YOUR_BUCKET_NAME",
                        "arn:aws:s3:::YOUR_BUCKET_NAME/*"
                    ]
                }
            ]
        }
        ```
      </Tab>
      <Tab title="Azure File Share">
        1. Create an Azure storage account and a file share in it. Set `storage.azureFileshare.accountName` and `storage.azureFileshare.fileShare`.
        2. [Create an Azure cloud account](https://docs.controlplane.com/guides/create-cloud-account) in Control Plane if you do not have one. Set `storage.azureFileshare.cloudAccountName` to its name.
        3. Set `storage.azureFileshare.scope` to the storage account's full resource ID, in the form `/subscriptions/<id>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<name>`. The template grants the identity the **Reader and Data Access** role at exactly that scope, and mounts the file share into the web server at `/app/data`.
      </Tab>
    </Tabs>
  </Step>
</Steps>

<Warning>
**Create both secrets before installing, or the deployment wedges silently.** A name that points at a secret which does not exist installs successfully and then never starts. The container never runs, so `cpln logs` returns no lines at all. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments web-server --gvc GVC_NAME -o yaml
```

```text
The secret my-cpln-trivy-post-token no longer exists. Workload updates are
paused until the secret is added or the reference to the secret removed.
```

Use `get-deployments`; plain `cpln workload get` has no `versions` key. Once you create the missing secret the workload recovers on its own after several minutes, or immediately with a forced redeployment:

```bash
cpln workload force-redeployment web-server --gvc GVC_NAME
```
</Warning>

## Installation

Install with the values for your storage, secrets and service account. This example uses S3:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/cpln-trivy \
  --version 1.2.0 --gvc GVC_NAME \
  --set storage.s3.cloudAccountName=CLOUD_ACCOUNT_NAME \
  --set storage.s3.bucket=BUCKET_NAME \
  --set storage.s3.region=AWS_REGION \
  --set storage.s3.policyName=IAM_POLICY_NAME \
  --set postToken.secretName=POST_TOKEN_SECRET_NAME \
  --set trivyAuth.secretName=REGISTRY_SECRET_NAME \
  --set serviceAccountName=SERVICE_ACCOUNT_NAME
```

For Azure, set `storage.type=azureFileshare` and the four `storage.azureFileshare.*` values instead of the `storage.s3.*` values. You can also install from the UI, Terraform or Pulumi:

## Configuration

### Storage

Configure only the block that matches `storage.type`.

```yaml
# Storage backend for vulnerability reports. Options: "s3" or "azureFileshare"
storage:
  type: s3

  s3:
    cloudAccountName: my-aws-cloud-account # AWS cloud account name registered in Control Plane
    bucket: trivy-reports-bucket           # S3 bucket name
    region: us-east-1                      # AWS region
    policyName: my-trivy-s3-policy         # Name of the IAM policy scoped to the bucket above

  azureFileshare:
    cloudAccountName: my-azure-cloud-account # Azure cloud account name registered in Control Plane
    accountName: mystorageaccount            # Azure storage account name
    fileShare: trivy-reports                 # Azure file share name
    scope: "" # /subscriptions/<id>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<name>
```

### Authentication

Both secret names must point at secrets that already exist (see [Prerequisites](#prerequisites)).

```yaml
postToken:
  secretName: my-cpln-trivy-post-token # opaque secret holding the report upload bearer token

trivyAuth:
  secretName: trivy-credentials # opaque secret holding the service account key

serviceAccountName: trivy-service-account # service account Trivy pulls images with
```

### Scanning

```yaml
schedule: "*/59 * * * *" # cron schedule for the scanning daemon
rescanAfter: 7d          # rescan images last scanned longer ago than this; "" = scan once only
```

`rescanAfter` must be a number followed by `d` (days) or `h` (hours), such as `7d` or `24h`. With an empty value each image is scanned once; see [Forcing a Rescan](#forcing-a-rescan) to scan it again.

### Workloads

```yaml
daemon:
  image: ghcr.io/controlplane-com/cpln-trivy-daemon:1.2.0
  resources:
    cpu: 1
    memory: 1Gi
  firewall:
    outboundAllowCIDR:
      - 0.0.0.0/0 # must reach the Control Plane API and the web server

trivyApi:
  image: ghcr.io/controlplane-com/cpln-trivy-trivy-api:1.2.0
  resources:
    cpu: 2      # scanning is CPU-bound; lowering this lengthens every run
    memory: 4Gi

webServer:
  image: ghcr.io/controlplane-com/cpln-trivy-web-server:1.2.0
  resources:
    cpu: 150m
    memory: 128Mi
  autoscaling:
    minScale: 1
    maxScale: 3
  firewall:
    inboundAllowCIDR:
      - 0.0.0.0/0 # the daemon uploads over this public path; reports are readable by URL
    outboundAllowCIDR:
      - 0.0.0.0/0 # must reach S3 or Azure storage
```

<Warning>
**Narrowing `webServer.firewall.inboundAllowCIDR` also blocks the daemon.** The daemon delivers reports to the web server through its public endpoint, so if you restrict inbound access to keep reports private, include the address range your daemon's traffic leaves from, or uploads stop.
</Warning>

## Connecting

The template has no login screen. Each scan result is an HTML report served by the `web-server` workload at the URL stored in the image's `cpln/trivy-scan` tag.

| What | Where | Notes |
|---|---|---|
| A scan report | The `cpln/trivy-scan` tag on the scanned image | Open the image in the Control Plane console and follow the tag link, or read it with `cpln image get` |
| Web server (public) | `status.canonicalEndpoint` of the `web-server` workload | Read it with `cpln workload get web-server --gvc GVC_NAME -o yaml` |
| Web server (internal) | Not reachable inside the GVC | Internal access is closed; the daemon uses the public endpoint |
| Report upload token | Your `postToken.secretName` secret | `cpln secret reveal POST_TOKEN_SECRET_NAME -o yaml` |
| Report storage | Your S3 bucket, or the Azure file share | Reports are stored there by the web server |

Report reads are not authenticated: anyone who has a report URL can open it. Upload requests must carry `Authorization: Bearer` followed by the token.

### Reading Scan Results

List every image that has been scanned:

```bash
cpln image query --tag cpln/trivy-scan --max 0 -o json | jq -r '.items[].name'
```

Print the report link and scan time for one image, then open the link in a browser:

```bash
cpln image get IMAGE_NAME:TAG -o json | jq -r '.tags["cpln/trivy-scan"], .tags["cpln/trivy-scan-time"]'
```

Images with no `cpln/trivy-scan` tag have not been scanned yet. The daemon picks them up on its next scheduled run.

## Operations

### Upgrading from 1.1.0

Version `1.2.0` moved the report post token out of Helm values. Through `1.1.0` it was the plain value `postToken`; it is now an opaque secret you create, named by `postToken.secretName`.

| | `1.1.0` and earlier | `1.2.0` |
|---|---|---|
| Post token | `postToken`, a plain string value | `postToken.secretName`, an opaque secret whose payload is the token |
| Registry service account key | `trivyAuth.secretName` prerequisite secret | Unchanged |

An upgrade that still sets `postToken` as a string fails at render and leaves the running release untouched:

```text
cpln-trivy: postToken is no longer a plain value in 1.2.0. Put the token in an opaque secret (encoding: plain) and set postToken.secretName to its name — see the README. Reuse the SAME token your install already has, or the daemon's uploads start returning 401.
```

<Steps>
  <Step title="Create the post token secret with your current token">
    Put **the same token your install already uses** into a new opaque secret. A different token also works for this release, but anything outside it that used the old token stops working.

    ```bash
    printf '%s' 'CURRENT-POST-TOKEN' | cpln secret create-opaque --name POST_TOKEN_SECRET_NAME --encoding plain -f -
    ```
  </Step>
  <Step title="Replace the removed key in your values">
    Delete the `postToken:` string and set `postToken.secretName` to the secret name. Leave `trivyAuth.secretName` and `serviceAccountName` as they are.
  </Step>
  <Step title="Upgrade the release">
    ```bash
    cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/cpln-trivy \
      --version 1.2.0 --gvc GVC_NAME \
      --set postToken.secretName=POST_TOKEN_SECRET_NAME
    ```

    Pass your other existing values (storage, `trivyAuth.secretName`, `serviceAccountName`) the same way you did at install. Reports already stored keep their URLs.
  </Step>
</Steps>

### Rotating Secrets

Both prerequisite secrets are opaque, so rotate one by applying the whole secret with the new value. Save this as `rotate.yaml`:

```yaml
kind: secret
name: SECRET_NAME
type: opaque
data:
  encoding: plain
  payload: NEW-VALUE
```

```bash
cpln apply -f rotate.yaml
cpln secret reveal SECRET_NAME -o yaml
```

A running workload keeps the old value until it is redeployed, so force a redeployment afterwards.

- **Post token:** the daemon and the web server must use the same token, so redeploy both together. If only one picks up the new token, uploads are refused with `401` while both workloads still look healthy.

  ```bash
  cpln workload force-redeployment daemon --gvc GVC_NAME
  cpln workload force-redeployment web-server --gvc GVC_NAME
  ```

- **Service account key:** add a new key to the service account, put it in the `trivyAuth.secretName` secret, redeploy `daemon`, then delete the old key. No reinstall is needed.

### Forcing a Rescan

With `rescanAfter` set, images are rescanned automatically once their last scan is older than that window, and the report is replaced at the same URL. To rescan an image sooner, remove its scan tags so the next run treats it as unscanned:

```bash
cpln image tag IMAGE_NAME:TAG --remove-tag cpln/trivy-scan --remove-tag cpln/trivy-scan-time
```

<Note>
This command shape is taken from `cpln image tag --help` and has not been run against a live install.
</Note>

### Troubleshooting

<AccordionGroup>
  <Accordion title="The workload never starts and cpln logs returns nothing">
    **Cause:** a secret named by `postToken.secretName` or `trivyAuth.secretName` does not exist. `status.versions[].message` from `cpln workload get-deployments web-server --gvc GVC_NAME -o yaml` names it, for example `The secret my-cpln-trivy-post-token no longer exists.`

    **Fix:** create the secret as in [Prerequisites](#prerequisites), then wait for recovery or run `cpln workload force-redeployment web-server --gvc GVC_NAME`.
  </Accordion>
  <Accordion title="Install or upgrade fails with postToken is no longer a plain value">
    **Cause:** your values still set `postToken` as a string from `1.1.0` or earlier.

    **Fix:** follow [Upgrading from 1.1.0](#upgrading-from-1-1-0).
  </Accordion>
  <Accordion title="Install fails with rescanAfter must be a number followed by d or h">
    **Cause:** `rescanAfter` is not in the form `7d` or `24h`. The full error reads `rescanAfter must be a number followed by 'd' (days) or 'h' (hours), e.g. '7d' or '24h'`.

    **Fix:** use a whole number followed by `d` or `h`, or `""` to scan each image only once.
  </Accordion>
  <Accordion title="Scans run but no new reports appear">
    **Cause:** the web server refuses the daemon's uploads. This happens when the two workloads hold different post tokens after a rotation, or when `webServer.firewall.inboundAllowCIDR` no longer admits the daemon's traffic.

    **Fix:** redeploy both workloads together after a token change, and widen the inbound CIDR list if you narrowed it. Check the daemon's output:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="daemon"}' --limit 50 --since 10m
    ```
  </Accordion>
  <Accordion title="The daemon logs a 404 tagging error">
    **Cause:** an image was deleted while a run was in progress.

    **Fix:** none needed. The run continues with the remaining images.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create both prerequisite secrets before installing.** A missing one wedges the deployment with no log output.
- **Every image in the organization is scanned and tagged**, not only images this install created.
- **Report URLs are readable without authentication.** Narrow `webServer.firewall.inboundAllowCIDR` to keep them private, and keep the daemon's traffic allowed when you do.
- **Redeploy `daemon` and `web-server` together after changing the post token.** They must agree or uploads fail with `401`.
- **Runs never overlap.** A long run on a large registry delays the next scheduled run rather than starting a second one.
- **Install once per GVC.** The workloads are always named `daemon` and `web-server`.
