## Overview

TiDB is a distributed, MySQL-compatible database designed for horizontal scalability and high availability. It separates compute from storage across three components: a SQL processing layer (tidb-server), a distributed key-value store (TiKV), and a placement driver (PD) that holds cluster metadata and decides where data lives.

This template deploys all three tiers across one or more Control Plane locations using PingCAP's official images, with an optional one-time database bootstrap job, an optional ProxySQL connection pooler in every location, and optional scheduled backups to AWS S3. Database credentials are **not** template values: the init job reads the root password, application user, password and database name from a dictionary secret you create before installing, so none of them pass through Helm or land in the release.

<Note>
**This template deploys into an existing [GVC](/reference/gvc).** It does not create one. Every resource lands in the GVC you install into, so `cpln workload exec`, `cpln logs` and uninstalling all work against that GVC, and uninstalling can never delete it. Every location you list in `locations` must already be on that GVC. A GVC location you did not list simply starts nothing — the console shows it as `This workload location is deactivated because maxScale is set to 0.`, which is the expected state, not a fault.
</Note>

## Prerequisites

Two things must be in place before you install: a GVC that has every location you intend to use, and a credentials secret. Backups additionally need a bucket and a cloud account — see [Backing Up](#backing-up).

<Steps>
  <Step title="Make sure the GVC has every location you will list">
    The GVC may have *more* locations than you list — nothing TiDB-related runs in those — but every entry in `locations` must be on it. Read the GVC's locations from `spec.staticPlacement.locationLinks`:

    ```bash
    cpln gvc get GVC_NAME -o yaml
    ```

    The shipped default is a single location, `aws-us-east-1`. If your GVC uses a different location, set `locations` at install time (see [Installation](#installation)). This release starts nothing in a GVC location you did not list, but other workloads in that GVC do run in every location the GVC has, so add locations to a shared GVC deliberately.
  </Step>
  <Step title="Create the database credentials secret">
    Required whenever `autoCreateDatabase.enabled` is `true` (the default). A [dictionary secret](/guides/create-secret/dictionary) holding exactly four keys — `rootPassword`, `user`, `password` and `db`. The init job sets the root password, then creates that user and that database. Secrets are org-level, so no `--gvc` flag is involved:

    ```bash
    cpln secret create-dictionary --name SECRET_NAME \
      --entry rootPassword='YOUR-ROOT-PASSWORD' \
      --entry user=myuser \
      --entry password='YOUR-STRONG-PASSWORD' \
      --entry db=mydb
    ```

    Set `autoCreateDatabase.credentialsSecretName` to this name. Secret names are org-wide, so give each release its own.
  </Step>
</Steps>

<Warning>
**Create the secret before installing, or the deployment wedges silently.** A `credentialsSecretName` pointing at a secret that does not exist installs successfully and then never starts. The container never runs, so `cpln logs` returns zero lines. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-server --gvc GVC_NAME -o yaml
```

```text
The secret SECRET_NAME no longer exists. Workload updates are paused until the
secret is added or the reference to the secret removed.
```

Use `get-deployments` — plain `cpln workload get` has no `versions` key. Once the secret exists the deployment recovers on its own after several minutes, or force a redeployment to skip the wait:

```bash
cpln workload force-redeployment RELEASE_NAME-server --gvc GVC_NAME
```
</Warning>

<Warning>
**A location the GVC does not have is not caught at install time.** The install succeeds, and PD then refuses to bootstrap, restarting with this in its logs:

```text
[tidb-pd] FATAL: locations declared in values are not in GVC 'GVC_NAME': aws-us-west-2
[tidb-pd] GVC 'GVC_NAME' has: aws-us-east-1 aws-us-east-2
```

Add the missing location to the GVC, or remove it from `locations`. A PD member that already holds data logs a `WARNING` instead and keeps serving, so this check never takes down a running cluster.
</Warning>

## Installation

Create the credentials secret first, then install into the GVC that has your locations:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/tidb \
  --version 2.1.0 --gvc GVC_NAME \
  --set autoCreateDatabase.credentialsSecretName=SECRET_NAME
```

`locations` is a list, so when your GVC does not use the default `aws-us-east-1` pass it in a values file rather than with `--set` (a `--set locations[0].name=...` on its own replaces the whole list element and drops `tikvReplicas` and `serverReplicas`):

```yaml
# values.yaml
locations:
  - name: aws-us-west-2
    tikvReplicas: 3
    serverReplicas: 3
autoCreateDatabase:
  credentialsSecretName: SECRET_NAME
```

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/tidb \
  --version 2.1.0 --gvc GVC_NAME -f values.yaml
```

## Configuration

### Locations

```yaml
locations:
  - name: aws-us-east-1
    tikvReplicas: 3    # TiKV storage nodes in this location; must be at least 1
    serverReplicas: 3  # TiDB SQL servers in this location; must be at least 1

pdReplicas: 3   # PD members across all locations; odd only (1, 3, 5 or 7); 1 is for testing
```

Every location listed must already exist in the GVC you install into. `tikvReplicas` and `serverReplicas` set the TiKV storage nodes and TiDB SQL servers in that location independently. `pdReplicas` members are spread evenly across `locations`, with any remainder going to the first ones. A count of `0` is refused at render — remove the location from the list instead.

Clients reach only the TiDB servers in their own location, so run your applications in a location listed in `locations`. A client in a GVC location this release does not run in cannot connect. Set `serverReplicas` to 2 or more to keep a location serving when one of its SQL servers fails.

The default — one location, three TiKV nodes, three SQL servers, three PD members — survives the loss of a node. It does **not** survive the loss of a location. For that, use three locations with one PD member and one TiKV node each:

```yaml
locations:
  - name: aws-us-east-1
    tikvReplicas: 1
    serverReplicas: 2
  - name: aws-us-west-2
    tikvReplicas: 1
    serverReplicas: 2
  - name: aws-eu-central-1
    tikvReplicas: 1
    serverReplicas: 2
pdReplicas: 3
proxysql:
  enabled: true
```

PD then keeps quorum when one location goes away, and TiKV spreads each region's three copies one per location. All three locations must be on the GVC. Clients in the surviving locations keep connecting while new leaders are elected; writes pause briefly during the election, so use a client timeout of 30 seconds or more, or retry, so that pause is a delay rather than an error. Two SQL servers per location behind [ProxySQL](#connection-pooling-proxysql) keep each location serving through the failure of one server.

### Images and Resources

```yaml
images:
  server: pingcap/tidb:v8.5.7
  tikv: pingcap/tikv:v8.5.7
  pd: pingcap/pd:v8.5.7

resources:
  pd:
    cpu: 2
    memory: 4Gi
  server:
    cpu: 2
    memory: 2Gi
  tikv:
    cpu: 2
    memory: 4Gi
```

Bump `images.*` together with `backup.image`: from v8.5.7, `br` enforces a version match with the cluster. The shipped sizes are for testing. For production, PD wants 4–8 CPU / 8–16Gi, tidb-server 8–16 CPU / 16–32Gi (it scales with concurrent connections), and TiKV 8–16 CPU / 32–64Gi.

### Database Initialization

```yaml
autoCreateDatabase:
  enabled: true
  deployInitWorkload: true   # set to false after the DB has been initialized to remove the init workload
  credentialsSecretName: my-tidb-credentials   # REQUIRED prerequisite dictionary secret — create it BEFORE you install
  schedule: "*/5 * * * *"   # how often the init job runs; it fast-exits once the database exists
```

`credentialsSecretName` names the prerequisite secret from [Prerequisites](#prerequisites). The init job is a cron workload: it fast-exits once the database exists, so every run after the first is a no-op and `schedule` only controls how soon after install the database appears. Once the cluster is initialized, upgrade with `deployInitWorkload: false` to remove the job and its script secret; tidb-server keeps its reference to the credentials secret.

### Connection Pooling (ProxySQL)

```yaml
proxysql:
  enabled: false                   # set true for a ProxySQL pooler tier in every location
  image: proxysql/proxysql:3.0.11
  replicas: 2                      # pooler replicas per location
  resources:
    cpu: 500m
    memory: 512Mi
```

With `proxysql.enabled: true` the template runs a ProxySQL connection pooler in every configured location, in front of that location's TiDB servers. Clients then connect to `RELEASE_NAME-proxysql.GVC_NAME.cpln.local:4000` instead of `RELEASE_NAME-server`, with the same users and passwords (see [Connecting](#connecting)).

- **Requires `autoCreateDatabase.enabled: true`.** ProxySQL authenticates clients with the `user`, `password` and `rootPassword` from the credentials secret; the chart refuses to render with `proxysql.enabled` on and `autoCreateDatabase.enabled` off.
- **Reachable by whoever `internal_access.server` allows** — the pooler follows the SQL tier's access setting.
- **Clients must connect with a utf8mb4 charset.** Every modern driver defaults to it; the `mysql` command-line client takes its charset from the OS locale, so pass `--default-character-set=utf8mb4`.

### Storage

```yaml
volumeset:
  tikv:
    capacity: 10 # initial capacity in GiB (minimum is 10)
    autoscaling:
      enabled: false # Set to true to enable autoscaling
      maxCapacity: 100 # Maximum capacity in GiB
      minFreePercentage: 10 # Minimum free percentage before scaling triggers
      scalingFactor: 1.2 # Multiplier applied to current capacity when scaling
  pd:
    capacity: 10 # initial capacity in GiB (minimum is 10)
```

PD only holds cluster metadata, so it has no autoscaling knob. Both volume sets keep snapshots for 7 days and take a final snapshot when deleted.

### Access

```yaml
external_access: # Set if client is outside the GVC or in another location
  server_outboundAllowCIDR: []
  tikv_outboundAllowCIDR: [] # Note: when backup.enabled is true, the template automatically allows outbound access (0.0.0.0/0) regardless of this value.
  pd_outboundAllowCIDR: []

internal_access:
  server:
    type: same-gvc # options: same-gvc, same-org, workload-list
    workloads:  # Note: can only be used if type is workload-list
      #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
  tikv:
    type: same-gvc # options: same-gvc, same-org, workload-list
    workloads:  # Note: can only be used if type is workload-list
      #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
  pd:
    type: same-gvc # options: same-gvc, same-org, workload-list
    workloads:  # Note: can only be used if type is workload-list
      #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

| `internal_access.*.type` | Who may reach that tier |
|---|---|
| `same-gvc` | Every workload in the same GVC (default) |
| `same-org` | Every workload in the org |
| `workload-list` | Only the workloads listed under `workloads` |

<Note>
**With `workload-list`, list only your clients.** Every workload this release creates is always allowed, whatever you set — the three tiers have to reach each other, and each tier's own replicas have to reach each other.
</Note>

`external_access.*_outboundAllowCIDR` opens outbound internet access per tier. When `backup.enabled` is `true`, TiKV gets `0.0.0.0/0` outbound regardless, because TiKV uploads backup data to the bucket directly. **There is no public inbound access to the MySQL port**: reach tidb-server over internal GVC DNS or with `cpln port-forward` (see [Connecting](#connecting)). Allow several minutes for an access change to take effect before concluding it did not apply.

### Backup

```yaml
backup:
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/tidb-backup:8.5.7
  schedule: "0 2 * * *"  # daily at 2am UTC
  activeDeadlineSeconds: 14400  # 4 hours max per backup job
  location: aws-us-east-1  # MUST be one of `locations` above; put it near your bucket

  resources:
    cpu: 1
    memory: 1Gi

  provider: aws # Options: aws or gcp

  aws:
    bucket: my-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: tidb/backups

  gcp:
    bucket: my-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: tidb/backups
```

`backup.location` must be one of `locations`; the chart refuses to render otherwise, because the backup cron runs only there. Bucket, cloud account and IAM setup are under [Backing Up](#backing-up). Use `provider: aws` — see the GCS caveat there.

## Connecting

| What | Address | Notes |
|---|---|---|
| MySQL protocol (applications) | `RELEASE_NAME-server.GVC_NAME.cpln.local:4000` | `user` / `password` from the credentials secret; database `db` |
| MySQL protocol (root) | `RELEASE_NAME-server.GVC_NAME.cpln.local:4000` | `root` / `rootPassword` from the credentials secret |
| Pooled MySQL protocol (when `proxysql.enabled`) | `RELEASE_NAME-proxysql.GVC_NAME.cpln.local:4000` | Same users and passwords as above; connect with a utf8mb4 charset |
| PD HTTP API (cluster state) | `RELEASE_NAME-pd.GVC_NAME.cpln.local:2379` | No authentication; reachable only from inside the GVC |
| tidb-server status API | `RELEASE_NAME-server.GVC_NAME.cpln.local:10080` | No authentication; reachable only from inside the GVC |
| Public endpoint | none | The template publishes no public inbound port |
| Credentials | `cpln secret reveal SECRET_NAME -o yaml` | A bare `cpln secret reveal` prints only a summary table |

Always use the fully qualified `.GVC_NAME.cpln.local` form; the bare workload name is not reliable. Run the client in a location listed in `locations` — clients reach only the servers in their own location. From a workload in the same GVC, connect with any MySQL client:

```bash
mysql -h RELEASE_NAME-server.GVC_NAME.cpln.local -P 4000 -u myuser -p --default-character-set=utf8mb4
```

With ProxySQL enabled, point the same command at `RELEASE_NAME-proxysql.GVC_NAME.cpln.local` instead. Without it, clients connect to `RELEASE_NAME-server` directly.

The `pingcap/tidb` image ships no MySQL client, so to verify from your own machine forward the port and use a local client:

```bash
cpln port-forward RELEASE_NAME-server 4000:4000 --gvc GVC_NAME
```

```bash
mysql -h 127.0.0.1 -P 4000 -u myuser -p -e 'SELECT VERSION();'
```

To see the TiKV stores PD knows about, ask PD from inside the tidb-server container:

```bash
cpln workload exec RELEASE_NAME-server --gvc GVC_NAME --container tidb-server -- \
  curl -s http://RELEASE_NAME-pd.GVC_NAME.cpln.local:2379/pd/api/v1/stores
```

On a multi-location install add `--location LOCATION_NAME` to pick which location's replica runs the command. Depending on how many replicas and locations you configured, the cluster can take a few minutes after install to accept connections.

| Workload | Port | Protocol | Description |
|---|---|---|---|
| `RELEASE_NAME-server` | `4000` | TCP | MySQL-compatible SQL port |
| `RELEASE_NAME-server` | `10080` | HTTP | tidb-server status and metrics |
| `RELEASE_NAME-proxysql` | `4000` | TCP | Pooled MySQL-compatible SQL port (when `proxysql.enabled`) |
| `RELEASE_NAME-pd` | `2379` | TCP | PD client port (HTTP API) |
| `RELEASE_NAME-pd` | `2380` | TCP | PD peer port |
| `RELEASE_NAME-tikv` | `20160` | TCP | TiKV data port |
| `RELEASE_NAME-tikv` | `20180` | TCP | TiKV status port |

## Operations

### Backing Up

When `backup.enabled` is `true`, the `RELEASE_NAME-tidb-backup` cron workload runs TiDB's `br backup full` on `backup.schedule` from `backup.location` and writes a full cluster snapshot to `BUCKET/PREFIX/tidb-TIMESTAMP/`. TiKV nodes upload their data to the bucket directly, which is why the template opens TiKV outbound access whenever backups are on. Keep `backup.image` on the same TiDB version as `images.*`.

<Warning>
**Use AWS S3. The GCS path has never completed a verified backup on this template.** The chart accepts `provider: gcp` and the backup image carries the GCS fix that template 1.7.0 introduced, but no end-to-end GCS backup has passed testing. Do not rely on `provider: gcp` for data you need back.
</Warning>

<Steps>
  <Step title="Create the bucket">
    Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.
  </Step>
  <Step title="Create a cloud account">
    If you do not have one, [create a cloud account](/guides/create-cloud-account) for AWS. Set `backup.aws.cloudAccountName` to its name.
  </Step>
  <Step title="Create the IAM policy">
    Create an IAM policy with the JSON below, replacing `YOUR_BUCKET_NAME`, and set `backup.aws.policyName` to its name:

    ```json
    {
        "Version": "2012-10-17",
        "Statement": [
            {
                "Effect": "Allow",
                "Action": [
                    "s3:GetObject",
                    "s3:PutObject",
                    "s3:DeleteObject",
                    "s3:ListBucket",
                    "s3:GetObjectVersion",
                    "s3:DeleteObjectVersion",
                    "s3:GetBucketLocation",
                    "s3:AbortMultipartUpload",
                    "s3:ListBucketMultipartUploads",
                    "s3:ListMultipartUploadParts"
                ],
                "Resource": [
                    "arn:aws:s3:::YOUR_BUCKET_NAME",
                    "arn:aws:s3:::YOUR_BUCKET_NAME/*"
                ]
            }
        ]
    }
    ```
  </Step>
  <Step title="Enable backups">
    Set `backup.enabled: true`, `backup.location` to one of your `locations`, and `backup.aws.prefix` to the folder path for backups, then upgrade the release:

    ```bash
    cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/tidb \
      --version 2.1.0 --gvc GVC_NAME -f values.yaml
    ```
  </Step>
</Steps>

Confirm a backup ran by reading the cron's output; a successful run ends with `Backup completed`:

```bash
cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-tidb-backup"} |= "Backup completed"' --limit 50 --since 24h
```

To start a backup immediately rather than waiting for the schedule, the CLI offers `cpln workload cron start RELEASE_NAME-tidb-backup --gvc GVC_NAME --location LOCATION_NAME`. This command shape comes from the CLI help and has not been exercised against this template.

<Note>
**Switch providers with a fresh install, not an upgrade.** An identity's cloud-account binding is never removed once set, so a release switched from one provider to another keeps the old binding attached even though the chart no longer renders it.
</Note>

### Restoring a Backup

<Warning>
**This restore path has not been exercised against a backup produced by this template.** It is the upstream `br restore full` procedure applied to this chart's addresses. Rehearse it into a scratch release before you depend on it.
</Warning>

`br` must run from a workload **inside the GVC** — `*.cpln.local` names do not resolve from anywhere else — and must match the cluster version. The `ghcr.io/controlplane-com/backup-images/tidb-backup:8.5.7` image carries the matching `br` binary. Restore into a cluster that does not already contain conflicting data; the upstream guidance is an empty cluster, so a fresh release with `autoCreateDatabase.enabled: false` is the cleanest target.

```sh
br restore full \
  --pd="RELEASE_NAME-pd.GVC_NAME.cpln.local:2379" \
  --storage="s3://BUCKET_NAME/PREFIX/tidb-TIMESTAMP" \
  --s3.region="BUCKET_REGION"
```

These are the same `--pd`, `--storage` and `--s3.region` arguments the backup image passes to `br backup full`, so the restore authenticates the way the backup did — through the identity's cloud-account binding. The TiKV nodes download their data from the bucket directly, so they need outbound access; with `backup.enabled: true` the template opens it for them.

### Upgrading from 1.x

Template versions through 1.8.1 created their own GVC, so that GVC is part of the 1.x release's manifest. Versions 2.0.0 and later do not declare it — and Helm deletes what a chart stops declaring.

<Warning>
**Never `helm upgrade` a 1.x release onto 2.x.** The upgrade deletes the GVC the 1.x chart created and every workload, volume set and identity inside it, including your data. The 2.x chart refuses to render when your values still carry a `gvc` key, so an upgrade run with your old values file fails before touching anything:

```text
Error: execution error at (tidb/templates/identity.yaml:1:4): tidb 2.0.0: the `gvc` values key was
REMOVED. This chart no longer creates a GVC -- it deploys into the GVC you install into ...
```

That guard cannot see an upgrade run with no values file at all — a 1.x release installed on pure defaults has no `gvc` key to catch. Do not run the upgrade under any circumstances. Install a new release and move the data across.
</Warning>

<Steps>
  <Step title="Recover the credentials the existing cluster uses">
    Versions up to 1.7.0 took the credentials as Helm values and wrote them into a chart-owned secret named `RELEASE_NAME-tidb-user`; from 1.8.0 they live in the secret you created. Read them back with `cpln secret reveal SECRET_NAME -o yaml`. Any password that came from a pre-1.8.0 default was published in the public template repository — treat it as compromised and choose a new one for the new cluster.
  </Step>
  <Step title="Back up the old cluster">
    Enable `backup` with `provider: aws` on the 1.x release, or run `br backup full` by hand against its PD endpoint.
  </Step>
  <Step title="Choose the GVC for the new release">
    Create or pick a GVC that has every location you intend to list in `locations`. See [Prerequisites](#prerequisites).
  </Step>
  <Step title="Create the credentials secret and install 2.1.0 as a new release">
    Follow [Prerequisites](#prerequisites), then install into that GVC with a **different release name** — secret and policy names are org-wide, so a same-named release collides with the 1.x one even in another GVC.
  </Step>
  <Step title="Restore and cut over">
    Restore into the new cluster (see [Restoring a Backup](#restoring-a-backup)), then point your applications at the new `RELEASE_NAME-server.GVC_NAME.cpln.local:4000` endpoint.
  </Step>
  <Step title="Uninstall the old release against the GVC you installed it into">
    Not the GVC it created — the GVC you passed at install time is where Helm tracks the release, and uninstalling from there removes the created GVC with it:

    ```bash
    cpln helm uninstall RELEASE_NAME --gvc GVC_NAME
    ```
  </Step>
</Steps>

Values keys that moved or were removed since 1.x:

- `gvc.locations` is now the top-level `locations`, `gvc.pdReplicas` is now the top-level `pdReplicas`, and `gvc.name` is gone.
- `devMode` is gone. `locations` may hold a single location, and PD's replication factor is derived from the number of TiKV nodes you configure.
- `exposeServer` is gone. It never published the MySQL port — the only thing the public endpoint would have served was tidb-server's unauthenticated status API. Reach the server over internal GVC DNS or `cpln port-forward`.
- `autoCreateDatabase.database.*` is gone (since 1.8.0): the four values are the prerequisite dictionary secret named by `autoCreateDatabase.credentialsSecretName`.
- `replicas` on a location is now `tikvReplicas` plus `serverReplicas` (split in 2.1.0). A count of `0` is refused; remove the location from `locations` instead.

The guards fire on the mere presence of a removed key, so `exposeServer: false` and `devMode: false` fail too, each with an error naming the key and its replacement.

### Upgrading from 2.0.0

2.0.0 and 2.1.0 both deploy into an existing GVC, so this is a plain `cpln helm upgrade` with one values change.

<Steps>
  <Step title="Check the 2.0.0 cluster is healthy">
    A 2.0.0 bootstrap can leave a TiKV store that never comes up, so the cluster runs without fault tolerance or never serves SQL at all. Upgrading does not repair that. Ask PD for its stores (on a multi-location install add `--location LOCATION_NAME`):

    ```bash
    cpln workload exec RELEASE_NAME-pd --gvc GVC_NAME --replica RELEASE_NAME-pd-0 --container tidb-pd -- sh -c 'curl -s 127.0.0.1:2379/pd/api/v1/stores | grep state_name'
    ```

    Every store must report `"Up"`. If one is `"Down"` and the cluster has never served queries, it holds no data: uninstall it and install 2.1.0 fresh. If it has been serving with a store down, back it up and restore into a fresh 2.1.0 release (see [Backing Up](#backing-up) and [Restoring a Backup](#restoring-a-backup)).
  </Step>
  <Step title="Split replicas into tikvReplicas and serverReplicas">
    In every `locations` entry, replace `replicas: N` with `tikvReplicas: N` and `serverReplicas: N` to keep your current shape exactly:

    ```yaml
    locations:
      - name: aws-us-east-1
        tikvReplicas: 3
        serverReplicas: 3
    ```

    The chart refuses to render while a location still sets `replicas`, so an upgrade with your old values file fails before touching anything:

    ```text
    Error: execution error at (tidb/templates/workload-tikv.yaml:24:20): tidb: location 'aws-us-east-1' sets
    `replicas`, which 2.1.0 SPLIT into `tikvReplicas` (TiKV storage nodes) and `serverReplicas` (TiDB SQL servers) ...
    ```
  </Step>
  <Step title="Upgrade the release">
    ```bash
    cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/tidb \
      --version 2.1.0 --gvc GVC_NAME -f values.yaml
    ```
  </Step>
</Steps>

The upgrade restarts PD, TiKV and the TiDB servers. Replicas in the same location restart one at a time; separate locations restart at the same time, so on a multi-location install writes can pause briefly while PD re-forms. Data is not at risk. ProxySQL stays off unless you set `proxysql.enabled: true`.

### Scaling and Availability

- **Node loss.** The default shape (one location, three TiKV nodes, three PD members) keeps serving through the loss of a node. A TiDB server stays in service while TiKV is partly unavailable; affected statements return errors until TiKV recovers, without restarting the SQL tier.
- **Location loss.** Needs at least three locations with PD spread one per location, as in the [Locations](#locations) example. Clients in the lost location cannot connect until it returns; clients elsewhere keep working.
- **SQL server loss.** Clients reach only the servers in their own location, so `serverReplicas: 2` or more is what keeps a location serving through a server failure. Adding [ProxySQL](#connection-pooling-proxysql) in front smooths that over further.
- **Adding TiKV and tidb-server capacity.** Raise `locations[].tikvReplicas` or `locations[].serverReplicas` and upgrade. New TiKV stores register with PD and receive data; new tidb-server replicas join behind the same internal address.
- **PD's replication factor is fixed at bootstrap.** It is the number of TiKV nodes you configure, capped at 3, and PD persists it — scaling TiKV up later does not raise it. Start with at least 3 TiKV nodes if you ever want 3-way replication.
- **Scaling in** (reducing `tikvReplicas`) and **changing `pdReplicas` on a running cluster** are not covered by this template and have not been exercised. TiKV stores hold data; consult the [TiDB documentation](https://docs.pingcap.com/tidb/stable/) on scaling in before removing any.
- **Storage.** Enable `volumeset.tikv.autoscaling` to grow TiKV volumes as they fill. PD volumes are fixed-size.

### Rotating Credentials

The credentials secret is applied on first initialization only. Changing it afterwards does not change the cluster — it only changes what the init job and your clients present. Rotate inside TiDB first, then update the secret:

```sql
ALTER USER 'myuser'@'%' IDENTIFIED BY 'NEW-PASSWORD';
```

Write the whole secret back with every key present, then apply it:

```yaml
# credentials.yaml
kind: secret
name: SECRET_NAME
type: dictionary
data:
  rootPassword: YOUR-ROOT-PASSWORD
  user: myuser
  password: NEW-PASSWORD
  db: mydb
```

```bash
cpln apply -f credentials.yaml
```

A `cpln://secret` reference is resolved when a replica starts and is never re-read while it runs, so force a redeployment of tidb-server afterwards so its environment matches:

```bash
cpln workload force-redeployment RELEASE_NAME-server --gvc GVC_NAME
```

With ProxySQL enabled, redeploy the pooler too — it authenticates clients with the credentials from the secret:

```bash
cpln workload force-redeployment RELEASE_NAME-proxysql --gvc GVC_NAME
```

If the init job is still deployed, set `autoCreateDatabase.deployInitWorkload: false` before rotating — it checks the database with the credentials in the secret on every run.

### Troubleshooting

<AccordionGroup>
  <Accordion title="The deployment never starts and the logs are empty">
    **Symptom:** `cpln logs` returns nothing for `RELEASE_NAME-server` or `RELEASE_NAME-tidb-db-init`, and the workload never becomes ready.

    **Cause:** the credentials secret named by `autoCreateDatabase.credentialsSecretName` does not exist. The container never runs, so there is nothing to log.

    **Fix:** read the message, create the secret, and force a redeployment:

    ```bash
    cpln workload get-deployments RELEASE_NAME-server --gvc GVC_NAME -o yaml
    ```

    ```text
    The secret SECRET_NAME no longer exists. Workload updates are paused until the
    secret is added or the reference to the secret removed.
    ```

    ```bash
    cpln workload force-redeployment RELEASE_NAME-server --gvc GVC_NAME
    ```
  </Accordion>
  <Accordion title="PD restarts with FATAL locations declared in values are not in GVC">
    **Symptom:** `RELEASE_NAME-pd` crash-loops and its logs contain:

    ```text
    [tidb-pd] FATAL: locations declared in values are not in GVC 'GVC_NAME': aws-us-west-2
    [tidb-pd] GVC 'GVC_NAME' has: aws-us-east-1
    ```

    **Cause:** `locations` names a location the GVC does not have. The platform accepts the install; PD refuses to bootstrap a cluster whose members can never all appear.

    **Fix:** add the location to the GVC, or remove it from `locations` and upgrade. Check the GVC with `cpln gvc get GVC_NAME -o yaml` (`spec.staticPlacement.locationLinks`).
  </Accordion>
  <Accordion title="A GVC location shows red with This workload location is deactivated because maxScale is set to 0">
    **Symptom:** the console marks a location red on every TiDB workload with `This workload location is deactivated because maxScale is set to 0.`

    **Cause:** the GVC has a location you did not list in `locations`. Nothing TiDB-related runs there by design.

    **Fix:** none needed. To use that location, add it to `locations` with `tikvReplicas` and `serverReplicas` counts and upgrade.
  </Accordion>
  <Accordion title="tidb-server never becomes ready">
    **Symptom:** `RELEASE_NAME-server` stays unready after install.

    **Cause:** a TiDB server reports ready only once it has started against the cluster, and that needs a healthy PD and registered TiKV stores. Either tier is still starting, or TiKV cannot reach PD.

    **Fix:** check the other tiers in order — PD first, then TiKV:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-pd"}' --limit 50 --since 10m
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-tikv"}' --limit 50 --since 10m
    ```

    Then confirm what PD sees:

    ```bash
    cpln workload exec RELEASE_NAME-server --gvc GVC_NAME --container tidb-server -- \
      curl -s http://RELEASE_NAME-pd.GVC_NAME.cpln.local:2379/pd/api/v1/stores
    ```
  </Accordion>
  <Accordion title="helm upgrade fails at render saying a location sets replicas">
    **Symptom:** the upgrade exits before touching anything with `tidb: location 'LOCATION_NAME' sets replicas, which 2.1.0 SPLIT into tikvReplicas ... and serverReplicas`.

    **Cause:** your values file still uses the 2.0.0 `replicas` key. 2.1.0 sets TiKV nodes and SQL servers separately.

    **Fix:** replace `replicas: N` with `tikvReplicas: N` and `serverReplicas: N` in every `locations` entry. See [Upgrading from 2.0.0](#upgrading-from-2-0-0).
  </Accordion>
  <Accordion title="helm install fails with proxysql.enabled requires autoCreateDatabase.enabled">
    **Symptom:** rendering fails with `tidb: proxysql.enabled requires autoCreateDatabase.enabled`.

    **Cause:** ProxySQL authenticates clients with the credentials from the secret named by `autoCreateDatabase.credentialsSecretName`, which is only wired in when `autoCreateDatabase.enabled` is `true`.

    **Fix:** set `autoCreateDatabase.enabled: true` with a valid credentials secret, or leave `proxysql.enabled: false`.
  </Accordion>
  <Accordion title="Queries through ProxySQL fail intermittently with ERROR 1273">
    **Symptom:** a client works when connected to `RELEASE_NAME-server` directly, but through `RELEASE_NAME-proxysql` some queries fail with `ERROR 1273 ... latin1_swedish_ci`.

    **Cause:** the client requests a latin1 charset. TiDB accepts that on a direct connection but rejects it when ProxySQL applies the client charset.

    **Fix:** connect with utf8mb4. Modern drivers default to it; for the `mysql` command-line client pass `--default-character-set=utf8mb4`.
  </Accordion>
  <Accordion title="A client in another GVC location cannot connect">
    **Symptom:** an application in the same GVC gets connection failures against `RELEASE_NAME-server.GVC_NAME.cpln.local:4000`, while clients in other locations work.

    **Cause:** the client runs in a GVC location not listed in `locations`. Clients reach only the TiDB servers (and ProxySQL replicas) in their own location.

    **Fix:** run the client in a listed location, or add its location to `locations` and upgrade.
  </Accordion>
  <Accordion title="helm install or upgrade fails at render naming a REMOVED key">
    **Symptom:** the command exits before creating anything with an error such as `tidb: exposeServer was REMOVED in 2.0.0`, `the gvc values key was REMOVED`, `devMode` or `autoCreateDatabase.database was REMOVED`.

    **Cause:** your values file still carries a key that 2.0.0 removed. The guards fire on the key's presence, even when it is set to `false`.

    **Fix:** delete the key and use its replacement from the list in [Upgrading from 1.x](#upgrading-from-1-x). If this was an attempt to upgrade a 1.x release in place, stop — that path destroys the 1.x GVC. Install a new release instead.
  </Accordion>
  <Accordion title="helm install fails with backup.location is not one of locations">
    **Symptom:** rendering fails with `tidb: backup.location 'aws-us-west-2' is not one of locations (aws-us-east-1)`.

    **Cause:** the backup cron runs only in `backup.location`, which must be one of your `locations`.

    **Fix:** set `backup.location` to a location you configured, preferably the one nearest your bucket.
  </Accordion>
  <Accordion title="Clients cannot connect after switching internal access to workload-list">
    **Symptom:** your application gets connection refused or timeouts against `RELEASE_NAME-server.GVC_NAME.cpln.local:4000` after setting `internal_access.server.type: workload-list`.

    **Cause:** the client workload is missing from `internal_access.server.workloads`, or the change has not finished taking effect yet.

    **Fix:** add the client as `//gvc/GVC_NAME/workload/WORKLOAD_NAME`, upgrade, and allow several minutes. You never need to list this release's own workloads — they are always included.
  </Accordion>
  <Accordion title="The backup job exits immediately after upgrading TiDB">
    **Symptom:** `RELEASE_NAME-tidb-backup` runs fail right after `images.*` was bumped, and the `br` output refuses the cluster version.

    **Cause:** `br` must match the cluster version; from v8.5.7 it enforces the check even with `--check-requirements=false`.

    **Fix:** bump `backup.image` to the same TiDB version as `images.*` and upgrade.
  </Accordion>
  <Accordion title="The init job keeps running every five minutes">
    **Symptom:** `RELEASE_NAME-tidb-db-init` shows a new run on every tick of `autoCreateDatabase.schedule`, each logging `Database already initialized. Exiting.`

    **Cause:** expected. The job is a cron that fast-exits once the database exists.

    **Fix:** none required. To remove it, set `autoCreateDatabase.deployInitWorkload: false` and upgrade.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Never `helm upgrade` a 1.x release onto 2.x** — it deletes the GVC the 1.x chart created and everything in it. Install a new release: [Upgrading from 1.x](#upgrading-from-1-x).
- **Create the credentials secret before installing.** Without it the deployment wedges silently; the only diagnostic is `status.versions[].message` from `cpln workload get-deployments`.
- **Upgrading from 2.0.0 needs one values change**: replace each location's `replicas` with `tikvReplicas` and `serverReplicas`. See [Upgrading from 2.0.0](#upgrading-from-2-0-0).
- **The GVC must contain every location you list**, and may contain more. A missing location is not caught at install: PD exits with `FATAL: locations declared in values are not in GVC ...`.
- **Run clients in a listed location.** Clients reach only the TiDB servers in their own location; use `serverReplicas: 2` or more to keep a location serving through a server failure.
- **PD's replication factor is fixed when the cluster first bootstraps** (TiKV node count, capped at 3). Start with at least 3 TiKV nodes if you ever want 3-way replication.
- **Use AWS S3 for backups.** The GCS path has never completed a verified backup on this template. The restore procedure is unverified — rehearse it.
- **Keep `backup.image` and `images.*` on the same TiDB version.** `br` refuses a version mismatch.
- **Through ProxySQL, connect with a utf8mb4 charset** — a latin1 client fails intermittently with `ERROR 1273`.
- **There is no public access to the MySQL port.** Reach tidb-server over internal GVC DNS or `cpln port-forward RELEASE_NAME-server 4000:4000 --gvc GVC_NAME`.
- **Release names must be unique per org** — secrets and policies are org-wide, so two releases with the same name collide even in different GVCs.
- **Credentials apply on first initialization only.** Rotate with `ALTER USER` inside TiDB first, then update the secret, then force a redeployment of tidb-server (and of `RELEASE_NAME-proxysql` when enabled).
- **Switch backup providers with a fresh install**, not an upgrade — the identity keeps the old cloud-account binding.
