## Overview

NATS is an open-source, high-performance, lightweight messaging system for pub/sub, queueing and request/reply, with an optional built-in persistence layer (JetStream) for durable streams, consumers, a key-value store and an object store. This template deploys a NATS cluster per location you list — `replicas` servers in each — and joins the locations into a cross-region super cluster over NATS gateways when you list more than one. A WebSocket listener is on by default; Control Plane serves it on port 443 once you open the public firewall.

<Note>
This template deploys into an existing [GVC](/reference/gvc) you already have; it does not create, provision or manage one. Every location you list in `locations` must already be one of the GVC's locations. A GVC location you do not list runs nothing — its deployment reads `This workload location is deactivated because maxScale is set to 0`, which is the expected result of pinning the location list, not a fault.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-nats` | The NATS servers: a stateful workload running `replicas` servers in each listed location. Client port `4222`, route port `6222` between servers in one location, WebSocket port `8080` (when enabled), gateway port `7222` between locations (multi-location only) | — |
| Volume Set | `RELEASE_NAME-nats-vs` | `/data/nats` JetStream store, one `xfs` volume per server on general-purpose SSD | `jetstream.enabled: true` |
| Secret | `RELEASE_NAME-nats-secret` | The startup script that builds each server's `nats.conf` at boot from the location and replica it runs as | — |
| Secret | `RELEASE_NAME-nats-extra-data` | Your `nats_extra_config`, appended verbatim to the generated configuration | `nats_extra_config` non-empty |
| Identity | `RELEASE_NAME-nats-identity` | Bound to the workload so it can read its startup script and its own GVC | — |
| Policy | `RELEASE_NAME-nats-policy` | Grants the identity `reveal` on this release's secrets and nothing else | — |
| Policy | `RELEASE_NAME-nats-gvc-policy` | Grants the identity `view` on exactly the one GVC the release is installed into, so each server can confirm at boot that the GVC really has every location in `locations` | — |

The template creates no credential secret: NATS here runs without authentication, and access is governed by the internal firewall (see [Internal Access](#internal-access)) and the public CIDR list (see [Public Access](#public-access)).

## Prerequisites

<Steps>
  <Step title="A GVC that contains every location in locations">
    This template deploys into an existing GVC and does not create one. Read the GVC's locations and compare them with the list you intend to install with:

    ```bash
    cpln gvc get GVC_NAME -o yaml
    ```

    `spec.staticPlacement.locationLinks` is the list. Every `name` in `locations` must appear there; the GVC may have more locations than you list, and no NATS server runs in those. A declared location the GVC lacks is not caught at install time — each server reports it at boot (see [Troubleshooting](#troubleshooting)). To add a location to a GVC, see [GVC Locations](/reference/gvc#gvc-locations); every workload in that GVC then runs there, so add locations to a shared GVC deliberately.
  </Step>
</Steps>

Nothing else is needed: no secret to create, no cloud account, no bucket, no custom domain.

## Installation

The default `locations` list is a single location, `aws-us-east-1`, with three servers. If your GVC has that location, the defaults install as-is; otherwise put your GVC's own location(s) in a values file first — `locations` is a list, so set it with `-f` rather than `--set`:

```yaml
# nats-locations.yaml — one NATS cluster per location; every name must already be in the GVC
locations:
  - name: LOCATION_1
    replicas: 3
```

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/nats \
  --version 3.0.0 --gvc GVC_NAME -f nats-locations.yaml
```

## Configuration

Each subsection below shows the shipped default for one area of `values.yaml`. Override only what you need with a values file or `--set`.

### Locations and Cluster Sizing

```yaml
# Every location listed here MUST already exist in the GVC you install into.
# One entry = one NATS cluster; `replicas` = servers in that cluster. Two or more
# locations are joined into a super cluster over NATS gateways.
locations:
  - name: aws-us-east-1
    replicas: 3
```

- `locations[].name` — A location of the GVC you install into. Listing the same location twice is rejected at render time.
- `locations[].replicas` — How many NATS servers run in that location; at least `1`. A location with `replicas: 0` is rejected at render time — to stop running somewhere, remove the entry.

The default is one location with three servers: the smallest shape that is both a real NATS cluster and installable on any single-location GVC. Core NATS needs no quorum, so any server count routes messages; JetStream's meta group is a RAFT group over every server in the super cluster, so the **total** server count decides what JetStream survives:

| Servers | Core NATS | JetStream |
|---|---|---|
| 1 | Works | Standalone. `R1` streams only, no fault tolerance |
| 2 | Works | **Refused by this template** — quorum is 2 of 2, so losing either server takes JetStream down entirely. Strictly worse than a single server |
| 3 | Works | Survives losing one server. NATS's recommended minimum |
| 5 | Works | Survives losing two servers |

Adding a **second location** does not change the quorum arithmetic — it buys geographic locality. Each location is its own NATS cluster, so clients connect to servers near them, and gateways forward only the traffic that has interested subscribers on the other side. Size the total server count against the table above, and give each location at least 3 servers if you want streams to survive losing a whole location. Cross-region gateway traffic is billed, which is why a single location is the default.

### Image and Resources

```yaml
image: nats:2.11.6-alpine # official NATS image tag — bump to upgrade NATS

resources:
  cpu: 100m
  memory: 256Mi
```

- `image` — The NATS container image. Bump the tag to upgrade NATS.
- `resources.cpu` / `resources.memory` — CPU and memory limit for each server. The defaults are small; raise them for real throughput.

### Listeners

```yaml
# Each listener binds 0.0.0.0 on the port below. Monitoring is fixed on 8222 and
# is not published as a container port.
nats_defaults:
  port: 4222 # client port (nats:// and internal GVC clients)
  cluster:
    port: 6222 # route connections between replicas in the SAME location
  gateway:
    port: 7222 # gateway connections BETWEEN locations; unused with one location
  websocket:
    enabled: true # publishes the workload's public endpoint; Control Plane serves it on 443
    port: 8080
    compression: false
    noTls: true # Control Plane terminates TLS — leave true unless you supply certs
```

- `nats_defaults.port` — Client port, for `nats://` clients inside the GVC.
- `nats_defaults.cluster.port` — Route connections between servers in the **same** location.
- `nats_defaults.gateway.port` — Gateway connections **between** locations. Published as a container port only when more than one location is configured.
- `nats_defaults.websocket.enabled` — Serves a WebSocket listener and publishes the workload's public endpoint. Control Plane serves it on port 443; who can reach it is decided by [Public Access](#public-access).
- `nats_defaults.websocket.port` / `compression` / `noTls` — The internal WebSocket port, per-message compression, and whether the listener itself runs without TLS. Leave `noTls: true` unless you supply certificates through `nats_extra_config`.

The template refuses at render time to bind a port Control Plane reserves for system use, and to put two listeners on the same port. Both failures are otherwise invisible to `helm template`: a reserved port is rejected by the API at install, and a port collision is accepted and then stops the container at boot with `address already in use`.

### Public Access

```yaml
# Inbound public CIDRs for the WebSocket endpoint, which Control Plane exposes on
# port 443. EMPTY = no public access, which is the default.
allowCIDR: []
```

- `allowCIDR` — The inbound CIDR ranges allowed to reach the WebSocket endpoint from the internet. It applies to the WebSocket port only — the client (`4222`), route (`6222`) and gateway (`7222`) ports are never exposed publicly.

<Warning>
**This template configures no NATS authentication, so opening `allowCIDR` publishes an unauthenticated message bus.** An anonymous outside client can publish, subscribe, and read the cluster name and every server name. Version 3.0.0 changed the default from `0.0.0.0/0` to `[]` for this reason. Open it only alongside an `authorization { ... }` block in [`nats_extra_config`](#extra-nats-configuration), and prefer the narrowest ranges that cover your clients.
</Warning>

<Note>
Do not pin a single `/32`. A client behind a proxy pool or a rotating egress address moves to a different IP, and a perfectly healthy deployment then returns `403` to it. Use a range wide enough to cover your egress, not just the address you happen to have today. A firewall change takes a few minutes to take effect; re-test rather than trusting the first response.
</Note>

To reach a closed deployment from your own machine without opening it at all, tunnel to the client port with `cpln port-forward` — see [Connecting](#connecting).

### JetStream

```yaml
jetstream:
  enabled: false # set to true for durable streams, consumers, K/V and object store

volumeset:
  capacity: 10 # initial capacity in GiB per replica (minimum is 10)
```

- `jetstream.enabled` — Without JetStream, NATS is in-flight only: a message with no connected subscriber is gone. Enabling it adds durable streams, durable consumers, a key-value store and an object store, and creates the volume set. Sizing is decided by the total server count — see the table under [Locations and Cluster Sizing](#locations-and-cluster-sizing); exactly two servers is refused.
- `volumeset.capacity` — Size in GiB of the persistent volume each server gets for `/data/nats` (minimum 10). Used only when `jetstream.enabled` is `true`. Uninstalling the release deletes the volume set and the JetStream data on it.

<Note>
Streams default to a single replica, so stream data lives on one server. A stream only survives losing a server if you create it with three or more replicas — `nats stream add STREAM --subjects "SUBJECT.>" --replicas=3 --defaults` — which is per-stream, in your application, not a setting in this template.
</Note>

### Extra NATS Configuration

```yaml
# Any additional valid NATS configuration — appended verbatim to the generated
# server config at startup. A syntax error here is a container that will not
# start, not a render failure.
nats_extra_config: ""
```

- `nats_extra_config` — Appended verbatim to the generated server configuration. Use it for anything the template does not expose — payload limits, accounts, authorization:

```yaml
nats_extra_config: |
  max_payload: 8MB
  authorization {
    user: USERNAME
    password: PASSWORD
  }
```

<Warning>
**This block is injected verbatim and is not validated at render time.** A syntax error here is a container that will not start, which is easy to mistake for an infrastructure problem — read the server's own parse error in the workload log (see [Troubleshooting](#troubleshooting)). Note also that the template has no prerequisite-secret path for NATS credentials: anything you put here is stored in the Helm release values and in the `RELEASE_NAME-nats-extra-data` secret.
</Warning>

### Internal Access

```yaml
internalAccess:
  type: same-gvc # options: none, same-gvc, same-org, workload-list
  workloads: [] # only used when type is workload-list; the NATS workload is added automatically
  #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

- `internalAccess.type` — Controls which workloads can reach the servers from inside Control Plane.

| Type | Description |
|------|-------------|
| `none` | No internal access. **Refused at render time for any deployment with more than one server** — see below |
| `same-gvc` | Allow access from all workloads in the same GVC (recommended) |
| `same-org` | Allow access from all workloads in the org |
| `workload-list` | Allow access only from the workloads in `internalAccess.workloads`, plus this release's own workload, which the template adds for you |

- `internalAccess.workloads` — The workload links allowed in when `type` is `workload-list`. **List only your clients.**

<Warning>
**This setting governs the servers' traffic to each other, not just client traffic.** The same internal firewall carries the route connections between servers in a location and the gateway connections between locations. A `workload-list` naming only your applications would cut the cluster off from itself — routes never establish, each server runs alone, and JetStream loses its meta group — while every replica still reports `ready: true`, because this workload has no readiness probe and readiness says nothing about clustering. The template therefore adds its own workload to the list for you, and refuses `internalAccess.type: none` for any deployment with more than one server; `none` is valid only for a single server reached over the public WebSocket endpoint.
</Warning>

## Connecting

| What | Address | Notes |
|---|---|---|
| Clients in the same GVC | `nats://RELEASE_NAME-nats.GVC_NAME.cpln.local:4222` | Resolves to a server; the one address to give to clients |
| A specific server | `nats://replica-N.RELEASE_NAME-nats.LOCATION.GVC_NAME.cpln.local:4222` | `N` is `0` to `replicas - 1`; `LOCATION` is one of the names in `locations` |
| Browser and WebSocket clients from the internet | `wss://` + the workload's canonical endpoint | Only once `allowCIDR` covers the client; Control Plane terminates TLS and serves it on port 443 |
| Monitoring | `http://127.0.0.1:8222` from inside a server's container | `/healthz`, `/varz`, `/routez`, `/gatewayz`, `/jsz`; not published as a container port |
| Credentials | none | No authentication unless you add an `authorization { ... }` block in [`nats_extra_config`](#extra-nats-configuration) |

Always use the fully qualified hostname; the bare workload name is not reliably resolvable. Read the public hostname rather than assembling it — its shape varies between GVCs:

```bash
cpln workload get RELEASE_NAME-nats --gvc GVC_NAME -o yaml
```

The value is `status.canonicalEndpoint`; connect with `wss://` on the default port.

Verify a server from inside its container. The image carries no `nats` CLI, but it does carry `wget`, and the monitoring listener answers on loopback:

```bash
cpln workload exec RELEASE_NAME-nats --gvc GVC_NAME --container nats -- wget -qO- http://127.0.0.1:8222/healthz
cpln workload exec RELEASE_NAME-nats --gvc GVC_NAME --container nats -- wget -qO- http://127.0.0.1:8222/routez
```

`/healthz` returns `{"status":"ok"}` on a healthy server, and `/routez` lists the route connections to the other servers in the same location — an empty `routes` list on a multi-server deployment means the cluster has not formed (see [Troubleshooting](#troubleshooting)). On a multi-location release, `/gatewayz` lists the other locations as gateways.

To publish and subscribe from your own machine, forward the client port and point a local [`nats` CLI](https://github.com/nats-io/natscli) at `127.0.0.1`:

```bash
cpln port-forward RELEASE_NAME-nats 4222:4222 --gvc GVC_NAME
```

```bash
nats --server nats://127.0.0.1:4222 sub demo.hello
nats --server nats://127.0.0.1:4222 pub demo.hello 'hello from Control Plane'
```

## Operations

### Backing Up

Without JetStream there is nothing to back up — messages are in flight only. With `jetstream.enabled: true`, the data lives on the volume set `RELEASE_NAME-nats-vs`, one volume per server, and two independent layers can protect it:

- **Volume set snapshots.** The template configures no snapshot schedule, so take them on demand, naming the location of the volume you want:

  ```bash
  cpln volumeset snapshot create RELEASE_NAME-nats-vs --gvc GVC_NAME --snapshot-name NAME --location LOCATION
  cpln volumeset snapshot get RELEASE_NAME-nats-vs --gvc GVC_NAME
  ```

- **A stream snapshot.** The `nats` CLI can write a complete copy of one stream — every message, its configuration and, with `--consumers`, its consumers' positions — to a local directory. Run it from your machine through a port-forward tunnel (see [Connecting](#connecting)):

  ```bash
  nats --server nats://127.0.0.1:4222 backup stream STREAM ./backups/STREAM --consumers
  ```

  Memory-storage streams cannot be snapshotted on this server version; only file-backed streams can. Follow the upstream [stream backup and restore guide](https://docs.nats.io/learn/backup-recovery/stream-backup-restore) for the options.

<Note>
The stream backup command above follows the upstream guide but has not been exercised against a live install of this template. Run it once on a test release and confirm `nats backup validate ./backups/STREAM` passes before you rely on it.
</Note>

### Restoring a Backup

**Restoring is not a procedure this template performs or has verified.** Two upstream paths exist, and neither has been exercised against a live install of this template:

- **A stream snapshot** is restored with `nats --server nats://127.0.0.1:4222 backup restore stream ./backups/STREAM` against a JetStream-enabled cluster in which the stream does **not** already exist — restore recreates the stream and fails if one of that name is present. Rehearse it on a throwaway release first.
- **A volume set snapshot** can in principle be restored with `cpln volumeset snapshot restore`, but this template gives you no supported way to stop a server and replace `/data/nats` underneath it, so treat that path as unverified and prefer the stream-level restore.

### Migrating from 2.x

Template versions through 2.0.0 created their own GVC; 3.0.0 deploys into one you already have.

<Warning>
**Do not `cpln helm upgrade` a 2.x release onto 3.0.0.** A 2.x release owns the GVC it created, and Helm deletes what a chart stops declaring — the upgrade destroys that GVC and **every workload, volume set and identity inside it**, including your JetStream data. The chart refuses to render when your values still carry the 2.x `gvc` key, so a values-carrying upgrade fails safely before any resource is touched:

```text
Error: execution error at (nats/templates/workloads.yaml:3:4): nats 3.0.0: the `gvc` values key was
REMOVED. This chart no longer creates a GVC -- it deploys into the GVC you install into, and
`gvc.locations` moved to the top-level `locations`. DO NOT `helm upgrade` a 2.x release onto 3.0.0 ...
```

That guard cannot fire on an upgrade run with **no values at all** — a 2.x release installed on pure defaults has no `gvc` key for the chart to see. The procedure below is the safety; the render guard is only a backstop.
</Warning>

Install 3.0.0 as a **new release against an existing GVC**, move the traffic, then remove the old release.

<Steps>
  <Step title="Choose the target GVC">
    Pick a GVC whose locations include every one you want servers in, and read them back with `cpln gvc get GVC_NAME -o yaml` — `spec.staticPlacement.locationLinks` is the list. Do **not** point the new release at the GVC the old release created: that GVC is still owned by the old Helm release, and uninstalling it later would take the new workloads with it.
  </Step>
  <Step title="Install 3.0.0 as a new release">
    Use a **different release name**: secret names are org-wide, so a same-named release collides with the 2.x one even in another GVC. Translate the old `gvc.locations` entries into the top-level `locations` list and install as shown in [Installation](#installation). Note that `allowCIDR` now defaults to closed — if the 2.x deployment served browser clients over WebSocket, set your own ranges explicitly, together with an `authorization { ... }` block.
  </Step>
  <Step title="Move the traffic">
    Point publishers and subscribers at the new release's address. With JetStream, a stream is not carried by the chart — recreate your streams on the new release, or snapshot and restore them with the `nats` CLI as described in [Backing Up](#backing-up) and [Restoring a Backup](#restoring-a-backup).
  </Step>
  <Step title="Remove the old release">
    ```bash
    cpln helm uninstall OLD_RELEASE_NAME --gvc OLD_GVC_NAME
    ```

    Run it against the GVC the old release was *installed into*, not the one it created — that is where Helm tracks the release. Uninstalling removes the old release **and the GVC it created**, including its volume sets.
  </Step>
</Steps>

Values that moved or were removed in 3.0.0. The chart names each one at render time rather than ignoring it, so an old values file produces an error instead of a silent misconfiguration:

| 2.x | 3.0.0 |
|---|---|
| `gvc.name` | Gone. The chart deploys into the GVC you install into |
| `gvc.locations` | `locations`, at the top level |
| `nats_defaults.cluster.listen` | Gone. Derived as `0.0.0.0:<port>`, so it can no longer disagree with the port |
| `nats_defaults.gateway.listen` | Gone, for the same reason |
| `nats_defaults.cluster.noAdvertise` | Gone. It was never wired to anything. Use `cluster { no_advertise: true }` in `nats_extra_config` if you need it |
| `allowCIDR: [0.0.0.0/0]` | Default is now `[]` (no public access) |
| `volumeset.autoscaling` | Gone. `volumeset.capacity` is the only storage knob |
| `locations[].replicas: 0` | Not allowed. Remove the location instead |

### Scaling and Availability

- **Fault tolerance follows the total server count.** Core NATS keeps routing with any number of servers up. JetStream keeps serving while a majority of servers is up: 3 survive losing one, 5 survive losing two, and 2 survive none, which is why that shape is refused (see [Locations and Cluster Sizing](#locations-and-cluster-sizing)).
- **A stream survives a server only if you created it with replicas.** Stream data is placed per stream at creation time — a default `R1` stream lives on one server and is lost with it, whatever the cluster size. Create streams with `--replicas=3` on a 3-or-more-server cluster.
- **Losing a whole location** takes that location's cluster with it. Clients connected to the other locations keep working, and streams with enough replicas in the surviving locations keep serving — give each location at least 3 servers if a location's loss must not take a stream down.
- **Change `locations[].replicas` with a `cpln helm upgrade`.** The servers restart to pick up the new route list. With JetStream, do not pass through the 2-server shape — the chart refuses it at render time, and a 3-server roster whose GVC is missing a location becomes it at runtime.
- **A server rescheduled with its volume intact rejoins on its own.** Each server derives its name, cluster and peers from the location and replica it runs as, so the configuration is stable across restarts.

<Note>
The failure-tolerance statements above follow the NATS clustering model and the chart's configuration; they have not been re-verified against a live install for this page. Rehearse the loss you care about on a test release before you depend on it.
</Note>

### Troubleshooting

When a server will not come up or a cluster will not form, its own `[nats]` log lines name the reason:

```bash
cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-nats"} |= "[nats]"' --limit 50 --since 10m
```

<AccordionGroup>
  <Accordion title="Install or upgrade fails: the gvc values key was REMOVED">
    **Cause:** Your values still carry the 2.x `gvc` block. Version 3.0.0 no longer creates a GVC and refuses to render rather than let an in-place upgrade delete the one the old release created.

    **Fix:** Do not upgrade in place. Follow [Migrating from 2.x](#migrating-from-2-x): install 3.0.0 as a new release with a top-level `locations` list, move the traffic, then uninstall the old release.
  </Accordion>
  <Accordion title="Install fails: locations must be a LIST of name and replicas entries">
    **Cause:** `--set locations=[]` (or any `--set` of the whole key) sets a string, not a list. The chart rejects it before any resource is created.

    **Fix:** Put `locations` in a values file and pass it with `-f`, as shown in [Installation](#installation). Indexed overrides such as `--set 'locations[0].replicas=5'` on top of a values file are fine.
  </Accordion>
  <Accordion title="Install fails: JetStream on exactly 2 servers has no fault tolerance and is worse than 1">
    **Cause:** `jetstream.enabled` is `true` and `replicas` across all locations adds up to 2. The JetStream meta group's quorum would be 2 of 2, so losing either server takes JetStream down completely.

    **Fix:** Use 1 server (standalone JetStream) or at least 3 in total.
  </Accordion>
  <Accordion title="Install fails: internalAccess.type none closes the internal path the replicas use to reach EACH OTHER">
    **Cause:** `internalAccess.type: none` with more than one server would leave every server running alone — routes never establish and JetStream gets no meta group.

    **Fix:** Use `same-gvc`, or `workload-list` naming your clients (the template adds its own workload to the list). `none` is only valid for a single server reached over the public WebSocket endpoint.
  </Accordion>
  <Accordion title="Install fails: port is reserved for system use, or port is used by both">
    **Cause:** One of the `nats_defaults` ports is a port Control Plane reserves (`8012`, `8022`, `9090`, `9091`, `15000`, `15001`, `15006`, `15020`, `15021`, `15090`, `41000`), or two listeners — including the fixed monitoring port `8222` — share a port.

    **Fix:** Pick another port for the listener the error names. Both cases are caught at render time because they are invisible to `helm template` otherwise.
  </Accordion>
  <Accordion title="Server exits with [nats] FATAL: refusing to bootstrap JetStream on a cluster smaller than it was configured to be">
    **Symptom:** With JetStream enabled, a fresh server exits with code `1`; its log reads `locations declared in values are not in GVC '...'`, lists what the GVC has, and says how many of the declared servers can actually start.

    **Cause:** `locations` names a location the GVC does not have. The platform accepts and stores it without any error, so the servers declared there never start, and every running server keeps retrying route and gateway URLs that can never answer. A server with an **empty** JetStream store refuses to bootstrap a cluster smaller than configured; a server whose store already holds data logs the same lines as a warning and keeps serving, so the check can never take a live cluster down. With JetStream off, it only ever warns.

    **Fix:** Add the missing location to the GVC, or remove it from `locations`, and redeploy. `cpln gvc get GVC_NAME -o yaml` shows the GVC's list under `spec.staticPlacement.locationLinks`.
  </Accordion>
  <Accordion title="Server exits with [nats] FATAL: this server is running in location ..., which is not in the configured location list">
    **Cause:** A replica started in a GVC location that `locations` does not list. Such a server would name its cluster after its own location, so no other server has a route to it and no gateway names it — it would accept clients into a cluster of one and silently drop what they publish. It exits instead, fresh or not.

    **Fix:** Add that location to `locations` and upgrade, or remove it from the GVC. Normally an unlisted GVC location runs nothing at all; this line only appears if a replica was placed there anyway.
  </Accordion>
  <Accordion title="Log shows [nats] WARNING: could not read the location list of GVC">
    **Cause:** The server could not read its own GVC at boot — the API was briefly unavailable, or the `RELEASE_NAME-nats-gvc-policy` policy is missing (the log then adds `A 403 here means the GVC-read policy is missing`) — so it skipped the location check and started anyway. NATS runs normally.

    **Fix:** Nothing, if the warning was transient. If it recurs on every start, confirm the policy exists and grants `view` on the GVC the release is installed into:

    ```bash
    cpln policy get RELEASE_NAME-nats-gvc-policy -o yaml
    ```
  </Accordion>
  <Accordion title="Log shows [nats] WARNING: exactly 2 servers are running">
    **Cause:** The roster in `locations` adds up to more than 2, but only 2 declared servers can actually start — typically because one location is missing from the GVC. At runtime this is the 2-server shape the chart refuses in values: with JetStream enabled its quorum is 2 of 2, and without JetStream the warning tells you not to enable it on this shape.

    **Fix:** Resolve the missing location as in the `FATAL` entry above so the full roster runs, or change `locations` to a 1- or 3-plus-server total.
  </Accordion>
  <Accordion title="Container restarts immediately after setting nats_extra_config">
    **Cause:** The block is appended verbatim and is not validated at render time, so a syntax error reaches `nats-server`, which refuses to start and prints its own parse error.

    **Fix:** Read the server's error and correct the block:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-nats"}' --limit 50 --since 10m
    ```
  </Accordion>
  <Accordion title="Servers are ready but /routez shows no routes">
    **Cause:** `ready: true` says nothing about clustering — this workload has no readiness probe. An empty `routes` list on a multi-server deployment means the servers cannot reach each other on the route port: `internalAccess` is `workload-list` with a list that was edited outside the chart, or a declared location is missing from the GVC so the peers never started.

    **Fix:** Check the `[nats]` log lines with the command at the top of this section, confirm `internalAccess` as shown in [Internal Access](#internal-access), and give a firewall change a few minutes to take effect before re-testing.
  </Accordion>
  <Accordion title="WebSocket clients get 403 from the public endpoint">
    **Cause:** `allowCIDR` is empty (the default), or does not cover the client's current egress address — a client behind a proxy pool or a rotating address moves to an IP outside a narrow range.

    **Fix:** Set `allowCIDR` to a range that covers your clients' egress, together with an `authorization { ... }` block in `nats_extra_config`, and upgrade the release. Allow a few minutes for the change to take effect.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Do not `cpln helm upgrade` a 2.x release onto this version.** It deletes the GVC the old release created and everything inside it. Follow [Migrating from 2.x](#migrating-from-2-x).
- **`locations` must match the GVC's locations.** A declared location the GVC lacks is not caught at install; a fresh JetStream server refuses to start on it, and every other server warns. Read the GVC's list with `cpln gvc get GVC_NAME -o yaml` before installing.
- **A GVC location you did not list runs nothing.** Its deployment reads `This workload location is deactivated because maxScale is set to 0`; that is expected.
- **No public access by default, and no authentication.** Opening `allowCIDR` without an `authorization { ... }` block in `nats_extra_config` publishes an unauthenticated message bus. Never pin a single `/32`.
- **`internalAccess` governs the servers' traffic to each other.** With `workload-list`, list only your clients — the template adds its own workload. `none` is refused for more than one server.
- **JetStream data lives on the volume set and is deleted when you uninstall.** Streams default to one replica; create them with `--replicas=3` if a stream must survive a server loss.
- **Do not run JetStream on exactly two servers.** The chart refuses it in values and warns if a missing GVC location produces it at runtime.
- **`nats_extra_config` is injected verbatim**, so a syntax error there stops the container rather than failing the render, and anything you put in it is stored in the release values.
- **A firewall change takes a few minutes to take effect.** After changing `allowCIDR` or `internalAccess`, keep re-testing rather than concluding the knob is broken.
