## Overview

Redis is a high-performance in-memory data store used as a cache, session store, message broker and queue backend. This template deploys a master-replica Redis cluster fronted by Redis Sentinel, which elects a new master automatically when the current one fails and gives clients a stable address to discover it. One `engine` knob runs both tiers on [Valkey](https://valkey.io/), the BSD-licensed fork of Redis, instead; leaving it alone changes nothing.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have. It does not create, provision or manage a GVC.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-redis` | Redis or Valkey data nodes (stateful, 3 replicas, port `6379`); replica 0 boots as the first master, the others replicate from it | — |
| Workload | `RELEASE_NAME-sentinel` | Sentinel quorum (stateful, 3 replicas, port `26379`); monitors the master and promotes a replica when it fails | — |
| Workload | `RELEASE_NAME-redis-backup` | Cron job that uploads an RDB snapshot to S3 or GCS | `backup.enabled: true` |
| Secret | `RELEASE_NAME-redis-config` | `redis.conf`, file-mounted into each Redis container | — |
| Secret | `RELEASE_NAME-sentinel-config` | `sentinel.conf`, file-mounted into each Sentinel container | — |
| Secret | `RELEASE_NAME-redis-auth-password` | Redis password | `redis.auth.password.enabled: true` |
| Secret | `RELEASE_NAME-sentinel-auth-password` | Sentinel password | `sentinel.auth.password.enabled: true` |
| Secret | `RELEASE_NAME-redis-backup-config` | Bucket and region for the backup job | `backup.enabled: true` |
| Identity | `RELEASE_NAME-redis-identity` | Redis workload identity; carries the cloud account binding when backup is enabled | — |
| Identity | `RELEASE_NAME-sentinel-identity` | Sentinel workload identity | — |
| Policy | `RELEASE_NAME-redis-policy` | `reveal` on the Redis config and password secrets | — |
| Policy | `RELEASE_NAME-sentinel-policy` | `reveal` on the Sentinel config and password secrets | — |
| Policy | `RELEASE_NAME-redis-backup-policy` | `reveal` on the backup config secret | `backup.enabled: true` |

## Prerequisites

None for a default install. Three optional features need something to exist first:

<Steps>
  <Step title="Optional: bring your own password secret">
    By default authentication is off, and `redis.auth.password` creates the password secret for you. To supply the password from a secret you manage instead, create a dictionary secret whose key matches `passwordKey` (default `password`) before installing. Use a separate secret for the Sentinel tier if you enable `sentinel.auth.fromSecret`.

    ```bash
    cpln secret create-dictionary --name SECRET_NAME \
      --entry password='YOUR-STRONG-PASSWORD'
    ```

    Set `redis.auth.fromSecret.name` (and `sentinel.auth.fromSecret.name`) to this name and `fromSecret.enabled` to `true`. See [Authentication](#authentication).

    <Warning>
    If the secret does not exist when the workload starts, the deployment wedges silently: `cpln logs` returns nothing and the workload never becomes ready. The missing secret is named only in `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-redis --gvc GVC_NAME -o yaml
    ```

    Create the secret and the deployment recovers on its own after several minutes, or run `cpln workload force-redeployment RELEASE_NAME-redis --gvc GVC_NAME` to skip the wait.
    </Warning>
  </Step>
  <Step title="Optional: public TCP access">
    Public access needs a domain you control, the Dedicated Load Balancer enabled on your GVC, and DNS records created **before** the first deploy. See [Public Access and Firewall](#public-access-and-firewall).
  </Step>
  <Step title="Optional: scheduled backups">
    Backups need an S3 or GCS bucket, a Control Plane cloud account and (on AWS) a bucket-scoped IAM policy. See [Backing Up](#backing-up).
  </Step>
</Steps>

## Configuration

### Engine

```yaml
engine: redis                     # redis | valkey — chosen at INSTALL time; an existing data directory cannot move between engines
# Used for BOTH tiers when engine is valkey; redis.image / sentinel.image are
# then ignored. Only the Debian-based tags are supported (the -alpine tags have
# no bash and this chart's probes require it).
valkeyImage: valkey/valkey:8.1.9
```

`engine: valkey` moves the Redis *and* Sentinel workloads onto `valkeyImage` together; a Redis-Sentinel / Valkey-server hybrid cannot be produced. Nothing else changes: the Valkey image ships `redis-server`, `redis-cli` and `redis-sentinel` compatibility symlinks, so every command and config directive on this page applies to both engines. Valkey reports `redis_version:7.2.4` in `INFO` for client compatibility and carries its real version in `server_name` and `valkey_version`; check that before switching if your client library gates features on `redis_version`.

<Warning>
**The engine cannot be switched on a running deployment.** Valkey does not read the data format Redis 8 writes: with persistence enabled the replaced replica crash-loops with `Can't handle RDB format version 15`, and with persistence disabled it silently starts empty. Migrate between engines with dump/restore or replication, never by changing `engine`. Setting `engine` back recovers the release.
</Warning>

### Redis

#### Image and Resources

```yaml
redis:
  image: redis:8                  # redis:7.4 remains a supported value; the upgrade from 7.4 to 8 is one-way
  resources:
    maxCpu: 200m
    maxMemory: 256Mi
    minCpu: 80m
    minMemory: 128Mi
  replicas: 3                     # one master plus (replicas - 1) read replicas
  timeoutSeconds: 15
  multiZone: false                # spread replicas across availability zones within the location
  replicaDirect: false # https://docs.controlplane.com/reference/workload/general#internal-endpoint-formatting
  serverCommand: redis-server  # correct for both engines — the Valkey image ships a redis-server symlink
  # extraArgs: "--maxclients 20000 --maxmemory 200mb --maxmemory-policy allkeys-lru"
  env: []
  tags: {}
  requestRetryPolicy: {}
  dataDir: /data
```

#### Authentication

Authentication is off by default. Enable exactly one method per tier; the chart refuses to render with both enabled. The Sentinel tier takes the same two options under `sentinel.auth`.

```yaml
redis:
  auth:
    fromSecret:
      enabled: false              # set true to read the password from a secret you created (see Prerequisites)
      name: example-redis-auth-password
      passwordKey: password
    password:
      enabled: false              # set true to have the chart create the password secret from `value`
      value: change-me-redis-password
```

<Warning>
**Do not change the password on a running cluster.** Changing `redis.auth.password.value` (or the contents of the referenced secret) stalls the rolling update: the first restarted node cannot replicate from the not-yet-restarted master, logging `Unable to AUTH to MASTER: -WRONGPASS invalid username-password pair or user is disabled.`, and its readiness probe never passes. Re-apply the previous password to recover. To change the password, uninstall and reinstall, or accept a planned outage.
</Warning>

#### Public Access and Firewall

```yaml
redis:
  publicAccess:
    enabled: false                # true creates a domain resource routing one public TCP port per replica
    address: redis-test.example-cpln.com
  firewall:
    internal_inboundAllowType: "same-gvc" # Options: same-org / same-gvc(Recommended) / workload-list
    # external_inboundAllowCIDR: 0.0.0.0/0 # Provide a comma-separated list — REQUIRED when publicAccess is enabled
    # # You can specify additional workloads with either same-gvc or workload-list:
    # inboundAllowWorkload:
    #   - //gvc/GVC_NAME/workload/WORKLOAD_NAME
    # external_outboundAllowCIDR: "0.0.0.0/0" # Provide a comma-separated list
```

Public access exposes Redis and Sentinel over the internet through a Control Plane [domain](/reference/domain) with per-replica TCP port routing. Before enabling it:

1. **Enable the Dedicated Load Balancer on your GVC** — required for arbitrary TCP port routing. It is under the GVC's settings in the console.
2. **Create the DNS records before deploying** — ownership is verified when the domain resource is first created, and the deploy fails with `Unable to apply domain` if they are missing. Disable any proxying: TCP must pass straight through.

| Type | Name | Value |
|---|---|---|
| TXT | `_cpln-SUBDOMAIN` | your Control Plane org name or org ID |
| CNAME | `SUBDOMAIN` | `GVC_ALIAS.cpln.app` (the alias is shown in the GVC's settings) |

3. **Set `external_inboundAllowCIDR`** on each tier you expose. Without it the workload's external firewall stays closed and the domain routes nowhere.

```yaml
redis:
  publicAccess:
    enabled: true
    address: redis.example.com
  firewall:
    internal_inboundAllowType: "same-gvc"
    external_inboundAllowCIDR: "0.0.0.0/0"   # or a comma-separated list of the CIDRs allowed in

sentinel:
  publicAccess:
    enabled: true
    address: redis-sentinel.example.com
  firewall:
    internal_inboundAllowType: "same-gvc"
    external_inboundAllowCIDR: "0.0.0.0/0"
```

Ports are assigned one per replica: Redis replica *N* on `6380 + N`, Sentinel replica *N* on `26380 + N`.

Firewall changes take a few minutes to take effect; re-check before concluding a rule is not working.

#### Replication and Probes

```yaml
redis:
  # Replication tuning. See secret-redis-config.yaml for how these are rendered.
  # backlogSize: sized for (peak write throughput × tolerable disconnect window).
  #   1mb (Redis default) escalates any brief disconnect to a full RDB resync. 1gb
  #   covers ~5 minutes of disconnect at ~3MB/s of writes.
  # timeout (seconds): bound on full-resync transfer + RDB load + heartbeat.
  #   60s (Redis default) is too low for multi-GB datasets — master/slave drop the
  #   link mid-sync. 300s covers ~30GB at typical 1Gbps + load throughput.
  # slaveOutputBufferLimit: "<hard> <soft> <seconds>". Default
  #   "256mb 64mb 60" can't sustain a full resync of a multi-GB dataset at high
  #   write rate — master kills the replica mid-stream. Bump for production loads.
  replication:
    backlogSize: 1gb
    timeout: 300
    slaveOutputBufferLimit: "2gb 512mb 300"
  probes:
    readiness:
      failureThreshold: 10
      initialDelaySeconds: 10  # extend if AOF load takes longer than this
      periodSeconds: 5         # also controls startup window: budget = initialDelay + 30×period
      timeoutSeconds: 4
    liveness:
      failureThreshold: 5
      initialDelaySeconds: 30
      periodSeconds: 10
      timeoutSeconds: 5
```

The readiness probe holds a replica out of rotation until it has finished syncing from the master; the liveness probe only checks that the process is up, so a replica mid-resync is never killed. The startup window is `initialDelaySeconds + 30 × periodSeconds` (160 seconds by default). With persistence enabled and a large dataset, a replica must load its AOF before it can sync, so raise `periodSeconds` to widen the window — for example `initialDelaySeconds: 35` and `periodSeconds: 20` gives 635 seconds.

#### Metrics Exporter

```yaml
redis:
  exporter:
    enabled: false    # adds a redis_exporter sidecar that exposes metrics at :9121/metrics
    image: oliver006/redis_exporter:v1.67.0-alpine
    resources:
      maxCpu: 50m
      maxMemory: 64Mi
      minCpu: 25m
      minMemory: 32Mi
    dropMetrics: []  # e.g., ["redis_command_.*", "redis_keyspace_.*"]
```

When enabled, Control Plane scrapes `:9121/metrics` on each Redis replica and the metrics appear in the console. `dropMetrics` takes regular expressions matched against metric names, for filtering high-cardinality series such as `redis_commands_latencies_usec_bucket` before they are stored. The exporter authenticates with the Redis password automatically when auth is enabled.

#### Persistence

```yaml
redis:
  persistence:
    # Set at INSTALL time. Enabling this on an already-running release stalls
    # the rollout indefinitely (volumes stay unbound) — see the README.
    enabled: false
    volumes:
      data:
        initialCapacity: 10 # In GB
        performanceClass: general-purpose-ssd # general-purpose-ssd / high-throughput-ssd (Min 1000GB)
        fileSystemType: ext4 # ext4 / xfs
        snapshots:
          retentionDuration: 7d
          schedule: 0 0 * * * # UTC
        autoscaling:
          maxCapacity: 100 # In GB
          minFreePercentage: 20
          scalingFactor: 1.2
        # customEncryption:
        #   enabled: true
        #   region: aws-us-east-1 # Replace with the appropriate region
        #   keyId: arn:aws:kms:us-east-1:1234567890:key/d411f35a-1d31-4515-9934-4f193e042d80 # Replace with your AWS KMS key ARN
```

With persistence enabled each Redis replica keeps its data in `redis.dataDir` on a [volume set](/reference/volumeset) with both AOF and RDB persistence on, so data survives restarts and redeployments. Lifecycle hooks remove orphaned temporary RDB and AOF-rewrite files on every container start and stop. Without persistence the data lives in memory and on the container's ephemeral filesystem only.

<Warning>
**Enable persistence at install time, not on a running release.** Turning `redis.persistence.enabled` or `sentinel.persistence.enabled` on for a deployment that is already running stalls the rollout indefinitely: every replica sits on `Replica N will be restarted shortly`, the volume set's volumes stay `unbound`, and a forced redeployment does not clear it. Uninstall and reinstall with persistence enabled instead. A fresh install with persistence comes up normally, and upgrading a release that already owns its volume rolls fine.
</Warning>

### Sentinel

```yaml
sentinel:
  image: redis:8
  resources:
    maxCpu: 200m
    maxMemory: 256Mi
    minCpu: 80m
    minMemory: 128Mi
  replicas: 3                     # keep it odd; quorum is a majority
  timeoutSeconds: 10
  multiZone: false
  replicaDirect: false # https://docs.controlplane.com/reference/workload/general#internal-endpoint-formatting
  quorumAutoCalculation: true  # Set to false if you want to override quorum. Quorum is (replicas/2)+1
  quorumOverride: null  # Only used if quorumAutoCalculation is false
  auth:
    fromSecret:
      enabled: false
      name: example-redis-auth-password
      passwordKey: password
    password:
      enabled: false
      value: change-me-sentinel-password
  publicAccess:
    enabled: false
    address: redis-sentinel-test.example-cpln.com
  firewall:
    internal_inboundAllowType: "same-gvc" # Options: same-org / same-gvc(Recommended)
  env: []
  tags: {}
  requestRetryPolicy: {}
  # Sentinel persistence preserves the post-failover master across restarts via
  # CONFIG REWRITE. Replicas query sentinel at startup, so persisted state lets
  # them rejoin the real master rather than redis-0. Recommended ON in prod.
  persistence:
    # Set at INSTALL time. Enabling this on an already-running release stalls
    # the rollout indefinitely (volumes stay unbound) — see the README.
    enabled: false
    volumes:
      data:
        initialCapacity: 10 # In GB
        performanceClass: general-purpose-ssd # general-purpose-ssd / high-throughput-ssd (Min 1000GB)
        fileSystemType: ext4 # ext4 / xfs
        snapshots:
          retentionDuration: 7d
          schedule: 0 0 * * * # UTC
        autoscaling:
          maxCapacity: 50 # In GB
          minFreePercentage: 20
          scalingFactor: 1.2
```

Sentinel monitors the master under the name `mymaster`, marks it down after 5 seconds without a response, and promotes a replica once a quorum of Sentinels agrees. Enable `sentinel.persistence` in production: without it, a Sentinel that restarts forgets which replica was promoted and answers from its static config (replica 0) until it re-learns the cluster.

## Connecting

| What | Address | Notes |
|---|---|---|
| Redis, inside the GVC | `RELEASE_NAME-redis.GVC_NAME.cpln.local:6379` | Resolves to any data node, so a plain connection may land on a read replica |
| Sentinel, inside the GVC | `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379` | Master name `mymaster`; Sentinel-aware clients use this and always reach the current master |
| Redis, public | the `redis.publicAccess.address` value, port `6380 + N` for replica *N* | Only with `redis.publicAccess.enabled: true` |
| Sentinel, public | the `sentinel.publicAccess.address` value, port `26380 + N` for replica *N* | Only with `sentinel.publicAccess.enabled: true` |
| Password, chart-created | `cpln secret reveal RELEASE_NAME-redis-auth-password -o yaml` | With `redis.auth.password.enabled: true`; the Sentinel password is in `RELEASE_NAME-sentinel-auth-password` |
| Password, your own secret | `cpln secret reveal SECRET_NAME -o yaml` | With `redis.auth.fromSecret.enabled: true` |

Point your client library at the Sentinel address with master name `mymaster` rather than at a specific Redis replica: the master moves during failovers and rolling upgrades, and writes sent to a replica are refused with `READONLY You can't write against a read only replica.`

To verify the cluster, ask any data node to respond and ask Sentinel which node is the master (add `-a PASSWORD` when auth is enabled):

```bash
cpln workload exec RELEASE_NAME-redis --gvc GVC_NAME --container redis -- redis-cli ping

cpln workload exec RELEASE_NAME-sentinel --gvc GVC_NAME --container sentinel -- \
  redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
```

The second command prints the current master's announced hostname and port. To confirm which engine a deployment is running, run `redis-cli INFO server` the same way: Valkey answers with `server_name:valkey` and a `valkey_version` line, Redis has neither.

With public access enabled, connect from outside with the standard client, one port per replica:

```bash
redis-cli -h redis.example.com -p 6380 ping            # Redis replica 0
redis-cli -h redis-sentinel.example.com -p 26380 ping  # Sentinel replica 0
```

## Operations

### Backing Up

Backups are off by default. When `backup.enabled` is `true`, a cron workload runs on `backup.schedule`, takes an RDB snapshot of the cluster and uploads it to your bucket as `PREFIX/redis-YYYY-MM-DDTHH-MM-SSZ.rdb.gz`. The job authenticates to the bucket through the Redis identity's cloud account binding — no static keys. Step schedules such as `*/30 * * * *` are supported.

<Note>
Switching `backup.provider` between `aws` and `gcp` on an existing release leaves the previous provider's cloud binding on `RELEASE_NAME-redis-identity`: the rendered manifest is correct, but identity updates are merged rather than replaced. If least privilege matters to you, inspect the identity in the console after a provider switch and remove the stale binding, or reinstall the release.
</Note>

#### AWS S3

1. Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.
2. [Create a cloud account](/guides/create-cloud-account) for your AWS account if you do not have one. Set `backup.aws.cloudAccountName` to its name.
3. Create an IAM policy with the following JSON, replacing `YOUR_BUCKET_NAME`, and set `backup.aws.policyName` to its name:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion",
                "s3:GetBucketLocation",
                "s3:AbortMultipartUpload",
                "s3:ListBucketMultipartUploads",
                "s3:ListMultipartUploadParts"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.prefix` to the folder path where backups will be stored, then set `backup.enabled: true` and `backup.provider: aws`.

#### GCS

1. Create a GCS bucket. Set `backup.gcp.bucket` to its name.
2. [Create a cloud account](/guides/create-cloud-account) for your GCP project if you do not have one. Set `backup.gcp.cloudAccountName` to its name.
3. Grant the **Storage Admin** role to the GCP service account associated with the cloud account.
4. Set `backup.gcp.prefix` to the folder path where backups will be stored, then set `backup.enabled: true` and `backup.provider: gcp`.

### Restoring a Backup

<Warning>
**There is no verified procedure for restoring one of these snapshots into a running release of this template.** Two things that look like they should work do not:

- Copying the file into the data directory as `dump.rdb` and restarting does nothing. The chart runs with `appendonly yes`, and when both AOF and RDB persistence are enabled Redis rebuilds the dataset from the AOF at startup and ignores `dump.rdb`.
- `redis-cli --rdb FILE` *downloads* an RDB from a server; it does not load one. Running it against the cluster overwrites your downloaded backup with the live dataset.
</Warning>

What the backup is: a standard, gzipped RDB file, and RDB files are portable. The upstream-documented way to read one is to start a standalone Redis or Valkey server with AOF disabled and the decompressed file in place as its `dump.rdb` (or, on Redis 8.10 and later, with `preload-file rdb:/path/to/file.rdb`), for example on a local machine with Docker. From there you can inspect the data or replay it into your cluster with your own tooling. Loading the file into this template's cluster in place has not been tested; if you need that path, test it against a throwaway release before relying on it.

If you enabled `redis.persistence`, the volume set also takes its own scheduled snapshots on `redis.persistence.volumes.data.snapshots.schedule`; those are managed through the volume set, independently of the bucket backups.

### Upgrading from an Earlier Version

- **From 3.5.1 or earlier — resource keys were renamed.** Blocks that expose both a reservation and a limit now name the limit `maxCpu` / `maxMemory` instead of `cpu` / `memory`: `redis.resources`, `sentinel.resources` and `redis.exporter.resources`. Rename them in your values before upgrading; an upgrade that still carries the old names is refused at render with `redis.resources.cpu was RENAMED to redis.resources.maxCpu`. `backup.resources`, which exposes only a limit, keeps bare `cpu` / `memory`.
- **From 3.5.0 or earlier with AWS backups — permissions narrowed.** Version 3.5.1 removed the AWS managed policy `ReadOnlyAccess` from the backup identity. It granted read access to every bucket in your account and had been silently supplying any read action your own policy omitted. Update your IAM policy to the full action list under [Backing Up](#backing-up) before upgrading; if it already matches, nothing changes.
- **From 3.4.x — Redis 7.4 to Redis 8 is one-way.** Version 3.5.0 moved the default image to `redis:8`. Redis 8 reads 7.4 data directly, so an upgrade with persistence enabled keeps your data, but once a node has written under Redis 8 a 7.4 image can no longer load it. Snapshot the volume set first if you want a rollback path, or pin `redis.image` and `sentinel.image` to `redis:7.4`.

A rolling upgrade replaces replicas one at a time. The master is replaced along the way, which triggers a Sentinel failover; clients that discover the master through Sentinel follow it, clients pinned to replica 0 start receiving `READONLY` errors.

### Scaling and Availability

- The default shape is already highly available: three data nodes (one master, two replicas) and three Sentinels with a quorum of two. Change `redis.replicas` and `sentinel.replicas` to resize either tier; keep the Sentinel count odd. A `1` + `1` shape is a valid development size with no failover.
- When the master stops responding, Sentinel marks it down after 5 seconds, elects a replica and repoints the remaining replicas at it. The old master rejoins as a replica when it comes back. Writes pause for the duration of the failover; reads from replicas continue.
- Write capacity is that of a single node: replicas take reads only. For more memory or throughput, raise `redis.resources` and `redis.persistence.volumes.data` rather than adding replicas.
- Enable `sentinel.persistence` so the elected master survives Sentinel restarts, and `redis.persistence` so data survives Redis restarts. Both are install-time choices.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Rollout stalls on `Replica N will be restarted shortly` after enabling persistence">
    **Symptom:** after a `cpln helm upgrade` that turned `redis.persistence.enabled` or `sentinel.persistence.enabled` on, every replica reports `Replica N will be restarted shortly` indefinitely and the volume set's volumes stay `unbound`.

    **Cause:** a volume set cannot be attached to a release that is already running.

    **Fix:** uninstall the release and reinstall it with persistence enabled from the start. Data in a release without persistence lives in memory only, so take a backup first if it matters.
  </Accordion>
  <Accordion title="`Unable to AUTH to MASTER: -WRONGPASS invalid username-password pair or user is disabled.`">
    **Symptom:** after changing the Redis password, the rollout stops at the first restarted node, which logs this line and never becomes ready.

    **Cause:** the restarted node uses the new password; the master it must replicate from still runs with the old one.

    **Fix:** run `cpln helm upgrade` again with the previous password to recover. To change the password, uninstall and reinstall, or accept a planned outage.
  </Accordion>
  <Accordion title="`READONLY You can't write against a read only replica.`">
    **Symptom:** writes that used to succeed are refused after a failover or a rolling upgrade.

    **Cause:** the client is connected to a fixed Redis replica that is no longer the master.

    **Fix:** configure the client for Sentinel at `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379` with master name `mymaster`, so it follows the master.
  </Accordion>
  <Accordion title="`Can't handle RDB format version 15` after changing `engine`">
    **Symptom:** the first replaced replica exits with `# Can't handle RDB format version 15` / `# Error reading the RDB base file appendonly.aof.1.base.rdb, AOF loading aborted` and crash-loops.

    **Cause:** `engine` was changed to `valkey` on a release whose data directory was written by Redis 8, which Valkey cannot read.

    **Fix:** set `engine` back to `redis` and upgrade; the rollout halts on the unhealthy replica, so the remaining nodes keep serving throughout. Migrate between engines with dump/restore or replication.
  </Accordion>
  <Accordion title="Deployment never becomes ready after enabling `auth.fromSecret`">
    **Symptom:** the workload never reaches ready and `cpln logs` returns nothing at all.

    **Cause:** the secret named in `redis.auth.fromSecret.name` or `sentinel.auth.fromSecret.name` does not exist, so the container never starts.

    **Fix:** read the missing secret's name from `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-redis --gvc GVC_NAME -o yaml
    ```

    Create it as shown under [Prerequisites](#prerequisites). The deployment recovers on its own after several minutes, or run `cpln workload force-redeployment RELEASE_NAME-redis --gvc GVC_NAME` to skip the wait.
  </Accordion>
  <Accordion title="`Unable to apply domain` when installing with public access">
    **Symptom:** the install fails while creating the domain resource for `redis.publicAccess.address` or `sentinel.publicAccess.address`.

    **Cause:** domain ownership is verified when the resource is first created, and the TXT or CNAME record is missing.

    **Fix:** create the records listed under [Public Access and Firewall](#public-access-and-firewall) with proxying disabled, wait for DNS to propagate, then install again.
  </Accordion>
  <Accordion title="Render fails with `redis.resources.cpu was RENAMED to redis.resources.maxCpu`">
    **Symptom:** `cpln helm install` or `cpln helm upgrade` refuses to render and prints this message (or the `memory`, `sentinel` or `exporter` variant).

    **Cause:** your values file still uses the pre-3.6.0 key names.

    **Fix:** rename `cpu` to `maxCpu` and `memory` to `maxMemory` under `redis.resources`, `sentinel.resources` and `redis.exporter.resources`.
  </Accordion>
  <Accordion title="Clients can still connect after tightening the firewall">
    **Symptom:** after changing `internal_inboundAllowType` or `inboundAllowWorkload`, previously allowed clients keep connecting.

    **Cause:** firewall changes take a few minutes to propagate.

    **Fix:** wait and re-test before concluding the rule is not applied.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Choose `engine` at install time.** Switching it on a running release does not migrate anything; Valkey cannot read data written by Redis 8.
- **Choose persistence at install time.** Enabling `redis.persistence` or `sentinel.persistence` on a running release stalls the rollout indefinitely; uninstall and reinstall instead.
- **Never change the password in place.** It deadlocks the rolling update; re-apply the previous password to recover and reinstall to change it.
- **Always discover the master through Sentinel** (`mymaster` at `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379`). A client pinned to replica 0 gets `READONLY` errors after any failover or upgrade.
- **Enable `sentinel.persistence` in production** so the elected master survives Sentinel restarts.
- **The Redis 7.4 to 8 upgrade is one-way.** Snapshot the volume set before upgrading if you need a rollback path.
- **Public access needs the DNS records in place before the first deploy and `external_inboundAllowCIDR` uncommented**, or the domain is rejected or routes nowhere.
- **Bucket backups have no verified in-place restore.** Treat them as portable RDB files; see [Restoring a Backup](#restoring-a-backup).
