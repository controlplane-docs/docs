## Overview

Umami is a privacy-first, cookieless web and product analytics platform — a self-hosted, MIT-licensed alternative to Google Analytics. This template deploys the stateless Umami v3 app tier backed by a bundled PostgreSQL store, serving the analytics dashboard and the tracking endpoint on the same port. You embed a small tracking script on your site; visitor events are posted back to the same workload and stored in PostgreSQL, with no cookies and no personal data collected.

The install starts **private**: Umami seeds a hardcoded `admin` / `umami` account that no setting can override, so `publicAccess.enabled` defaults to `false` and you publish the install only after changing that password. Tracking collects nothing until you do — follow [First Run](#first-run).

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have — it does not create or manage a GVC. Every workload below runs in each location of that GVC.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-umami` | Umami dashboard, API and tracking endpoint (standard, 1 replica by default, HTTP port `3000`, private by default) | — |
| Workload | `RELEASE_NAME-postgres` | Single-instance PostgreSQL store (stateful, 1 replica, port `5432`) | Default; `postgres.enabled: true` |
| Workload | `RELEASE_NAME-postgres-backup` | Scheduled logical backup of the single-instance store (cron) | `postgres.backup.enabled: true` |
| Workload | `RELEASE_NAME-postgres-ha` | Patroni PostgreSQL store (stateful, 3 replicas) | `postgresHA.enabled: true` |
| Workload | `RELEASE_NAME-postgres-ha-proxy` | HAProxy leader endpoint Umami connects through (standard, port `5432`) | `postgresHA.enabled: true` |
| Workload | `RELEASE_NAME-etcd` | Consensus store for the highly available database (stateful, 3 replicas) | `postgresHA.enabled: true` |
| Workload | `RELEASE_NAME-postgres-ha-backup` | Scheduled logical backup of the highly available store (cron) | `postgresHA.backup.enabled: true` with `mode: logical` |
| Volume set | `RELEASE_NAME-pg-vs` | Single-instance database data (10 GiB by default; takes no scheduled snapshots; a final snapshot is taken when the volume set is deleted and kept 7 days) | Default; `postgres.enabled: true` |
| Volume set | `RELEASE_NAME-postgres-ha-vs`, `RELEASE_NAME-etcd-vs` | Highly available database and consensus-store data (10 GiB per replica by default) | `postgresHA.enabled: true` |
| Secret | `RELEASE_NAME-etcd-startup`, `RELEASE_NAME-patroni-startup`, `RELEASE_NAME-postgres-proxy-startup`, `RELEASE_NAME-wal-g-backup-script` | Startup scripts of the highly available database tier | `postgresHA.enabled: true` |
| Secret | `RELEASE_NAME-postgres-config` | Non-sensitive backup settings of the highly available database | `postgresHA.backup.enabled: true` |
| Identity / Policy | `RELEASE_NAME-umami-identity`, `RELEASE_NAME-umami-policy` | `reveal` on exactly two secrets: your app secret and the database credentials secret | — |
| Identity / Policy | `RELEASE_NAME-pg-identity`, `RELEASE_NAME-pg-policy` | The single-instance database's own identity and policy | Default; `postgres.enabled: true` |
| Identity / Policy | `RELEASE_NAME-postgres-ha-identity`, `RELEASE_NAME-postgres-ha-policy`, `RELEASE_NAME-etcd-identity`, `RELEASE_NAME-etcd-policy` | The highly available database tier's own identities and policies | `postgresHA.enabled: true` |

Umami itself has no volume set — every user, website, session and event lives in PostgreSQL. The app secret and the database credentials secret are **prerequisite secrets you create yourself**; the chart references them by name and never creates, modifies or deletes them.

## Prerequisites

Two secrets must exist before you install: an [opaque secret](/guides/create-secret/opaque) for the app secret and a [dictionary secret](/guides/create-secret/dictionary) for the database credentials. They hold credentials, so they are prerequisite secrets rather than values — a value would sit in plaintext in the Helm release for the life of the install. Secrets are org-level, so no `--gvc` flag is involved.

<Steps>
  <Step title="Create the app secret">
    The app secret signs Umami's auth tokens and sessions — anyone holding it can forge a login — so it is never a Helm value and never lands in the release. Generate a random value and store it as the secret's payload:

    ```bash
    printf '%s' "$(openssl rand -base64 32)" | cpln secret create-opaque --name APP_SECRET_NAME --encoding plain -f -
    ```

    Keep it for the life of the install: changing it logs every user out. Set `app.appSecretName` to this name.
  </Step>
  <Step title="Create the database credentials secret">
    The bundled PostgreSQL initializes with these values and Umami connects with them, in **both** database modes:

    ```bash
    cpln secret create-dictionary --name my-umami-db-credentials \
      --entry username=umami \
      --entry password="$(openssl rand -hex 24)" \
      --entry database=umami
    ```

    Set its name in the key of the store you use: `postgres.config.credentialsSecretName` (single-instance, the default) or `postgresHA.config.credentialsSecretName` (HA). Umami builds its connection URL from the three keys, so keep them URL-safe (letters, digits, `-`, `_`). PostgreSQL reads the secret only when its data is first initialized — see [Rotating the Database Password](#rotating-the-database-password).
  </Step>
</Steps>

<Warning>
**A missing app secret or database credentials secret wedges the install rather than failing it.** `cpln helm install` reports success and every resource is created, but the Umami container never starts — so `cpln logs` returns **zero lines**. The only place the missing secret is named is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-umami --gvc GVC_NAME -o yaml
```

The message reads `The secret <name> no longer exists. Workload updates are paused until the secret is added or the reference to the secret removed.` It is `get-deployments` — plain `cpln workload get` has no `versions` key. Create the missing secret and the deployment recovers on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-umami --gvc GVC_NAME` to skip the wait.
</Warning>

Optional, for two-factor authentication (`app.twoFactorKeySecretName`, opaque): a 64-character hex key that encrypts users' TOTP secrets. Without it, two-factor setup in **Settings** reports that 2FA is not configured:

```bash
printf '%s' "$(openssl rand -hex 32)" | cpln secret create-opaque --name my-umami-2fa-key --encoding plain -f -
```

Keep it for the life of the install. Changing or removing it locks every enrolled user, admin included, out of their account until the same key is restored.

Optional database backups need a bucket and access setup on AWS S3, Google Cloud Storage or an S3-compatible server, and S3-compatible servers additionally need a dictionary secret with the bucket keys — see [Backing Up](#backing-up).

## Installation

Once both secrets exist, install the template into your GVC, naming them:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/umami \
  --version 1.5.0 --gvc GVC_NAME \
  --set app.appSecretName=APP_SECRET_NAME \
  --set postgres.config.credentialsSecretName=my-umami-db-credentials
```

Keep these settings in a values file (`--values`) rather than `--set`, because every later upgrade must pass them again. If you run more than one release of this template in the same org, create a separate database credentials secret for each — see [Backing Store](#backing-store).

## Configuration

### Application

```yaml
image: ghcr.io/umami-software/umami:3.4.1 # versions before 3.4.1 are refused (Critical CVEs)

replicas: 1 # 1 = single instance; 2+ = always-on tier with zero-downtime rolling restarts

resources: # per replica
  minCpu: 100m
  maxCpu: 500m
  minMemory: 256Mi
  maxMemory: 512Mi

app:
  # Opaque secret (encoding: plain) holding the app secret, which signs auth tokens
  # and sessions. MUST EXIST BEFORE INSTALL; its value must stay stable.
  appSecretName: my-umami-app-secret
  disableTelemetry: true # opt out of Umami's anonymous usage telemetry
  twoFactorKeySecretName: "" # optional opaque secret holding the two-factor key; "" = 2FA unavailable
```

Replicas are independent — they share only the database and the app secret, so a session opened against one replica is honored by the others.

### Tracker

```yaml
tracker:
  scriptName: ""      # custom tracker script path, e.g. "s.js" (dodges ad blockers); "" = default /script.js; not "recorder.js" (Umami's session-replay script)
  collectEndpoint: "" # custom collect API path, e.g. "/api/track"; "" = default /api/send
```

Custom paths are **aliases, not replacements**: the default `/script.js` and `/api/send` keep working. They help because your site loads a path ad blockers do not recognise. The custom collect path is baked into the script Umami serves, so the snippet you embed picks it up automatically.

### Backing Store

Enable exactly one of the two stores — the chart refuses to render with both or neither. Umami is wired to whichever is active.

```yaml
postgres: # default: single-instance PostgreSQL — set postgresHA.enabled: true (and this false) for failover
  enabled: true
  image: postgres:18
  config:
    # REQUIRED PREREQUISITE SECRET (single-instance mode) — CREATE IT BEFORE YOU
    # INSTALL. If it does not exist the deployment WEDGES silently and looks like a
    # platform fault. A `dictionary` secret holding exactly three keys: username,
    # password, database. PostgreSQL reads it once, when its data is first
    # initialized, and Umami connects with the same keys. See Prerequisites.
    credentialsSecretName: my-umami-db-credentials
  resources:
    minCpu: 250m
    maxCpu: 1
    minMemory: 512Mi
    maxMemory: 1Gi
  volumeset:
    capacity: 10 # initial capacity in GiB (minimum is 10)

postgresHA: # durable HA: 3-replica Patroni store with an HAProxy leader endpoint
  enabled: false
  config:
    # REQUIRED PREREQUISITE SECRET (HA mode) — the same kind of `dictionary`
    # secret as postgres.config.credentialsSecretName above (keys: username,
    # password, database). Create it BEFORE you install.
    credentialsSecretName: my-umami-db-credentials
  replicas: 3
  image: controlplanecorporation/patroni-postgres:0.8 # pgvector 0.8.7 (CVE-2026-103484); tags 0.1-0.7 are refused
  volumeset:
    capacity: 10 # initial capacity in GiB per replica (minimum is 10)
```

#### Choosing a Database Mode

| | `postgres` (default) | `postgresHA` |
|---|---|---|
| What runs | One single-replica PostgreSQL workload | 3 Patroni PostgreSQL replicas, 3 etcd replicas, an HAProxy leader endpoint |
| Database failover | None — a failed node is rescheduled onto the same volume | Automatic leader election |
| Best for | Most installs — analytics can tolerate a few minutes of downtime | Installs where the dashboard and collection must stay up through a database failure |

To use HA mode on a **new** install, set `postgres.enabled: false` and `postgresHA.enabled: true`. The credentials come from your prerequisite database credentials secret in both modes, named by `postgresHA.config.credentialsSecretName` in HA mode. Switching an existing release between modes does not move data — the other store starts empty.

Secret names are org-wide, so if you run more than one release of this template in the same org, create a separate database credentials secret for each and point each release's `postgres.config.credentialsSecretName` (or `postgresHA.config.credentialsSecretName` in HA mode) at its own.

Database backups are configured under `postgres.backup` / `postgresHA.backup` — see [Backing Up](#backing-up).

### Access

```yaml
publicAccess:
  # false = nothing reaches Umami from the internet. Change the hardcoded admin
  # password first, then set this true — tracking needs it.
  enabled: false

internalAccess:
  type: same-gvc # options: none, same-gvc, same-org, workload-list
  workloads: []  # only used when type is same-gvc or workload-list
```

| `internalAccess.type` | Who inside Control Plane can reach Umami |
|---|---|
| `none` | No workload |
| `same-gvc` | Every workload in the same GVC (default) |
| `same-org` | Every workload in the org |
| `workload-list` | Only the workloads listed in `internalAccess.workloads` |

**Tracking collects nothing while `publicAccess.enabled` is `false`** — browsers on the sites you track must reach the tracking script and the collect endpoint. Turn it on once the admin password is changed. An access change takes a few minutes to take effect, so re-test rather than trusting the first response.

## Connecting

| What | Address | Notes |
|---|---|---|
| Dashboard (public) | `status.canonicalEndpoint` of `RELEASE_NAME-umami`, then `/login` | `cpln workload get RELEASE_NAME-umami --gvc GVC_NAME -o yaml`; present while `publicAccess.enabled` is `true` |
| Tracking script | `https://CANONICAL_ENDPOINT/script.js` (or your `tracker.scriptName`) | Must be the **public** address — the browsers of your visitors load it |
| Collect endpoint | `https://CANONICAL_ENDPOINT/api/send` (or your `tracker.collectEndpoint`) | Where the tracker posts events; public for the same reason |
| Dashboard (private) | `http://localhost:3000` through `cpln port-forward` | Works with public access off — see the command below |
| Internal | `http://RELEASE_NAME-umami.GVC_NAME.cpln.local:3000` | Reachable per `internalAccess.type`; for server-side event tracking from your own workloads |
| Admin login | `admin` / `umami` until you change it | Hardcoded by Umami — change it before publishing, see [First Run](#first-run) |
| Database credentials | Your prerequisite secret, named by `postgres.config.credentialsSecretName` (HA mode: `postgresHA.config.credentialsSecretName`) | `cpln secret reveal DB_CREDENTIALS_SECRET_NAME -o yaml`; keys `username`, `password`, `database` |

`CANONICAL_ENDPOINT` is the host of `status.canonicalEndpoint`. Open a tunnel to the dashboard from your machine — this works whether or not public access is on:

```bash
cpln port-forward RELEASE_NAME-umami 3000:3000 --gvc GVC_NAME
```

Then confirm the app answers with `curl -sS http://localhost:3000/api/heartbeat`. The heartbeat does not touch the database, so a `200` there proves only that the app tier is up; loading the dashboard is the check that the database is reachable too.

### First Run

Umami's bootstrap admin is a hardcoded `admin` / `umami`, seeded by its first database migration and published in Umami's own documentation. The install therefore starts private, and you publish it once the password is changed.

<Steps>
  <Step title="Install with public access off">
    Install as shown in [Installation](#installation), leaving `publicAccess.enabled` at its default `false`. Wait until the workload reports ready:

    ```bash
    cpln workload get-deployments RELEASE_NAME-umami --gvc GVC_NAME -o yaml
    ```
  </Step>
  <Step title="Open the dashboard through a tunnel">
    ```bash
    cpln port-forward RELEASE_NAME-umami 3000:3000 --gvc GVC_NAME
    ```

    `cpln port-forward` is a top-level command, not a subcommand of `cpln workload`. Open `http://localhost:3000/login` in a browser and sign in as `admin` / `umami`.
  </Step>
  <Step title="Change the admin password">
    In the dashboard, open **Settings → Profile** and change the password. From then on the old password is rejected.
  </Step>
  <Step title="Publish the dashboard and tracking endpoint">
    Upgrade the release with `publicAccess.enabled=true`, passing the **same** app secret and database credentials secret names you installed with (or the same values file):

    ```bash
    cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/umami \
      --version 1.5.0 --gvc GVC_NAME \
      --set app.appSecretName=APP_SECRET_NAME \
      --set postgres.config.credentialsSecretName=my-umami-db-credentials \
      --set publicAccess.enabled=true
    ```

    Upgrading through the marketplace UI is the alternative. Allow a few minutes for public access to take effect, then read the endpoint with `cpln workload get RELEASE_NAME-umami --gvc GVC_NAME -o yaml`.
  </Step>
  <Step title="Add your website and embed the tracker">
    In the dashboard, add a website, then paste the generated `<script>` tag into the HTML of your site. It loads the tracking script from the public address and posts events to the collect endpoint.
  </Step>
</Steps>

<Warning>
**The publishing upgrade is the first upgrade after the install, and it can restart the bundled database** even though no database value changed. Expect Umami to be briefly unreachable while the database comes back; this is not a failed upgrade — do not roll back. Confirm recovery by loading the dashboard rather than by `/api/heartbeat`, which answers even while the database is down.
</Warning>

## Operations

### Backing Up

Database backups are optional and disabled by default. They cover everything that makes up your Umami instance — users, websites, sessions and events. They are a pass-through to the bundled database template, which runs the backup as a scheduled job; enable them on whichever store is active and complete the storage setup for your provider **before** installing or upgrading with them on.

Single-instance mode:

```yaml
postgres:
  backup:
    enabled: false
    image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0 # 18.1.0 = PG18, 17.1.0 = PG17
    schedule: "0 2 * * *"  # daily at 2am UTC
    resources:
      cpu: 100m
      memory: 128Mi
    provider: aws          # aws, gcp, or minio
    aws:
      bucket: my-backup-bucket
      region: us-east-1
      cloudAccountName: my-backup-cloudaccount
      policyName: my-backup-policy
      prefix: umami/backups
    gcp:
      bucket: my-backup-bucket
      cloudAccountName: my-backup-cloudaccount
      prefix: umami/backups
    minio:                 # any S3-compatible endpoint (e.g. an internal MinIO template)
      endpoint: http://my-minio-workload:9000
      bucket: my-backup-bucket
      credentialsSecretName: my-umami-minio-credentials # prerequisite dictionary secret, minio only
      prefix: umami/backups
```

HA mode — the same providers, plus a choice of backup mode:

```yaml
postgresHA:
  backup:
    enabled: false
    mode: logical          # logical or wal-g
    resources:
      cpu: 100m
      memory: 128Mi
    logical:
      image: ghcr.io/controlplane-com/backup-images/postgres-backup:17.1.0
      schedule: "0 2 * * *" # daily at 2am UTC
    walg:
      intervalSeconds: 21600 # every 6 hours
    provider: aws          # aws, gcp, or minio
    aws:
      bucket: my-backup-bucket
      region: us-east-1
      cloudAccountName: my-backup-cloudaccount
      policyName: my-backup-policy
      prefix: umami/backups
    gcp:
      bucket: my-backup-bucket
      cloudAccountName: my-backup-cloudaccount
      prefix: umami/backups
    minio:
      endpoint: http://my-minio-workload:9000
      bucket: my-backup-bucket
      credentialsSecretName: my-umami-minio-credentials # prerequisite dictionary secret, minio only
      prefix: umami/backups
```

        If you do not have one, [create a cloud account](/guides/create-cloud-account) for your GCP project and grant its service account **Storage Object Admin** (`roles/storage.objectAdmin`) on the bucket. Set `backup.gcp.cloudAccountName` to its name.
      </Step>
    </Steps>
  </Tab>
  <Tab title="S3-compatible (MinIO)">
    <Steps>
      <Step title="Create a bucket">
        Create the bucket on your server. Set `backup.minio.bucket` to its name and `backup.minio.endpoint` to the S3 API address including the port. No cloud account is required.
      </Step>
      <Step title="Create the credentials secret">
        A [dictionary secret](/guides/create-secret/dictionary) holding the keys `accessKey` and `secretKey`. It must exist before you install or upgrade with backups on:

        ```bash
        cpln secret create-dictionary --name MINIO_SECRET_NAME \
          --entry accessKey=MINIO_ACCESS_KEY \
          --entry secretKey='MINIO_SECRET_KEY'
        ```

        Set `backup.minio.credentialsSecretName` on the active store to this name.
      </Step>
    </Steps>
  </Tab>
</Tabs>

### Restoring a Backup

<Note>
No restore path has been rehearsed against this template. A restore goes into the **database**, not into Umami, and follows the bundled database template — rehearse it against a scratch release before you depend on it. Restoring from a volume set snapshot is likewise unverified here.
</Note>

Use the procedure on the [postgres](/template-catalog/templates/postgres#restoring-a-backup) page in single-instance mode, or the [postgres-highly-available](/template-catalog/templates/postgres-highly-available#restoring-a-backup) page in HA mode, with these Umami-specific values:

- The database workload is `RELEASE_NAME-postgres` (single-instance) or `RELEASE_NAME-postgres-ha-proxy` (HA mode — always go through the leader endpoint).
- The username, password and database name are the keys of the credentials secret: `cpln secret reveal DB_CREDENTIALS_SECRET_NAME -o yaml`.
- The Umami container has neither `psql` nor a cloud CLI, so run the restore from a client that can reach both the bucket and the database — your own machine with a `cpln port-forward` to the database workload open, for example.
- Restore into an empty database and keep Umami from writing until the replay has finished; replaying into a database Umami has already migrated collides with the existing schema.

The restored data carries its own users, so after a restore you sign in with the passwords stored in the backup, not `admin` / `umami`.

### Upgrading From 1.0.0

Version 1.0.0 did not compact the etcd cluster inside the bundled highly available database, so etcd's backend grows with time alone and goes read-only once it reaches its quota — taking PostgreSQL failover with it. Only installs running the HA database are affected (`postgresHA.enabled`). Upgrading to 1.0.1 or later turns compaction on: that stops further growth but cannot shrink a backend that has already grown, and a cluster that has already raised a `NOSPACE` alarm needs operator recovery rather than an upgrade. See [etcd History Compaction](/template-catalog/templates/postgres-highly-available#etcd-history-compaction).

### Upgrading From 1.0.1

Version 1.1.0 is a security release that renames three values. Carrying a 1.0.1 values file forward **fails at render** with a message naming the replacement, so nothing silently reverts to a default:

| 1.0.1 | 1.1.0 and later | Why |
|---|---|---|
| `app.appSecret` | `app.appSecretName` | The app secret is now a prerequisite opaque secret you create — see [Prerequisites](#prerequisites). Put the **same** value you used before into the new secret, or every user is logged out |
| `resources.cpu` | `resources.maxCpu` | The block exposes both a reservation and a limit |
| `resources.memory` | `resources.maxMemory` | Same |

`publicAccess.enabled` also changed its default to `false`. An upgrade that does not set it explicitly makes the install private and **stops data collection** — pass `publicAccess.enabled=true` once the admin password is changed.

### Upgrading From 1.1.0

Version 1.2.0 moved the single-instance database credentials. Carrying the old keys forward fails at render:

| 1.1.0 | 1.2.0 and later |
|---|---|
| `postgres.config.username`, `postgres.config.password`, `postgres.config.database` | The `username`, `password` and `database` keys of the database credentials secret, named by `postgres.config.credentialsSecretName` |
| `postgres.backup.minio.accessKey`, `postgres.backup.minio.secretKey` | A dictionary secret holding `accessKey` and `secretKey`, named by `postgres.backup.minio.credentialsSecretName` |

Put the values your single-instance database was initialized with into the database credentials secret under [Prerequisites](#prerequisites), set `postgres.config.credentialsSecretName` to its name, and remove the three keys. The error message comes from the bundled database (`config.username was REMOVED in postgres 3.4.0`). The MinIO keys are a prerequisite secret too: create it as shown in [Backing Up](#backing-up).

### Upgrading From 1.2.0

Version 1.3.0 removed the HA database credentials block. Carrying the old block forward fails at render with `the postgres block was REMOVED in 2.5.0`.

Put the `username`, `password` and `database` values that sat in a `postgres` block under `postgresHA` **unchanged** into the database credentials secret under [Prerequisites](#prerequisites) — the HA database was initialized with them — set `postgresHA.config.credentialsSecretName` to its name, and delete the block. Take a backup before upgrading. Single-instance installs need no action.

### Upgrading From 1.3.0

Version 1.3.1 moved the HA database's MinIO backup keys into a prerequisite secret. With HA-mode MinIO backups on, the old `accessKey` and `secretKey` values under `postgresHA.backup.minio` now fail at render: create a dictionary secret holding `accessKey` and `secretKey` as shown in [Backing Up](#backing-up) and set `postgresHA.backup.minio.credentialsSecretName` to its name. No other install needs action.

### Upgrading From 1.3.1

Version 1.4.0 removed `postgres.credentials`: the database credentials are now a prerequisite secret, the same one the database templates require on their own. Carrying the old key forward fails the render.

1.3.x created the database secret itself, so **this upgrade deletes it**. Before upgrading, create a secret under a **new** name holding the values your database was initialized with — not new ones, or Umami loses its database connection. `OLD_SECRET_NAME` is the `credentialsSecretName` of the mode you use (default `my-umami-db-credentials`):

```bash
cpln secret reveal OLD_SECRET_NAME -o yaml   # the CURRENT values, until the upgrade deletes this secret
cpln secret create-dictionary --name RELEASE_NAME-postgres-credentials \
  --entry username='YOUR_CURRENT_USERNAME' --entry password='YOUR_CURRENT_PASSWORD' --entry database='YOUR_CURRENT_DATABASE'
```

Then upgrade with `postgres.config.credentialsSecretName` (single-instance mode) or `postgresHA.config.credentialsSecretName` (HA mode) set to that name, and `postgres.credentials` removed. Your current values are also in `postgres.credentials` of the 1.3.x release.

The upgrade restarts the bundled PostgreSQL too (it now reads the new secret), so Umami briefly loses its database and reconnects by itself. The new version of a workload can also wait for several minutes, with `get-deployments` reporting that it is not allowed to reveal the secret, while access to the new secret propagates; the previous version keeps serving meanwhile, and it clears by itself.

### Upgrading From 1.4.0

The image moves from Umami 3.2.0 to 3.4.1, which fixes Critical vulnerabilities in its bundled Next.js. The chart refuses any `ghcr.io/umami-software/umami` tag below 3.4.1, so if your values pin `image`, set it to `ghcr.io/umami-software/umami:3.4.1` or remove it.

Umami migrates its database on first start (two-factor, session linking, annotations, API keys). Rolling back to `1.4.0` afterwards is not supported, so take a backup first if you need a way back.

Two-factor authentication (new in Umami 3.3) needs the optional key secret described under [Prerequisites](#prerequisites). If you add it in the same upgrade, the new version can wait several minutes with `is not allowed to reveal the secret` in `get-deployments` while the new grant propagates; the previous version keeps serving.

In HA mode (`postgresHA`) the database moves to `controlplanecorporation/patroni-postgres:0.8`, which carries pgvector 0.8.7. The database members restart and nothing limits that rollout, so expect a brief interruption of writes while the leader changes; Umami itself restarts as on any upgrade, and with a single Umami replica (the default) that is the longer interruption, because the old replica stops before the new one serves. Upgrade in a quiet window. Umami does not use the `vector` extension; if you created it yourself in a database, run this there after the upgrade. If your values set `postgresHA.image`, set it to the `0.8` tag: tags `0.1` to `0.7` are refused at render.

```sql
ALTER EXTENSION vector UPDATE;
```

### Rotating the Database Password

PostgreSQL keeps the password it was initialized with, and a running workload keeps the values it started with, so a rotation takes three steps in order (single-instance; in HA mode follow [Rotating the Database Password in HA Mode](#rotating-the-database-password-in-ha-mode) instead):

1. Change it in the database: `ALTER ROLE DB_USERNAME PASSWORD 'NEW_PASSWORD';` (connected as that user, from inside the GVC).
2. Update the secret: `cpln secret edit SECRET_NAME`.
3. Right away, redeploy Umami with `cpln workload force-redeployment RELEASE_NAME-umami --gvc GVC_NAME`, and wait until `get-deployments` shows a higher version number, alone and ready (right after the command the status may not show the restart yet, and `ready: true` alone can still describe the old replica). Do not redeploy the database: PostgreSQL reads the secret only when it is first initialized, so restarting it only adds downtime.

Umami keeps serving on the database connections it already has open, so logins fail only briefly while its replica is swapped. Do step 3 right away: if those connections drop before Umami restarts, it cannot open new ones.

### Rotating the Database Password in HA Mode

The HA database (`postgresHA`) needs its own order. The replication role `repl` shares the password, and a member that restarts with the old password can be promoted to leader, which splits the cluster. Move the leader to member `-0` first, so it restarts last, after every other member already has the new password. `pgx` runs a command in one member (`LOCATION` is your GVC's location, `DB_USERNAME` the secret's `username`):

```bash
pgx() { cpln workload exec RELEASE_NAME-postgres-ha --gvc GVC_NAME --location LOCATION \
  --container patroni-postgres --replica "RELEASE_NAME-postgres-ha-$1" -- "${@:2}"; }
# 1. Find the leader ("role": "leader"); the other two must be "streaming" on the same "timeline"
pgx 0 curl -s localhost:8008/cluster
# 2. If the leader is not RELEASE_NAME-postgres-ha-0, move it there (N = current leader), then repeat step 1
pgx 0 curl -s -XPOST -d '{"leader":"RELEASE_NAME-postgres-ha-N","candidate":"RELEASE_NAME-postgres-ha-0"}' localhost:8008/switchover
# 3-5. Back to back: change BOTH roles on -0, put the same password in the secret, restart the members
pgx 0 psql -h 127.0.0.1 -d postgres -c "ALTER ROLE DB_USERNAME PASSWORD 'NEW_PASSWORD'; ALTER ROLE repl PASSWORD 'NEW_PASSWORD';"
cpln secret edit SECRET_NAME
cpln workload force-redeployment RELEASE_NAME-postgres-ha --gvc GVC_NAME
# 6. Once the members have restarted, confirm one leader and two "streaming" replicas on one timeline (repeat step 1)
# 7. Optional: remove the install-time password Patroni keeps in its cluster config
pgx 0 curl -s -XPATCH -d '{"postgresql":{"authentication":null}}' localhost:8008/config
```

Then force-redeploy `RELEASE_NAME-umami`, which keeps the old password until it restarts. The database drops connections briefly at each switchover, and the app cannot open new connections from the `ALTER ROLE` until its own redeploy finishes, so rotate in a quiet window. If a member stays `starting`, or `running` without `streaming` for several minutes, re-copy it from the leader. This copies the whole database, so it costs network traffic in proportion to its size:

```bash
pgx N curl -s -XPOST -d '{"force": true}' localhost:8008/reinitialize
```

### Scaling and Availability

- **The app tier scales with `replicas`.** It is stateless — replicas share only the database and the app secret — so `2` or more gives an always-on tier whose rolling restarts cycle one replica at a time.
- **The database is the availability limit.** In single-instance mode a database restart makes the dashboard and collection briefly unavailable; set `postgresHA.enabled: true` on a new install for automatic failover.
- **The first `helm upgrade` after an install can restart the bundled database** even when no database value changed.
- **Uninstall deletes every volume set the chart created**, so all analytics data is lost and does not survive a reinstall. The GVC is yours and is left alone, and your prerequisite secrets survive. Enable backups if the data matters.

### Troubleshooting

<AccordionGroup>
  <Accordion title="The Umami workload sits at 0 replicas after install while helm reported success">
    **Symptom:** `cpln helm install` succeeded, but `RELEASE_NAME-umami` shows no containers and `cpln logs` returns nothing.

    **Cause:** The secret named by `app.appSecretName`, or the database credentials secret named by `postgres.config.credentialsSecretName` (HA mode: `postgresHA.config.credentialsSecretName`), does not exist. The deployment pauses on the unresolved reference.

    **Fix:** Read the message naming the secret, then create it as shown in [Prerequisites](#prerequisites):

    ```bash
    cpln workload get-deployments RELEASE_NAME-umami --gvc GVC_NAME -o yaml
    ```

    The message reads `The secret <name> no longer exists. Workload updates are paused until the secret is added or the reference to the secret removed.` Once the secret exists the deployment recovers on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-umami --gvc GVC_NAME` to skip the wait.
  </Accordion>
  <Accordion title="The dashboard shows no visitors">
    **Symptom:** The website is added and the tracker is embedded, but no pageviews arrive.

    **Cause:** Most often `publicAccess.enabled` is still `false`, so browsers cannot reach the tracking script or the collect endpoint — or the embedded script points at an address other than the public canonical endpoint. Ad blockers also block the default `/script.js` and `/api/send`.

    **Fix:** Set `publicAccess.enabled=true` (see [First Run](#first-run)), confirm the `<script>` tag uses the public address, and set `tracker.scriptName` / `tracker.collectEndpoint` to custom paths to reduce ad-blocker interception.
  </Accordion>
  <Accordion title="Render fails with enable exactly one backing store">
    **Symptom:** The install stops with `umami: enable exactly one backing store — set either postgres.enabled or postgresHA.enabled to true, not both`, or the variant naming `postgres.enabled (default) or postgresHA.enabled (durable HA)`.

    **Cause:** Both `postgres.enabled` and `postgresHA.enabled` are `true`, or both are `false`.

    **Fix:** Enable exactly one — see [Choosing a Database Mode](#choosing-a-database-mode). For HA mode set `postgres.enabled: false` together with `postgresHA.enabled: true`.
  </Accordion>
  <Accordion title="Every user is logged out after a change">
    **Symptom:** All dashboard sessions end at once and everyone has to sign in again.

    **Cause:** The payload of the secret named by `app.appSecretName` changed, or `app.appSecretName` now points at a different secret. Existing tokens were signed with the old value.

    **Fix:** Nothing is lost — users sign in again. To avoid it, keep the app secret stable for the life of the install.
  </Accordion>
  <Accordion title="Upgrade fails with a key that was REMOVED or RENAMED">
    **Symptom:** `helm upgrade` stops at render with `app.appSecret was removed in 1.1.0`, `resources.cpu was renamed to resources.maxCpu`, `config.username was REMOVED in postgres 3.4.0`, `the postgres block was REMOVED in 2.5.0`, `backup.minio.accessKey and backup.minio.secretKey were REMOVED`, or `postgres.credentials was REMOVED in 1.4.0`.

    **Cause:** Your values still carry a key that moved in template versions 1.1.0 to 1.4.0. The existing release is left untouched and running.

    **Fix:** Follow the matching migration note above — [Upgrading From 1.0.1](#upgrading-from-1-0-1), [Upgrading From 1.1.0](#upgrading-from-1-1-0), [Upgrading From 1.2.0](#upgrading-from-1-2-0), [Upgrading From 1.3.0](#upgrading-from-1-3-0) or [Upgrading From 1.3.1](#upgrading-from-1-3-1) — keeping the credentials the database already uses in your database credentials secret.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the app secret and the database credentials secret before installing.** A missing one does not fail the install — the workload waits on it with no logs; see [Prerequisites](#prerequisites) for the diagnostic.
- **Editing the database credentials secret alone changes nothing** — rotate with `ALTER ROLE` plus a forced redeployment of Umami (not the database); see [Rotating the Database Password](#rotating-the-database-password). In HA mode a leader switchover comes first.
- **Change the hardcoded `admin` / `umami` password before turning public access on** — follow [First Run](#first-run) in order.
- **Tracking collects nothing until `publicAccess.enabled` is `true`**, and the tracking script must be loaded from the public address.
- **Keep the app secret stable** — changing it logs every user out. It is not owned by the release: it survives `helm uninstall` and must be deleted manually.
- **Pass the same app secret and database credentials secret names on every upgrade** — a values file is the simplest way.
- **Give each release its own database credentials secret** — secret names are org-wide.
- **Uninstall deletes the database volume sets** — enable backups if the analytics data matters.
