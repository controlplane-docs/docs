## Overview

Redis is an in-memory data store used as a cache, session store, message broker and queue backend. This template deploys **one** Redis master-replica cluster whose members span several Control Plane locations, with a Redis Sentinel instance in every location that monitors the master and elects a replacement from any location when the current one is lost. It is not a sharded Redis Cluster and not one independent Redis per region: every instance in every location belongs to the same replication group. One `engine` value runs both tiers on [Valkey](https://valkey.io/), the BSD-licensed fork of Redis, instead of Redis; leaving it alone changes nothing.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have, and that GVC must have **at least two locations**. It does not create, provision or manage a GVC. The locations this release runs in are the ones you list in `global.locations`, and every one of them must already be a location of that GVC. A GVC location you do not list starts nothing: its deployment reads `This workload location is deactivated because maxScale is set to 0.` For a Sentinel cluster inside a single location, use the [Redis](/template-catalog/templates/redis) template instead.
</Note>

### How Many Locations You Need

A failover needs a **majority of Sentinels** to agree, and Sentinel runs exactly one instance per location. That arithmetic decides what the cluster survives.

| Locations | Majority | Location losses survived | What happens when one location is lost |
|---|---|---|---|
| **2** | 2 | **0** | Surviving replicas hold the data, but **no automatic failover** — the vote cannot be reached. |
| **3** | 2 | **1** | **Automatic failover.** A replica in a surviving location is promoted. |
| **5** | 3 | **2** | Survives losing **two** locations. |

With N locations you survive `floor((N-1)/2)` losses, so an even count buys nothing over the odd count below it.

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-redis` | Redis or Valkey instances (stateful, `redis.replicasPerLocation` per declared location, port `6379`); replica 0 in the first declared location boots as the initial master, every other instance replicates from the current master | — |
| Workload | `RELEASE_NAME-sentinel` | Sentinel (stateful, exactly 1 per declared location, port `26379`); monitors the master under the name `mymaster` and holds the failover vote | — |
| Workload | `RELEASE_NAME-redis-backup` | Cron job that uploads an RDB snapshot to S3 or GCS; runs in the first declared location only | `backup.enabled: true` |
| Secret | `RELEASE_NAME-redis-config` | `redis.conf`, file-mounted into each Redis container; contains no password | — |
| Secret | `RELEASE_NAME-sentinel-config` | `sentinel.conf`, file-mounted into each Sentinel container; contains no password | — |
| Identity | `RELEASE_NAME-redis-identity` | Redis and backup workload identity; carries the cloud account binding when backup is enabled | — |
| Identity | `RELEASE_NAME-sentinel-identity` | Sentinel workload identity | — |
| Policy | `RELEASE_NAME-redis-policy` | `reveal` on the Redis config secret and on the password secrets you name | — |
| Policy | `RELEASE_NAME-sentinel-policy` | `reveal` on the Sentinel config secret and on the password secrets you name | — |
| Policy | `RELEASE_NAME-redis-gvc-policy` | `view` on the one GVC this release is installed into, so each Redis instance can confirm at start that every declared location exists there | — |
| Volume set | `RELEASE_NAME-redis-vs` | Redis data directory (`/data`), `ext4`, `redis.volumeset.initialCapacity` GiB per instance | — |
| Volume set | `RELEASE_NAME-sentinel-vs` | Sentinel state (`/etc/sentinel`), 10 GiB per instance, so the elected master survives a Sentinel restart | — |

| Domain | the `sentinel.publicAccess.address` value | Public TCP entry point for Sentinel, one port per location (`26380`, `26381`, ...) | `sentinel.publicAccess.enabled: true` |

## Prerequisites

<Steps>
  <Step title="An existing GVC with at least two locations">
    Read the GVC's locations back and compare them with the list you intend to put in `global.locations`; every name you list must appear under `spec.staticPlacement.locationLinks`:

    ```bash
    cpln gvc get GVC_NAME -o yaml
    ```

    Extra locations in the GVC are fine; nothing from this release runs in them. A location you list that the GVC lacks is a different matter: a fresh install refuses to start and names it in the logs. See [Locations](#locations).
  </Step>
  <Step title="Optional: password secrets">
    Authentication is off by default. To enable it, create one [opaque secret](/guides/create-secret/opaque) per tier **before** installing. Each secret's payload **is** the password — one value, no keys — and the two tiers are independent, so you may create either, both or neither:

    ```bash
    # Redis password (redis.passwordSecretName)
    printf '%s' "$(openssl rand -hex 32)" | cpln secret create-opaque --name REDIS_PASSWORD_SECRET_NAME --encoding plain -f -

    # Sentinel password (sentinel.passwordSecretName), independent of the one above
    printf '%s' "$(openssl rand -hex 32)" | cpln secret create-opaque --name SENTINEL_PASSWORD_SECRET_NAME --encoding plain -f -
    ```

    Set `redis.passwordSecretName` and `sentinel.passwordSecretName` to the names you used. Leave either value empty to run that tier without a password. See [Authentication](#authentication).

    <Warning>
    If a named secret does not exist when the workload starts, the deployment wedges silently: `cpln logs` returns nothing and the workload never becomes ready. The missing secret is named only in `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-redis --gvc GVC_NAME -o yaml
    ```

    Create the secret and the deployment recovers on its own after several minutes, or run `cpln workload force-redeployment RELEASE_NAME-redis --gvc GVC_NAME` to skip the wait.
    </Warning>
  </Step>
  <Step title="Optional: public TCP access">
    Public access needs a domain you control, the dedicated load balancer enabled on your GVC, and DNS records in place before the deploy that turns it on. See [Public Access](#public-access).
  </Step>
  <Step title="Optional: scheduled backups">
    Backups need an S3 or GCS bucket, a Control Plane cloud account and (on AWS) a bucket-scoped IAM policy. See [Backing Up](#backing-up).
  </Step>
</Steps>

## Installation

Put your location list in a values file — the default list names three AWS locations your GVC is unlikely to have — and install into the GVC that has them:

```yaml
# values.yaml
global:
  locations:
    - name: aws-us-east-1
    - name: aws-eu-central-1
    - name: aws-us-west-2
```

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/redis-multi-location \
  --version 3.0.0 --gvc GVC_NAME -f values.yaml
```

Pass the list from a file rather than with `--set`: `--set global.locations[0].name=aws-us-east-1` replaces the whole list with that single entry, and the install is refused with `redis-multi-location requires at least 2 entries in global.locations`.

## Configuration

### Locations

```yaml
global:
  locations:
    - name: aws-us-east-1
    - name: aws-eu-central-1
    - name: aws-us-west-2
```

- Every entry must already be a location of the GVC you install into. At least two are required; an **odd** count is what buys automatic failover — see [How Many Locations You Need](#how-many-locations-you-need).
- The **first** entry is where the initial master is seeded and where the backup job runs.
- `global.locations[].replicas` is deliberately **not** read — set `redis.replicasPerLocation` instead, which applies to every location. A standalone install that sets `replicas` is refused at render with `global.locations[].replicas is not read by redis-multi-location`.
- To add or remove a location, edit this list and run `cpln helm upgrade`. Every instance restarts (see [Scaling and Availability](#scaling-and-availability)).

The platform does not check that a listed location exists in the GVC: a location the GVC lacks is accepted and simply runs nothing, which silently removes part of the Sentinel quorum. The Redis instances therefore check the GVC's location list themselves at start and log a `[redis]` line with the result. On a **fresh** data directory a mismatch is fatal — the container exits and logs `[redis] FATAL:` naming the missing location — so a misconfigured cluster never bootstraps. On an **already-initialised** cluster the same conditions log `[redis] WARNING:` and the instance keeps serving, so a location that has genuinely gone away cannot take the cluster down with it. Read them with:

```bash
cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-redis"} |= "[redis]"' --limit 50 --since 10m
```

The exact lines are listed under [Troubleshooting](#troubleshooting).

### Redis or Valkey

```yaml
engine: redis # redis | valkey
valkeyImage: valkey/valkey:8.1.9
```

`engine` picks the server **both** tiers run and is the only difference between the two shapes — topology, replica counts, configuration, Sentinel behaviour, secrets, firewall and backups are identical. Setting `engine: valkey` makes `redis.image` and `sentinel.image` inert and runs the Redis and Sentinel workloads on `valkeyImage`, so a Valkey server behind a Redis Sentinel cannot be produced by accident.

| | `engine: redis` (default) | `engine: valkey` |
|---|---|---|
| Image | `redis.image` / `sentinel.image` (`redis:7.4`) | `valkeyImage` (`valkey/valkey:8.1.9`) for **both** tiers |
| License | Redis Source Available / SSPL | BSD-3-Clause, Linux Foundation — no paid edition, nothing feature-gated |
| On-disk format | RDB 12 | RDB 11 (the Redis 7.2 format) |

The Valkey image ships `redis-server`, `redis-cli` and `redis-sentinel` compatibility symlinks, so every command, configuration directive and connection string on this page is unchanged on either engine, and `redis.serverCommand` stays `redis-server`. Two things to know when running Valkey:

- **`INFO` reports `redis_version:7.2.4`** for client compatibility. Read `server_name` and `valkey_version` to see what is really running; a client library that version-gates on `redis_version` believes it is talking to Redis 7.2.
- **Use a Debian-based `valkeyImage` tag.** Both tiers assemble their configuration in a way the `-alpine` images do not support, and an `-alpine` tag fails at start with `Bad directive or wrong number of arguments`. The `redis` `-alpine` tags fail the same way through `redis.image` and `sentinel.image`. Valkey 9.x tags are reachable through `valkeyImage` but have not been tested with this template.

<Warning>
**`engine` is an install-time choice and cannot be changed on an existing install.** This template runs with `appendonly yes`, and `redis:7.4` writes its append-only base file in RDB format 12, which Valkey 8 refuses to read. A `helm upgrade` that flips the value reports success, then every Redis instance crash-loops with `Can't handle RDB format version 12` and `Error reading the RDB base file appendonly.aof.N.base.rdb, AOF loading aborted`. Setting `engine` back to `redis` and upgrading again recovers the data untouched. Move between engines with a dump and restore, or by replicating into a fresh install — never by changing the value.
</Warning>

### Redis

```yaml
redis:
  image: redis:7.4 # ignored when engine is valkey
  replicasPerLocation: 2 # Redis instances in EVERY location; total = this × locations
  resources:
    cpu: 200m
    memory: 256Mi
  serverCommand: redis-server # correct for both engines — the Valkey image ships a redis-server symlink
  extraArgs: "" # e.g. "--maxmemory 200mb --maxmemory-policy allkeys-lru"
  passwordSecretName: "" # e.g. my-redis-password — OPTIONAL prerequisite secret, see Authentication
  publicAccess:
    enabled: false
    address: redis.my-domain.com # a domain you own; prove ownership before enabling
  volumeset:
    initialCapacity: 20 # GiB
    autoscaling:
      enabled: false
      maxCapacity: 100 # GiB
      minFreePercentage: 10
      scalingFactor: 1.2
```

Each Redis instance gets its own `redis.volumeset.initialCapacity` GiB volume at `/data`, with both AOF and RDB persistence on, so data survives restarts, redeployments and upgrades. `redis.extraArgs` is appended to the server command line and overrides the equivalent directive in the base configuration.

### Sentinel

```yaml
sentinel:
  image: redis:7.4 # ignored when engine is valkey
  resources:
    cpu: 200m
    memory: 256Mi
  extraArgs: "" # e.g. "--sentinel down-after-milliseconds mymaster 5000"
  passwordSecretName: "" # e.g. my-redis-sentinel-password — OPTIONAL prerequisite secret, independent of the Redis one
  publicAccess:
    enabled: false
    address: redis-sentinel.my-domain.com # a domain you own
```

Exactly one Sentinel runs per location; the count is not configurable, and the quorum is a majority of them, computed from the number of locations. Sentinel monitors the master under the name `mymaster`, marks it down after 5 seconds without a response and promotes a replica once the quorum agrees. It keeps the elected master and its peer list on its own 10 GiB volume, so a Sentinel that restarts rejoins knowing which instance is the master rather than starting from its static configuration.

### Authentication

```yaml
redis:
  passwordSecretName: "" # e.g. my-redis-password
sentinel:
  passwordSecretName: "" # e.g. my-redis-sentinel-password
```

Authentication is off by default. Each value names an opaque secret you create beforehand (see [Prerequisites](#prerequisites)) whose payload is the password; passwords are never Helm values, so they never land in the release.

- `redis.passwordSecretName` — applied as both `requirepass` and `masterauth` on every Redis instance, and used by Sentinel to authenticate to the master. Empty means no Redis password at all.
- `sentinel.passwordSecretName` — applied as `requirepass` on every Sentinel. Independent of the Redis password; empty means Sentinel itself is unauthenticated.

Both tiers read their secret at container start, so a password change takes effect only when the containers restart. To rotate a password, update the secret and then force a redeployment of each affected tier, Sentinel first and Redis second:

```yaml
# redis-password.yaml — the whole secret, with the new payload
kind: secret
name: REDIS_PASSWORD_SECRET_NAME
type: opaque
data:
  encoding: plain
  payload: YOUR-NEW-STRONG-PASSWORD
```

```bash
cpln apply -f redis-password.yaml
cpln workload force-redeployment RELEASE_NAME-sentinel --gvc GVC_NAME
cpln workload force-redeployment RELEASE_NAME-redis --gvc GVC_NAME
```

<Warning>
**Updating the secret alone changes nothing.** Without the forced redeployment the running instances keep the password they started with, and the old credential goes on working indefinitely with every status surface reporting healthy. Redeploying the Redis tier restarts **every** Redis instance in every location at once, which takes the master out of service and triggers a failover — treat a Redis password change as a planned restart of the whole tier. Changing only the Sentinel password is safe: a Sentinel-only restart triggers no failover vote.
</Warning>

Adding, changing or removing `redis.passwordSecretName` through a `helm upgrade` has the same effect as the forced redeployment above, because every Redis instance restarts.

### Public Access

```yaml
redis:
  publicAccess:
    enabled: false
    address: redis.my-domain.com # a domain you own; prove ownership before enabling
sentinel:
  publicAccess:
    enabled: false
    address: redis-sentinel.my-domain.com # a domain you own
firewall:
  externalInboundAllowCIDR: "" # comma-separated; defaults to 0.0.0.0/0 when publicAccess is on
```

Redis and Sentinel can be exposed over the internet as raw TCP through a Control Plane [domain](/reference/domain), one public port per instance. Before enabling either:

1. **Enable the [dedicated load balancer](/reference/gvc#dedicated-load-balancer) on your GVC.** Arbitrary TCP ports need one, and it is a paid feature. This template deploys into a GVC you already own, so it cannot turn that on for you; a domain pointed at a GVC without one is created but never serves traffic.
2. **Add the DNS records before the deploy that turns public access on.** Domain ownership is verified when the domain resource is first created; if the records are missing the deploy fails and the error lists the exact TXT and CNAME records required (see [Required DNS Records](/guides/configure-domain#required-dns-records)). Add them, then upgrade the release. Disable any DNS proxying — TCP traffic must pass straight through.
3. **Decide who may connect.** `firewall.externalInboundAllowCIDR` defaults to `0.0.0.0/0` when public access is on; set it to the CIDRs your clients actually come from. Do not pin it to a single `/32` unless that address is genuinely static — when your office, VPN or NAT egress rotates its IP you lose access to your own cluster from outside.

| Workload | Public ports |
|---|---|
| Redis | `6380`, `6381`, ... — one per instance across all locations, in replica order |
| Sentinel | `26380`, `26381`, ... — one per location |

```bash
redis-cli -h redis.my-domain.com -p 6380 ping            # Redis replica 0
redis-cli -h redis-sentinel.my-domain.com -p 26380 ping  # Sentinel in the first location
```

Add `--no-auth-warning -a "$PASSWORD"` to either command when the matching tier has a password.

### Firewall

```yaml
firewall:
  internalAllowType: same-gvc # options: same-gvc, same-org, workload-list
  # Only used when internalAllowType is workload-list. This release's OWN
  # workloads (Redis, Sentinel, the backup cron) are added automatically.
  # List your clients here; do not list this release's workloads.
  workloads: []
  #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
  externalInboundAllowCIDR: "" # comma-separated; defaults to 0.0.0.0/0 when publicAccess is on
  externalOutboundAllowCIDR: "" # comma-separated
```

One firewall configuration applies to both the Redis and Sentinel workloads.

| `internalAllowType` | Who can connect inside Control Plane |
|---|---|
| `same-gvc` | Every workload in the same GVC (recommended) |
| `same-org` | Every workload in the same org |
| `workload-list` | Only the workloads listed in `firewall.workloads`, plus this release's own |

With `workload-list`, list **only your clients**. The same list governs Redis-to-Redis replication and Sentinel's monitoring of both tiers, so the Redis, Sentinel and backup workloads are appended for you; a client that is not listed is refused. Firewall changes take a few minutes to take effect — re-test before concluding a rule did not apply.

### Backup

```yaml
backup:
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/redis-backup:1.0.0
  schedule: "0 2 * * *" # cron schedule, default is daily at 02:00 UTC

  resources:
    cpu: 100m
    memory: 128Mi

  provider: aws # options: aws or gcp

  aws:
    bucket: my-redis-bucket
    region: us-east-1
    cloudAccountName: my-s3-cloud-account
    policyName: my-redis-backup-policy # bucket-scoped IAM policy, see Backing Up
    prefix: redis/backups # folder within the bucket

  gcp:
    bucket: my-redis-bucket
    cloudAccountName: my-gcs-cloud-account
    prefix: redis/backups # folder within the bucket
```

The bucket, cloud account and (on AWS) IAM policy must exist before you enable backups — see [Backing Up](#backing-up) for the per-provider steps.

## Connecting

| What | Address | Notes |
|---|---|---|
| Redis, any instance | `RELEASE_NAME-redis.GVC_NAME.cpln.local:6379` | Load-balanced across every instance in every location, so a plain connection may land on a read replica |
| Redis, one specific instance | `replica-N.RELEASE_NAME-redis.LOCATION_NAME.GVC_NAME.cpln.local:6379` | `N` counts from 0 within each location |
| Sentinel, any instance | `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379` | Master name `mymaster`; Sentinel-aware clients use this and always reach the current master |
| Sentinel, one specific location | `replica-0.RELEASE_NAME-sentinel.LOCATION_NAME.GVC_NAME.cpln.local:26379` | Exactly one Sentinel per location |
| Redis, public | the `redis.publicAccess.address` value, port `6380 + N` | Only with `redis.publicAccess.enabled: true` |
| Sentinel, public | the `sentinel.publicAccess.address` value, port `26380 + N` | Only with `sentinel.publicAccess.enabled: true` |
| Passwords | `cpln secret reveal REDIS_PASSWORD_SECRET_NAME -o yaml` | Likewise `SENTINEL_PASSWORD_SECRET_NAME`; only when you set the matching `passwordSecretName` |

Writes must go to the **current master**, which moves on every failover and on every upgrade. Point your client library at the Sentinel address with master name `mymaster` rather than at a specific instance: a write sent to a replica is refused with `READONLY You can't write against a read only replica.` Sentinel answers with the master's in-GVC hostname (`replica-N.RELEASE_NAME-redis.LOCATION_NAME.GVC_NAME.cpln.local`), so Sentinel-aware clients must run inside Control Plane; from outside, use the public per-instance ports.

To verify the cluster, ask the Sentinel in one location where the master is, then ask that location's first Redis instance to respond. The commands are the same on both engines; add `--no-auth-warning -a PASSWORD` to `redis-cli` when the matching tier has a password:

```bash
cpln workload exec RELEASE_NAME-sentinel --gvc GVC_NAME --location LOCATION_NAME \
  --replica RELEASE_NAME-sentinel-0 --container sentinel -- \
  redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

cpln workload exec RELEASE_NAME-redis --gvc GVC_NAME --location LOCATION_NAME \
  --replica RELEASE_NAME-redis-0 --container redis -- redis-cli ping
```

The first command prints the master's announced hostname and port; `redis-cli INFO replication` against any instance shows its `role` and, on a replica, `master_link_status:up` once it has synced. To confirm which engine is running, `redis-cli INFO server` answers with `server_name:valkey` and a `valkey_version` line on Valkey and with neither on Redis.

Shell-style scripts inside the GVC can follow the master the same way the instances themselves do:

```bash
MASTER_INFO=$(redis-cli -h RELEASE_NAME-sentinel.GVC_NAME.cpln.local -p 26379 SENTINEL get-master-addr-by-name mymaster)
MASTER_HOST=$(echo $MASTER_INFO | cut -d' ' -f1)
MASTER_PORT=$(echo $MASTER_INFO | cut -d' ' -f2)
redis-cli -h $MASTER_HOST -p $MASTER_PORT SET my-key "Hello world"
```

## Operations

### Backing Up

Backups are off by default. When `backup.enabled` is `true`, a cron workload (`RELEASE_NAME-redis-backup`) runs on `backup.schedule` in the **first** declared location only, takes an RDB snapshot and uploads it to your bucket as `PREFIX/redis-YYYY-MM-DDTHH-MM-SSZ.rdb.gz`. The job authenticates to the bucket through the Redis identity's cloud account binding — no static keys. It runs in one location because a cron workload otherwise fires in every location of its GVC and would write one copy of the same dump per location into the same bucket.

<Note>
The job connects to the load-balanced Redis address, so the snapshot is taken from whichever instance answers — often a replica rather than the master. Replicas apply writes asynchronously, so a snapshot can be marginally behind the master at the instant it was taken.
</Note>

#### AWS S3

1. Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.
2. [Create a cloud account](/guides/create-cloud-account) for your AWS account if you do not have one. Set `backup.aws.cloudAccountName` to its name.
3. Create an IAM policy with the following JSON, replacing `YOUR_BUCKET_NAME`, and set `backup.aws.policyName` to its name. The workload identity is granted this policy and `cpln-connector` only — no broad managed policy:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.prefix` to the folder path where backups will be stored, then set `backup.enabled: true` and `backup.provider: aws`.

#### GCS

1. Create a GCS bucket. Set `backup.gcp.bucket` to its name.
2. [Create a cloud account](/guides/create-cloud-account) for your GCP project if you do not have one. Set `backup.gcp.cloudAccountName` to its name.
3. Grant the **Storage Admin** (`roles/storage.admin`) role to the GCP service account associated with the cloud account. The template additionally binds the identity to `roles/storage.objectAdmin` on exactly the bucket named in `backup.gcp.bucket`.
4. Set `backup.gcp.prefix` to the folder path where backups will be stored, then set `backup.enabled: true` and `backup.provider: gcp`.

### Restoring a Backup

<Warning>
**There is no verified procedure for restoring one of these snapshots into a running release of this template.** Two things that look like they should work do not:

- Copying the file into an instance's data directory as `/data/dump.rdb` and restarting does nothing. This template runs with `appendonly yes`, and when AOF is enabled Redis rebuilds the dataset from `appendonlydir/` at start and ignores `dump.rdb` — with no error.
- `redis-cli --rdb FILE` *downloads* an RDB from a server; it does not load one. Running it against the cluster overwrites your downloaded backup with the live dataset.

The `redis:7.4` and `valkey/valkey:8.1.9` images also ship neither `aws` nor `gsutil`, so the object cannot be fetched from inside a Redis container.
</Warning>

What the backup is: a standard, gzipped RDB file. The upstream-documented way to read one is to start a standalone server of the **same engine** that wrote it (Valkey 8 cannot read an RDB written by Redis 7.4) with AOF disabled and the decompressed file in place as its `dump.rdb` — see [Restoring a backup in the Redis persistence documentation](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/#restoring-a-backup) — for example on a local machine with Docker. From there you can inspect the data or replay it into the cluster's current master with your own tooling (`redis-cli --scan` with `DUMP`/`RESTORE`, or a migration tool). Loading the file into this template's instances in place has not been tested; if you need that path, rehearse it against a throwaway release before relying on it, rather than attempting it for the first time during an incident.

### Upgrading from Version 2

Every release before 3.0.0 created its own GVC. **Do not `helm upgrade` a 2.x release onto 3.0.0.** Once the chart stops declaring a GVC, Helm deletes the one the old release created — and deleting a GVC deletes every workload, volume set and identity inside it, while the command prints `upgraded successfully`.

<Warning>
The chart refuses to render when your values still carry the 2.x `global.gvc` key, so an upgrade that passes your old values file fails safely before any resource is touched, with a message saying the `global.gvc` values key was REMOVED. That guard **cannot** fire on an upgrade run with no values at all, because it then sees only 3.0.0's own defaults. The procedure below is the safety; the render guard is only a backstop.
</Warning>

Install 3.0.0 as a **new release against an existing GVC**, copy the keyspace across, then remove the old release:

<Steps>
  <Step title="Pick the target GVC">
    It needs at least two locations, and every entry you put in `global.locations` must be one of them.
  </Step>
  <Step title="Install 3.0.0 as a new release and keep the old one running">
    In your values, delete `global.gvc.name` and rename `global.gvc.locations` to a top-level `global.locations`, then install under a **new** release name as shown under [Installation](#installation).
  </Step>
  <Step title="Move the data">
    Point a client at the old cluster's current master and the new one's (ask each release's Sentinel with `SENTINEL get-master-addr-by-name mymaster`) and copy the keyspace across — `redis-cli --scan` plus `DUMP`/`RESTORE`, or replication from the old master, whichever suits your dataset. Confirm the new cluster serves reads and writes before going on.
  </Step>
  <Step title="Cut clients over">
    Every internal hostname contains the GVC name, so every connection string changes.
  </Step>
  <Step title="Remove the old release">
    `cpln helm uninstall` of the old release deletes the GVC it created and the old volume sets with it, so make sure the previous step is genuinely complete and nothing else depends on that GVC.
  </Step>
</Steps>

Values that changed:

| 2.x | 3.0.0 |
|---|---|
| `global.gvc.name` | Removed — the GVC is wherever you install |
| `global.gvc.locations` | `global.locations` |

Two behaviours also changed with the GVC: public access needs a dedicated load balancer you enable on your GVC yourself (2.x enabled it on the GVC it created — see [Public Access](#public-access)), and with `firewall.internalAllowType: workload-list` this release's own workloads are now added to the list for you, so remove them from `firewall.workloads` if you had listed them.

### Scaling and Availability

- **Shape.** The cluster has `redis.replicasPerLocation` Redis instances in each of your `global.locations` and one Sentinel per location — six Redis instances and three Sentinels by default. One Redis instance is the master; every other instance, in every location, is a replica of it. Write capacity is that of a single instance; replicas serve reads only.
- **What a failover looks like.** When the master stops responding, the Sentinels mark it down after 5 seconds and, if a majority of them agree, promote a replica — in any location — and repoint the rest at it. Writes pause for the duration; reads from replicas continue; the old master rejoins as a replica when it returns. Clients that discover the master through Sentinel follow it; clients pinned to one instance get `READONLY` errors.
- **What it survives.** With three or more locations, losing the master instance or an entire location leaves a quorum of Sentinels standing and a replica in a surviving location is promoted. With two locations the surviving replicas keep the data but **no automatic failover** happens — the vote cannot reach a majority. See [How Many Locations You Need](#how-many-locations-you-need).
- **Replication is asynchronous**, so a failover can lose the writes the promoted replica had not yet received, bounded by the replication lag at the moment of failure.
- **Every `cpln helm upgrade`, and every forced redeployment of the Redis tier, restarts all Redis instances in every location at once** rather than one at a time. Treat it as a planned write outage and expect the master to move afterwards.
- **Resizing.** Change `redis.replicasPerLocation` to add or remove instances in every location, or edit `global.locations` to add or remove a location; both are a `cpln helm upgrade` and both restart the tier. Grow a volume with `redis.volumeset.autoscaling` or a larger `initialCapacity`. Data survives upgrades, but `cpln helm uninstall` deletes both volume sets.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Deployment never becomes ready and cpln logs returns nothing">
    **Symptom:** after an install with `redis.passwordSecretName` or `sentinel.passwordSecretName` set, the workload never reaches ready and `cpln logs` returns no lines at all.

    **Cause:** the named secret does not exist, so the container never starts. Nothing is logged because nothing ran.

    **Fix:** read the missing secret's name from `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-redis --gvc GVC_NAME -o yaml
    ```

    Create it as shown under [Prerequisites](#prerequisites). The deployment recovers on its own after several minutes, or run `cpln workload force-redeployment RELEASE_NAME-redis --gvc GVC_NAME` to skip the wait.
  </Accordion>
  <Accordion title="Redis exits with a [redis] FATAL line about a location not in the GVC">
    **Symptom:** on a fresh install the Redis containers exit and the logs carry one of:

    - `[redis] FATAL: the first location in global.locations ('LOCATION_NAME') is not in GVC 'GVC_NAME'` — every Sentinel is seeded to monitor replica 0 in that location, so no master would ever form.
    - `[redis] FATAL: Sentinel can never reach its failover quorum.` — fewer declared locations exist in the GVC than the quorum needs.
    - `[redis] FATAL: locations declared in global.locations are not in GVC 'GVC_NAME'` — some other declared location is missing, so losing any one location would end automatic failover.
    - `[redis] FATAL: this instance is running in location 'LOCATION_NAME', which is not in the configured location list` — the workload is running somewhere `global.locations` does not name.

    **Cause:** `global.locations` and the GVC's actual location list disagree. The platform accepts the mismatch silently; the instances refuse to bootstrap a cluster that could never fail over.

    **Fix:** compare `spec.staticPlacement.locationLinks` from `cpln gvc get GVC_NAME -o yaml` with your values, then either add the missing location to the GVC or remove it from `global.locations` and run `cpln helm upgrade`. On an already-initialised cluster the same conditions appear as `[redis] WARNING:` lines and the instances keep serving; fix the list the same way. A `[redis] WARNING: could not read the location list of GVC` line means the check was skipped this start and nothing was refused.
  </Accordion>
  <Accordion title="Can't handle RDB format version 12 after changing engine">
    **Symptom:** after a `cpln helm upgrade` that set `engine: valkey`, every Redis instance crash-loops with `Can't handle RDB format version 12` and `Error reading the RDB base file appendonly.aof.N.base.rdb, AOF loading aborted`.

    **Cause:** the data directories were written by Redis 7.4, whose on-disk format Valkey 8 cannot read. `engine` is an install-time choice.

    **Fix:** set `engine` back to `redis` and upgrade again; the data is recovered untouched. Move between engines with a dump and restore, or by replicating into a fresh install. See [Redis or Valkey](#redis-or-valkey).
  </Accordion>
  <Accordion title="Bad directive or wrong number of arguments at start">
    **Symptom:** a Redis or Sentinel container exits immediately with `Bad directive or wrong number of arguments`.

    **Cause:** `valkeyImage`, `redis.image` or `sentinel.image` points at an `-alpine` tag. Both tiers assemble their configuration in a way those images do not support.

    **Fix:** use a Debian-based tag such as `redis:7.4` or `valkey/valkey:8.1.9`.
  </Accordion>
  <Accordion title="Render fails with the global.gvc values key was REMOVED">
    **Symptom:** `cpln helm install` or `cpln helm upgrade` refuses to render and prints a message beginning `redis-multi-location 3.0.0:` saying the `global.gvc` values key was REMOVED.

    **Cause:** your values file is from a 2.x release.

    **Fix:** do **not** upgrade the 2.x release in place. Follow [Upgrading from Version 2](#upgrading-from-version-2): delete `global.gvc.name`, rename `global.gvc.locations` to `global.locations`, and install as a new release.
  </Accordion>
  <Accordion title="Render fails with requires at least 2 entries in global.locations">
    **Symptom:** the install is refused with `redis-multi-location requires at least 2 entries in global.locations` although your values list several.

    **Cause:** the list was passed with `--set global.locations[0].name=...`, which replaces the whole list with that one entry.

    **Fix:** pass the location list from a values file with `-f values.yaml` as shown under [Installation](#installation). For a single-location cluster, use the [Redis](/template-catalog/templates/redis) template.
  </Accordion>
  <Accordion title="Render fails with global.locations[].replicas is not read by redis-multi-location">
    **Symptom:** the install is refused with `global.locations[].replicas is not read by redis-multi-location — set redis.replicasPerLocation instead`.

    **Cause:** a `replicas` field on a `global.locations` entry. That field belongs to other multi-location templates that share the same list shape.

    **Fix:** remove `replicas` from every location entry and set `redis.replicasPerLocation`, which applies to every location.
  </Accordion>
  <Accordion title="The old password still works after rotating the secret">
    **Symptom:** you updated the secret named by `redis.passwordSecretName` or `sentinel.passwordSecretName`, but the old password is still accepted and the new one is not.

    **Cause:** both tiers read the secret at container start, and updating a secret does not restart anything.

    **Fix:** force a redeployment of each affected tier, Sentinel first and Redis second, as shown under [Authentication](#authentication). Expect the Redis redeployment to restart every instance at once and trigger a failover.
  </Accordion>
  <Accordion title="READONLY You can't write against a read only replica">
    **Symptom:** writes that used to succeed are refused with `READONLY You can't write against a read only replica.` after a failover or an upgrade.

    **Cause:** the client is connected to a fixed instance, or to the load-balanced Redis address, and landed on a replica.

    **Fix:** configure the client for Sentinel at `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379` with master name `mymaster`, so it follows the master wherever it moves.
  </Accordion>
  <Accordion title="A client is refused after switching to workload-list">
    **Symptom:** after setting `firewall.internalAllowType: workload-list`, a client workload can no longer connect while the cluster itself is healthy.

    **Cause:** the client's workload link is not in `firewall.workloads`, or the change has not propagated yet.

    **Fix:** add `//gvc/GVC_NAME/workload/WORKLOAD_NAME` for each client to `firewall.workloads` and upgrade. This release's own workloads are added for you and must not be listed. Firewall changes take a few minutes to take effect.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Never `helm upgrade` a 2.x release onto 3.0.0** — it deletes the GVC the old release created and everything in it. Install a new release and migrate; see [Upgrading from Version 2](#upgrading-from-version-2).
- **Every entry in `global.locations` must already be a location of the GVC**, and there must be at least two. A fresh install that names a missing location refuses to start and says which one; an already-running cluster warns and keeps serving.
- **Choose `engine` before the first install.** Switching it on a running release crash-loops every instance until it is set back; migrate with a dump and restore instead.
- **Create the password secrets before installing.** A `passwordSecretName` that points at a secret that does not exist wedges the deployment silently; the name appears only in `status.versions[].message`.
- **Rotating a password needs a forced redeployment**, Sentinel first and Redis second. Updating the secret alone leaves the old password in force.
- **Always discover the master through Sentinel** (`mymaster` at `RELEASE_NAME-sentinel.GVC_NAME.cpln.local:26379`). A client pinned to one instance gets `READONLY` errors after any failover or upgrade.
- **Two locations give no automatic failover.** Use three or more to survive losing a location, and remember replication is asynchronous.
- **Every `helm upgrade` restarts all Redis instances in every location at once** — plan it as a short write outage and expect a new master.
- **Pass `global.locations` from a values file**, never with `--set`, which replaces the list with a single entry.
- **With `firewall.internalAllowType: workload-list`, list only your clients** — this release's own workloads are added for you.
- **Public access needs the dedicated load balancer enabled on your GVC and the DNS records in place first**; otherwise the domain is rejected or never serves.
- **Bucket backups have no verified in-place restore.** Treat them as portable RDB files; see [Restoring a Backup](#restoring-a-backup).
- **Data survives an upgrade but not an uninstall** — `cpln helm uninstall` deletes both volume sets.
