## Overview

Temporal is an open-source (MIT) durable-execution platform: applications write workflows as ordinary code, and the Temporal server guarantees they run to completion, surviving process crashes, restarts, and long waits. This template deploys the Temporal server (one replica by default, or a cluster of up to five) with its gRPC frontend and HTTP API, plus the Temporal Web UI, all internal-only. By default the server is backed by the [Postgres Highly Available](/template-catalog/templates/postgres-highly-available) template as a bundled subchart; a single-instance [Postgres](/template-catalog/templates/postgres) subchart is available for lighter installs. Database creation, schema migrations and the `default` namespace are handled automatically.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have. It does not create one.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-temporal` | Temporal server (standard, `replicas` replicas, default 1, no volume). Each replica runs a `temporal` container (frontend, history, matching and worker services in one process; gRPC on `7233`, HTTP API on `7243`) and an `admin` sidecar that migrates the schema and serves the `temporal` CLI | — |
| Workload | `RELEASE_NAME-temporal-ui` | Temporal Web UI on port `8080` (standard, 1 replica) | `ui.enabled: false` removes it |
| Identity & Policy | `RELEASE_NAME-temporal-identity`, `RELEASE_NAME-temporal-policy` | Server identity with `reveal` on exactly the database credentials secret. The UI has no identity because it mounts no secrets | — |
| Secret | `my-temporal-db-credentials` | Dictionary secret **created by this chart** from `postgres.credentials.*`, holding `username`, `password` and `database`. Its name is the active database block's `config.credentialsSecretName` | — |
| Workload | `RELEASE_NAME-postgres-ha` | Patroni PostgreSQL cluster (stateful, 3 replicas) | HA mode (default) |
| Workload | `RELEASE_NAME-etcd` | etcd consensus store for Patroni (stateful, 3 replicas) | HA mode |
| Workload | `RELEASE_NAME-postgres-ha-proxy` | HAProxy leader endpoint Temporal connects through (standard, 2 replicas) | HA mode |
| Volume Set | `RELEASE_NAME-postgres-ha-vs`, `RELEASE_NAME-etcd-vs` | 10 GiB `ext4` per replica | HA mode |
| Identity & Policy | `RELEASE_NAME-postgres-ha-identity`, `RELEASE_NAME-postgres-ha-policy`, `RELEASE_NAME-etcd-identity`, `RELEASE_NAME-etcd-policy` | Subchart identities with `reveal` on their own startup-script secrets and the credentials secret | HA mode |
| Secret | `RELEASE_NAME-patroni-startup`, `RELEASE_NAME-postgres-proxy-startup`, `RELEASE_NAME-etcd-startup`, `RELEASE_NAME-wal-g-backup-script` | Opaque startup scripts for the HA subchart | HA mode |
| Workload | `RELEASE_NAME-postgres-ha-backup` | Scheduled `pg_dumpall` cron job | `postgresHA.backup.enabled: true` with `mode: logical` |
| Secret | `RELEASE_NAME-postgres-config` | Non-sensitive backup settings (bucket, region or endpoint) | `postgresHA.backup.enabled: true` |
| Workload | `RELEASE_NAME-postgres` | Single-instance PostgreSQL (stateful, 1 replica) | `postgres.enabled: true` |
| Volume Set | `RELEASE_NAME-pg-vs` | 10 GiB `ext4` | `postgres.enabled: true` |
| Identity & Policy | `RELEASE_NAME-pg-identity`, `RELEASE_NAME-pg-policy` | Subchart identity with `reveal` on the credentials secret | `postgres.enabled: true` |
| Workload | `RELEASE_NAME-postgres-backup` | Scheduled `pg_dumpall` cron job | `postgres.backup.enabled: true` |

In HA mode with `postgresHA.backup.mode: wal-g`, no cron workload is created; a `wal-g-backup` sidecar container runs inside `RELEASE_NAME-postgres-ha` instead.

## Prerequisites

None for a default install. The database credentials are **not** a prerequisite: this chart creates the credentials secret for you from `postgres.credentials.*` and hands it to the bundled database by name. You only have to change the password before installing.

Optional database backups need a bucket and, for AWS or GCP, a Control Plane Cloud Account. Backups to MinIO or another S3-compatible endpoint additionally need a dictionary secret holding `accessKey` and `secretKey`, which must exist before you enable them. See [Backing Up](#backing-up).

## Installation

Install with the database password set to something strong. Nothing else is required for a default install:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/temporal \
  --version 2.0.0 --gvc GVC_NAME \
  --set postgres.credentials.password='YOUR-STRONG-PASSWORD'
```

## Configuration

### Temporal Server

```yaml
image: temporalio/server:1.32.1 # 1.30.x, 1.31.x or 1.32.x; step one minor version per upgrade

replicas: 1 # 1-5; 3 survives a replica loss. See Scaling and Availability

resources: # per replica
  maxCpu: 1000m
  maxMemory: 2Gi
  minCpu: 500m
  minMemory: 1Gi

adminTools:
  image: temporalio/admin-tools:1.32.1 # schema migrations + `temporal` CLI sidecar; same tag as image

historyShards: 512 # fixed at first install; a later change is ignored (the cluster keeps its original count)
namespaceRetention: 72h # retention of the `default` namespace, applied when it is first created
```

- `image` / `adminTools.image` — The Temporal server and the `admin` sidecar that runs alongside it in every replica. Both must carry the same tag, and the chart accepts only tags in the 1.30, 1.31 and 1.32 minors. Temporal upgrades one minor version at a time; see [Upgrading from 1.x](#upgrading-from-1-x).
- `replicas` — Every replica runs the full server, and together they form one Temporal cluster. See [Scaling and Availability](#scaling-and-availability) before changing it.
- `historyShards` — Fixed when the cluster is first created. A later change has no effect: the server keeps the original count. `512` suits most deployments, so size it before installing.
- `namespaceRetention` — How long closed workflow histories stay queryable in the `default` namespace, as a Go duration such as `72h` or `168h`. It is applied only when the namespace is first created; a later change does not alter an existing namespace.

### Web UI

```yaml
ui: # internal-only: the Temporal UI has no built-in authentication
  enabled: true # set false to remove the UI workload
  image: temporalio/ui:2.55.0
  resources:
    maxCpu: 500m
    maxMemory: 512Mi
    minCpu: 125m
    minMemory: 128Mi
```

<Warning>
The Temporal Web UI has **no built-in authentication**, so this template keeps it internal-only and has no knob to expose it publicly. Reach it from your own machine with `cpln port-forward` (see [Connecting](#connecting)), or put your own authenticating proxy in front of it.
</Warning>

### Access

```yaml
internalAccess: # internal firewall scope for the server (gRPC :7233, HTTP API :7243) and the UI (:8080)
  type: same-gvc # options: none, same-gvc, same-org, workload-list
  workloads: [] # used with workload-list; the server and UI workloads are always added
  # workloads:
  #   - //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

Both workloads are internal-only; there is no public-access option in this template. `internalAccess.type` sets the internal firewall scope for the server and the UI:

| Type | Description |
|------|-------------|
| `none` | No internal access. |
| `same-gvc` | Allow access from all workloads in the same GVC (default). |
| `same-org` | Allow access from all workloads in the same organization. |
| `workload-list` | Allow access only from the workloads listed in `internalAccess.workloads`. The Temporal server and Web UI workloads are added to the list automatically, so list only your own workers and clients. |

Changing `internalAccess` restarts every server replica, and a change can take a few minutes to take effect. Re-test rather than trusting the first response.

### PostgreSQL

Exactly one of `postgresHA` and `postgres` must be enabled; the chart refuses to render otherwise.

| | `postgresHA` (default) | `postgres` |
|---|---|---|
| What runs | 3 Patroni PostgreSQL replicas, 3 etcd replicas, 2 HAProxy replicas | One single-replica PostgreSQL workload |
| Database failover | Automatic (Patroni leader election) | None |
| Best for | Production | Development and lightweight installs |

#### Highly Available PostgreSQL

```yaml
postgresHA: # default: highly available PostgreSQL
  enabled: true
  config:
    credentialsSecretName: my-temporal-db-credentials # name of the dictionary secret THIS CHART creates from postgres.credentials.*; give each release its own
  replicas: 3
  volumeset:
    capacity: 10 # initial capacity in GiB per replica (minimum is 10)

  backup: # optional database backups; see Backing Up
    enabled: false
    mode: logical # logical or wal-g
    resources:
      cpu: 100m
      memory: 512Mi # 128Mi OOMKills wal-g mid-backup
    logical:
      image: ghcr.io/controlplane-com/backup-images/postgres-backup:17.1.0
      schedule: "0 2 * * *"
    walg:
      intervalSeconds: 21600
    provider: aws # options: aws, gcp, minio
    aws:
      bucket: temporal-pg-backup-bucket
      region: us-east-1
      cloudAccountName: my-s3-cloud-account
      policyName: temporal-pg-backup-policy
      prefix: postgres/backups
    gcp:
      bucket: temporal-pg-backup-bucket
      cloudAccountName: my-gcs-cloud-account
      prefix: postgres/backups
    minio:
      endpoint: http://my-minio-workload:9000
      bucket: temporal-pg-backup-bucket
      credentialsSecretName: my-temporal-minio-credentials # REQUIRED prerequisite dictionary secret holding accessKey and secretKey, only when provider is minio
      prefix: postgres/backups
```

- `postgresHA.config.credentialsSecretName` — Name of the dictionary secret this chart creates and the HA cluster reads. Its contents come from `postgres.credentials.*` below, in both database modes. Secret names are organization-wide, so give each Temporal release its own name: a second release left on the default is refused at install and creates nothing, and the first release is unaffected.
- `postgresHA.replicas` / `postgresHA.volumeset.capacity` — PostgreSQL replica count and volume size per replica. The remaining cluster settings take the defaults of the [Postgres Highly Available](/template-catalog/templates/postgres-highly-available) template; the HAProxy leader endpoint must stay enabled because it is the address Temporal connects to.
- `postgresHA.backup.*` — Optional backups of both Temporal databases, as scheduled logical dumps or continuous WAL-G archiving. Keep `resources.memory` at `512Mi` or more for WAL-G. See [Backing Up](#backing-up).

#### Single-Instance PostgreSQL

Enable this block and disable `postgresHA` for a lighter non-HA deployment.

```yaml
postgres: # dev/lightweight: single-instance PostgreSQL (disable postgresHA first)
  enabled: false
  credentials: # the chart writes these into the credentials secret; used in BOTH database modes
    username: temporal
    password: change-me-temporal-db-password # change before installing
    database: temporal # MUST stay temporal (render-enforced in both modes)
  config:
    credentialsSecretName: my-temporal-db-credentials # secret names are org-wide; give each release its own
  volumeset:
    capacity: 10 # initial capacity in GiB (minimum is 10)

  backup: # optional database backups; see Backing Up
    enabled: false
    image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0
    schedule: "0 2 * * *"
    resources:
      cpu: 100m
      memory: 128Mi
    provider: aws # options: aws, gcp, minio
    aws:
      bucket: temporal-pg-backup-bucket
      region: us-east-1
      cloudAccountName: my-s3-cloud-account
      policyName: temporal-pg-backup-policy
      prefix: postgres/backups
    gcp:
      bucket: temporal-pg-backup-bucket
      cloudAccountName: my-gcs-cloud-account
      prefix: postgres/backups
    minio:
      endpoint: http://my-minio-workload:9000
      bucket: temporal-pg-backup-bucket
      credentialsSecretName: my-temporal-minio-credentials # REQUIRED prerequisite dictionary secret holding accessKey and secretKey, only when provider is minio
      prefix: postgres/backups
```

- `postgres.credentials.username` / `postgres.credentials.password` — The bundled database's credentials. **Change the password before installing.** These two values populate the chart-created credentials secret in **both** database modes, even though they sit under the `postgres` block.
- `postgres.credentials.database` — Must remain `temporal`. The server reads its main store as the literal database `temporal`, so the chart refuses to render any other value.
- `postgres.config.credentialsSecretName` — Name of the credentials secret in single-instance mode (the HA counterpart is `postgresHA.config.credentialsSecretName`).

<Note>
The credentials are applied once, when the database volume is first initialized. Changing `postgres.credentials.password` on an existing release only rewrites the secret, not the password PostgreSQL enforces, so the server can no longer connect.
</Note>

## Connecting

This template exposes no public endpoint. Everything below is reachable from workloads inside the `internalAccess` scope, or from your own machine through `cpln port-forward`.

| What | Address | Notes |
|---|---|---|
| gRPC frontend | `RELEASE_NAME-temporal.GVC_NAME.cpln.local:7233` | Workers and clients connect here, namespace `default`. Always use the full `.cpln.local` hostname; short workload names do not resolve. |
| HTTP API | `http://RELEASE_NAME-temporal.GVC_NAME.cpln.local:7243` | For example `/api/v1/namespaces/default`. |
| Web UI | `cpln port-forward RELEASE_NAME-temporal-ui 8080:8080 --gvc GVC_NAME`, then `http://localhost:8080` | Internal only, no authentication. |
| `temporal` CLI | The `admin` container of `RELEASE_NAME-temporal` | Already pointed at the server; see the command below. |
| PostgreSQL (HA mode) | `RELEASE_NAME-postgres-ha-proxy.GVC_NAME.cpln.local:5432` | The HAProxy leader endpoint Temporal itself uses. |
| PostgreSQL (single mode) | `RELEASE_NAME-postgres.GVC_NAME.cpln.local:5432` | Only when `postgres.enabled: true`. |
| Database credentials | `cpln secret reveal SECRET_NAME -o yaml` | `SECRET_NAME` is the active database block's `config.credentialsSecretName` (default `my-temporal-db-credentials`). |

Confirm the server is serving by listing workflows with the `temporal` CLI in the `admin` sidecar. On a fresh install the list is empty and the command exits without an error:

```bash
cpln workload exec RELEASE_NAME-temporal --gvc GVC_NAME --container admin -- temporal workflow list
```

To open the Web UI from your own machine, tunnel to the UI workload and browse to `http://localhost:8080`:

```bash
cpln port-forward RELEASE_NAME-temporal-ui 8080:8080 --gvc GVC_NAME
```

If the UI stops loading pages through `cpln port-forward` after some navigation, restart the port-forward and reload the page.

### First Run

Temporal has no setup wizard. A fresh install already has a `default` namespace, so the first run is a worker and a workflow.

<Steps>
  <Step title="Check the namespace in the Web UI">
    With the port-forward above running, open `http://localhost:8080`. The `default` namespace is already registered, with the retention you set in `namespaceRetention`.
  </Step>
  <Step title="Run a worker">
    Workers run as their own workloads inside the `internalAccess` scope and connect to the gRPC frontend by its full hostname. A minimal Python worker:

    ```python
    import asyncio
    from temporalio.client import Client
    from temporalio.worker import Worker

    async def main():
        client = await Client.connect(
            "RELEASE_NAME-temporal.GVC_NAME.cpln.local:7233",  # full hostname required
            namespace="default",
        )
        worker = Worker(
            client,
            task_queue="my-task-queue",
            workflows=[MyWorkflow],
            activities=[my_activity],
        )
        await worker.run()

    if __name__ == "__main__":  # required, see note below
        asyncio.run(main())
    ```

    <Note>
    Python workers must guard their entrypoint with `if __name__ == "__main__":`. The Temporal Python SDK's workflow sandbox re-imports the worker module, and an unguarded module-level `main()` crashes the worker.
    </Note>
  </Step>
  <Step title="Start a workflow">
    Start a workflow on the worker's task queue from the Web UI's **Start Workflow** form, or with the `temporal` CLI in the `admin` sidecar:

    ```bash
    cpln workload exec RELEASE_NAME-temporal --gvc GVC_NAME --container admin \
      -- temporal workflow start --namespace default \
      --task-queue my-task-queue --type MyWorkflow --workflow-id first-run
    ```

    The run appears in the Web UI under Workflows.
  </Step>
</Steps>

## Operations

### Backing Up

Database backups are optional and disabled by default. They cover both Temporal databases, `temporal` (workflow histories, task queues, timers) and `temporal_visibility`. Enable them with `postgresHA.backup.enabled` or `postgres.backup.enabled`, matching your database mode, and complete the storage setup for your provider **before** enabling. The keys below are written as `backup.*`; set them inside the enabled database block.

In HA mode, `postgresHA.backup.mode` selects `logical` (a scheduled `pg_dumpall` from the `RELEASE_NAME-postgres-ha-backup` cron workload) or `wal-g` (continuous WAL archiving from a `wal-g-backup` sidecar inside `RELEASE_NAME-postgres-ha`, with a base backup every `walg.intervalSeconds`). Single-instance mode takes scheduled logical dumps only.

<Tabs>
  <Tab title="AWS S3">
    <Steps>
      <Step title="Create a bucket">
        Create an S3 bucket. Set `backup.aws.bucket` and `backup.aws.region` to match.
      </Step>
      <Step title="Set up a Cloud Account">
        If you do not have one, [create a Cloud Account](/guides/create-cloud-account) for your AWS account. Set `backup.aws.cloudAccountName` to its name.
      </Step>
      <Step title="Create a bucket-scoped IAM policy">
        Create an AWS IAM policy with the JSON below (replace `YOUR_BUCKET`), then set `backup.aws.policyName` to the policy's name. The template attaches that policy to the backup identity and nothing else, so the bucket in your policy is the only storage the backup can reach:

        ```json
        {
          "Version": "2012-10-17",
          "Statement": [{
            "Effect": "Allow",
            "Action": [
              "s3:GetObject",
              "s3:PutObject",
              "s3:DeleteObject",
              "s3:ListBucket",
              "s3:GetObjectVersion",
              "s3:DeleteObjectVersion",
              "s3:GetBucketLocation",
              "s3:AbortMultipartUpload",
              "s3:ListBucketMultipartUploads",
              "s3:ListMultipartUploadParts"
            ],
            "Resource": [
              "arn:aws:s3:::YOUR_BUCKET",
              "arn:aws:s3:::YOUR_BUCKET/*"
            ]
          }]
        }
        ```
      </Step>
    </Steps>
  </Tab>
  <Tab title="Google Cloud Storage">
    <Steps>
      <Step title="Create a bucket">
        Create a GCS bucket. Set `backup.gcp.bucket` to its name.
      </Step>
      <Step title="Set up a Cloud Account">
        If you do not have one, [create a Cloud Account](/guides/create-cloud-account) for your GCP project and grant its service account the **Storage Admin** role on the bucket. Set `backup.gcp.cloudAccountName` to its name. The backup identity reaches the bucket with no stored credentials.
      </Step>
    </Steps>
  </Tab>
  <Tab title="S3-compatible (MinIO, R2, Wasabi)">
    <Steps>
      <Step title="Create a bucket">
        Create the bucket on your server. Set `backup.minio.bucket` to its name.
      </Step>
      <Step title="Set the endpoint">
        Set `backup.minio.endpoint` to the S3 API address including the port. For the [MinIO](/template-catalog/templates/minio) template deployed in the same GVC, this is `http://WORKLOAD_NAME.GVC_NAME.cpln.local:9000`.
      </Step>
      <Step title="Create the credentials secret">
        Create a [dictionary secret](/guides/create-secret/dictionary) holding exactly the keys `accessKey` and `secretKey`, with credentials that can read and write the bucket:

        ```bash
        cpln secret create-dictionary --name SECRET_NAME \
          --entry accessKey=ACCESS_KEY \
          --entry secretKey=SECRET_KEY
        ```

        Set `backup.minio.credentialsSecretName` to this name. The same key is used in both database modes.
      </Step>
    </Steps>

    <Warning>
    **Create the MinIO secret before enabling backups, or the workload that references it wedges silently.** In `logical` mode that is the backup cron workload; in `wal-g` mode it is the database workload `RELEASE_NAME-postgres-ha` itself, because the sidecar reads the secret. The container never starts, so `cpln logs` returns nothing. The one place the reason appears is `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-postgres-ha-backup --gvc GVC_NAME -o yaml
    ```

    Use `get-deployments`; plain `cpln workload get` has no `versions` key. Creating the missing secret repairs the deployment on its own after several minutes, or run `cpln workload force-redeployment` on the affected workload to skip the wait.
    </Warning>
  </Tab>
</Tabs>

To take a logical backup on demand, for example before an upgrade, start the cron job once and check that its run reports `Successful`:

```bash
cpln workload cron start RELEASE_NAME-postgres-ha-backup --gvc GVC_NAME
cpln workload cron get RELEASE_NAME-postgres-ha-backup --gvc GVC_NAME
```

In single-instance mode the cron workload is `RELEASE_NAME-postgres-backup`. With WAL-G, the leader's `wal-g-backup` container logs `Backup complete` after each base backup.

<Warning>
**Volume set snapshots are not a supported restore path for the HA database.** Restoring them onto a running Patroni cluster does not bring the database back to its earlier state. Use the backups above.
</Warning>

### Restoring a Backup

<Warning>
**This restore path has not been exercised against a Temporal install.** It is derived from the backup image (a `pg_dumpall` of the whole server, gzip-compressed) and from the restore procedure of the bundled database templates. Rehearse it on a throwaway release before you depend on it.
</Warning>

A logical backup is a full-server dump (`pg_dumpall`), so one file holds both Temporal databases and the `temporal` role. Restore into a database Temporal is not writing to: the dump recreates `temporal` and `temporal_visibility`, so the cleanest target is a database from which both have been dropped, with the Temporal server not running against it.

Then run the pipeline documented by the bundled database template from a client with access to the bucket, using the `username` and `password` from `cpln secret reveal SECRET_NAME -o yaml` and the matching host: `RELEASE_NAME-postgres-ha-proxy.GVC_NAME.cpln.local` in HA mode, `RELEASE_NAME-postgres.GVC_NAME.cpln.local` in single mode.

```bash
export PGPASSWORD="PASSWORD"

aws s3 cp "s3://BUCKET_NAME/PREFIX/BACKUP_FILE.sql.gz" - \
  | gunzip \
  | psql \
      --host=RELEASE_NAME-postgres-ha-proxy.GVC_NAME.cpln.local \
      --port=5432 \
      --username=temporal \
      --dbname=postgres

unset PGPASSWORD
```

For GCS replace the first line of the pipeline with `gsutil cp "gs://BUCKET_NAME/PREFIX/BACKUP_FILE.sql.gz" -`; for MinIO export `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, run `aws configure set default.s3.addressing_style path`, and add `--endpoint-url "http://MINIO_ENDPOINT:9000"` to the `aws s3 cp`. The WAL-G point-in-time procedure for HA mode is documented on the [Postgres Highly Available](/template-catalog/templates/postgres-highly-available) page and carries the same caveat above.

### Upgrading from 1.0.x

Apply every subsection from your version onward, in order, ending with [Upgrading from 1.x](#upgrading-from-1-x). Each removed key is rejected at render, so an upgrade that still carries one fails before anything is applied and the running release is left untouched.

Version `1.1.0` moved the bundled single-instance database to the `postgres` 3.4.1 template, which no longer takes credentials or MinIO keys as values. This template absorbed the credentials change rather than passing it on: it creates the credentials secret itself, so there is **no new prerequisite for the database**, only renames on the single-instance path:

| Removed key | Replacement |
|---|---|
| `postgres.config.username` | `postgres.credentials.username` |
| `postgres.config.password` | `postgres.credentials.password` |
| `postgres.config.database` | `postgres.credentials.database` (must be `temporal`) |
| `postgres.backup.minio.accessKey`, `postgres.backup.minio.secretKey` | `postgres.backup.minio.credentialsSecretName`, a dictionary secret you create (MinIO backups only, see [Backing Up](#backing-up)) |

Carrying an old credentials key forward fails with the **bundled Postgres template's** message, which begins `config.username was REMOVED in postgres 3.4.0` and tells you to create a dictionary secret yourself. Ignore that advice for the three credentials keys: this template creates that secret from `postgres.credentials.*`. Use the username and password your database was initialized with, not new ones.

<Warning>
**Template version `1.0.0` did not compact the etcd cluster inside the bundled HA database**, so its backend grew with time alone and eventually went read-only, taking PostgreSQL failover with it. Only HA-mode installs are affected. Upgrading to `1.0.1` or later turns compaction on, which stops further growth but cannot shrink a backend that has already grown; a cluster that has already raised a `NOSPACE` alarm needs operator recovery rather than an upgrade. The mechanism and the inspection commands are on the [Postgres Highly Available](/template-catalog/templates/postgres-highly-available) page.
</Warning>

### Upgrading from 1.1.0

Version `1.2.0` moved the bundled HA database to `postgres-highly-available` 2.5.0, which removed the `postgresHA.postgres` block. The HA cluster now reads the same chart-created credentials secret as the single-instance path:

| Removed key | Replacement |
|---|---|
| `postgresHA.postgres.username` | `postgres.credentials.username` |
| `postgresHA.postgres.password` | `postgres.credentials.password` |
| `postgresHA.postgres.database` | `postgres.credentials.database` (must be `temporal`) |
| — | `postgresHA.config.credentialsSecretName` names the secret this chart creates (default `my-temporal-db-credentials`) |

<Warning>
**Use the credentials your cluster already has.** The HA cluster was initialized with the `postgresHA.postgres.*` values you installed with, and PostgreSQL still enforces them. Copy that username and password into `postgres.credentials.username` and `postgres.credentials.password` before upgrading. Putting new values there updates the secret but not the database, and Temporal can no longer authenticate.
</Warning>

An upgrade that still carries the `postgresHA.postgres` block fails with the HA template's message, which begins ``postgres-highly-available: the `postgres` block was REMOVED in 2.5.0`` and tells you to create a dictionary secret. Ignore that part: delete the block and set `postgres.credentials.*` instead.

### Upgrading from 1.2.x

- **From `1.2.0`, HA MinIO backups only:** version `1.2.1` replaced `postgresHA.backup.minio.accessKey` and `postgresHA.backup.minio.secretKey` with `postgresHA.backup.minio.credentialsSecretName`, a dictionary secret you create holding `accessKey` and `secretKey`; see [Backing Up](#backing-up). The HA and single-instance paths now use the same shape.
- **From `1.2.0` or `1.2.1`:** version `1.3.0` renamed the resource limits so the ceiling is no longer ambiguous next to the floor. Rename these keys in your values; an upgrade carrying an old name is refused at render with `resources.cpu was RENAMED to resources.maxCpu` (or the matching message for the other three):

| Removed key | Replacement |
|---|---|
| `resources.cpu` | `resources.maxCpu` |
| `resources.memory` | `resources.maxMemory` |
| `ui.resources.cpu` | `ui.resources.maxCpu` |
| `ui.resources.memory` | `ui.resources.maxMemory` |

The values themselves are unchanged (`1000m` / `2Gi` for the server, `500m` / `512Mi` for the UI), so a release on the defaults upgrades with no resource change.

### Upgrading from 1.x

Temporal supports upgrading **one minor version at a time**. Every 1.x release of this template runs Temporal server 1.29.7, and version 2.0.0 defaults to 1.32.1, so the move takes three upgrades: 1.30.8, then 1.31.4, then the chart defaults. A direct upgrade with the defaults is refused before the database is touched. Run all three steps at `replicas: 1`, and raise `replicas` only after the last one.

<Steps>
  <Step title="Back up first">
    A migrated schema cannot be rolled back. If backups are not on yet, enable `postgresHA.backup` (HA) or `postgres.backup` (single-instance) on your current release as described in [Backing Up](#backing-up), then take a backup now and confirm it succeeded. With logical backups:

    ```bash
    cpln workload cron start RELEASE_NAME-postgres-ha-backup --gvc GVC_NAME
    cpln workload cron get RELEASE_NAME-postgres-ha-backup --gvc GVC_NAME
    ```

    In single-instance mode the cron workload is `RELEASE_NAME-postgres-backup`. With WAL-G, wait for `Backup complete` in the leader's `wal-g-backup` container logs. Volume set snapshots are **not** a supported recovery path for the HA database.
  </Step>
  <Step title="Upgrade to 2.0.0 on Temporal 1.30">
    Upgrade with your existing values file and both images pinned to 1.30.8:

    ```bash
    cpln helm upgrade RELEASE_NAME oci://ghcr.io/controlplane-com/templates/temporal \
      --version 2.0.0 --gvc GVC_NAME -f values.yaml \
      --set image=temporalio/server:1.30.8 --set adminTools.image=temporalio/admin-tools:1.30.8
    ```

    If your values file sets `image: temporalio/auto-setup:…`, delete that line first: version 2.0.0 refuses the auto-setup image.

    <Warning>
    **On the HA database, plan this first step in a maintenance window.** It also updates the bundled PostgreSQL cluster, which restarts every member and fails the leader over, leaving Temporal without its database for about 2.5 minutes after the schema step has finished. Workflows resume afterwards. The later steps, and the single-instance database, have no such outage.
    </Warning>
  </Step>
  <Step title="Wait">
    Wait until the server is ready, then about 10 more minutes.
  </Step>
  <Step title="Upgrade to Temporal 1.31">
    Run the same command with `1.31.4` in both `--set` values, then wait again.
  </Step>
  <Step title="Upgrade to Temporal 1.32">
    Run the same command without the two `--set` values; the chart defaults are 1.32.1.
  </Step>
</Steps>

Each step migrates the schema before the new server starts. A step that skips a minor version is refused before the database is touched: the new replica never becomes ready while the old one keeps serving, and its `admin` container logs `CPLN_TEMPORAL_SKIP_GUARD` with the tag to use next. Set that tag and upgrade again.

Also in this version:

- **AWS backups:** the HA backup no longer attaches AWS's `ReadOnlyAccess` policy. Update your bucket-scoped IAM policy to the full action list under [Backing Up](#backing-up) before upgrading.
- **Temporal 1.32 visibility queries are stricter:** a list filter that compares a search attribute with the wrong type, or an empty `Text` filter, now returns an error instead of results.

### Scaling and Availability

- **`replicas` sets the server count, from 1 to 5.** Every replica runs the full server and they form one Temporal cluster. `3` survives the loss of a replica with capacity to spare; `1` is fine when a short gap per upgrade or restart is acceptable.
- **Add replicas for availability, not throughput.** Each replica's database connection pools shrink as replicas are added, so that the whole cluster stays within the bundled database's connection limit.
- **Changing `replicas` restarts every server replica**, not just an added or removed one, because the per-replica pool sizes change. Changing `internalAccess` also restarts every server replica. Members join or drain and work rebalances on its own.
- **Change `replicas` under light load.** While replicas with the old and the new pool sizes run side by side, the total connection count can briefly exceed the database's limit.
- **Rolling restarts with more than one replica take several minutes.** Replicas are replaced one at a time. A newly started replica may restart its worker service a few times in its first minutes before settling; clients are not affected.
- **Losing a replica:** the remaining replicas take over its workflows and the platform replaces it. Timers fire on time and nothing is lost; clients may see a few timed-out calls right after the loss.
- **Workers scale independently.** Run as many worker workloads and replicas as your task queues need.
- **Database availability is the HA cluster's job.** In the default `postgresHA` mode a PostgreSQL leader failure is handled by Patroni and the HAProxy endpoint keeps the same address. In `postgres` mode there is no failover.
- **Durability is in the database, not the server.** The server workload has no volume. `cpln helm uninstall` deletes the database volume sets and the chart-created credentials secret, taking every workflow history with it.

### Troubleshooting

<AccordionGroup>
  <Accordion title="A server replica stays not ready">
    **Symptom:** A new `RELEASE_NAME-temporal` replica never becomes ready after an install or upgrade.

    **Cause:** The `admin` sidecar gates the server on the schema. Read its logs:

    ```bash
    cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-temporal"}' --limit 50 --since 10m
    ```

    `CPLN_TEMPORAL_SKIP_GUARD` means the image skips a minor version, and the message names the tag to use next. `another replica is migrating the schema` is normal during an upgrade with several replicas.

    **Fix:** For a skipped minor, upgrade again with the named tag on both `image` and `adminTools.image`, as in [Upgrading from 1.x](#upgrading-from-1-x). The old replica keeps serving until then.
  </Accordion>
  <Accordion title="Upgrade fails with the retired auto-setup image">
    **Symptom:** `helm upgrade` stops at render with `temporal: image "temporalio/auto-setup:…" is the retired auto-setup image`.

    **Cause:** Your values file still sets the 1.x server image.

    **Fix:** Delete the `image` line and follow [Upgrading from 1.x](#upgrading-from-1-x).
  </Accordion>
  <Accordion title="Render fails with must carry the same tag">
    **Symptom:** Render fails with `temporal: image (…) and adminTools.image (…) must carry the same tag`.

    **Cause:** Only one of the two images was changed.

    **Fix:** Set both `image` and `adminTools.image` to the same tag.
  </Accordion>
  <Accordion title="Render fails with image tag is not supported">
    **Symptom:** Render fails with `temporal: image tag "…" is not supported`.

    **Cause:** The chart runs only Temporal server 1.30.x, 1.31.x or 1.32.x, given as a full tag.

    **Fix:** Use a full tag in one of those minors, such as `1.32.1`.
  </Accordion>
  <Accordion title="Render fails with replicas must be a whole number from 1 to 5">
    **Symptom:** Render fails with `temporal: replicas must be a whole number from 1 to 5`.

    **Cause:** `replicas` is outside the supported range.

    **Fix:** Set `replicas` between 1 and 5.
  </Accordion>
  <Accordion title="Install fails with enable exactly one database">
    **Symptom:** `helm install` or `helm upgrade` stops at render with `temporal: enable exactly one database`.

    **Cause:** Both database blocks are enabled, or neither is.

    **Fix:** Set exactly one of `postgresHA.enabled` and `postgres.enabled` to `true`. Switching an existing release between modes is a new database, not a migration; the data stays on the old mode's volume set.
  </Accordion>
  <Accordion title="Install fails with postgres.credentials.database must be temporal">
    **Symptom:** Render fails with `temporal: postgres.credentials.database must be "temporal"`.

    **Cause:** The server reads its main store as the literal database `temporal`, so the chart refuses any other value.

    **Fix:** Leave `postgres.credentials.database` at `temporal`.
  </Accordion>
  <Accordion title="Upgrade fails with resources.cpu was RENAMED to resources.maxCpu">
    **Symptom:** `helm upgrade` stops at render with `temporal: resources.cpu was RENAMED to resources.maxCpu` (or the same message for `resources.memory`, `ui.resources.cpu`, `ui.resources.memory`).

    **Cause:** Your values file predates template version `1.3.0`.

    **Fix:** Rename the keys as listed in [Upgrading from 1.2.x](#upgrading-from-1-2-x).
  </Accordion>
  <Accordion title="Upgrade fails with the postgres block was REMOVED in 2.5.0">
    **Symptom:** `helm upgrade` stops at render with a message beginning ``postgres-highly-available: the `postgres` block was REMOVED in 2.5.0``.

    **Cause:** Your values still carry `postgresHA.postgres.username`, `postgresHA.postgres.password` or `postgresHA.postgres.database` from template version `1.1.0` or earlier.

    **Fix:** Delete the `postgresHA.postgres` block and copy the same username and password into `postgres.credentials.*`. Do not create a secret yourself; this chart creates it. See [Upgrading from 1.1.0](#upgrading-from-1-1-0).
  </Accordion>
  <Accordion title="Upgrade fails with config.username was REMOVED in postgres 3.4.0">
    **Symptom:** `helm upgrade` stops at render with `config.username was REMOVED in postgres 3.4.0` (or the same for `config.password` / `config.database`).

    **Cause:** Your single-instance values still use `postgres.config.username`, `postgres.config.password` or `postgres.config.database` from template version `1.0.x`.

    **Fix:** Move the three values to `postgres.credentials.*`. Do not create a secret yourself. See [Upgrading from 1.0.x](#upgrading-from-1-0-x).
  </Accordion>
  <Accordion title="Second release fails with managed by a different release">
    **Symptom:** Installing a second Temporal release in the same org fails with `The resource 'my-temporal-db-credentials' cannot be updated because it is being managed by a different release`, and nothing is created.

    **Cause:** Secret names are organization-wide, and both releases are trying to create the credentials secret under the default name.

    **Fix:** Give the new release its own `postgresHA.config.credentialsSecretName` (or `postgres.config.credentialsSecretName` in single mode). The first release is unaffected.
  </Accordion>
  <Accordion title="Changing historyShards has no effect">
    **Symptom:** After an upgrade that changed `historyShards`, the cluster still reports its original shard count.

    **Cause:** The shard count is fixed when the cluster is first created; the server keeps the original value and ignores the new one.

    **Fix:** None is needed for a running cluster. A different shard count means a new release with a fresh database.
  </Accordion>
  <Accordion title="Workers cannot connect to the frontend">
    **Symptom:** A worker or client fails to resolve or reach the server.

    **Cause:** Either the worker uses the short workload name, which does not resolve, or it runs outside the `internalAccess` scope.

    **Fix:** Connect to `RELEASE_NAME-temporal.GVC_NAME.cpln.local:7233` and make sure the worker's workload is covered by `internalAccess.type` (or listed in `internalAccess.workloads` for `workload-list`). After changing the scope, allow a few minutes before re-testing.
  </Accordion>
  <Accordion title="Backup workload never starts and logs nothing">
    **Symptom:** With MinIO backups enabled, `RELEASE_NAME-postgres-ha-backup` (or `RELEASE_NAME-postgres-backup`, or in `wal-g` mode `RELEASE_NAME-postgres-ha` itself) never becomes ready and `cpln logs` returns zero lines.

    **Cause:** The secret named by `backup.minio.credentialsSecretName` did not exist when the workload was applied.

    **Fix:** Create it as shown in [Backing Up](#backing-up), then read `status.versions[].message` with `cpln workload get-deployments WORKLOAD_NAME --gvc GVC_NAME -o yaml` to confirm the reference resolves, or force a redeployment of the affected workload.
  </Accordion>
  <Accordion title="Python worker crashes on start">
    **Symptom:** A single-file Python worker crashes immediately with an error from inside the Temporal workflow sandbox.

    **Cause:** The module calls `main()` at import time. The SDK's sandbox re-imports the worker module, re-running it.

    **Fix:** Guard the entrypoint with `if __name__ == "__main__":` as in the [First Run](#first-run) sample.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Change `postgres.credentials.password` before installing.** The default `change-me-temporal-db-password` is published in the template repository, and it is the database password in both database modes. It is set once, when the database volume is first initialized.
- **Upgrade Temporal one minor version at a time**, and back up through the database backup first. A skipped minor is refused; see [Upgrading from 1.x](#upgrading-from-1-x).
- **`historyShards` is fixed at first install.** A later change is ignored, so size it before installing.
- **Never expose the Web UI publicly.** It has no authentication, and this template deliberately has no knob to do so. Use `cpln port-forward` or your own authenticating proxy.
- **Use the full `.cpln.local` hostname** in every worker and client; short workload names do not resolve.
- **Give each release its own `config.credentialsSecretName`.** Secret names are organization-wide; a second release on the default name is refused at install.
- **Keep the GVC to one location.** Each location would run its own servers against its own database.
- **Uninstall deletes the database volume sets** and the chart-created credentials secret, taking every workflow history with it. Enable backups if the data matters.
