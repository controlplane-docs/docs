## Overview

TimescaleDB is a time-series database built as a PostgreSQL extension: hypertables that partition by time automatically, columnar compression, continuous aggregates and retention policies, all alongside ordinary relational tables and reachable from any PostgreSQL client or ORM. This template deploys one PostgreSQL 18 server with the TimescaleDB Community extension preloaded and created in your database, on a persistent volume, with an optional [PgBouncer](https://www.pgbouncer.org/) connection pooler in front of it and an optional cron job that writes compressed `pg_dumpall` backups to AWS S3, Google Cloud Storage or a MinIO (S3-compatible) bucket.

Database credentials are **not** template values. The server reads its username, password and database name from a [dictionary secret](/guides/create-secret/dictionary) you create before installing, so no password passes through Helm or lands in the release. The template creates no credential secret of its own.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have. It does not create or manage a GVC.
</Note>

<Note>
This is a single server, not a cluster — there is no replication or failover. For an automatically failing-over TimescaleDB cluster use [TimescaleDB Highly Available](/template-catalog/templates/timescaledb-highly-available).
</Note>

<Info>
TimescaleDB is licensed under the Apache-2.0 license for its core and the Timescale License (TSL) for the Community features. It is free to self-host, including compression, continuous aggregates and retention; the license only forbids reselling TimescaleDB itself as a managed database service.
</Info>

## Prerequisites

One secret must exist before you install. It holds the credentials your applications put in their connection strings. Secrets are org-level, so no GVC flag is involved.

<Steps>
  <Step title="Create the database credentials secret">
    A [dictionary secret](/guides/create-secret/dictionary) holding exactly three keys — `username`, `password` and `database`. The server creates that role (as a superuser) and that database the first time the volume is initialized, and creates the TimescaleDB extension inside that database:

    ```bash
    cpln secret create-dictionary --name SECRET_NAME \
      --entry username=postgres \
      --entry password='YOUR-STRONG-PASSWORD' \
      --entry database=mydb
    ```

    Set `config.credentialsSecretName` to this name. Read it back later with `cpln secret reveal SECRET_NAME -o yaml` — a bare `cpln secret reveal` prints only a summary table, not the values.
  </Step>
</Steps>

<Warning>
**Create the secret before installing, or the deployment wedges silently.** A `config.credentialsSecretName` that points at a secret which does not exist installs successfully and then never starts. The container never runs, so `cpln logs` returns zero lines. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-timescaledb --gvc GVC_NAME -o yaml
```

```text
The secret SECRET_NAME no longer exists. Workload updates are paused until the
secret is added or the reference to the secret removed.
```

Use `get-deployments` — plain `cpln workload get` has no `versions` key. Creating the missing secret repairs the deployment on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-timescaledb --gvc GVC_NAME` to skip the wait.
</Warning>

Backups are optional and need a bucket plus, for AWS or GCP, a Control Plane [cloud account](/guides/create-cloud-account) — and for MinIO a second prerequisite secret. See [Backing Up](#backing-up). Nothing else is required for a default install.

## Configuration

Each block below is the shipped default for that part of `values.yaml`.

### Image and Resources

```yaml
image: timescale/timescaledb:2.28.3-pg18 # PostgreSQL 18 + TimescaleDB Community edition

resources:
  minCpu: 200m
  minMemory: 512Mi
  maxCpu: 500m
  maxMemory: 1024Mi # timescaledb-tune sizes shared_buffers/workers from this at first boot
```

Keep `image` in the default (Community) tag series. The `-oss` tags are an Apache-only build that removes compression, continuous aggregates and retention policies. If you pin a different PostgreSQL major, match `backup.image` to it (see [Backup](#backup)).

<Note>
`timescaledb-tune` sizes PostgreSQL's memory and worker settings from the container limit only at first boot, while the data volume is empty. Raising `resources.maxMemory` on an existing deployment does not retune the server — change the settings with `ALTER SYSTEM` inside PostgreSQL, or reinstall on a fresh volume. On a stateful workload the ratio of `maxCpu` to `minCpu` may not exceed 4:1; raising `maxCpu` alone can cross that limit and is rejected when the workload is applied.
</Note>

### Credentials

```yaml
config:
  # REQUIRED PREREQUISITE SECRET — CREATE IT BEFORE YOU INSTALL.
  # A `dictionary` secret holding exactly three keys: `username`, `password`
  # and `database`. If it does not exist at install time the deployment
  # WEDGES silently — `cpln logs` returns nothing at all. See Prerequisites
  # in the README for the exact `cpln secret create-dictionary` command.
  credentialsSecretName: my-timescaledb-credentials
```

The TimescaleDB extension is created automatically in the database named by the secret's `database` key. The three keys are applied only when the volume is first initialized; changing the secret afterwards does not change the stored password — see [Rotating the Password](#rotating-the-password).

### Storage

```yaml
volumeset:
  capacity: 10 # initial capacity in GiB (minimum is 10)
  autoscaling:
    enabled: false # Set to true to enable autoscaling
    maxCapacity: 100 # Maximum capacity in GiB when autoscaling is enabled
    minFreePercentage: 10 # Minimum free percentage to trigger scaling when autoscaling is enabled
    scalingFactor: 1.2 # Scaling factor to determine how much to scale up when autoscaling is triggered
```

### Internal Access

```yaml
internalAccess: # Sets the internal firewall scope - if set to none, replicas will not be able to reach each other
  type: same-gvc # options: none, same-gvc, same-org, workload-list
  workloads:  # Note: can only be used if type is same-gvc or workload-list
    #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

| Type | Who can reach port `5432` |
|------|-------------|
| `none` | No workload |
| `same-gvc` | Every workload in the same GVC |
| `same-org` | Every workload in the same org |
| `workload-list` | Only the workloads listed in `internalAccess.workloads` |

The same setting applies to the PgBouncer workload when it is enabled. A change to `internalAccess` can take several minutes to take effect — re-test before concluding it did not apply.

### Public Access

```yaml
publicAccess:
  enabled: false # exposes 5432 via a TCP load balancer; connections are unencrypted — prefer internal access
```

<Warning>
Public access is unencrypted. The image ships no TLS certificates, so every connection over the public endpoint is plaintext. Keep `publicAccess.enabled: false` and connect from inside the GVC or through `cpln port-forward` unless you accept plaintext connections.
</Warning>

### PgBouncer

PgBouncer multiplexes many application connections into a small pool of real database connections. When enabled it becomes the endpoint your applications connect to, and it reads the same credentials secret and identity as the server — nothing extra to configure.

```yaml
pgbouncer:
  enabled: false
  image: edoburu/pgbouncer:v1.25.1-p0
  poolMode: transaction # options: session, transaction, statement
  defaultPoolSize: 25   # number of real Postgres connections PgBouncer maintains
  maxClientConn: 1000   # maximum number of client connections PgBouncer accepts
  replicas: 1

  resources:
    cpu: 200m
    memory: 128Mi
```

| `poolMode` | Behaviour |
|------|-------------|
| `transaction` | The server connection is held for one transaction. Best for most web and API workloads; not compatible with `SET` variables, temporary tables or advisory locks. |
| `session` | Held for the whole client session. Compatible with everything, less reuse — raise `defaultPoolSize` to your expected concurrency. |
| `statement` | Returned after every statement. Transactions are not supported. |

### Backup

A cron workload runs `pg_dumpall` on the schedule and uploads a gzip-compressed SQL dump of every database and role to the bucket for the chosen `provider`. It authenticates with the `username` and `password` from your credentials secret. Each provider's bucket, cloud account and secret steps are under [Backing Up](#backing-up).

```yaml
backup:
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0 # PG18 client, matches server major
  schedule: "0 2 * * *"   # daily at 2am UTC

  resources:
    cpu: 100m
    memory: 128Mi

  provider: aws # Options: aws, gcp, or minio

  aws:
    bucket: my-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: timescaledb/backups # folder name where your backups will be stored

  gcp:
    bucket: my-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: timescaledb/backups # folder name where your backups will be stored

  minio: # Backup to a self-hosted MinIO workload (or any S3-compatible endpoint)
    endpoint: http://my-minio-workload:9000 # e.g. http://WORKLOAD_NAME:9000 for an internal MinIO template deployment
    bucket: my-backup-bucket
    # REQUIRED PREREQUISITE SECRET when provider is `minio` — a `dictionary`
    # secret holding exactly two keys: `accessKey` and `secretKey`. For the
    # minio template these are its admin.username and admin.password.
    credentialsSecretName: my-timescaledb-minio-credentials
    prefix: timescaledb/backups # folder name where your backups will be stored
```

<Note>
`backup.image` must match the server's PostgreSQL major version: tag `18.1.0` for the default `-pg18` image, `17.1.0` if you pin a `-pg17` image.
</Note>

## Connecting

Everything below is reachable from inside the GVC, subject to `internalAccess.type`; the public endpoint exists only when `publicAccess.enabled: true`.

| What | Address | Notes |
|---|---|---|
| TimescaleDB, direct | `RELEASE_NAME-timescaledb.GVC_NAME.cpln.local:5432` | Always available. |
| TimescaleDB, pooled | `RELEASE_NAME-pgbouncer.GVC_NAME.cpln.local:5432` | Only when `pgbouncer.enabled: true`. Prefer it when the pooler is on. |
| Public endpoint | `status.canonicalEndpoint` of the `RELEASE_NAME-timescaledb` workload, port `5432` | Only when `publicAccess.enabled: true`; unencrypted. Read it with `cpln workload get RELEASE_NAME-timescaledb --gvc GVC_NAME -o yaml`. |
| Credentials | `cpln secret reveal SECRET_NAME -o yaml` | The `username`, `password` and `database` keys. Never stored in the Helm release. |

To verify from your own machine, tunnel to the server and connect with `psql`:

```bash
cpln port-forward RELEASE_NAME-timescaledb 5432:5432 --gvc GVC_NAME
```

```bash
psql "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -c "select extversion from pg_extension where extname = 'timescaledb'"
```

Or run `psql` inside the container, where the credentials are already present as environment variables:

```bash
cpln workload exec RELEASE_NAME-timescaledb --gvc GVC_NAME --container timescaledb -- psql -U USERNAME -d DATABASE -c 'select version()'
```

### Using Hypertables

Any PostgreSQL client or ORM works unchanged. Turn a regular table into a [hypertable](https://docs.timescale.com/use-timescale/latest/hypertables/) (automatically partitioned by time) and query it with time buckets:

```sql
CREATE TABLE metrics (time timestamptz NOT NULL, device text, value double precision);
SELECT create_hypertable('metrics', by_range('time'));

INSERT INTO metrics VALUES (now(), 'sensor-1', 23.5);

SELECT time_bucket('1 hour', time) AS bucket, device, avg(value)
FROM metrics
GROUP BY bucket, device
ORDER BY bucket;
```

From here you can add columnar compression, continuous aggregates and retention policies — all Community features included in the default image. Compression and retention run as background jobs inside the database; their status is in the `timescaledb_information.jobs` and `timescaledb_information.job_errors` views.

## Operations

### Backing Up

Backups are off by default. Enable them with `backup.enabled: true`, pick a `backup.provider`, and complete that provider's setup below first. The job writes `postgres-TIMESTAMP.sql.gz` objects under `backup.PROVIDER.prefix` in your bucket on every run of `backup.schedule`. Rehearse a backup and a [restore](#restoring-a-backup) before relying on either.

#### AWS S3

1. Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.

2. If you do not have one yet, create a Control Plane [cloud account](/guides/create-cloud-account) for the AWS account holding the bucket. Set `backup.aws.cloudAccountName` to its name.

3. Create an IAM policy scoped to exactly that bucket, replacing `YOUR_BUCKET_NAME`:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion",
                "s3:GetBucketLocation",
                "s3:AbortMultipartUpload",
                "s3:ListBucketMultipartUploads",
                "s3:ListMultipartUploadParts"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.policyName` to that policy's name. The template attaches it to the workload identity and nothing else — the bucket in your policy is the only storage the backup job can reach.

#### GCS

1. Create a GCS bucket. Set `backup.gcp.bucket` to its name.

2. Create a Control Plane [cloud account](/guides/create-cloud-account) for the GCP project holding the bucket, and set `backup.gcp.cloudAccountName` to its name. Access is keyless — no stored credentials.

3. Grant the cloud account's service account the **Storage Admin** role (`roles/storage.objectAdmin` scoped to the bucket also works). The template additionally binds the identity to `roles/storage.objectAdmin` on exactly the bucket in `backup.gcp.bucket`.

#### MinIO

No cloud account is needed — the job authenticates with a second prerequisite secret.

1. Create the bucket in MinIO. Set `backup.minio.bucket` to its name.

2. Set `backup.minio.endpoint` to the S3 API address including the port. For the [MinIO](/template-catalog/templates/minio) template deployed in the same GVC that is `http://WORKLOAD_NAME.GVC_NAME.cpln.local:9000`.

3. Create a [dictionary secret](/guides/create-secret/dictionary) holding exactly the keys `accessKey` and `secretKey`, and set `backup.minio.credentialsSecretName` to its name. For the MinIO template these are the `username` and `password` from its own credentials secret:

```bash
cpln secret create-dictionary --name SECRET_NAME \
  --entry accessKey=MINIO_ACCESS_KEY \
  --entry secretKey=MINIO_SECRET_KEY
```

The policy this template creates grants the identity `reveal` on this secret as well as the database credentials secret, and on nothing else. Like the database credentials secret, it must exist before you install or upgrade with `provider: minio` — a missing secret wedges the backup workload the same way, and the render refuses an empty `backup.minio.credentialsSecretName`.

### Restoring a Backup

Restoring TimescaleDB is **not** the vanilla PostgreSQL procedure. The target database must already have the TimescaleDB extension at the **same version** as the dump, and the replay must be wrapped in `timescaledb_pre_restore()` and `timescaledb_post_restore()` — the first stops the background workers and puts the database in restoring mode, the second brings it back. Skipping `timescaledb_post_restore()` leaves compression and retention jobs paused.

<Warning>
The procedures below follow the chart's configuration, the backup image's script and the upstream TimescaleDB documentation, but they have **not** been exercised end to end against this template. Rehearse them on a throwaway release before you need them.
</Warning>

Each scheduled backup is a gzip-compressed `pg_dumpall` script that recreates every role and database it contains. Restore it into a **fresh install** running the same image tag as the one the dump was taken from: the first boot has already created your database with the extension, so you prepare that database, replay the script against the `postgres` maintenance database, then finish. Run the commands from a client that can reach both the bucket and the server — a workload inside the GVC, or your own machine with `cpln port-forward RELEASE_NAME-timescaledb 5432:5432 --gvc GVC_NAME` open and `--host=127.0.0.1` in place of the internal hostname.

<Tabs>
  <Tab title="AWS S3">

    export PGPASSWORD="PASSWORD"

    psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=DATABASE \
      -c "SELECT timescaledb_pre_restore();"

    aws s3 cp "s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - \
      | gunzip \
      | psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=postgres

    psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=DATABASE \
      -c "SELECT timescaledb_post_restore();"

    unset PGPASSWORD
    ```

    psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=DATABASE \
      -c "SELECT timescaledb_pre_restore();"

    aws s3 cp "s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - --endpoint-url "http://MINIO_ENDPOINT:9000" \
      | gunzip \
      | psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=postgres

    psql --host=RELEASE_NAME-timescaledb.GVC_NAME.cpln.local --port=5432 --username=USERNAME --dbname=DATABASE \
      -c "SELECT timescaledb_post_restore();"

    unset PGPASSWORD AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
    ```
  </Tab>
</Tabs>

`already exists` errors for the role and database that the server created at first boot are expected; the rest of the script loads normally. If the dump holds additional databases, they are created during the replay without `timescaledb_pre_restore()` having run in them — restore those one at a time with the per-database procedure below instead.

**Single database, upstream procedure.** TimescaleDB's own documentation describes a per-database `pg_dump -Fc` and `pg_restore` cycle. With `cpln port-forward RELEASE_NAME-timescaledb 5432:5432 --gvc GVC_NAME` open you can run it from your machine against this template; the target database must exist with the extension already created, and `pg_restore` must **not** use `-j`, which does not restore the TimescaleDB catalogs correctly:

```bash
pg_dump -Fc "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -f DATABASE.bak
```

```bash
psql "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -c "SELECT timescaledb_pre_restore();"
pg_restore -Fc -d "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" DATABASE.bak
psql "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -c "SELECT timescaledb_post_restore();"
```

### Rotating the Password

The server reads the secret only when the volume is first initialized, so change the password inside PostgreSQL first, then update the secret to match:

```sql
ALTER ROLE USERNAME WITH PASSWORD 'NEW-STRONG-PASSWORD';
```

Workloads resolve the secret when a replica starts, so an updated secret is not picked up by a running replica. The backup job reads it fresh on its next scheduled run; if PgBouncer is enabled, force a redeployment so it reconnects with the new password:

```bash
cpln workload force-redeployment RELEASE_NAME-pgbouncer --gvc GVC_NAME
```

### Upgrading From Earlier Versions

Three template versions changed what you must supply. An upgrade that still carries a removed key is refused at render, so `cpln helm upgrade` fails and your existing release is left running rather than restarted against a different password.

| | Before | After |
|---|---|---|
| Database credentials (1.1.0) | `config.username`, `config.password`, `config.database` values, written to the chart-created secret `RELEASE_NAME-tsdb-config` | `config.credentialsSecretName` → a dictionary secret you create; `RELEASE_NAME-tsdb-config` is now created only for backups and holds no credentials |
| AWS backup identity (1.1.1) | Bucket-scoped policy plus the AWS managed policy `aws::ReadOnlyAccess`, which read every bucket in the account | Bucket-scoped policy only — update your IAM policy to the full action list under [AWS S3](#aws-s3) **before** upgrading, since the managed policy was silently supplying any read action yours omitted |
| MinIO backup credentials (1.2.0) | `backup.minio.accessKey`, `backup.minio.secretKey` values | `backup.minio.credentialsSecretName` → a dictionary secret you create |

<Steps>
  <Step title="Read the credentials the database already uses">
    An existing database keeps the credentials it was initialized with. Recover them from your current values file, or from the secret the old version created — **before** upgrading from 1.0.0:

    ```bash
    cpln secret reveal RELEASE_NAME-tsdb-config -o yaml
    ```
  </Step>
  <Step title="Create the prerequisite secret with those same values">
    Follow [Prerequisites](#prerequisites) using the existing `username`, `password` and `database`. Different values here do not change the database — they only leave the workload unable to authenticate.
  </Step>
  <Step title="Remove the old keys from your values">
    Delete `config.username`, `config.password` and `config.database`, and set `config.credentialsSecretName` to your secret's name. If you back up to MinIO, replace `backup.minio.accessKey` and `backup.minio.secretKey` with `backup.minio.credentialsSecretName` and create that secret as described under [MinIO](#minio). If you back up to AWS, check your IAM policy against the action list under [AWS S3](#aws-s3).
  </Step>
  <Step title="Upgrade, then rotate any default password">
    After the upgrade succeeds, change any password that came from a 1.0.0 default — those defaults were published in the public template repository, so treat them as compromised. Follow [Rotating the Password](#rotating-the-password).
  </Step>
</Steps>

<Warning>
**`RELEASE_NAME-tsdb-config` no longer holds credentials.** Anything outside this release that read the username or password from it by name — another workload's environment, a policy, or a parent chart bundling TimescaleDB as a subchart — must be pointed at the secret you created instead. A reference to a key that no longer exists does not fail loudly; it wedges the referring workload silently, exactly as described in [Prerequisites](#prerequisites).
</Warning>

### Scaling and Availability

- The server is pinned to one replica. Do not raise it — a single volume set backs a single server, and a second replica cannot mount it. Choose [TimescaleDB Highly Available](/template-catalog/templates/timescaledb-highly-available) when you need failover.
- PgBouncer is stateless; `pgbouncer.replicas` scales it horizontally for high connection counts.
- Every `cpln helm upgrade` restarts the server, including the first upgrade after an install even when nothing changed. Plan each one as a short write outage.
- A node failure reschedules the server and reattaches the same volume. The exposure is minutes of downtime, not data loss.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Workload never becomes ready and cpln logs returns nothing">
    **Symptom:** the install succeeds, the workload stays not ready indefinitely, and `cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-timescaledb"}' --limit 50 --since 10m` returns zero lines.

    **Cause:** `config.credentialsSecretName` names a secret that does not exist, so the container is never started. The message is only visible in `status.versions[].message`:

    ```bash
    cpln workload get-deployments RELEASE_NAME-timescaledb --gvc GVC_NAME -o yaml
    ```

    ```text
    The secret SECRET_NAME no longer exists. Workload updates are paused until the
    secret is added or the reference to the secret removed.
    ```

    **Fix:** create the secret as in [Prerequisites](#prerequisites). The deployment recovers on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-timescaledb --gvc GVC_NAME`. The same applies to `RELEASE_NAME-timescaledb-backup` when `backup.minio.credentialsSecretName` names a missing secret.
  </Accordion>
  <Accordion title="Upgrade fails with 'config.username and config.password were REMOVED'">
    **Symptom:** `cpln helm upgrade` stops before touching any resource:

    ```text
    Error: execution error at (timescaledb/templates/identity.yaml:1:4): timescaledb: config.username
    and config.password were REMOVED — they are now a `dictionary` secret you create, named by
    config.credentialsSecretName, holding the keys `username`, `password` and `database`. Delete
    them from your values. See Prerequisites in the README.
    ```

    **Cause:** your values still carry the credential keys that were removed in 1.1.0.

    **Fix:** follow [Upgrading From Earlier Versions](#upgrading-from-earlier-versions). Your running release is unaffected until the upgrade succeeds.
  </Accordion>
  <Accordion title="Upgrade fails with 'backup.minio.accessKey and backup.minio.secretKey were REMOVED'">
    **Symptom:** `cpln helm upgrade` (or a fresh install) with `backup.provider: minio` stops at render:

    ```text
    Error: execution error at (timescaledb/templates/identity.yaml:2:4): timescaledb: backup.minio.accessKey
    and backup.minio.secretKey were REMOVED — they are now a `dictionary` secret you create, named by
    backup.minio.credentialsSecretName, holding the keys `accessKey` and `secretKey`. Delete them from
    your values. See Backup setup in the README.
    ```

    An empty `backup.minio.credentialsSecretName` is refused with its own message: `backup.minio.credentialsSecretName is required when provider is 'minio'`.

    **Cause:** your values still carry the MinIO credential keys that were removed in 1.2.0, or do not name the replacement secret.

    **Fix:** create the MinIO credentials secret as described under [MinIO](#minio), set `backup.minio.credentialsSecretName`, and delete the two old keys.
  </Accordion>
  <Accordion title="Password changed in the secret but the old one still works">
    **Symptom:** you updated the `password` key in the credentials secret, but the server still accepts the previous password and rejects the new one.

    **Cause:** the secret is applied only when the volume is first initialized. Afterwards the stored password lives in the database, not the secret.

    **Fix:** change it inside PostgreSQL and then update the secret to match — see [Rotating the Password](#rotating-the-password).
  </Accordion>
  <Accordion title="Compression, continuous aggregate or retention calls fail with 'function ... does not exist'">
    **Symptom:** `add_compression_policy`, `add_retention_policy` or `CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)` fails with a `function ... does not exist` style error, while hypertables work.

    **Cause:** `image` points at an `-oss` tag. Those are Apache-only builds with the Community (TSL) features removed.

    **Fix:** use a tag from the default series, such as the shipped `timescale/timescaledb:2.28.3-pg18`.
  </Accordion>
  <Accordion title="Compression or retention jobs stop running after a restore">
    **Symptom:** `timescaledb_information.jobs` shows the policies but nothing executes, typically after a restore.

    **Cause:** `timescaledb_pre_restore()` was run and `timescaledb_post_restore()` was not. Background workers stay stopped until the second call.

    **Fix:** run `SELECT timescaledb_post_restore();` in the affected database. Check `timescaledb_information.job_errors` for anything that failed in between.
  </Accordion>
  <Accordion title="Queries through PgBouncer fail on SET, temporary tables or advisory locks">
    **Symptom:** statements that work against `RELEASE_NAME-timescaledb` directly fail or behave inconsistently through `RELEASE_NAME-pgbouncer`.

    **Cause:** `pgbouncer.poolMode: transaction` returns the server connection after every transaction, so session-level state is not preserved.

    **Fix:** switch to `pgbouncer.poolMode: session` (and raise `defaultPoolSize` to your expected concurrency), or connect such clients to the server directly.
  </Accordion>
  <Accordion title="Apply rejected with 'The ratio between cpu and minCpu must be less than 4:1'">
    **Symptom:** an install or upgrade fails and the server workload is not created or updated.

    **Cause:** `resources.maxCpu` is more than four times `resources.minCpu`, which the platform rejects on a stateful workload.

    **Fix:** raise `resources.minCpu` or lower `resources.maxCpu` so the ratio is at most 4:1.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the credentials secret before installing.** A reference to a secret that does not exist wedges the workload with no log output; see [Prerequisites](#prerequisites) for the one command that shows the reason.
- **Credentials are read only when the volume is first initialized.** Rotate with `ALTER ROLE` inside PostgreSQL, then update the secret — see [Rotating the Password](#rotating-the-password).
- **Tuning is captured at first boot only.** `timescaledb-tune` sizes memory settings from the container limit while the volume is empty; raising `resources.maxMemory` later does not retune.
- **Do not scale the server past one replica.** It is a single instance on a single volume, not a replicated cluster.
- **Keep the image tag in the default (Community) series.** `-oss` tags remove compression, continuous aggregates and retention policies. Match `backup.image` to the server's PostgreSQL major.
- **Public access is unencrypted.** The image ships no TLS certificates — keep `publicAccess.enabled: false` unless you accept plaintext connections.
- **Restores need `timescaledb_pre_restore()` and `timescaledb_post_restore()`** around the replay, on a server with the same extension version — see [Restoring a Backup](#restoring-a-backup).
- **`cpln helm uninstall` deletes the volume set** and the database with it; a final snapshot is kept for 7 days. Your credentials secrets are yours and are left alone.
- **Every `cpln helm upgrade` restarts the server.** Treat each one as a short planned write outage.
