## Overview

ToolJet is an open-source, low-code platform for building internal tools: a visual app builder with 50+ datasource connectors, workflows, and the built-in ToolJet Database. This template deploys the ToolJet server — UI and API on port `3000`, with PostgREST and a fallback Redis bundled inside the image — backed by a bundled PostgreSQL that holds both the application database and the ToolJet Database. The default is a single replica; `tooljet.replicas` scales out once the optional Redis is enabled.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have — it does not create or manage a GVC.
</Note>

## Prerequisites

ToolJet reads its three root-of-trust keys from a [dictionary secret](/guides/create-secret/dictionary) that you create **before** installing. The key values never pass through Helm values.

<Steps>
  <Step title="Create the key secret">
    Generate the three keys the same way ToolJet's own setup scripts do, straight into the secret:

    ```bash
    cpln secret create-dictionary --name KEYS_SECRET_NAME \
      --entry SECRET_KEY_BASE="$(openssl rand -hex 64)" \
      --entry LOCKBOX_MASTER_KEY="$(openssl rand -hex 32)" \
      --entry PGRST_JWT_SECRET="$(openssl rand -hex 32)"
    ```

    | Key | Purpose |
    |---|---|
    | `SECRET_KEY_BASE` | Signs sessions and cookies. |
    | `LOCKBOX_MASTER_KEY` | Encrypts every stored datasource credential. |
    | `PGRST_JWT_SECRET` | Signs the JWTs the in-image PostgREST accepts for ToolJet Database requests. |

    Set `secrets.name` to this name. Secrets are org-level, so no GVC flag is involved.
  </Step>
  <Step title="Back the keys up outside Control Plane">
    `SECRET_KEY_BASE` and `LOCKBOX_MASTER_KEY` are write-once: rotating `LOCKBOX_MASTER_KEY` makes every datasource credential ToolJet has stored undecryptable. Keep a copy of all three values somewhere safe.
  </Step>
</Steps>

<Warning>
Create the secret **before** installing. Installing without it reports success, but the deployment then wedges silently — `cpln logs` returns nothing, and the only place the missing secret is named is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-tooljet --gvc GVC_NAME -o yaml
```

The message reads `The secret KEYS_SECRET_NAME no longer exists. Workload updates are paused until the secret is added or the reference to the secret removed.` Creating the secret lets the deployment recover on its own; `cpln workload force-redeployment RELEASE_NAME-tooljet --gvc GVC_NAME` skips the wait.
</Warning>

Everything else works with the defaults. Two optional features need their own setup first:

- **Authenticated SMTP** — a dictionary secret holding `SMTP_USERNAME` and `SMTP_PASSWORD`, and a decision made **before** installing, because ToolJet only picks up mail settings on its first boot. See [Email](#email).
- **Scheduled database backups** — a bucket and cloud account for the bundled PostgreSQL. See [Backing Up](#backing-up).

## Installation

Once your key secret exists, install from the marketplace registry, pointing `secrets.name` at it and replacing the bundled database password:

```bash
cpln helm install RELEASE_NAME oci://ghcr.io/controlplane-com/templates/tooljet \
  --version 1.2.0 --gvc GVC_NAME \
  --set secrets.name=KEYS_SECRET_NAME \
  --set postgres.credentials.password='YOUR-DB-PASSWORD'
```

Installing a second ToolJet release in the same org? Also set `postgres.config.credentialsSecretName` to a name no other release uses — secret names are org-wide. If you want email invitations, add the `smtp.*` values to this first install as well (see [Email](#email)).

## Configuration

### ToolJet Server

```yaml
tooljet:
  image: tooljet/tooljet:v3.20.204-lts   # official LTS image; PostgREST and a fallback Redis are bundled in-image
  replicas: 1                 # >=2 requires redis.enabled=true (shared job queue + multiplayer coordination)
  host: ""                    # public base URL ToolJet advertises, scheme included; empty = derive from the canonical endpoint
  resources:
    minCpu: 500m
    maxCpu: 2000m
    minMemory: 1Gi
    maxMemory: 4Gi   # first-boot migrations OOM below this (image bakes a 4096MB Node heap)
```

Set `tooljet.host` only when you serve ToolJet on a custom domain; leave it empty and ToolJet derives its public URL from the workload's canonical endpoint.

<Warning>
Do not lower `tooljet.resources.maxMemory` below the default `4Gi`. The image bakes a 4096 MB Node heap, and the first boot's schema migrations are killed for running out of memory at smaller limits (the container exits with code `137`), leaving the workload in a crash loop that never finishes migrating.
</Warning>

### Key Secret

```yaml
secrets:
  name: my-tooljet-secrets    # dictionary secret with SECRET_KEY_BASE, LOCKBOX_MASTER_KEY and PGRST_JWT_SECRET — MUST exist before install
```

The secret itself is created in [Prerequisites](#prerequisites); only its name is a value.

### Email

SMTP powers user invitations and password resets. It is off by default, and a default install works without it — the first visitor still becomes Super Admin.

```yaml
smtp:
  enabled: false               # only takes effect at INITIAL install — a first-boot migration seeds it; enabling via a later upgrade does nothing
  host: smtp.example.com       # SMTP server host (SMTP_DOMAIN)
  port: 587                    # SMTP server port
  fromEmail: no-reply@example.com   # DEFAULT_FROM_EMAIL
  auth:
    secretName: ""             # optional dictionary secret with SMTP_USERNAME + SMTP_PASSWORD; empty = unauthenticated relay
```

For an authenticated relay, create the credentials secret before installing and set `smtp.auth.secretName` to its name. The ToolJet identity is granted `reveal` on exactly that secret.

```bash
cpln secret create-dictionary --name SMTP_SECRET_NAME \
  --entry SMTP_USERNAME=apikey \
  --entry SMTP_PASSWORD='YOUR-SMTP-PASSWORD'
```

<Warning>
Configure SMTP at the **initial install**. ToolJet seeds its mail settings from the environment during a first-boot migration, so enabling `smtp.*` through a later `helm upgrade` has no effect — the values reach the workload, but ToolJet keeps mail disabled. Decide before you install.
</Warning>

### Access

```yaml
publicAccess:
  enabled: true               # HTTPS UI + API on the auto *.cpln.app endpoint; false = internal-only
internalAccess:
  type: same-gvc              # none | same-gvc | same-org | workload-list
  workloads: []               # used only with workload-list, e.g. //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

With `publicAccess.enabled: false` there is no public endpoint; external requests are refused and only workloads allowed by `internalAccess` reach ToolJet (plus your own machine through a tunnel — see [Connecting](#connecting)).

| `internalAccess.type` | Description |
|---|---|
| `none` | No internal access. |
| `same-gvc` | Allow access from all workloads in the same GVC (default). |
| `same-org` | Allow access from all workloads in the same organization. |
| `workload-list` | Allow access only from the workloads listed in `internalAccess.workloads`. |

### Bundled PostgreSQL

```yaml
postgres:
  image: postgres:16          # upstream-proven with the bundled PostgREST 12.2.0
  credentials:                # the chart writes these into the secret named below — nothing for you to create
    username: tooljet
    password: change-me-tooljet-pg   # change before installing — seeds the database on first boot
    database: tooljet         # application database; tooljet_db is auto-created alongside it
  config:
    credentialsSecretName: my-tooljet-db-credentials   # secret this chart CREATES; names are org-wide, so one per release
  resources:
    minCpu: 250m
    maxCpu: 1000m
    minMemory: 512Mi
    maxMemory: 1Gi
  volumeset:
    capacity: 10              # GiB (minimum 10)
```

One PostgreSQL instance backs the whole deployment, and ToolJet's boot scripts create every database it needs using the credentials above:

| Database | Contents |
|---|---|
| `tooljet` | Apps, users, workspaces, settings, and encrypted datasource credentials. |
| `tooljet_db` | The ToolJet Database — user tables created in the UI, served through the in-image PostgREST. |
| `sample_db` | Sample data created by ToolJet's boot scripts. |

`postgres.credentials.password` seeds the database on first boot and is not updated by later value edits — set it before you install. It is bundled plumbing, so the chart creates the credentials secret for you; it is not a prerequisite. Scheduled backups of this database are configured under [Backing Up](#backing-up).

<Note>
The ToolJet Database is a core part of ToolJet 3.x and cannot be turned off.
</Note>

### Bundled Redis

```yaml
redis:
  enabled: false              # false = a single ToolJet replica uses the Redis bundled in the image
  redis:
    image: redis:7.4
    replicas: 1               # keep at 1 — ToolJet is not Sentinel-aware
    auth:
      password:
        enabled: false        # true = require AUTH; the password is wired into ToolJet as REDIS_PASSWORD
        value: change-me-tooljet-redis
    resources:
      cpu: 200m
      memory: 256Mi
      minCpu: 80m
      minMemory: 128Mi
  sentinel:
    image: redis:7.4
    replicas: 1               # monitor only — no failover target exists with one data node
    resources:
      cpu: 200m
      memory: 256Mi
      minCpu: 80m
      minMemory: 128Mi
```

`redis.enabled: true` deploys the [redis](/template-catalog/templates/redis) template and points ToolJet at it; it is required for more than one ToolJet replica (see [Scaling and Availability](#scaling-and-availability)). With `redis.redis.auth.password.enabled: true` the password is stored in the chart-created `RELEASE_NAME-redis-auth-password` secret, which the ToolJet identity is granted `reveal` on.

<Warning>
Keep `redis.redis.replicas` and `redis.sentinel.replicas` at `1`. ToolJet's Redis client is not Sentinel-aware and connects straight to the service DNS name, so additional data nodes would spread writes onto read-only replicas. The chart refuses to render any other value.
</Warning>

## Connecting

| What | Address | Notes |
|---|---|---|
| Public UI and API | `https://<canonical>.cpln.app` | Assigned automatically while `publicAccess.enabled` is `true`. Read it from `status.canonicalEndpoint` with `cpln workload get RELEASE_NAME-tooljet --gvc GVC_NAME -o yaml`. |
| Health check | `/api/health` | Unauthenticated, on the same host. In the free tier its `license` field reports as invalid — that is expected. |
| Internal (same GVC) | `http://RELEASE_NAME-tooljet.GVC_NAME.cpln.local:3000` | Reachable per `internalAccess.type`. |
| Login | The Super Admin account created during first-run onboarding | ToolJet ships no default account. |
| PostgreSQL | `RELEASE_NAME-postgres.GVC_NAME.cpln.local:5432` | `username` / `password` / `database` from `cpln secret reveal SECRET_NAME -o yaml`, where `SECRET_NAME` is your `postgres.config.credentialsSecretName`. |
| Redis | `RELEASE_NAME-redis.GVC_NAME.cpln.local:6379` | Only with `redis.enabled: true`. |

With `publicAccess.enabled: false` there is no public endpoint; reach the UI from your machine through a tunnel instead and open `http://localhost:3000`:

```bash
cpln port-forward RELEASE_NAME-tooljet 3000:3000 --gvc GVC_NAME
```

### First Run

ToolJet ships no default account. The first person to open the endpoint completes the Super Admin onboarding and creates the initial workspace — and with the default `publicAccess.enabled: true` that form is reachable by anyone who finds the endpoint, so claim it as soon as the workload reports ready.

<Steps>
  <Step title="Wait for the ToolJet workload to report ready">
    The container waits for PostgreSQL, creates its databases, and runs all of its schema migrations before it starts serving. The first boot takes several minutes, and the very first pull of the multi-gigabyte image adds to that.

    ```bash
    cpln workload get-deployments RELEASE_NAME-tooljet --gvc GVC_NAME -o yaml
    ```
  </Step>
  <Step title="Open the endpoint and complete the Super Admin form">
    Browse to the canonical endpoint (or the port-forward URL) and fill in the Super Admin onboarding. That account owns the instance. Self-signup stays off until the Super Admin enables it.
  </Step>
  <Step title="Invite your team">
    Invitations are sent by email, so they only work if you configured [SMTP](#email) at install time.
  </Step>
</Steps>

## Operations

### Backing Up

The bundled PostgreSQL is the [postgres](/template-catalog/templates/postgres) template, so its scheduled backup is available here under the `postgres` key — nothing extra to install. It is off by default. Enabling it adds the cron workload `RELEASE_NAME-postgres-backup`, which uploads a gzipped SQL dump of the whole instance (all three databases) to your bucket under the configured prefix.

```yaml
postgres:
  backup:
    enabled: true
    schedule: "0 2 * * *"      # daily at 02:00 UTC
    provider: aws              # aws | gcp | minio
    aws:
      bucket: my-tooljet-pg-backup-bucket
      region: us-east-1
      cloudAccountName: my-s3-cloud-account
      policyName: my-tooljet-pg-backup-policy   # bucket-scoped IAM policy
      prefix: postgres/backups
```

Create the bucket, the Control Plane [cloud account](/guides/create-cloud-account), and (for AWS) the bucket-scoped IAM policy **before** installing or upgrading with backups on. The per-provider steps, the IAM policy JSON, the GCS role, and the `gcp` / `minio` value blocks are on the postgres template page under [Backup Prerequisites](/template-catalog/templates/postgres#backup-prerequisites); use the same keys here, nested under `postgres.backup`.

<Warning>
The bundled database runs `postgres:16`, while the postgres template documents its backup feature for PostgreSQL 17 and later and ships a backup image built for the newer major. Scheduled backups have not been exercised against this template — rehearse a backup and a restore on a throwaway release before you rely on them, and check each object's size: a near-empty gzip is a failed run, not a backup.
</Warning>

The dump does not cover your three keys — they live in the secret you created, so back that up separately. The PostgreSQL volume set `RELEASE_NAME-pg-vs` also takes a final [volume set snapshot](/reference/volumeset) when the release is uninstalled, retained for 7 days.

### Restoring a Backup

Each backup is a gzipped plain-SQL dump of the whole PostgreSQL instance. Restoring means replaying that SQL into the bundled PostgreSQL, following the restore procedure on the [postgres template page](/template-catalog/templates/postgres#restoring-a-backup) against `RELEASE_NAME-postgres.GVC_NAME.cpln.local` with the credentials from your `postgres.config.credentialsSecretName` secret. From a client without network access to the GVC, the one transport that carries a dump into the container intact is `cpln workload exec` with `--stdin` and a `base64` wrapper on both ends — raw binary piped through exec is corrupted:

```bash
gunzip -c BACKUP_FILE.sql.gz | base64 | cpln workload exec RELEASE_NAME-postgres --gvc GVC_NAME \
  --container postgresql --stdin --quiet -- sh -c 'base64 -d | psql -U "$POSTGRES_USER" -d postgres'
```

Two constraints make this a planned operation: the dump contains `CREATE ROLE` and `CREATE DATABASE` statements, so a straight replay collides with the databases ToolJet already created and migrated on first boot; and no ToolJet replica may be connected while you drop and recreate those databases before the replay.

<Warning>
This restore path has not been exercised against this template end to end. Rehearse it on a throwaway release before you depend on it. Restoring from a volume set snapshot is likewise unverified here.
</Warning>

### Upgrading from 1.0.0

Version 1.1.0 adopted the `postgres` 3.4.1 template, which stopped taking database credentials as values. ToolJet absorbed that change rather than passing it on — the chart now creates the credentials secret itself — so there is **no new prerequisite**, only a rename of three keys:

| Removed key (1.0.0) | Replacement (1.1.0 and later) |
|---|---|
| `postgres.config.username` | `postgres.credentials.username` |
| `postgres.config.password` | `postgres.credentials.password` |
| `postgres.config.database` | `postgres.credentials.database` |

Move the three keys, keep the same values so the running database still matches, and upgrade in place. A values file that still carries an old key fails the render with the **postgres template's** message — `config.username was REMOVED in postgres 3.4.0` — which tells you to create a dictionary secret yourself; ignore that advice here, this template creates it. Then continue with the section below.

### Upgrading from 1.1.0

Version 1.2.0 changes no values. The ToolJet container now starts through a chart-provided script that waits until PostgreSQL actually accepts connections before running the image's own entrypoint, which removes a failed first attempt that earlier versions logged on a fresh install. Upgrade in place.

<Note>
The first `helm upgrade` after an install can restart the bundled PostgreSQL even when nothing about it changed, which interrupts ToolJet briefly; later upgrades of the same release do not.
</Note>

### Scaling and Availability

`tooljet.replicas` sets how many ToolJet replicas run. With more than one replica, all replicas must share one Redis for the job queue and for multiplayer coordination in the app editor, so `redis.enabled` must be `true` — the single-instance Redis bundled in the image cannot be shared. Sessions are valid on every replica, so no sticky routing is needed.

```yaml
tooljet:
  replicas: 2
redis:
  enabled: true
```

The chart refuses to render `tooljet.replicas` of `2` or more while `redis.enabled` is `false`. The database tier is a single PostgreSQL instance by design; the Redis tier is pinned to one data node and one monitor-only Sentinel because ToolJet's Redis client is not Sentinel-aware.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Deployment never becomes ready and the logs are empty">
    **Symptom:** `cpln helm install` reported success, `cpln logs` returns nothing, and `cpln workload get-deployments RELEASE_NAME-tooljet --gvc GVC_NAME -o yaml` shows `The secret KEYS_SECRET_NAME no longer exists. Workload updates are paused until the secret is added or the reference to the secret removed.` under `status.versions[].message`.

    **Cause:** The key secret named by `secrets.name` does not exist. The same applies to an `smtp.auth.secretName` that was set but never created.

    **Fix:** Create it (see [Prerequisites](#prerequisites)). The deployment recovers on its own once the secret exists; `cpln workload force-redeployment RELEASE_NAME-tooljet --gvc GVC_NAME` skips the wait.
  </Accordion>
  <Accordion title="Container restarts with exit code 137 and never finishes migrating">
    **Symptom:** On a fresh install the ToolJet container keeps restarting; `cpln workload get-deployments RELEASE_NAME-tooljet --gvc GVC_NAME -o yaml` shows an exit code of `137`, and the logs end partway through the schema migrations.

    **Cause:** `tooljet.resources.maxMemory` was set below `4Gi`. The image bakes a 4096 MB Node heap and the first-boot migrations exceed smaller limits, so the container is killed for running out of memory.

    **Fix:** Restore `tooljet.resources.maxMemory: 4Gi` and upgrade. The migrations complete on the next boot.
  </Accordion>
  <Accordion title="Render fails because replicas above 1 require Redis">
    **Symptom:** `tooljet: tooljet.replicas >= 2 requires redis.enabled=true — multiple replicas must share an external Redis for job-queue and multiplayer coordination (the in-image Redis is single-instance-only)`.

    **Cause:** `tooljet.replicas` is `2` or more while `redis.enabled` is `false`.

    **Fix:** Set `redis.enabled: true` (see [Scaling and Availability](#scaling-and-availability)), or keep a single replica.
  </Accordion>
  <Accordion title="Render fails because the Redis replica counts must stay 1">
    **Symptom:** `tooljet: redis.redis.replicas must stay 1 — ToolJet is not Sentinel-aware ...` or `tooljet: redis.sentinel.replicas must stay 1 — with a single data node there is no failover target ...`.

    **Cause:** `redis.redis.replicas` or `redis.sentinel.replicas` was changed from `1`.

    **Fix:** Set both back to `1`. ToolJet connects to the Redis service name directly, so extra data nodes would receive writes they cannot accept.
  </Accordion>
  <Accordion title="Second install refused as managed by a different release">
    **Symptom:** Installing a second ToolJet release fails with `cannot be updated because it is being managed by a different release` and creates nothing.

    **Cause:** Both releases use the same `postgres.config.credentialsSecretName`. Secret names are org-wide, and the first release owns that one. Nothing is shared, overwritten, or deleted.

    **Fix:** Set `postgres.config.credentialsSecretName` to a distinct name for the second release and install again.
  </Accordion>
  <Accordion title="SMTP was enabled through an upgrade but no email is sent">
    **Symptom:** `smtp.enabled: true` was applied with `helm upgrade`, the `SMTP_*` variables are on the workload, yet invitations and password resets send nothing and the instance still reports mail as disabled.

    **Cause:** ToolJet seeds its mail settings from the environment during a first-boot migration only. Values added later reach the container but are never applied.

    **Fix:** SMTP has to be part of the initial install (see [Email](#email)). Enabling it on an existing instance through values is not supported by this template.
  </Accordion>
  <Accordion title="Upgrade from 1.0.0 fails asking you to create a dictionary secret">
    **Symptom:** The render fails with `config.username was REMOVED in postgres 3.4.0` and advice about a prerequisite dictionary secret.

    **Cause:** Your values file still carries `postgres.config.username`, `postgres.config.password`, or `postgres.config.database`.

    **Fix:** Rename them to `postgres.credentials.*` as described in [Upgrading from 1.0.0](#upgrading-from-1-0-0). Do not create a secret yourself — this template creates it.
  </Accordion>
  <Accordion title="Logs repeat Invalid License Key and the health check reports an invalid license">
    **Symptom:** The ToolJet logs repeat `Invalid License Key:Parse error`, and `/api/health` reports the license as invalid or expired.

    **Cause:** The image is ToolJet's LTS build, which includes the licensed edition's code but runs the free tier without a license key. The license check logs this on every pass.

    **Fix:** None needed — this is the free tier working as intended. The same applies to `npm warn using --force` lines from the image's entrypoint.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the key secret before installing** — `secrets.name` must name an existing dictionary secret with `SECRET_KEY_BASE`, `LOCKBOX_MASTER_KEY`, and `PGRST_JWT_SECRET`. A missing secret wedges the deployment silently.
- **`SECRET_KEY_BASE` and `LOCKBOX_MASTER_KEY` are write-once** — rotating `LOCKBOX_MASTER_KEY` makes every stored datasource credential undecryptable. Back the keys up outside Control Plane.
- **Do not lower `tooljet.resources.maxMemory` below `4Gi`** — the first boot's migrations run out of memory below it and the workload never becomes ready.
- **Claim the Super Admin account right after install** — the first visitor to complete onboarding owns the instance, and the endpoint is public by default.
- **Configure SMTP at the initial install** — enabling it through a later upgrade does nothing.
- **`tooljet.replicas` of `2` or more requires `redis.enabled: true`**, and both the Redis data node and the Sentinel must stay at one replica.
- **Change `postgres.credentials.password` before installing** — it seeds the database on first boot and is not updated by later value edits.
- **Give each release its own `postgres.config.credentialsSecretName`** — secret names are org-wide, and a second release on the same name is refused at install.
- **Uninstalling deletes the PostgreSQL volume set** and every app, user, and ToolJet Database table in it; your key secret is yours and survives.
- **ToolJet is licensed under the AGPL** — the deployed image is the LTS build and runs the free tier without a license key.
