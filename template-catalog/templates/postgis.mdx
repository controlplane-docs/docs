## Overview

PostGIS extends PostgreSQL with geographic object types, spatial indexes and spatial SQL functions, making it the standard choice for location-aware applications. This template deploys one PostgreSQL 18 server with PostGIS 3.6 on a persistent volume, and an optional cron job that writes compressed `pg_dumpall` backups to AWS S3 or Google Cloud Storage.

Database credentials are **not** template values. The server reads its username, password and database name from a [dictionary secret](/guides/create-secret/dictionary) you create before installing, so no password passes through Helm or lands in the release. The template creates no credential secret of its own.

<Note>
This template deploys into an existing [GVC](/reference/gvc) that you already have. It does not create or manage a GVC.
</Note>

<Note>
This is a single server, not a cluster — there is no replication or failover. There is no PostGIS variant of the clustered PostgreSQL templates; if you need both spatial support and automatic failover, start from [PostgreSQL Highly Available](/template-catalog/templates/postgres-highly-available) and install the extension yourself.
</Note>

### What Gets Created

| Resource | Name | Purpose | Optional |
|---|---|---|---|
| Workload | `RELEASE_NAME-postgis` | PostgreSQL 18 + PostGIS 3.6 server (stateful, 1 replica, TCP `5432`) | — |
| Volume Set | `RELEASE_NAME-postgis-vs` | `PGDATA` on an `ext4` general-purpose SSD volume; a final snapshot is taken on deletion and kept for 7 days | — |
| Identity | `RELEASE_NAME-postgis-identity` | Shared by the server and backup workloads; carries the cloud account binding when backups are enabled | — |
| Policy | `RELEASE_NAME-postgis-policy` | Grants the identity `reveal` on exactly the credentials secret you created, plus the backup config secret when backups are enabled | — |
| Secret | `RELEASE_NAME-postgis-config` | Backup bucket name (and AWS region) only — holds no credentials | `backup.enabled: true` |
| Workload | `RELEASE_NAME-postgis-backup` | Scheduled `pg_dumpall` to S3 or GCS (cron) | `backup.enabled: true` |

## Prerequisites

One secret must exist before you install. It holds the credentials your applications put in their connection strings. Secrets are org-level, so no GVC flag is involved.

<Steps>
  <Step title="Create the database credentials secret">
    A [dictionary secret](/guides/create-secret/dictionary) holding exactly three keys — `username`, `password` and `database`. The first time the volume is initialized, the server creates that user (as a superuser) and that database, and loads the PostGIS extensions into it:

    ```bash
    cpln secret create-dictionary --name SECRET_NAME \
      --entry username=postgres \
      --entry password='YOUR-STRONG-PASSWORD' \
      --entry database=mydb
    ```

    Set `config.credentialsSecretName` to this name. Read it back later with `cpln secret reveal SECRET_NAME -o yaml` — a bare `cpln secret reveal` prints only a summary table, not the values.
  </Step>
</Steps>

<Warning>
**Create the secret before installing, or the deployment wedges silently.** A `config.credentialsSecretName` that points at a secret which does not exist installs successfully and then never starts. The container never runs, so `cpln logs` returns zero lines. The one place the reason appears is `status.versions[].message`:

```bash
cpln workload get-deployments RELEASE_NAME-postgis --gvc GVC_NAME -o yaml
```

```text
The secret SECRET_NAME no longer exists. Workload updates are paused until the
secret is added or the reference to the secret removed.
```

Use `get-deployments` — plain `cpln workload get` has no `versions` key. Creating the missing secret repairs the deployment on its own within several minutes, or run `cpln workload force-redeployment RELEASE_NAME-postgis --gvc GVC_NAME` to skip the wait.
</Warning>

Backups are optional and need a bucket plus a Control Plane [cloud account](/guides/create-cloud-account) — see [Backing Up](#backing-up). Nothing else is required for a default install.

## Configuration

Each block below is the shipped default for that part of `values.yaml`.

### Server and Resources

```yaml
image: postgis/postgis:18-3.6

resources:
  minCpu: 200m
  minMemory: 528Mi
  maxCpu: 500m
  maxMemory: 1024Mi
```

<Note>
On a stateful workload the ratio of `maxCpu` to `minCpu` may not exceed 4:1. Raising `maxCpu` without raising `minCpu` can cross that limit and is rejected when the workload is applied.
</Note>

### Credentials

```yaml
config:
  # REQUIRED PREREQUISITE SECRET — CREATE IT BEFORE YOU INSTALL.
  # A `dictionary` secret holding exactly three keys: `username`, `password`
  # and `database`. If it does not exist at install time the deployment
  # WEDGES silently — `cpln logs` returns nothing at all. See Prerequisites
  # in the README for the exact `cpln secret create-dictionary` command.
  credentialsSecretName: my-postgis-credentials
```

The three keys are applied only when the volume is first initialized. Changing the secret afterwards does not change the stored password — see [Rotating the Password](#rotating-the-password).

### Storage

```yaml
volumeset:
  capacity: 10 # initial capacity in GiB (minimum is 10)
  autoscaling:
    enabled: false # Set to true to enable autoscaling
    maxCapacity: 100 # Maximum capacity in GiB when autoscaling is enabled
    minFreePercentage: 10 # Minimum free percentage to trigger scaling when autoscaling is enabled
    scalingFactor: 1.2 # Scaling factor to determine how much to scale up when autoscaling is triggered
```

### Internal Access

```yaml
internalAccess: # Sets the internal firewall scope - if set to none, replicas will not be able to reach each other
  type: same-gvc # options: none, same-gvc, same-org, workload-list
  workloads:  # Note: can only be used if type is same-gvc or workload-list
    #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
    #- //gvc/GVC_NAME/workload/WORKLOAD_NAME
```

| Type | Who can reach port `5432` |
|------|-------------|
| `none` | No workload |
| `same-gvc` | Every workload in the same GVC |
| `same-org` | Every workload in the same org |
| `workload-list` | Only the workloads listed in `internalAccess.workloads` |

This template has no public access knob; the server is reachable only from inside Control Plane. A change to `internalAccess` can take several minutes to take effect — re-test before concluding it did not apply.

### Backup

A cron workload runs `pg_dumpall` on the schedule and uploads a gzip-compressed SQL dump of every database and role to the bucket for the chosen `provider`. It authenticates with the `username` and `password` from your credentials secret. Each provider's bucket, cloud account and policy steps are under [Backing Up](#backing-up).

```yaml
backup: # compatible with Postgis 17+
  enabled: false
  image: ghcr.io/controlplane-com/backup-images/postgres-backup:18.1.0 # tag 18.1.0 = Postgres 18, 17.1.0 = Postgres 17
  schedule: "0 2 * * *"   # daily at 2am UTC

  resources:
    cpu: 100m
    memory: 128Mi

  provider: aws # Options: aws or gcp

  aws:
    bucket: my-backup-bucket
    region: us-east-1
    cloudAccountName: my-backup-cloudaccount
    policyName: my-backup-policy
    prefix: postgis/backups # folder name where your backups will be stored

  gcp:
    bucket: my-backup-bucket
    cloudAccountName: my-backup-cloudaccount
    prefix: postgis/backups # folder name where your backups will be stored
```

<Note>
Backups require PostgreSQL 17 or later, and `backup.image` must match the server's major version: tag `18.1.0` for `postgis/postgis:18-*`, `17.1.0` for `postgis/postgis:17-*`. A mismatched client refuses to dump a newer server.
</Note>

## Connecting

This template exposes no public endpoint. Everything below is reachable from inside the GVC, subject to `internalAccess.type`.

| What | Address | Notes |
|---|---|---|
| PostGIS | `RELEASE_NAME-postgis.GVC_NAME.cpln.local:5432` | Standard PostgreSQL wire protocol; any PostgreSQL client or driver works. |
| Credentials | `cpln secret reveal SECRET_NAME -o yaml` | The `username`, `password` and `database` keys. Never stored in the Helm release. |

The database named in your secret has the `postgis` and `postgis_topology` extensions (plus `fuzzystrmatch` and `postgis_tiger_geocoder` on PostGIS 3.6) loaded at first boot. The image also creates a `template_postgis` template database with the same extensions, so `CREATE DATABASE newdb TEMPLATE template_postgis;` gives any additional database spatial support without running `CREATE EXTENSION` yourself.

To verify from your own machine, tunnel to the server and connect with `psql`:

```bash
cpln port-forward RELEASE_NAME-postgis 5432:5432 --gvc GVC_NAME
```

```bash
psql "postgresql://USERNAME:PASSWORD@127.0.0.1:5432/DATABASE" -c 'select postgis_full_version()'
```

Or run `psql` inside the container, where local connections need no password:

```bash
cpln workload exec RELEASE_NAME-postgis --gvc GVC_NAME --container postgis -- psql -U USERNAME -d DATABASE -c 'select postgis_full_version()'
```

## Operations

### Backing Up

Backups are off by default. Enable them with `backup.enabled: true`, pick a `backup.provider`, and complete that provider's setup below first. The job writes `postgres-TIMESTAMP.sql.gz` objects under `backup.PROVIDER.prefix` in your bucket on every run of `backup.schedule`.

<Note>
The backup and restore procedures on this page follow the chart's configuration and the published backup image, which are shared with the [PostgreSQL](/template-catalog/templates/postgres) template, but they have not been exercised end to end on a PostGIS install. Rehearse a backup and a restore before relying on them.
</Note>

#### AWS S3

1. Create an S3 bucket. Set `backup.aws.bucket` to its name and `backup.aws.region` to its region.

2. If you do not have one yet, create a Control Plane [cloud account](/guides/create-cloud-account) for the AWS account holding the bucket. Set `backup.aws.cloudAccountName` to its name.

3. Create an IAM policy scoped to exactly that bucket, replacing `YOUR_BUCKET_NAME`:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject",
                "s3:ListBucket",
                "s3:GetObjectVersion",
                "s3:DeleteObjectVersion",
                "s3:GetBucketLocation",
                "s3:AbortMultipartUpload",
                "s3:ListBucketMultipartUploads",
                "s3:ListMultipartUploadParts"
            ],
            "Resource": [
                "arn:aws:s3:::YOUR_BUCKET_NAME",
                "arn:aws:s3:::YOUR_BUCKET_NAME/*"
            ]
        }
    ]
}
```

4. Set `backup.aws.policyName` to that policy's name. The template attaches it to the workload identity and nothing else — the bucket in your policy is the only storage the backup job can reach.

#### GCS

1. Create a GCS bucket. Set `backup.gcp.bucket` to its name.

2. Create a Control Plane [cloud account](/guides/create-cloud-account) for the GCP project holding the bucket, and set `backup.gcp.cloudAccountName` to its name.

3. Grant the cloud account's service account the **Storage Admin** (`roles/storage.admin`) role. The template additionally binds the identity to `roles/storage.objectAdmin` on exactly the bucket in `backup.gcp.bucket`.

#### On-Demand Dump

Without scheduled backups, or before a risky change, take a single-database dump with `pg_dump` inside the container. Binary output must be wrapped in `base64` on both sides — `cpln workload exec` corrupts raw binary streams:

```bash
cpln workload exec RELEASE_NAME-postgis --gvc GVC_NAME --container postgis --quiet -- sh -c 'pg_dump -Fc -U USERNAME DATABASE | base64' | base64 -d > DATABASE.dump
```

Check the file before trusting it — `pg_restore -l DATABASE.dump` lists its contents and fails on a corrupted archive.

### Restoring a Backup

Each scheduled backup is a gzip-compressed `pg_dumpall` script, so it is restored by connecting to the `postgres` maintenance database as the superuser from your credentials secret; the script recreates the roles and databases it contains, including the `CREATE EXTENSION` statements for PostGIS. Run the commands from a client that can reach both the bucket and the server — a workload inside the GVC, or your own machine with `cpln port-forward RELEASE_NAME-postgis 5432:5432 --gvc GVC_NAME` open and `--host=127.0.0.1` in place of the internal hostname.

<Tabs>
  <Tab title="AWS S3">
    ```bash
    export PGPASSWORD="PASSWORD"

    aws s3 cp "s3://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - \
      | gunzip \
      | psql \
          --host=RELEASE_NAME-postgis.GVC_NAME.cpln.local \
          --port=5432 \
          --username=USERNAME \
          --dbname=postgres

    unset PGPASSWORD
    ```
  </Tab>
  <Tab title="GCS">
    ```bash
    export PGPASSWORD="PASSWORD"

    gsutil cp "gs://BUCKET_NAME/PREFIX/postgres-TIMESTAMP.sql.gz" - \
      | gunzip \
      | psql \
          --host=RELEASE_NAME-postgis.GVC_NAME.cpln.local \
          --port=5432 \
          --username=USERNAME \
          --dbname=postgres

    unset PGPASSWORD
    ```
  </Tab>
</Tabs>

`already exists` errors for the role, the database and the `template_postgis` template that the server created at first boot are expected; the rest of the script loads normally. Restore into an empty server (a fresh install, or one whose databases you have dropped) to avoid duplicate-object errors on existing tables.

To restore an [on-demand dump](#on-demand-dump), send it back through `cpln workload exec` with `--stdin` — stdin is off by default and a file piped in without it is silently discarded. Restore into an empty database; `CREATE DATABASE DATABASE TEMPLATE template_postgis;` gives you one with the extensions already loaded:

```bash
base64 < DATABASE.dump | cpln workload exec RELEASE_NAME-postgis --gvc GVC_NAME --container postgis --stdin -- sh -c 'base64 -d | pg_restore -U USERNAME -d DATABASE'
```

### Rotating the Password

The server reads the secret only when the volume is first initialized, so change the password inside PostgreSQL first, then update the secret to match:

```sql
ALTER ROLE USERNAME WITH PASSWORD 'NEW-STRONG-PASSWORD';
```

Workloads resolve the secret when a replica starts, so an updated secret is not picked up by a running replica. The server does not need one — it keeps serving with the password now stored in the database — and the backup job reads the secret fresh on its next scheduled run.

### Upgrading From 1.3.2 or Earlier

Template versions up to 1.3.2 took the database credentials as plain Helm values with a working default password, and wrote them into a chart-owned secret named after the release. Version 1.4.0 removed both, and an upgrade that still carries the old keys is refused at render — your existing release is left running rather than restarted against a different password.

| | 1.3.2 and earlier | 1.4.0 and later |
|---|---|---|
| Database credentials | `config.username`, `config.password`, `config.database` values | `config.credentialsSecretName` → a dictionary secret you create |
| `RELEASE_NAME-postgis-config` | Created by the chart, held the credentials | Created only when `backup.enabled: true`, holds only the backup bucket and region |
| Resource limits | `resources.cpu`, `resources.memory` | `resources.maxCpu`, `resources.maxMemory` |

<Steps>
  <Step title="Read the credentials the database already uses">
    An existing database keeps the credentials it was initialized with. Recover them from your current values file, or from the secret the old version created — **before** upgrading:

    ```bash
    cpln secret reveal RELEASE_NAME-postgis-config -o yaml
    ```
  </Step>
  <Step title="Create the prerequisite secret with those same values">
    Follow [Prerequisites](#prerequisites) using the existing `username`, `password` and `database`. Different values here do not change the database — they only leave the workload unable to authenticate.
  </Step>
  <Step title="Remove the old keys from your values">
    Delete `config.username`, `config.password` and `config.database`, and set `config.credentialsSecretName` to your secret's name. If you set `resources.cpu` or `resources.memory`, rename them to `resources.maxCpu` and `resources.maxMemory`.
  </Step>
  <Step title="Upgrade, then rotate any default password">
    After the upgrade succeeds, change any password that came from a 1.3.x default — those defaults were published in the public template repository, so treat them as compromised. Follow [Rotating the Password](#rotating-the-password).
  </Step>
</Steps>

<Warning>
**`RELEASE_NAME-postgis-config` no longer holds credentials.** Anything outside this release that read the username or password from it by name — another workload's environment, a policy, or a parent chart that bundles PostGIS as a subchart — must be pointed at the secret you created instead. A reference to a key that no longer exists does not fail loudly; it wedges the referring workload silently, exactly as described in [Prerequisites](#prerequisites).
</Warning>

### Upgrading From 1.4.0

Version 1.4.1 removes the `aws::ReadOnlyAccess` managed policy from the backup identity. That policy granted read access to every bucket in your AWS account and contained no write actions, so it never carried the backup itself — but it was silently supplying any read action your own bucket-scoped policy happened to omit. The identity now carries `cpln-connector` and your `backup.aws.policyName` policy only.

Before upgrading an AWS-backed release, check that your IAM policy contains the full action list under [AWS S3](#aws-s3). If it already matches, no action is needed. GCS-backed releases and releases without backups are unaffected.

### Scaling and Availability

- The server is pinned to one replica. Do not raise it — a single volume set backs a single server, and a second replica cannot mount it. A second replica would be an isolated instance, not a member of a cluster.
- Every `cpln helm upgrade` restarts the server, including the first upgrade after an install even when nothing changed. Plan each one as a short write outage.
- A node failure reschedules the server and reattaches the same volume. The exposure is minutes of downtime, not data loss.

### Troubleshooting

<AccordionGroup>
  <Accordion title="Workload never becomes ready and cpln logs returns nothing">

    ```

    ```

  </Accordion>
  <Accordion title="Upgrade fails with 'config.username and config.password were REMOVED'">

  </Accordion>
  <Accordion title="Password changed in the secret but the old one still works">
    **Symptom:** you updated the `password` key in the credentials secret, but the server still accepts the previous password and rejects the new one.

    **Cause:** the secret is applied only when the volume is first initialized. Afterwards the stored password lives in the database, not the secret.

    **Fix:** change it inside PostgreSQL and then update the secret to match — see [Rotating the Password](#rotating-the-password).
  </Accordion>
  <Accordion title="Backup job fails with 'aborting because of server version mismatch'">
    **Symptom:** `cpln logs '{gvc="GVC_NAME", workload="RELEASE_NAME-postgis-backup"}' --limit 50 --since 1d` shows the run ending in `aborting because of server version mismatch`, and no new object appears in the bucket.

    **Cause:** `backup.image` carries an older PostgreSQL major than `image`. `pg_dumpall` refuses to dump a server newer than itself.

    **Fix:** set `backup.image` to the tag matching your server — `18.1.0` for a PostgreSQL 18 image, `17.1.0` for 17 — and upgrade the release.
  </Accordion>
  <Accordion title="Apply rejected with 'The ratio between cpu and minCpu must be less than 4:1'">
    **Symptom:** an install or upgrade fails and the server workload is not created or updated.

    **Cause:** `resources.maxCpu` is more than four times `resources.minCpu`, which the platform rejects on a stateful workload.

    **Fix:** raise `resources.minCpu` or lower `resources.maxCpu` so the ratio is at most 4:1.
  </Accordion>
</AccordionGroup>

## Important Notes

- **Create the credentials secret before installing.** A reference to a secret that does not exist wedges the workload with no log output; see [Prerequisites](#prerequisites) for the one command that shows the reason.
- **Credentials are read only when the volume is first initialized.** Rotate with `ALTER ROLE` inside PostgreSQL, then update the secret — see [Rotating the Password](#rotating-the-password).
- **Do not scale the server past one replica.** It is a single instance on a single volume, not a replicated cluster.
- **`cpln helm uninstall` deletes the volume set** and the database with it; a final snapshot is kept for 7 days. Your credentials secret is yours and is left alone.
- **Every `cpln helm upgrade` restarts the server.** Treat each one as a short planned write outage.
- **Match `backup.image` to the server's major version** (`18.1.0` for PostgreSQL 18, `17.1.0` for 17), or the backup job fails on every run.
- **Upgrading from 1.3.2 or earlier is a breaking change** — the removed keys stop the upgrade rather than resetting a password. See [Upgrading From 1.3.2 or Earlier](#upgrading-from-1-3-2-or-earlier).
