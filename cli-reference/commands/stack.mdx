#### stack deploy


deploy from a docker-compose file

Refer to the [compose deploy guide](/guides/compose-deploy) for more details.

**Usage**

```none
cpln stack deploy [OPTIONS]
```

<Info>

- Variables such as `${VERSION}` are substituted from the environment and the `.env` file next to the compose file, or from the files given with `--env-file`. A service that names its image next to `build`, such as `image: api:${VERSION}`, is built and pushed to your org's registry under that name and tag. Pass `--no-interpolate` to keep every value as written.
- A service's `env_file` loads each listed file into its containers, a later file overriding an earlier one and `environment` overriding them all. Unlike `.env`, a listed file must exist, or the command stops before building or deploying anything. Give the entry `required: false` in the long syntax to skip it while it is missing.
- Services deploy in `depends_on` order. A dependency waited for with `service_healthy` must become ready, and one waited for with `service_completed_successfully` runs once as a job, before the services that need it are applied. `--wait-timeout` sets how long each wait lasts. Pass `--no-deps` to apply every workload at once.

</Info>


<Accordion title="Reference">

```text
Command options:
  --directory, --dir  Path to parent folder of docker-compose file
  --compose-file      Name of the docker-compose file if alternative naming was used
  --build             Build images  [boolean] [default: true]
  --interpolate       Substitute the variables the compose file references, such as ${VERSION}, from the environment and the .env file, as docker compose does. Use --no-interpolate to keep them as written  [boolean] [default: true]
  --env-file          Read the variables to substitute from this file instead of the .env file next to the compose file. Give it more than once to layer files, a later file winning
  --deps              Honor depends_on: a service that another waits for with service_completed_successfully becomes a job, and stack deploy runs it and follows the dependency order. Use --no-deps to ignore depends_on  [boolean] [default: true]
  --wait-timeout      Seconds to wait for each depends_on condition: a workload becoming ready, or a job completing  [number] [default: 600]

Context options:
  --profile  Override the profile. The default profile can be set using the `cpln profile set-default` command or by setting the CPLN_PROFILE environment variable
  --org      Override the organization. The default organization can be set in your profile by using the `cpln profile update` command
  --gvc      Override the global virtual cloud. The default global virtual cloud can be set in your profile by using the `cpln profile update` command

Options:
  --help  Show help  [boolean]
```

#### stack manifest


Generate a CPLN spec file from a compose project and print it to stdout. With `--build`, it also builds the images and pushes them to your org's registry.



**Usage**

```none
cpln stack manifest [OPTIONS]
```

<Note>

A service waited for with `service_completed_successfully` converts to a cron workload that runs only when started. A manifest cannot carry the order: `cpln apply` creates every workload at once and starts no job. Use [cpln stack deploy](#stack-deploy) for an ordered deploy, or start the job yourself with `cpln workload cron start NAME --location LOCATION`. Pass `--no-deps` to ignore `depends_on`.

</Note>

#### stack rm


Delete all resources generated from a docker compose project.



**Usage**

```none
cpln stack rm [OPTIONS]
```

<Note>

If the compose file references variables, for example `image: api:${VERSION}` next to `build`, set the same variables and pass the same `--env-file` options you deployed with. Resource names never come from variables, so the same resources are removed either way.

</Note>
